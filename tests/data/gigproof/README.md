# gigproof — a minimal valid `.gig` for GigPlayer verification

`sine440.gig`, `pingpong.gig`, and `single-frame-loop.gig` are small one-instrument, one-sample
GigaStudio files used by `PluginPortsMigrationTest` to exercise `GigPlayer`.
The sine fixture proves that the migrated plugin renders sample-exactly the
same output as its pre-migration reference sources. The ping-pong fixture
checks that a bidirectional loop reverses at its exclusive end.

`keyboard-dimension.gig` is a two-zone fixture used by the same test to check
that normal notes select the keyboard zone matching their MIDI key. Zone zero
contains a tone and zone one is silent, making a stale zone selection audible
to the regression.

Without a configure-time `sine440.gig`, the sample-exact harness comparison
would render silence on both sides and pass vacuously. The CMake gate in
`tests/CMakeLists.txt` therefore only builds the `gigplayer` harness module
when this fixture (or another file named `sine440.gig`) is present. The
tracked `pingpong.gig` is loaded by the directional-loop regression whenever
that module is available; otherwise `unprovenGaps()` reports `gigplayer` as
UNPROVEN.

The instrument has two samples: the 440 Hz sine used for ordinary notes and a
constant-level probe used by the release zone. Its two adjacent key regions
put a release-trigger dimension in the first region, which covers MIDI key
60; the later region has no release-trigger dimension and does not cover that
key. This reproduces the region ordering involved in the GigPlayer
release-flag regression while allowing the test to identify release playback
by its nonzero mean level.

The ping-pong fixture contains a signed 16-bit ramp and a bidirectional loop
over frames `[64, 128)`. Its frame values make forward wrapping and reading the
exclusive endpoint distinguishable from reflecting backward. The one-frame
fixture loops over `[64, 65)` and uses distinct neighboring samples to prove
that every post-loop frame repeats frame 64.

The sample data is a 2 s 440 Hz sine (16-bit mono, 44.1 kHz) with a 5 ms
fade-in and 50 ms fade-out, plus a 2 s constant release probe, generated by `make_gig.cpp` itself — no
third-party or copyrighted sample material is included. The file is a test
tone in the public domain.

## Regenerating

Requires `libgig-dev` (Ubuntu: `sudo apt-get install -y libgig-dev`).

```sh
g++ -std=c++17 -O2 make_gig.cpp -o make_gig $(pkg-config --cflags --libs gig)
./make_gig sine440.gig
sha256sum sine440.gig   # expect 5382e8b48923d6154c6a7f9b43dc997cdbd27af2ae254b63951b3eed55fc4c11
./make_gig --pingpong pingpong.gig
sha256sum pingpong.gig  # expect d83de8483b5168af623187b214829f715efcaa5082997ae66df4f7137b9ca701
./make_gig --single-frame-loop single-frame-loop.gig
./make_gig keyboard-dimension.gig --keyboard
sha256sum keyboard-dimension.gig  # expect f3412f85f7e6763e837b77271df2c07725a3d792d239097170360c3631009239
```

The generator is deterministic: the same libgig version produces the same
bytes (the sample table's CRC-32 entries are derived from the PCM data).

## Verifying independently

`gigdump` comes from the `gigtools` package (not required to build LMMS):

```sh
gigdump --verify sine440.gig   # "All checks passed successfully! :-)"
gigdump sine440.gig            # one instrument "Sine440", two samples
```

## Provenance

Created 2026-09-09 for task #589 (Part C slice 8, plugin port migration),
after `find / -xdev -iname '*.gig'` proved no `.gig` file existed anywhere on
the development host. The file was produced locally with libgig 4.3.0 via
`make_gig.cpp`, verified with `gigdump --verify`, and rendered non-silently
by the migrated `GigPlayer` plugin (peak 0.24998 at 44.1 kHz, 0.0 for a
negative control pointing at a non-existent file).
