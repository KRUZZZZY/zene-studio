# Q050-442 — High-contrast track movement grip

Unit: fix, L13, S, member `R-accessibility-37`. The track movement handle (the dots at the left of a
track row, dragged to reorder the track) was drawn from a fixed 6 x 25 bitmap scaled down from a 24 px
Lucide glyph: at that size its dots reached the row at a fraction of the colour's opacity (alpha
102/255 in the raster, measured at **1.05–1.06:1** when rendered), so the handle was practically
invisible in the dark palette, stayed invisible in the high-contrast palette, and sat outside every
contrast audit. The fix draws the handle from the palette's primary foreground role
(`tokens::palette().text`) as pixel-aligned squares, so it follows the palette (and a theme's `text`
override) exactly, and audits the **rendered** grip at WCAG 1.4.11's 3:1 — the existing non-text
component threshold in `include/WcagContrast.h` — in the standard dark and high-contrast palettes.

Out of scope, as the unit brief records: new grip commands, changes to track movement, Ctrl-drag or
custom track colour behaviour, a project setting, and contrast work on other controls. The guarantee
is for the palette-controlled stock track-row surfaces.

## What was built

- `src/gui/tracks/TrackGrip.cpp` — the two cached `QPixmap`s and the tiled-pixmap draw are gone. The
  grip paints ten whole-pixel dots (5 rows × 2 columns, dot side 2 px released / 3 px grabbed, 4 px
  between columns, 5 px between rows) from `tokens::palette().text` with antialiasing off, so each dot
  reaches the role's exact colour. The widget keeps its inherited width (10 px: the old 6 px artwork
  plus its 2 px margin, which is exactly the grabbed dots' width), so the row's buttons stay in place
  in both states. The mouse path — grab signals, cursor change, Ctrl-drag copy, custom-colour fill,
  mute check — is unchanged.
- `include/TrackGrip.h` — the two static `QPixmap` pointers (and the `QPixmap` forward declaration)
  are removed; nothing else changes.
- `tests/src/gui/TrackGripContrastTest.cpp` (new, registered in `tests/CMakeLists.txt` beside
  `TrackIconsLevelBarTest`, in `tests/fork-sources.txt`, and re-derived in `tests/all-sources.txt`) —
  starts the real application over a throwaway home, creates a real sample track, renders the real
  row with `view->grab()`, and measures the grip's own rect with `a11y::contrastRatio`:
  - `theGripIsLegibleInTheStandardPalette` — the dark palette, no restart needed;
  - `theGripIsLegibleInTheHighContrastPalette` — chooses **Project tools ▸ Customise ▸ Theme ▸
    Palette ▸ high_contrast** (a real `QAction::trigger`, the same `window.appearance` the agent
    surface runs), checks the reply says `restart_pending`, re-runs the executable as a **child that
    loads the config this start saved** (the real next-start path, since `tokens::palette()` is
    latched), and verifies the child drew white text on the black surface at ≥3:1; back in the parent
    one `control.undo` restores the palette;
  - `aChangedForegroundRoleReachesTheGrip` — changes the `text` role where a person does: **Theme
    Colours… ▸ the text row's Change… form**, typing `#ffcc00` and clicking **Run** (the same
    registered `theme.set_token` an agent runs), confirms `theme.get` agrees, re-runs as the next
    start, and verifies the rendered handle is exactly that colour and passes 3:1 against the row;
    one `control.undo` drops it;
  - `theGrabbedGripIsStillDrawnInThePalette` — a real mouse press draws more role-coloured pixels
    (the dots grow) at the same role and still ≥3:1; release restores the released image exactly.

  Every measurement asserts the rendered handle is at least 3:1 against the surface it is drawn on,
  that at least 20 pixels are exactly the role colour (so a translucent or near-matching pixmap cannot
  pass), and that the role itself meets the component threshold on that surface.
- `tests/upstream-modifications.txt` — ledger entries for the two inherited files, with the reason.
- `data/manual/index.html` — the Customising section describes the handle: the theme's text colour at
  full strength, the high-contrast palette strengthening it, a changed role reaching it on the next
  start, at least 3:1 against the row (WCAG 1.4.11), and the slight growth while held.
- No command, schema, reversibility class or project-format change: the palette stays a user
  preference (`ui/theme`) written by the existing `window.appearance` / `theme.set_token`, which keep
  their one-undo-step behaviour. There is no new GUI entry point either — the grip has none and needs
  none; the GUI paths the test drives are the existing Theme menu and Theme Colours list.

## New commands and reversibility

None. No command id, argument or result field was added or changed, so the snapshot still measures 917
ids / 78 groups (`doc-figures-gate.py`, exit 0, before and after the manual edit). `window.appearance`
and `theme.set_token` keep their existing `true_inverse` rows and their own one-undo-step behaviour;
the test uses `control.undo` to put each change back, which is what the table promises.

## Format changes

None. The palette and its overrides are user configuration (`ui/theme` in the config file), not
project state; no project reader or writer was touched, so old projects load and render as before.

## Known limits

- The audit covers the palette-controlled stock track-row surface, as the brief scopes it: a track with
  its own colour paints that colour behind the handle and is not re-audited here (custom track colour
  is explicitly out of scope). The handle still follows the palette role there.
- The palette is latched at start (`Appearance.h`, `DesignTokens.cpp`), so a role change reaches the
  grip at the next start — the existing theme lifecycle, not a live recolour; the test proves exactly
  that path.
- The handle is fixed at 10 px wide (the inherited artwork plus margin). Accessible mode widens the
  widget to the 44 px touch target in `TrackOperationsWidget`, and the paint centres the dots in
  whatever width it is given, so the touch layout is unaffected.
- The contrast is measured against the most common colour in the grip's rect (the row surface). The
  dots' own antialiasing is off, so every inked pixel is exactly the role colour rather than a
  blend.
