# Q050-180.1 — Several positioned video clips with correct lane and render behaviour (consolidation completion)

**Unit.** A project's video track holds several clips, each a file at its own song-tick start with a stable id; they
save and reopen independently addressable, the arranger's video lane draws and seeks each, the video window shows the
clip at the play position, and a range render gives the right frame at every song tick with nothing stale before,
after or between clips (0.5.0 L04; members B-ED-054, R-workflow-40; Q050-139 folded in by the owner, 2026-10-25).

**Where it started.** Q050-139's implementation (`d66c0ffcef`, `ea9ed92301`) sat unmerged on
`feat/050-Q050-114-oc`; the train's video files were unchanged since its parent, so it was applied as is and finished
here. This unit then fixed what it left open: `video.attach`'s undo restored only the first clip; the video window kept
the previous clip's picture up after a jump into another clip and showed a late frame of a clip no longer at the play
position; there was no range render; the lane's tag arithmetic capped clips at 100 and overflowed after ~21k reloads,
and every tile used the first clip's aspect; a drag also seeked; the first clip had no GUI entry (the lane is hidden
while the track is empty).

## Format

Additive, no version bump: `<video>` keeps the first clip's legacy attributes and gains `<clip id path offset fps
duration width height audio>` children. A project with no `<clip>` children loads its `<video>` as one clip; a project
without `<video>` loads none, and an empty track saves none (byte-for-byte unchanged for projects without video).

## Realtime

No audio-thread code changed. `VideoReference` is read and written on the interface thread only (commands, the
window's timer, the lane's paint); decoding stays on `VideoFramePump`'s worker, and `video.render_frames` decodes with
its own `VideoDecoder` in the command handler on the interface thread. The window's late-answer drop is single-threaded:
`take()` runs from a queued signal on the interface thread. Local TSan does not run on this box; the reasoning above is
by design reading, not a sanitizer run.

## Known limits

- One video track; no compositing, transitions, encoded video export or source trimming (the unit's stated scope;
  "offset" is the song-tick start). Overlapping clips: the first in list order is shown.
- `video.render_frames` runs to completion before it answers (max 10000 frames) and blocks the interface meanwhile.
- A drag shows no live preview; the clip lands on release.
- `ControlVideoClipsMcp` needs an interpreter whose `mcp` takes the bridge's 2.x `Server(on_list_tools=...)` API. Since
  the train-22 integration it picks one itself (`bridge_python()` in `tests/control-video-clips-mcp.py`: the candidates
  of `server_python()`, keeping the first that passes an API probe) and SKIPs (77) when none does. The shared
  `ControlMcpGroupCoverage` still takes the first interpreter that imports `mcp` and fails on this box (system `mcp` 1.29).
