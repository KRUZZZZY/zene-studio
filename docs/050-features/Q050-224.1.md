# Q050-224.1 - Alternate signal stacks for the engine workers

Type: completion (P2, size L), stage 1 of 4 of Q050-224. Members: `R-performance-57`, `R-platform-52`.
Area: L15. Branch: `feat/050-Q050-224.1-oc`, cut from `050/m0-train-35`.

## What was built

The crash reporter (Q050-157 / cluster 5039) installs its handlers with `SA_ONSTACK`, but
`sigaltstack()` is a **per-thread** attribute: a thread that never registers has no alternate stack, so a
stack overflow on that thread cannot run the handler and leaves no report. Four Zene-owned worker threads
are in scope for this stage, and each now registers the reporter's stack **as the first statement of its
`std::thread` launch lambda**, before its entry function can run:

| Launch site | Thread | Entry called after registration |
|---|---|---|
| `src/core/lv2/Lv2Worker.cpp:89` | LV2 plug-in worker | `workerFunc()` |
| `src/core/RubberBandStretch.cpp:83` | Rubber Band voice recycler | `run()` |
| `src/core/StemJobManager.cpp:90` | stem-separation inference worker | `workerLoop()` |
| `src/wasm/WasmWorkerPool.cpp:73` | wasm DSP lane (all lanes) | `laneMain(i)` |

Registering in the lambda - not at the top of the loop body - is deliberate: the stack is set before the
thread can reach any of its work, including a constructor-time path and the first iteration, and the gate
below rejects the loop-body placement.

The registration is `crashreporter::installAlternateStackForCurrentThread()`, reused unchanged from
`src/core/CrashReporter.cpp:266`: a fixed `thread_local` 32 KiB buffer plus one `sigaltstack()` call, once
per thread. Nothing on the audio thread changed: the call happens at worker startup, outside any render
callback, and allocates, locks and does I/O exactly as much as a `sigaltstack()` syscall does at thread
start (it never touches the project, the model or the audio device).

No user-visible behaviour changes. The manual has no crash-report section, and this unit adds no UI,
command or format: its whole effect is that an overflow on an engine worker is now *reported* instead of
silently killing the process.

## Coverage and exclusions (the inventory is explicit)

In scope and covered by this unit: the four launch sites above. The LV2 worker has a runtime proof; the
other three have the source gate (their callbacks are not injectable without shipping test hooks in the
product, which this unit does not do).

Already covered before this unit (Q050-157 / cluster 5039, unchanged): the audio engine's render worker
(`src/core/AudioEngineWorkerThread.cpp:307`), the `renderNextPeriod()` backstop
(`src/core/AudioEngine.cpp:1208`), the offline renderer (`src/core/ProjectRenderer.cpp:286`), the dummy
device (`include/AudioDummy.h:105`) and every audio-device I/O thread that Zene starts
(`AudioAlsa.cpp:298,611`, `AudioJack.cpp:416`, `AudioOss.cpp:227`, `AudioPortAudio.cpp:214`,
`AudioPulseAudio.cpp:185`, `AudioSdl.cpp:174,192`, `AudioSndio.cpp:134`, `AudioSoundIo.cpp:256`).

Explicitly **not** in this stage, with the reason each is left out:

| Thread family | Where it is created | Why it is not registered here |
|---|---|---|
| Recorder writers | `src/core/Record*.cpp` / capture path writers | Their own file sinks run on the device capture thread (already registered) and the writer helpers are called from it; no separate Zene-owned worker exists for this unit to register. |
| Profiler | `src/core/AudioEngineProfiler.cpp` worker | Diagnostics-only thread, started only when the profiler is armed; it does not run DSP or process buffers. Left for the stage that owns profiler context. |
| Transport / scheduler | transport and session scheduler helpers | They do not own a long-running `std::thread` in this tree; transport is driven from the engine/control threads already registered. |
| MIDI | `src/core/midi/*` I/O threads | The MIDI backends' threads are owned by the platform MIDI libraries (ALSA/OSS/WinMM), not by a Zene launch lambda; a stack overflow there is the library's thread, not ours. |
| Control server pool | `src/core/ControlServer*.cpp` | Runs JSON-RPC handlers; a fault there is a control-session error, not an audio/DSP overflow, and the stage 1 scope is audio, render and DSP workers. |
| GUI thread pool | `src/gui/*`, `QThreadPool` users | The GUI/main thread registers through `install()` in `main.cpp`; pool threads are Qt-owned and the GUI must stay responsive to show the report, which it cannot do from a pool thread's crash. |
| Plug-in private threads | inside third-party plug-ins | Out of Zene's control; already documented as limitation 3 in `docs/CRASH-REPORTER.md`. |

## Commands, GUI, undo, format

- **No new or changed command.** This is engine plumbing, so there is no agent command, no GUI entry
  point and no `ControlRegistry` route to add; the "GUI and agent use the same command" rule is not
  applicable (an internal reliability change with no user action).
- **No undo step**: nothing edits the project, so there is no reversibility class to declare.
- **No format change**: no project data is written or read. Old projects load and render exactly as
  before; there is no new data to round-trip.
- **No manual change**: `data/manual/index.html` has no crash-report section, and inventing UI text for an
  invisible reliability improvement would be a claim the product does not make.

## Known limits

- The source gate proves *placement* of the call at each launch site; it cannot prove the call succeeds on
  every platform. On Windows `installAlternateStackForCurrentThread()` is the documented no-op
  (`src/core/CrashReporterWindows.cpp:51`), so the registration there is inert by design, as for every other
  site in the reporter.
- A thread that never reaches one of these launch points (a plug-in's own private thread, a library-owned
  callback thread) still has no alternate stack; that is the remaining platform limitation, restated in
  `docs/CRASH-REPORTER.md` limitation 3.
- Under ASan the overflow case is skipped: ASan intercepts stack overflow itself and the project's ASan
  recipe sets `use_sigaltstack=0` (Q050-157, `docs/050-features/Q050-157.md`). The skip is explicit in the
  test and reported by QtTest, never silent.
- TSan does not run on this box. The change is a one-shot call at thread start on data that is
  `thread_local`, and the reporter's `thread_local` flag is only read by the thread that sets it; there is
  no shared mutable state added and no lock taken.
- The runtime proof is for the LV2 worker; Stem, RubberBand and Wasm are proven structurally by the gate
  and compiled by the build (`zene` with `WANT_STEM_SPLIT=ON`/`WANT_WASM=ON`), not by an injected fault.
