# Q050-205 - An opt-in OSC control server

Type: feature (P2, size M). Members: R-interop-42, R-workflow-85. Area: L15.

## What was built
- `include/OscBridge.h`, `src/core/OscBridge.cpp` - the OSC 1.0 codec and the mapping of one request datagram onto
  `ControlRegistry::invoke()`. No socket, no Qt Network: built in every configuration. Schema validation, typed errors,
  the UI-thread dispatch and the transaction record (undo) stay the registry's.
- `include/OscServer.h`, `src/core/OscServer.cpp` - the UDP listener (Qt Network, built with `ZENE_HAVE_COLLAB` like the
  collaboration transport). It lives on the UI thread: it reads datagrams there, runs each through the bridge and
  writes the reply to the sender. At most 64 datagrams per event-loop turn; the rest wait for the next turn.
- `src/core/ControlCommandsOsc.cpp`, `src/core/ControlReversibilityTableOsc.cpp`, `include/OscCommands.h` - `osc.start`,
  `osc.stop`, `osc.get_state`. Without Qt Network, `osc.get_state` answers `available:false` and `osc.start` refuses
  with an "unavailable:" message, so the command set is the same in every build.
- GUI: Customise > OSC Control Server > Start... (the command's own form: address, port, scope), State, Stop
  (`src/gui/shell/ShellCommandMenus.cpp`). The menu entries run the same registered commands as an agent.
- Manual: "OSC control" in Scripts, agents and controllers (`data/manual/index.html`). `docs/KNOWN-LIMITATIONS.md`
  no longer says "OSC is out".

## Address map
| Direction | Address | Type tags | Arguments |
|---|---|---|---|
| request | `/zene/<command-id>` (e.g. `/zene/transport.play`, `/zene/mixer.set_volume`) | none, `s`, or pairs | none; one string = the JSON object of the command's arguments; or key/value pairs: a string key then its value (`i f h d s T F N`) |
| reply | `/zene/reply` | `ss` | the command id, the result as compact JSON |
| error | `/zene/error` | `sss` | the command id (or the address), the error kind, a message of at most 512 characters |

Error kinds: the registry's (`not_found`, `requires`, `invalid_args`, `busy`, `refused`, `irreversible`) plus
`malformed` (not a decodable OSC message, a bundle, a blob, more than 64 arguments, a datagram over 8 KiB) ,
`unsupported` (an address outside `/zene/`) and `too_large` (a result over 16 KiB; read it over the control socket).
Scope: `remote` (default) - the collaboration remote allow-list (`collab::remoteAllowList()`: transport, markers, mixer
faders, state reads, `control.ping`); `full` - every command except the `script`, `wasm`, `livecode`, `osc`, `collab`,
`crash`, `telemetry` and `feedback` groups, `control.quit` and the `controller.script_*` commands (Q050-081), and only
on a loopback address. In both scopes a request
whose arguments name a file path is refused. The server binds `127.0.0.1` unless the user gives another IP literal.

## New commands / reversibility / format changes
- `osc.start`, `osc.stop`, `osc.get_state` - all `not_mutating` (device state, the `surface.mcu_connect` / `collab.host`
  precedent). What an OSC request runs records as that command with its own class.
- No project or configuration format change: the server is not saved or remembered.

## Known limits
- Replies only: no unsolicited feedback, subscriptions or meter streaming; a controller polls `transport.get_state` /
  `mixer.get_state`.
- Not remembered across restarts (start it again, or have an agent call `osc.start`).
- No authentication: the `remote` scope on a LAN address lets anyone on that network run the allow-listed commands.
  The default is loopback.
- No OSC bundles, blobs, time tags or pattern matching in addresses.
- Builds without Qt Network have the commands but no server.
