# Q050-367 - VST2 editor teardown stability

Queue unit (fix, S, priority 60, area L10, member `R-effects-5`). Branch `feat/050-Q050-367-oc`, cut from
`050/m0-train-49`. Goal: a person can remove a VST2 effect while the plug-in's own editor is open, and nothing crashes.

The finding (`R-effects-5`) named the suspect and read it, but never reproduced a crash: the teardown order in
`src/gui/EffectRackView.cpp` (erase the view, `delete view`, `fxChain()->removeEffect(e)`, `e->deleteLater()`), the
legacy dialog's destructor (`plugins/VstEffect/VstEffectControlDialog.cpp`: `removeWidget` + `setParent(nullptr)`, no
`hideUI()`), and `VstPlugin::~VstPlugin()` (`delete m_pluginWidget`). Its acceptance allows either a reproduction
under the available VST2 fixture or a bounded not-reproduced result.

## What was found and built

**The crash was not reproduced (bounded result, evidence below).** This build tree has no VST2 host of any kind: the
Carla runtime the product hosts VST2 effects in is absent (`build/carla-runtime/lib` does not exist, nothing named
`libcarla_native-plugin*` or `libcarla_host-plugin*` on the box, `pacman -Q carla` empty), and the legacy VeSTige host
needs its `RemoteVstPlugin64`/`NativeLinuxRemoteVstPlugin64` external executables, which are not built here, plus a
display its X11 window embedding needs. Every case of `CarlaVst2EffectHostingTest` - the fixture test, including
`theEffectsOwnEditorOpensThroughCarla`, the case that opens the editor under the fixture - reports **Skipped** with
the reason. The fixture itself is present and built (`build/tests/data/vst2-test-effect/native/ZeneVst2TestEffect.so`,
source `tests/data/vst2-test-effect`). So the crash cannot be driven here, and this document does not claim it was.

**The teardown-order defect behind it was reproduced and fixed.** A device's own editor (`Plugin::openNativeEditor` /
`closeNativeEditor` / `nativeEditorOpen`: VST2 through Carla or through the legacy in-dialog host, VST3, CLAP, an AU)
belongs to the plug-in, and the plug-in is destroyed with the effect. Nothing closed that editor when the device left
its chain, so the effect went with its editor still open - the ordering the finding suspected, and the state in which
a plug-in's UI is torn down after the plug-in it draws for. Reproduced through the real user paths before the fix
(the run recorded in the negative control below: `open,destroyed-open`), and closed now:

- `src/core/EffectChain.cpp`, `removeEffect()`: the departing device's editor is closed and detached **before** the
  model change that takes it off the chain, so it happens while the effect is still alive and still on its chain.
  This is the one place the rack's `Remove this plugin` entry, `plugin.unload`, a device move and every other removal
  path end in, so no path can forget it. It runs outside the engine's change guard, so the render thread never waits
  on a plug-in's UI call.
- `src/core/EffectChain.cpp`, `clear()`: every device's editor is closed first, for the same reason, before any of
  them is deleted (a chain cleared under its devices is a track or channel going, a preset replacing what the chain
  carries, or the project closing).
- `plugins/VstEffect/VstEffectControlDialog.cpp`, destructor: the legacy VST2 host embeds the plug-in's window in
  this dialog and only ever showed/hid it from a button, so a dialog torn down with the editor showing left that
  window attached to a widget whose `VstPlugin` was about to be destroyed. It now calls `hideUI()` before detaching
  the widget, guarded by `hasEditor()` so a plug-in that failed to load, or has no editor, is left alone.

Nothing else about removal changed: the undo journal (`control::journalEffectRemoval`), the deferred deletion, the
routing-graph rebuild and the enabled flag are as they were.

`git diff <commit>^ <commit> -- src/core/EffectChain.cpp plugins/VstEffect/VstEffectControlDialog.cpp | git apply -R`,

## Commands, undo and format

No command was added, removed or given new metadata, so `tools/mcp-zene-control/zene_control/commands_snapshot.json`
is unchanged and needs no regeneration; `tests/doc-figures-gate.py` is unaffected. The saved project format is
unchanged: nothing new is written, and an editor is not project state (it is not saved and not journalled). Undo is
unchanged - closing an editor is not an edit and adds no undo step, and `plugin.unload` keeps its `true_inverse`
row: the recorded step still rebuilds the device from its settings document, and a rebuilt device's editor starts
closed, as before. Reversibility classes of the commands on this path (`plugin.unload`, `plugin.load`) are untouched.

## Realtime

Nothing added runs on the audio thread. `closeNativeEditor()` is called from `EffectChain::removeEffect()` and
`EffectChain::clear()`, which take the engine's model-change guard and are never called from a render period (the
same reason they already lock); the calls are placed **before** the guard so a plug-in's UI call never happens with
the render thread held off. `processImpl()` and every other audio-path function are untouched. Local TSan does not
run on this box, so this is reasoned from the call sites, not measured.

## Portability

No Qt-6-only API is used; the new test uses QtTest and QContextMenuEvent exactly as its neighbours do, and
`tests/src/gui/EffectEditorTeardownTest.cpp` needs no display (`QT_QPA_PLATFORM=offscreen`, like the rest).
`closeNativeEditor()` is a plain virtual on `Plugin` present in every build, so Qt 5.15 / MSVC / macOS builds
compile the same code; no `windows.h` identifier, no `std::filesystem`, no POSIX-only call was added.

## Projects

Old projects load and render as before: nothing in loading, saving or rendering changed, and a device's editor was
and is not saved. A project holding an open editor simply reopens with it closed (the editor was never restored
either). `CarlaVst2EffectHostingTest`'s save/load and export cases are untouched and keep their expectations.

## Known limits

- The crash itself is **not** reproduced: no VST2 host exists in this environment (see above), so the claim is
  bounded - the ordering defect that the finding named is reproduced and fixed, and the VST2 fixture cannot be run
  here to show the crash before the fix.
- The legacy-host half of the fix (`VstEffectControlDialog`'s destructor) is not covered by a test here for the same
  reason: reaching it needs a loaded legacy VST2 plug-in. It is guarded by `hasEditor()` and calls only the same
  `hideUI()` the dialog's own button calls.
- Moving a device between chains (`plugin.move`, a drag between racks) closes its editor, because a move is implemented
  as a remove plus an append. That is the honest consequence of closing at the one choke point; the editor button
  reopens it.
- A plug-in whose editor refuses to close still gets no extra protection beyond the close itself; the host does not
  force it.
