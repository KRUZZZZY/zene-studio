# Q050-026 - Honor the selected MIDI clock source

Type: fix (P0, size S). Member: R-interop-5. Area: L15.

## What was built

- `include/MidiClock.h` - the source a clock message arrived on is part of the engine's input contract:
  `handleInputMessage(message, value, timestampNs, sourcePort)` (no default argument, so every dispatch site
  has to say where its bytes came from), `setSlaveSourcePort(port, error)` now answers false for a name the
  follower cannot hold, `sourcePortProblem()` is the one place that reason is written, `slaveIgnoredCount()` is
  the drop counter, and `m_sourceChars` / `m_sourceLength` / `m_sourceVersion` are the published copy the MIDI
  reader thread compares against. **Rework r2:** each element of `m_sourceChars` is its own
  `std::atomic<quint16>` (`include/MidiClock.h:459`), so the reader and the writer never race on the buffer by
  the C++ memory model. **Rework r4:** `m_sourceVersion` is the odd-while-writing sequence counter of a
  *sequence lock*, and the payload accesses around it are ordered by `std::atomic_thread_fence` RELEASE/ACQUIRE
  fences (`include/MidiClock.h:446`) - r2's bare acquire version reads did not make the relaxed payload
  consistent, because a reader could pair an even version read with a code unit from the following write; the
  fences close exactly that gap.
- `src/core/MidiClock.cpp:301` `sourcePortProblem()`, `:311` `setSlaveSourcePort()` (a switch forgets the
  measurement; re-naming the current source is not a change), `:332` `publishSource()` (the writer half of the
  sequence lock: odd version, **release fence**, relaxed payload stores, **release fence**, even version - the
  fences order the payload around the markers, which is what a bare relaxed counter does not), `:359`
  `acceptsSource()` (the filter: no source configured = any source may follow; a configured source = exact whole
  name; **acquire fence**, relaxed payload loads, **acquire fence**, closing version read - so a snapshot with
  two equal even version reads is provably one published name and never a half-written mixture), `:408`
  `slaveIgnoredCount()`, and the filtered entry point at `:583`.
- `src/core/MidiClockState.cpp:92` - `clock.get_state`'s `slave` object reports `ignored`, so "nothing is
  arriving" (pulses 0, ignored 0) is distinguishable from "everything arriving is the wrong device".
- `src/core/midi/MidiAlsaSeq.cpp:715` `clockSenderName()` resolves a sequencer sender address to the port name
  once per address (cached, thread-local) and `:854` passes it with the event: the clock family names no port of
  OURS but it does name the SENDER, which is what the follower matches.
- `src/core/midi/MidiClient.cpp:136` and `:349` - a raw client passes an EMPTY source, which is the whole truth
  about one device (ALSA Raw-MIDI, JACK, OSS, sndio, the dummy), and the only value a follower without a chosen
  source follows.
- `src/core/ControlCommandsClock.cpp:169` - the PRESENCE of `source_port` decides: an explicit empty string
  CLEARS the choice (that is what "Any Input" is), omitting it keeps the current one, so the GUI entry is a
  real choice rather than a no-op. A source name `SourceNameCapacity` cannot hold is refused `invalid_args`
  BEFORE anything is applied, so a rejected call leaves the whole configuration as it was; the command
  descriptions and the result schema carry `ignored`.
- `src/core/ControlReversibilityTableSnapshot.cpp:310` - the `clock.slave_set` row states that a source switch

- `src/gui/MidiClockMenu.cpp:141` `rebuildSourceItems()` / `:82` `addSourceItem()` - Edit > MIDI Clock > Clock

## Known limits

- **A client with one unnamed input cannot be narrowed.** ALSA Raw-MIDI, JACK, OSS, sndio and the dummy client
  open one device and their bytes carry no port identity, so they deliver an unnamed clock. That matches an
  unset source and nothing else: on such a client the Clock Source submenu offers **Any Input** alone, and a
  source named through the socket follows nothing - honestly (`locked:false`, `ignored` climbing), never
  silently. ALSA **sequencer** is the backend that names its senders.
- **The sender's name is cached for the life of the client** (`clockSenderName`), so a device renumbered while
  Zene runs keeps being followed until the client is reopened; the follower's lock then drops on its own after
  `lock_timeout_ms`.
- **Only two backends deliver the clock family at all** - the ALSA sequencer and the raw parser. WinMM and
  CoreMIDI clients build note/control events only, so on Windows and macOS an incoming clock is not seen at all;
  a chosen source is not what keeps it unseen.
- **Not run under ThreadSanitizer on this box** (local TSan crashes at thread creation). The race is no longer
  only reasoned: the published name is a **sequence lock** whose snapshot consistency the C++ memory model
  guarantees - each code unit is an atomic (so `acceptsSource()` and `publishSource()` cannot race on the
  buffer) and `std::atomic_thread_fence` RELEASE/ACQUIRE fences order the payload around the odd/even version
  markers (**rework r4**; r2's bare acquire version reads did not order the relaxed payload). A concurrency slot
  (`concurrentReconfigurationNeverAdmitsAnotherPort`, with r4's overlap handshake) races a real writer against a
  real reader, and `MidiClockSourceTest` is registered in the hosted TSan job, so a hosted `-fsanitize=thread`
  run measures it. Locally the slot runs as a plain concurrency test; the reader still re-reads on any version
  change and returns "drop this one message" after `SourceReadAttempts` retries - it never reads a half-written
  name and never blocks. The `m_slavePort` QString stays control-thread-only.
- The control-socket transcript still cannot prove that another port's pulses are DROPPED (an incoming clock
  cannot be injected from a socket); that half is the QTest's subject, over the same engine entry point.
