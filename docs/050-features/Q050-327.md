# Q050-327 Freeze selected tracks as one parallel task

Branch `feat/050-Q050-327-oc` (cut from `050/m0-train-26`, `af010bc3cc`). Several tracks can be frozen
concurrently as ONE background task, and the whole batch is ONE undo step.

## How it works

- **Engine.** `BatchFreeze` (include/BatchFreeze.h, src/core/BatchFreeze.cpp) keeps the batches. Each target gets
  its own `BounceInPlace::PreparedRender` (the same scratch session copy and shipped CLI render child the render
  queue uses), captured on the UI thread with the track's XML fingerprint, the document identity and the tempo
  (map). Up to `parallelLimit()` child renders run at once (half the cores, 2..8); the render queue's one-at-a-time
  scheduler is not used. A finished child's trim/hash runs on a QThreadPool worker and reports back with a queued
  call. Each child has the render queue's 10-minute limit.
- **One task.** The batch is one TaskCenter entry (kind `freeze`, "Freeze N tracks", cancellable) with aggregate
  progress `rendered / N` and the status line "k of N tracks rendered, r rendering"; the status bar's Tasks list,
  `task.list` and `task.cancel` show and stop it.
- **All or nothing.** Nothing is installed until every target has rendered. Then, on the UI thread: every target is
  re-checked (same document, same track XML, not frozen, same tempo and tempo map); every staged take is moved to its
  output path (a previous file there is kept aside and restored on any failure); one `ProjectJournal` edit takes a
  Track checkpoint of each target and freezes it (`Track::freezeTo`, whole track), and `mergeCheckpointsSince`
  folds the checkpoints into ONE step. The completed edit is recorded as an A16 transaction (`freeze.tracks`).
  A cancel, a failed render, a stale target or a refused install ends the batch: running children are killed,
  and once every child and worker has reported back every scratch dir and staged file is removed. No track changes.
- **Agent surface.** `freeze.tracks {tracks: [ids], out_dir?}` (src/core/ControlCommandsFreezeBatch.cpp) refuses up
  front - with nothing started - fewer than two tracks, a repeated id, an unknown id, a track that is not an
  instrument or sample track, or one already frozen. It answers at once with `batch`, `task` (the task.list id),
  `state`, each track's output and `parallel`. `track.get_state` reads each track afterwards.
- **GUI.** An unfrozen instrument or sample track's menu gains **Freeze several tracks...** (src/gui/TrackRenderMenu.cpp,
  `openBatchFreezeDialog`): a non-modal dialog listing every unfrozen instrument/sample track as a checkable row,
  the track whose menu was opened pre-ticked; **Freeze** is enabled from two ticks and sends `freeze.tracks`.

## Format

None. The batch writes the per-track frozen-take attributes `freeze.track` already writes (`frozenAudio` /
`frozenStart` / `frozenEnd` on the track's element); batches themselves are session state and are not saved. Old
projects load and render exactly as before. Takes go to `<project>-bounces/trk-<n>-frozen.wav` (the same default name
`freeze.track` uses) or `out_dir`.

## Known limits

- Whole-track freezes only (no regions, buses or batch unfreeze - out of scope).
- `Track::freezeTo` decodes each take on the UI thread when the batch is applied, exactly as the render queue's
  freeze already does; the renders themselves and the trim/hash are off the UI thread.
- Concurrency is bounded by `parallelLimit()` (2..8 child renders); the rest of a larger batch waits its turn
  inside the same task.
- TSan does not run on this box. Race reasoning: all batch state is touched on the UI thread only (QProcess signals,
  queued calls); a worker receives a copy of the `PreparedRender` value (no model pointers) and posts its result
  back; scratch and staged files are removed only once `inFlight` is zero, so no worker can write after cleanup.
