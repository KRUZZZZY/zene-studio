# Q050-314 - WASM offline render reads its output through the refreshed memory view

Unit: P2, size S, area L10. Branch `feat/050-Q050-314-oc`, base `050/m0-train-24`. Finding R-effects-9.

Goal: a WASM effect that grows its linear memory during a processing call is rendered without a stale output
pointer, and an invalid view or a failed growth is a typed render failure, not a result.

## What was found

The fix itself was already in the base. `detail::callProcessAndRefreshMemory` (`src/wasm/WasmSandbox.h:154`) calls
`process()` and then re-resolves the data pointer **and** size (`refreshLinearMemoryAfterProcess`, `:146`); the inline
render (`src/wasm/WasmOfflineRender.cpp:124`) and the live worker (`src/wasm/WasmWorker.cpp:355`) pass their pointer to it
by reference and read the output plane only afterwards (`WasmOfflineRender.cpp:142`). A refreshed view that no longer holds
the block turns a normal return into `CallResult::Status::Error`. No product code changed in this unit.

What was missing was proof: the existing growth tests pass whether or not the pointer is refreshed (wasmtime need not move
its mapping), and nothing covered an invalid view or a refused growth. This unit adds that proof and records the contract in
`docs/WASM-EFFECT-ABI.md` (§5, §12.2).

## Commands, GUI, undo, formats

No command, GUI control, project format or reversibility class was added or changed; `wasm.render_offline` stays

the command snapshot are unchanged. The user manual has no WASM section and no user-visible behaviour changed, so it is
not edited.

## Limits

- **`WANT_WASM` is OFF in the unit's configured tree and wasmtime is not in it**, and the brief forbids configuring. So
  `WasmWorkerPoolTest` was built standalone (it compiles its own sources and needs no core) against the wasmtime C API in
  `zene-cachyos/third_party/wasmtime`, with `-std=c++20 -DLMMS_TESTING` and the test's own definitions, by
  `logs/standalone-build.sh`. It is the same source file ctest builds, but it was **not run through ctest**.
- `ControlWasmRenderTest` links the whole core and could not be built here. Its two new cases were compiled with the tree's
  own flags (`-fsyntax-only`, exit 0) and the two WAT modules they use were run through `renderOffline`
  (the function the command wraps; `logs/test-cmdmodules.log`): growth gives `[42,7]` on every run, invalid growth fails
  with "memory fault at wasm address 0x7ffffff8 ... out of bounds memory access". The handler maps any not-ok outcome to
  `Refused` (`src/core/ControlCommandsWasmRender.cpp:244`). The cases themselves have not been executed.
- The relocated-view and invalid-view cases use the existing `LMMS_TESTING` seam; they model a moving or vanishing
  mapping, they do not make wasmtime move one. TSan does not run on this box; the seam hook is read with atomics and the
  pooled run is sequential (one block in flight), so the test adds no new concurrency.
