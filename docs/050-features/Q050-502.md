# Q050-502 - Open plug-in windows on Wayland desktops (P0, completion, L10)

**Unit.** A hosted plug-in's own window opens on a Linux Wayland session (KDE, GNOME), not only under X11.

## Measured first (base `5c1c6715d`)

Both formats' editors embed only in an X11 window: `Vst3EditorSession::open` asks for
`kPlatformTypeX11EmbedWindowID` (`plugins/Vst3Effect/Vst3EditorSession.cpp:190`), and `HostedPlugin::openEditor` asks for
`CLAP_WINDOW_API_X11` (`plugins/ClapEffect/ClapHostGui.cpp:65`). `PluginNativeEditor::open` passed `view->winId()` as
that window. Nothing chose the Qt platform, so on a Wayland desktop Qt 6 runs on `wayland`.

The measurements ran in a nested, headless KWin, `kwin_wayland --virtual --xwayland`, on this CachyOS/KDE box. It runs
beside the owner's session and does not touch it. The logs are in the run folder `Q050-502.r1/logs`, named in brackets
below.

| What | `QT_QPA_PLATFORM=wayland` | `QT_QPA_PLATFORM=xcb` (XWayland) |
| --- | --- | --- |
| `winId()` of a native child widget (PySide6 6.12, Qt's own behaviour), then `xprop -id` on it [measure-4-*] | `0x55956fc2d690` (a heap pointer): X11 answers **BadWindow** | `0x40000a`: a real X11 window |
| `plugin.editor_open` on the VST3 fixture (`PluginCompatEditorProbe`, the real GUI application) [measure-2-wayland] | **`open: true`**: a false success | - |
| `ClapEffectIntegrationTest::testTheEffectsOwnEditorOpensInItsOwnWindow` / `Vst3InstrumentIntegrationTest::testTheInstrumentsOwnEditorOpensInItsOwnWindow` [measure-3-*] | both PASS: the fixtures store the id they are given | both PASS |

So before this change, on Wayland both formats reported an open editor. The plug-in had been handed an id that is
not an X11 window. A real plug-in calls `XReparentWindow` on it and gets BadWindow: under Xlib's default error handler
the process exits, and otherwise the window stays empty. The in-tree fixtures draw nothing, so they cannot show that
failure. The xprop measurement shows the cause directly. (The CLAP probe row reads "not listed" because the probe adds
devices to an instrument track and the CLAP fixture is an effect; the integration test covers the CLAP path instead.)

## The choice: run on XWayland, chosen at start-up

There were two ways to do this. One was to host each editor in an XWayland-backed window while the rest of the
application stays on Wayland. That would need a second, foreign X11 connection for each editor, managed outside Qt's
platform layer, with its own event loop integration. It would also need cross-protocol stacking and focus, which
Wayland does not define. The other way, which is what this change does, is to run the whole application on XWayland,
which is in practice what other Linux DAWs do (their Linux builds are X11 clients, so on a Wayland desktop they run on
XWayland; this is general knowledge and was not measured here):

- `pluginwindow::decide()` (`src/core/PluginWindowPlatform.cpp`) makes the decision without touching anything. A
  Wayland session is `WAYLAND_DISPLAY` set, or `XDG_SESSION_TYPE=wayland`. If that session has XWayland (`DISPLAY` is
  set, as KDE and GNOME set it), the choice is `QT_QPA_PLATFORM=xcb;wayland` (Qt 6's fallback list: a Qt without the
  xcb plug-in still starts, on Wayland). On Qt 5 it is plain `xcb`. If the session has no XWayland, the application
  stays on native Wayland. A `QT_QPA_PLATFORM` or `-platform` that the user set is never overridden. An X11 session,
  and Windows and macOS, are not touched.
- `chooseStartupPlatform()` runs in `main()` before the GUI application exists, and not for core-only (render, script)
  runs. It sets the variable and prints one line to stderr (for example `Wayland session: running on XWayland
  (QT_QPA_PLATFORM=xcb;wayland) so plug-in editors can open; set QT_QPA_PLATFORM=wayland to run natively without
  them`). A user's own choice is not logged.
- Both editor paths ask `pluginwindow::editorRefusal()`: `plugin.editor_open`, before the plug-in is touched, and
  `PluginNativeEditor::open`, before a window or an id exists. On a `wayland*` Qt platform it gives the reason: no
  XWayland, the user asked for native Wayland, or Qt's xcb plug-in is missing. `plugin.editor_open` returns that
  reason as a typed **`requires`** refusal (the same kind as "needs a display"), prefixed with
  `<target>/<plugin> (<name>):`. Every other platform (xcb, offscreen, windows, cocoa) gets no refusal, so the X11 path
  and its tests are unchanged.

Real binary, nested KWin [measure-5-*]: with no override, `zene` starts with the line above and its windows are X11
clients of XWayland (`xprop -root _NET_CLIENT_LIST` lists "Untitled - Zene Studio ..."). With
`QT_QPA_PLATFORM=wayland` it starts natively (no X11 clients). With `DISPLAY` unset it starts natively and prints the
no-XWayland line. After the change, on native Wayland, the VST3 probe answers `unsupported` with the reason, and the
integration tests' open is refused with the reason. On XWayland both still open [measure-6-*, measure-7-*].

## Commands, formats, limits

- **Commands.** No new command. `plugin.editor_open` gains the typed `requires` refusal on native Wayland, and its
  description says so (snapshot regenerated live: 868 ids / 76 groups, only that description changed). Its class is
  unchanged (`not_mutating`, interface state). There is no undo step, because nothing in the project changes.
- **GUI.** The same command behind Open Editor (device card), the "Show plugin editor" button (instrument view,
  effect dialog) and the command list. The refusal appears on the button's reason line. The start-up choice has no
  control in the interface: the user sets the platform with `QT_QPA_PLATFORM`, as for any Qt application, because Qt
  reads it before any window or setting exists.
- **Formats.** No project or preset format change.
- **Realtime.** Nothing runs on the audio thread: the decision runs once in `main()`, and the refusal runs on the main
  thread when an editor is opened.
- **Known limits.** There is no Wayland-native embedding. Under XWayland, scaling on a fractionally scaled screen
  follows KDE's X11 scaling setting. The choice is fixed for the session. The fixtures draw nothing, so the
  real-pixels check of a third-party editor on the owner's KDE desktop is still to do. LV2 UIs are still not opened at
  all (unchanged).
