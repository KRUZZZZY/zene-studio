# Q050-334.1 - Ordered, bounded local project-change events

Unit: feature, size L, priority P2, area L17, stage 1 of 2 of Q050-334 (the TypeScript SDK is stage 2). Branch
`feat/050-Q050-334.1-oc`, base `050/m0-train-24` (`2a7fd9f9c7`). Goal: local control clients subscribe to ordered
project-change events with bounded delivery, unsubscribe, and a defined recovery after disconnect or overflow.

## What was built

- **`ControlEventHub`** (`include/ControlEventHub.h`, `src/core/ControlEventHub.cpp`, new): one per process, UI thread.
  Every project change gets the next `seq`, subscribers or not, and goes on each subscriber's `ControlEventQueue`.
- **The sources.** `ControlRegistry::runHandler` reports each finished call: a successful mutating call not nested in a
  mutating one is one event, so a non-mutating wrapper's children are reported. The macro recorder's single observer
  slot is not touched. `ProjectJournal` gains a change listener: a step, undo or redo outside any handler is how an edit
  the interface makes directly appears (`source:"journal"`), and a journal that moved under a command that reported
  nothing itself (`control.undo`, `control.redo`) is reported once under that command's name. Project replacement is
  reported when the journal clears and again when the load or new project is complete.
- **The transports pull.** POSIX (`ControlServer::flushClientEvents`, `src/core/ControlServerEvents.cpp`) takes a line
  only while the client has no reply tail waiting. Windows (`win32PumpEvents` / `win32WriteEvents`,
  `src/core/ControlServerWin32.cpp`) moves lines to the worker's outbox only while it is empty; the worker's read stays
  pending in its own OVERLAPPED while it writes them. So all buffering is the hub's bound.
- **Connections.** Each dispatch runs inside a `ConnectionScope`, which is how `events.*` know who is asking. Nothing
  else on the surface changes, and a connection that never subscribes never sees an event line.
- **Idle timeout.** A subscribed connection with nothing waiting to be written is not retired by the 30 s idle timeout; one
  stalled on a tail still is.
- **MCP bridge.** `protocol.py` skips event lines while waiting for a reply. Skipped lines share the request's one reply deadline, so a busy
  subscription cannot hold a call past its timeout (`test_event_lines_do_not_reset_the_reply_deadline`).

## Wire contract

```
-> {"id":1,"cmd":"events.subscribe","args":{"queue_limit":256}}
<- {"id":1,"ok":true,"result":{"subscription":"sub-1","session":"<uuid>","seq":41,"queue_limit":256,"queue_byte_limit":1048576}}
<- {"event":"project_changed","subscription":"sub-1","session":"<uuid>","seq":42,"source":"command","kind":"edit","command":"track.rename","args":{...}}
<- {"event":"project_changed",...,"seq":43,"source":"journal","kind":"undo"}
<- {"event":"events_overflow","subscription":"sub-1","session":"<uuid>","last_delivered_seq":43,"first_missed_seq":44,"missed":6,"seq":49,"message":"..."}
```

- Event lines have `event` and no `id`. `seq` rises by exactly one per change in one `session` (one process).
- An edit's reply precedes its event when the edit came from the same connection on the POSIX and Windows paths,
  because the flush is queued after the reply; a handler that spins a nested event loop may let an event overtake its
  own reply, so clients match replies by `id` and order events by `seq`.
- **Overflow:** past the bound, the queued prefix is delivered in order, then one `events_overflow`, and the
  subscription is over. It never resumes after a gap, so a received sequence never hides one.
- **Recovery (overflow or reconnect):** `events.subscribe`, then reread with `project.get_state` and the other read
  commands: in that order no change falls between the two. The reply's `seq` against the last seen one (and `session`)
  says whether anything was missed. Missed events are not replayed.

## New commands

`events.subscribe`, `events.unsubscribe`, `events.get_state`: all `not_mutating` (rows in
`src/core/ControlReversibilityTableLivecode.cpp`), `requiresEngine=false`. Snapshot regenerated live: 881 ids / 78 groups.

## Format changes

None. Subscriptions, queues and `seq` are runtime state; nothing is written to a project.

## Known limits

- No GUI panel or menu: out of scope by the unit's brief, and subscribing is meaningless without a connected program.
  The commands refuse typed when no connection serves the call (Lua, a menu, the collaboration dispatcher).
- An interface change that leaves no undo step (not a project edit in the journal's sense) makes no event. `edit` from the journal
  carries no detail about what changed: reread.
- A client that stalls with a tail waiting is retired after the 30 s idle timeout, the rule every connection has; it
  detects that as a closed connection.
- A burst larger than `queue_limit` inside one event-loop turn (a wrapper command running many mutating children)
  overflows even a healthy reader, by design, and recovers the same way. Choose a larger `queue_limit` if that matters.
- **Windows transport not run here:** no Windows toolchain on this box. `ControlServerWin32.cpp` was type-checked against a stub
  `windows.h` with the real Qt headers (exit 0), and `ControlNamedPipeSmoke` gained check 9 (subscribe, event while
  parked in the read, unsubscribe), which only hosted CI can run on a real pipe. It passes here over the POSIX transport.
- TypeScript SDK: stage 2 (Q050-334.2).
- Thread-safety was reasoned, since TSan does not run on this box: the hub is UI-thread only; `journalChanged` posts to the UI
  thread if called elsewhere; the Windows outbox is the one shared buffer and is mutex-guarded; `ProjectJournal` is not
  on an audio path (its own header says so) and the listener only records or posts.
