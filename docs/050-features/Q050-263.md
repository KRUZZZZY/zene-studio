# Q050-263 - Per-slice SlicerT controls

Unit: P2, M, L10. Goal: a musician adjusts gain, pan, filter and random amount on each SlicerT slice,
and an agent reads and writes the same values through the control surface.

## What was built

- `include/SlicerSliceControls.h`: the one place the four controls' names, ranges and neutral values
  live (gain -48..12 dB, pan -1..1, filter -1..1, random 0..1; neutral 0) and the constants of the
  random bound and the filter sweep. The plug-in, the commands and the view all include it.
- `plugins/SlicerT/SlicerT.{h,cpp}`: every playable slice (the interval between two adjacent slice
  points; MIDI key `base + 1 + slice`; the base key still plays the whole sample and is not affected)
  has its four values in a fixed array of relaxed atomics (130 slices, the most `findSlices()` makes).
  - Audio thread: `applySliceControls()` runs after the existing fade, reads the four atomics once per
    period and returns at once when all are neutral, so an untouched slice renders exactly as before.
    Filter: a two-pole state-variable filter (low-pass for negative, high-pass for positive values,
    cutoff swept exponentially: 20 kHz down to 100 Hz, or 20 Hz up to 8 kHz). Gain: dB. Pan: a balance
    (the far channel is attenuated, the near one is untouched, so 0 leaves the stereo sample alone).
    Random: each trigger of a slice takes two draws in -1..1 (a hash of a running trigger counter, so
    no lock and no allocation) held in the note's own playback slot; at amount `r` the trigger's gain
    varies by up to +-6 dB * r and its pan by up to +-0.5 * r. 0 is exactly no variation.
    Nothing on this path allocates, frees, locks, waits, does I/O or emits a signal.
  - Control thread: `sliceCount`, `slicePoint`, `sliceControl`, `setSliceControl` are `Q_INVOKABLE`
    (the way `ControlCommandsOutOfProcessSupport.cpp` reaches its plug-ins), so the core needs no plug-in
    header. `setSliceControl` refuses an unknown slice or name and a value outside the range.
  - Slice edits: deleting a slice point (waveform right-click) merges two slices and keeps the earlier
    one's values (later slices keep theirs); a double click that adds a point gives both halves the split
    slice's values; Clear all slices, Reset slices and detecting slices again start every slice neutral.
- `plugins/SlicerT/SlicerTView.{h,cpp}`: a per-slice bar between the waveform and the sample name (the
  waveform is one bar shorter): a Slice selector (0-based) and Gain / Pan / Filter / Random spin boxes
  (keyboard tracking off, so one typed value or one arrow step is one command). Each edit invokes the
  registered `plugin.slice_set`; the panel shows the selected slice's stored values and follows every
  change (agent, undo). The selected slice is shaded in the waveform (`SlicerTWaveform::setSelectedSlice`).
- `src/core/ControlCommandsSlicerSlices.cpp`: the two commands, group `plugin`:
  - `plugin.slice_get` (`target`, optional `slice`): the slice count, `base_key`, the controls'
    ranges, and per slice its `key`, `start`/`end` (fraction of the sample) and `gain`/`pan`/`filter`/`random`.
    `not_mutating`.
  - `plugin.slice_set` (`target`, `slice`, any of `gain` `pan` `filter` `random`): every value is range
    checked before any is written (a refusal writes nothing; `invalid_args`, unknown slice `not_found`,
    a track without a SlicerT `invalid_args`). One call is one undo step: the track checkpoint, which
    restores the SlicerT's saved state (`true_inverse`, mechanism "ProjectJournal (Track checkpoint)").
- Registration: `ControlRegistryRegistrations.cpp` / `ControlRegistryGroups.h`; the two A16 rows are in
  `ControlReversibilityTableDevices.cpp`.

Why not `plugin.param_get/param_set`: those address `AutomatableModel`s, and 130 slices x 4 controls
would be 520 models on every SlicerT, in the automation menus and the model enumeration, for values that
are not automatable. A slice-addressed command pair is the smaller surface.

## Format changes

Additive only. SlicerT's state keeps `version="1"`, the sample, `totalSlices`, `slice_<n>`, `fadeOut`,
`threshold`, `origBPM` and `syncEnable`. For each slice control that is not neutral it adds one attribute
`sliceGain_<n>`, `slicePan_<n>`, `sliceFilter_<n>` or `sliceRandom_<n>` (n = the 0-based slice). Nothing
is written for neutral values, so a project that never touches the controls saves what it always did, and
a project without the attributes loads with every slice neutral (and renders as before; `loadSettings`
always resets the controls first, so an undo to before an edit leaves nothing behind).

## Commands

Two added: `plugin.slice_get` (`not_mutating`) and `plugin.slice_set` (`true_inverse`). The live
snapshot is 880 ids / 77 groups; the published A16 histogram is 889 rows: 435 `true_inverse`, 42
`snapshot`, 25 `irreversible`, 387 `not_mutating`.

## Known limits

- Detecting slices again (Reset slices, a new sample, a changed threshold followed by Reset) starts every
  slice neutral: the layout is new, so the old per-slice values have no slice to belong to.
- Dragging a slice point past its neighbour re-sorts the points but not the controls: values stay with
  the slice number, not with the audio.
- Random varies gain and pan only; the filter is not randomised. The trigger counter starts at 0 per
  SlicerT, so a fresh project replays the same variation sequence.
- No per-slice automation, MIDI learn, granular sync, formant or Beat Breaker modes (out of scope).
- Local TSan does not run on this box. The thread boundary: the control thread writes four relaxed
  atomics per slice and the audio thread reads them (a torn set across the four values is audible for at
  most one period and harmless); the structural helpers (`sliceMerged`, `sliceSplit`) run on the GUI
  thread like the existing slice-point edits, which already race the audio thread's read of
  `m_slicePoints` by the unit's earlier design (unchanged here).
