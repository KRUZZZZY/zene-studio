# Q050-154 - Live-code panel

Unit: completion, size M, priority P1, area L07. Branch `feat/050-Q050-154-oc`, base `050/m0-train-11`
(`dbb15dded`). Goal: edit Lua live-code scripts in the interface and schedule, unschedule and inspect them from the
panel, through the same `livecode.*` commands an agent uses.

## What was built

- **`LivecodePanel`** (`src/gui/LivecodePanel.cpp`, `include/LivecodePanel.h`, new): the live-code panel. A source editor,
  an id box (empty = the clock picks the next `lc-<n>`), a hook picker (bar / beat / transport) and an instruction
  budget, with **Schedule**, **Cancel Schedule**, **Load Source**, **Undo**, **Refresh** and **Open File...**. Every
  button invokes the registered command through `ControlRegistry` - `livecode.schedule`, `livecode.unschedule`,
  `livecode.get_source`, `control.undo` - never `ScriptClock` directly (SPEC A11).
- **Compile errors stay in the panel.** `livecode.schedule` refuses before the registry moves, so the panel prints the
  parser's message in its status label and the definition that was already scheduled keeps firing. The invalid buffer
  stays in the editor for the musician to fix.
- **The schedule table** reads `livecode.get_state`: id, hook, budget, source bytes, fires, errors, budget exceeded,
  last fire position and last failure, plus an aggregate summary line and a 500 ms refresh that never blocks (the
  handler runs on the same control thread).
- **`livecode.get_source`** (`src/core/ControlCommandsLivecode.cpp`, new command): the deliberate source-readback path.
  `livecode.get_state` reports `source_bytes` only so a poll never carries every definition (up to 64 x 64 KiB);
  `get_source` returns one schedule's exact text, hook and budget. It is what lets the panel load an agent-made
  schedule into the editor, and it is the proof the headless test uses that an undo restored the previous definition
  rather than only the id. `not_mutating`; typed `not_found` / `invalid_args`.
- **Undo** relies on the existing snapshot inverses: one `control.undo` after a replacement restores the previous
  source, hook and budget under the same id; one after a cancel rearms the id and its definition. The panel's Undo
  re-reads the loaded id through `get_source` so the editor never shows a definition the clock does not hold. Fire
  counters are runtime history and are not rolled back - the panel says so.
- **`window.livecode`** (`src/gui/ControlCommandsShell.cpp`): opens the panel non-modally and reports `shown` /
  `schedules`. Declared in the **Edit** menu as *Live Code...* (`src/gui/MainWindow.cpp`) and listed in the footer's
  **Tools** menu (`src/gui/shell/ShellToolsMenu.cpp`), so the action and the agent surface are one command.
- **Bounds, in the panel.** `helpText()` is built from the implementation's own constants
  (`ScriptClock::SourceByteCap`, `MaxScheduleCount`, `PollMs`, `ScriptClockGrid::CrossCap`,
  `ScriptEngine::Default/Min/MaxMemoryBudgetBytes`): a fresh Lua state per fire so globals do not persist; source
  capped at 65,536 bytes; at most 64 schedules; transport observed every 25 ms (a fire lands up to one poll after its
  boundary); more than four crossings in one observation coalesced; per-fire instruction budget; per-run Lua memory
  budget and where to set it; schedules are process-local and never run on the audio thread.

## Format changes

None. The schedule registry is in-memory runtime state (`ScriptClock`), and no project save/load path carries it, so
no `.mmp`/`.mmpz` data changed and old projects load and render exactly as before. The source/bounds caps are
constants, not new settings.

## Known limits

- Runtime schedules do not survive a restart and are not in the project file (stated in the panel and in
  `docs/KNOWN-LIMITATIONS.md`).
- A fire lands up to one 25 ms poll after its boundary, and more than four crossings in one observation coalesce; the
  panel reports the `coalesced` count but cannot show a dropped bar individually.
- The panel has no undo history list of its own: Undo is one `control.undo` step, exactly the agent's.
- `livecode.get_source` reads one definition at a time by id; there is no "dump every source" command, deliberately, so a
  poll cannot carry the whole 4 MiB registry.
- The panel's source editor is plain text (no Lua syntax highlighting, no completion).
