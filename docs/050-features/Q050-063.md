# Q050-063 - Author warp markers with on-clip preview

Unit: P1, size L, area L05. Branch `feat/050-Q050-063-oc`, base `050/m0-train-13`.

Goal: draw, move, snap and preview warp markers directly over a sample clip's waveform.

## What was built

- **Markers as lines through the waveform.** `SampleClipView` draws every warp marker as an amber line the height of the
  waveform with a grip at the top (`paintWarpGuides`, `src/gui/clips/SampleClipWarpEdit.cpp`). A marker is drawn at
  `offset_ticks + startTimeOffset` from the clip's left edge - the position `sourceFrameAt` / `timelinePosAt` map through,
  not a source-linear position. The view reads the clip's own `WarpMarkers` (no parallel UI map), so the lines show what
  `warp.list` reads.
- **Authoring gestures** (clip menu > Warp markers > Edit warp markers, off by default so a plain double-click still
  opens the sample dialog): a double-click on the waveform sends `warp.add` for the frame heard at the click, where it is
  heard (adding changes no sound); a press on a marker drags it; a double-click on a marker sends `warp.remove`. A drag
  sends ONE `warp.move` on release, so one drag is one undo step; nothing is written while the pointer moves. The marker
  keeps its source frame and stays strictly between its neighbours (warp.move's own rule). A locked clip refuses all of it.
- **Snap.** Warp markers > Snap to grid (the arrangement's snap size, relative to the timeline, not the clip), Snap to
  transients (the nearest detected transient, as the clip places it now, within eight pixels) or No snap; Alt drags
  unsnapped. `snapWarpOffset` is a pure function.
- **On-clip preview.** `warpWaveformSegments` cuts the audio at every marker and gives each stretch its own pixel range;
  the view draws each stretch with `SampleThumbnail` at that width. The same function draws the committed map and the
  drag's candidate map, so the waveform the drag showed is the waveform the release leaves. A clip with no markers (and a
  reversed clip) draws exactly as before.
- **The render honours the committed offset of every marker, the first included (review round 2).** The play handle
  chains rates from the pass's first source frame, and the pass used to start at the clip's start whatever the first
  marker said, so dragging the first marker moved the line and the preview but not the audio. `SampleClip::leadOutputFramesAt`
  (`src/core/SampleClip.cpp`, the function `SampleTrack::play` already adds to the handle's offset for a frame-exact
  lead) now also returns, for a warped clip, the output frames of silence owed until the map reaches the window's
  start (`timelineOffsetAt(sourceIn) - ticks already elapsed`); a first marker dragged earlier needs nothing,
  because the pass already starts at `sourceFrameAt(at)`. A clip with no markers returns what it did; a clip whose first marker sits where its audio
  naturally is returns 0, so its render is unchanged; only a clip whose first marker was authored off its natural place now
  renders where its map says (previously the audio ignored that offset). Pure arithmetic, no allocation or lock.
- **No new command.** `warp.add`, `warp.move` and `warp.remove` are unchanged and keep their `true_inverse` rows, so
  the command snapshot, the reversibility table and `include/ControlCommandsSnapshot` do not change. No file format
  change: the `<warp>` element is what it was. The view and the preview are GUI work.
- **A render pass holds one immutable generation of the map (review rounds 3-4).** Every write goes through
  `Clip::publishWarp` (drag release, `warp.*`, undo, load, clear, source replacement). The control thread keeps its own
  `m_warp` and publishes a copy as a new generation in `WarpPublication` (`include/WarpPublication.h`), swapping one atomic
  pointer. `SampleTrack::play` takes a `WarpSnapshot` per clip and holds it in a `Clip::WarpPassScope` while it computes
  the window and lead and builds the `SamplePlayHandle`. Inside the scope `passWarp()`, and so `sourceFrameAt`, `timelinePosAt`,
  `windowTicksFor`, `rendersLinearly`, `warpMarkers` and `leadOutputFramesAt`, answers from that generation through a thread-local pin, so
  `prefades::window` and `audioloop::window` needed no change. On the audio thread snapshot acquisition and release use
  atomic reader-count operations, and the snapshot loads one atomic pointer; the scope saves and restores its two
  thread-local entries. These operations take no lock and allocate, free or wait for nothing. A generation replaced while a pass holds one
  is freed by the control thread at a later publish or with the clip; the comment in the header gives the ordering argument.
  Round 3's use of the engine's change lock is gone, because a render period could wait for it.

## Known limits

- The stretched waveform is drawn from the thumbnail cache, so it is approximate (no re-analysis, no audition while
  dragging). A reversed clip shows its markers but its waveform is drawn unstretched.
- Transient snap uses the transients as the committed map places them; they do not move while a drag is in progress.
- `Edit warp markers` is per view and not saved: a reopened project starts with it off (the markers themselves are
  saved in the clip's `<warp>` element as before).

Known limit: `m_tempoMode` and `m_sourceTempo` are still plain writes from the control thread, as they were before this unit; only the marker map is published. `warp.move` and undo do other work besides publishing the map (journal, checkpoint restore, length updates) that this unit neither audited nor changed for lock use; only `setWarpMarkers` is proven not to wait. Local TSan does not run on this box, so the race-freedom rests on the ordering argument and these tests.
