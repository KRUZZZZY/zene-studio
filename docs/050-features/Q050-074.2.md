# Q050-074.2 - Audio-device timing and xrun diagnostics (stage 2 of 2 of Q050-074)

Unit: P1, L (split), feature, area L15. Goal: musicians and agents can diagnose whether backend and device
timing contribute to late audio (B-WF-104, R-performance-71/48/78). Builds on stage 1 (Q050-074.1: per-track
synthesis CPU and the engine's late periods, `mixer.cpu_load`, the CPU diagnostics window).

## What was built

- `include/AudioDevice.h`: `AudioDevice::DeviceTiming` - the backend name, the device's sample rate,
  period frames, buffer frames, input/output latency frames (each a `std::optional`: empty = the backend
  does not report it) with the basis of each latency, and whether the backend counts xruns; virtual
  `deviceTiming()` (empty by default, so every backend that does not override it reports nothing);
  `backendXruns()` and the protected `countBackendXrun()` - one relaxed `fetch_add` on an atomic, safe on
  the audio thread.
- `src/core/audio/AudioJack.cpp`: `jack_set_xrun_callback` counts the server's xrun notifications;
  `deviceTiming()` reads `jack_get_sample_rate`, `jack_get_buffer_size` (JACK's period) and the first
  ports' capture/playback latency ranges (off the audio thread). JACK does not report how many periods it
  queues, so the buffer is unavailable.
- `src/core/audio/AudioAlsa.cpp`: a playback underrun (`-EPIPE` in `handleError`) is counted before the
  same recovery; the rate the PCM granted is read back after `snd_pcm_hw_params`; `deviceTiming()` reports
  rate, period, buffer, the playback buffer as output latency (blocking writes keep it full) and, while
  capture is open, one capture period as input latency. Capture overruns stay in
  `record.input_get_state` and are not counted as playback xruns.
- `include/AudioDeviceDiagnostics.h`, `src/core/AudioDeviceDiagnostics.cpp` (new): `audioDeviceReport()`
  builds `mixer.cpu_load`'s `audio_device`: `backend`, `running`, `reports_timing`, `engine`
  (`sample_rate_hz`, `output_sample_rate_hz`, `period_frames`, `buffer_frames` - the engine's own), and the
  device readings `sample_rate` (Hz), `period_frames`, `buffer_frames` (frames), `input_latency`,
  `output_latency` (frames, plus `ms` and `basis`) and `xruns` (count). Each reading is
  `{available, value, unit}`; an unavailable one has `available: false` and no `value` - never 0.
- `mixer.cpu_load` (`src/core/ControlCommandsTrackLooks.cpp`) returns `audio_device` beside the unchanged
  `channels`, `tracks`, `late_periods`, ... ; with no audio device (the Dummy) every device reading is
  unavailable and the CPU and late-period state is still there.
- GUI: the CPU diagnostics window (header CPU readout > right-click > **CPU diagnostics...**) gains an
  **Audio device** table - backend, engine and device sample rate, engine and device period, device
  buffer, input and output latency, device xruns and engine late periods - filled from the same
  `mixer.cpu_load` reply it already reads through `ControlRegistry`, so the window and an agent read one
  state. Unavailable readings show "unavailable".
- Manual: `data/manual/index.html` (The window > Header).

## Format changes

None. Runtime telemetry only: nothing is serialised, old projects load and render exactly as before.

## Realtime

The only audio-thread additions are `countBackendXrun()` (a relaxed atomic add) in ALSA's underrun
recovery and in JACK's xrun callback. Everything else (`deviceTiming()`, the JSON) runs on the main thread
when the command is invoked. TSan does not run on this box; the counter is a `std::atomic<uint64_t>`, and
the ALSA fields `deviceTiming()` reads are written in the constructor (and `openCapture()` on the main
thread, published by the `m_captureOpen` atomic) - reasoning, not a run.

## Known limits

- JACK's buffer (period count) is not exposed by the JACK API: always unavailable on JACK.
- JACK latency is the first capture/playback port's latency range maximum; 0 is a real JACK report (an
  unconnected port), not "unavailable".
- ALSA output latency is the playback buffer size (the steady-state queue of a blocking writer), not a
  `snd_pcm_delay` measurement - calling into the PCM from the main thread while the playback thread writes
  is not safe. ALSA input latency is one capture period, and only while capture is open.
- Other backends (PulseAudio, PortAudio, SDL, OSS, sndio, soundio, the Dummy) report nothing yet: every
  device reading is unavailable on them (they keep their existing R2.2 latency figures for recording).
- The xrun count is since the device object was created; a device change starts it from 0.
