# Q050-093 - Detect tempo and auto-warp imported loops (P1, completion, L05)

**Unit.** Drop a loop, detect its tempo and key, and choose to follow the project tempo and key or keep it unstretched.
Members: B-ED-149, R-workflow-67, R-workflow-208.

**What it closes.** `detect.analyze` / `detect.apply` and `warp.*` existed side by side, but an import never derived or
applied clip warp state: `detect.apply` writes the *project's* tempo map and key, and a dropped loop always played at its
own rate. Now `clip.import_file` - the one command behind every file drop (Q050-031) and an agent's import - analyses
every audio file it imports with the same detector (`analyseAudioFile`) and takes a loop mode inside the same undo step.

## Commands and reversibility

- `clip.import_file` (changed, still `true_inverse`): the loop configuration is applied to the new clip inside the same step,
  so the existing Track checkpoint (or created-track action checkpoint) undoes clip and configuration together; redo
  rebuilds them from the checkpoint, which carries the new `<loopsource>` child, the warp element and the transpose.
- `clip.source_get_state` (new, `not_mutating`).
- The preference is written by the existing `settings.set` (its own class and inverse unchanged).
- Snapshot regenerated from a live instance: 879 ids / 77 groups on `050/m0-train-22` (README canary 878 -> 879); A16
  histogram `rows=888 true_inverse=434 snapshot=42 irreversible=25 not_mutating=387` (`docs/RELEASE-NOTES-v0.3.0-alpha.md`).

## Format changes

Additive only: a sample clip an import analysed writes a `<loopsource bpm tonic tonicname scale mode tempofollowed
keyfollowed transpose/>` child (`loopwarp::saveLoopSource`, `src/core/LoopImportWarp.cpp:187`). Load resets on absence
(`src/core/SampleClip.cpp:1084`), so a project without it - every older project - loads with no loop source, its own warp
element and transpose exactly as before (`LoopImportWarpTest::theLoopSourceRoundTripsAndAnOldClipLoadsAsBefore`). What
plays is the existing warp element and clip transpose; the new child is only description.

## Realtime

Nothing new on the audio thread. Analysis (file decode + detector), the loop source and every setter run in the command
handler on the control thread; the warp and stretch setters are the existing ones (`setWarpStretchMode` builds a Rubber Band
pool before publishing the mode, as `clip.set_transpose` relies on). `LoopSource` is never read by playback. TSan does not
run on this box; the reasoning is the design above.

## Known limits

- Analysis runs synchronously in the import (the detector reads at most the first 60 s); a long file holds the interface for
  the analysis time.
- The detected tempo is rounded to a whole BPM for the clip's source tempo (the exact estimate is kept and reported). A
  detector error of half a BPM or more would mis-stretch; accuracy on real music is unmeasured (`detect.*`'s own note).
- The key match is tonic to tonic, import-time only; a minor loop in a major project is moved to the project tonic, not to
  its relative key. Changing the project key later does not retune the clip.
- With no Rubber Band in the build the transpose is not applied (the note says so, the tempo still follows); this build has
  Rubber Band, so that branch is not exercised by a test here.
- Replacing a sample clip's audio by dropping onto it (`SampleClipView`) is not an import and is not analysed.
- Embedded ACID/loop metadata is not read; MIDI imports are unaffected (no `loop` in their reply).
