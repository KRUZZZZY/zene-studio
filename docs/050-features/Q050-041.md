# Q050-041 — Carla processing mutex fix

## What changed

Carla MIDI now crosses from `handleMidiEvent` to the render callback through the fixed-capacity `CarlaMidiHandoff` queue. `playImpl` stages queued events and calls Carla's native process function without taking a shared mutex. Queue reservation and each overflow-stamp update stop after eight compare-exchange attempts. A refused event is counted even if contention prevents its channel stamp from advancing. Overflow channel cuts and queued events share the fixed native-event budget; work that does not fit remains pending for the next period.

The output-budget regression was found while building the native event array: a due all-notes-off cut had not counted against the array capacity. `drainMidi` now caps successfully emitted events and cuts together.

## Round-four review response

Round three required two reworks. Both are done in `include/MidiHandoffQueue.h`.

| Finding | Change | Test | Evidence |
| --- | --- | --- | --- |
| Render-thread dequeue was still a `for (;;)` around `compare_exchange_weak`. | `pop()` is now single-consumer and wait-free: load the cell, compare its sequence with the dequeue position, copy the event, publish the next-lap sequence, store the advanced position. No loop, no compare-exchange. The single-consumer contract is in the class comment. `drainMidi()` is the only caller of `pop()` (grep: RemotePlugin, Vestige, ZynAddSubFx and CarlaMidiHandoff all go through it, each from its one render thread). | `MidiHandoffQueueTest::popHasNoRetryLoop` reads the header and rejects any loop keyword, compare-exchange or RMW inside the body of `pop()`. | Red on the round-3 header (`for (` found; test binary exit 2), green after (exit 0). |
| When the stamp-update budget was exhausted the channel kept a lower stamp, so the cut could fire before the last event accepted ahead of the refusal and a note-on could hang. | On exhaustion the producer sets a per-channel bit with one `fetch_or` (release), after `queuedBefore` was read. The consumer (`drainMidi`) takes the flags (acquire), reads `enqueued()` afterwards and keeps a consumer-private deferred stamp `enqueued() + 1`, never earlier than the refused event. A channel's cut is due when the shared or the deferred stamp is due; only the stamps that were due are cleared, so a not-yet-due cut is never lost. A deferred cut may land later than the exact refusal point: a newer note can be ended early, never left stuck. Every producer and consumer step is bounded. | `CarlaMidiHandoffTest::exhaustedStampUpdateNeverCutsBeforeAcceptedEvents` (production `enqueue` refusal, contention exhausts the budget, then `processPeriod` renders the stream: the last cut for the channel must come after the last accepted note-on); `MidiHandoffQueueTest::exhaustedStampUpdateDefersTheCutBehindQueuedEvents` (same at queue level). | Carla test red on the round-3 header (`lastCutIndex > noteOnIndex` FALSE, exit 1), green after (exit 0). |

Ordering of accepted events, the `drainMidi` event/cut budget, the refusal counters, allocation-free paths and the `LMMS_TESTING`-only hooks are unchanged.

## Carla runtime availability and limits

No system `libcarla`, `carla-host-plugin`, Carla executable, or Carla pkg-config metadata was available, including under `~/.local/zene-deps`. The configured build therefore uses weak Carla linking and its dummy native plug-in module. The tests compile the production hand-off against the bundled Carla native API header and pass a compile-time stand-in for `NativePluginDescriptor::process`.

This proves the queue, event encoding, ordering, output budgeting, render offsets, allocation behavior, and process-boundary delivery exercised by the stand-in. It does not prove behavior inside a real Carla instance or a third-party Carla plug-in, and the lock scan does not instrument runtime locks.
