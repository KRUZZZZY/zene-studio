# Q050-089.2 - Real-time hardware insert export (stage 2 of 3)

Type: completion (P1, size L, stage 2 of 3 of Q050-089). Members: R-mixing-18, R-performance-72. Area: L09.

## What was built

An offline export runs no audio device, so a channel's hardware insert is bypassed and the dry signal is
rendered (`HardwareIo.cpp` `processInsert`/`insertLatency`, unchanged). This stage adds a real-time render
that plays the song through the running device, so each insert's send goes out and its return is recorded.
It also makes the offline bypass explicit in `render.render`'s reply.

## Commands

- New: `render.realtime` (`not_mutating`; reversibility row in `ControlReversibilityTablePassive.cpp`). It writes an
  output file and changes nothing in the project; the loop switch and metronome are restored and the transport
  is stopped after the pass, as a Stop would.
- Changed: `render.render`'s result schema gains `hardware_inserts` (object) and its description says the
  render is offline with the inserts bypassed. Still `not_mutating`.
- Snapshot regenerated from a live instance: 872 ids / 76 groups. A16 histogram: one more `not_mutating` row.

## Format changes

None. Nothing new is saved; projects load and render as before. The tap is one atomic load per period while no
real-time render is armed, and an offline export takes exactly the path it took before.

## Realtime

On the audio thread: `realtimeexport::master()` and `RealtimeExportCapture::push()/keep()`. While idle that is one
acquire load. While armed they read the song position (the render thread's own state), scale into a fixed
512-frame member array and write the accumulator's pre-allocated lock-free ring; a full ring is counted as a gap,
padded on the drain thread. No allocation (proven by the allocation counter in `HardwareIoTest`), no lock, no I/O,
no signal. The accumulator is created by `arm()` on the control thread before the release store that arms the
take, and is only taken back once the state is `Done`, which the audio thread never leaves. A timed-out pass is
cancelled under the engine's change lock. The arm and the song's start share one change-lock section, so the
first period that sees the take armed is the song's first; the song's `m_playing` read on the render thread is
ordered by that lock. The WAV is written on the control thread after the pass. Local TSan does not run on this
box: this is reasoned from the design, not measured.

## Known limits

- The control surface and the interface wait while the song plays (like `render.render`'s child wait), at most
  600 s of song.
- Whole song only: no range, stems or per-track print; WAV only; the device's sample rate (no resampling to the
  export preset's rate); a stereo master only.
- External MIDI instruments are not printed.
- The project export dialog does not offer it yet: that is stage 3. The GUI entry here is the mixer channel's
  Hardware I/O menu.
- Found while writing the test, not changed here: `track.set_mixer_channel` on a track created before the channel
  answered with the new channel, but in 3 of 4 debug runs the track still played to the master (likely the
  track's channel model range, set when the track is made; not investigated further). The tests create the
  channel first, which routed correctly in every run.
