# Q050-501 - Tell users when a newer Zene version is available

Unit: P1, M, area L16. Goal: with the user's consent, tell them a newer release exists and take them to its download
page; nothing is downloaded or installed without them. Branch `feat/050-Q050-501-oc`, cut from `050/m0-train-24`; integrated onto `050/m0-train-25` (`081630835b`).

## What was built

- `include/UpdateCheck.h`, `src/core/UpdateCheck.cpp`: preferences in user configuration (`updatecheck/*`), SemVer validity
  (strict) and precedence (`ProjectVersion::compare` after validation), the feed parser, and `UpdateChecker`: one background
  `QNetworkReply`, a 15 s bound, a 4 MiB answer bound, https or loopback-http only, redirects never less safe, one
  `qInfo` line per failed check. The network manager is made by the first request, so an off setting never makes one.
- `src/core/ControlCommandsUpdateCheck.cpp`: `app.update_check_get` / `_set` / `_run`.
- `src/gui/UpdateCheckWindows.cpp`: the first-run question, the non-modal notice, Help > Check for Updates and
  `window.update_check` / `window.update_download_page`; the start-up step (4 s after the window, for a person only) and an
  hourly look at whether a day has passed. `src/gui/modals/SetupDialog.cpp`: Settings > General > Updates, saved through
  `app.update_check_set` and only for what changed.
- `-DZENE_UPDATE_CHECK=OFF` (`CMakeLists.txt`, `src/lmmsconfig.h.in`), independent of `ZENE_TELEMETRY`, compiles all of this out.
  `updatecheck::managedBy()` hides it at run time in a Flatpak or Snap: nothing registers and `check()` refuses.
- `app.whats_new`'s `update_check` now says whether checks are on (it was a constant false, still false on a fresh config).

## Commands and format

New commands (5; 922 ids, 78 groups on `050/m0-train-25`): `app.update_check_get` (not_mutating), `app.update_check_set` (true_inverse: one undo
step writing back the previous flags), `app.update_check_run` (not_mutating: stamps the time asked in config, no project
write; typed `refused` while off), `window.update_check`, `window.update_download_page` (not_mutating). `app.whats_new`'s
description changed. No project format change: all of it lives in the user's configuration, none in a project file.

## Realtime and threads

All of it runs on the main thread from timers, menu actions and command handlers; nothing is reachable from an audio
callback. Local TSan does not run here; by design there is one thread: Qt's network I/O is asynchronous and the lambdas
are connected with the checker as context, on the main thread.

## Known limits

See `docs/KNOWN-LIMITATIONS.md` ("Update check"). In short: the default GitHub feed was never contacted by any test; a
distribution package that does not set the option is not detected; the feed is not signed; a failed check waits for the
next day.
