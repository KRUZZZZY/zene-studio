# Q050-481.2 - Host VST2 effects through Carla (stage 2 of 4)

Queue unit (P1, L, modernisation, area L10). Branch `feat/050-Q050-481.2-oc`, cut from `050/m0-train-26` (`af010bc3cc`).
Goal: musicians and agents load native and Wine-bridged VST2 effects through Carla. Stage 1 (Q050-481.1, merged)
hosts VST2 instruments; stages 3-4 (converting VeSTige/VST-effect projects, removing `VstBase`/`Vestige`/`VstEffect`)
are later units. Nothing here has to be undone for them: the effect stores the same key attributes (`file`, `name`,
`uniqueid`, `binary`, `maker`) and Carla state the instrument does, which is what a converter will write.

## What was built

- **`plugins/CarlaVst2Effect` -> module `carlavst2effect`** (effect, built wherever Carla Rack is):
  - `CarlaVst2Effect` (a `DefaultEffect`) holds one VST2 plug-in in one Carla Rack instance (`carlavst2::Rack`,
    `CarlaVst2Rack.*`): the rack from `libcarla_native-plugin`, the plug-in added through Carla's host API
    (`carla_add_plugin` on `carla_create_native_plugin_host_handle`, from `libcarla_host-plugin`). Native binaries run
    in Carla; Windows `.dll`s in Carla's Wine bridge. No VST2 header is compiled anywhere (AGENTS.md rule 8).
  - `CarlaVst2EffectControls`: one automatable `CarlaParamFloatModel` per rack parameter slot; the slots the plug-in
    does not use have no name, so `plugin.param_*`, automation and the device's parameter lists see only the
    plug-in's parameters. State: Carla's project XML (binary, unique id, parameter values, the plug-in's chunk) plus
    each model's settings (`PARAM_KNOB_<n>`, automation links) - the instrument's format, inside the effect's controls
    element `<carlavst2effectcontrols>`.
  - `CarlaVst2EffectControlDialog`: a knob per parameter and the shared **Show plugin editor** button
    (`makeNativeEditorButton`, i.e. `plugin.editor_open`). `controlCount()` is at least 1, so even a plug-in without
    parameters gets the dialog (and the editor button).
  - The plug-in's own editor (`openNativeEditor`): embedded into Zene's editor window through `carla_embed_custom_ui`
    for a native plug-in; shown by Carla in its own Wine window for a Windows one.
  - `lmms_plugin_main` declines (placeholder, Q050-018) without a Carla runtime, without a key naming a binary, or
    when Carla cannot load it.
- **`plugins/CarlaVst2/CarlaVst2Renderer`** gains `Mode::Process` for effects (see Realtime). The instrument's
  `Mode::Generate` is unchanged.
- **Shared with the instrument host**: `CarlaVst2Discovery` moved from `plugins/CarlaVst2` into `carlabase` (exported),
  so both modules read one per-session discovery cache instead of running Carla's discovery tools twice per binary;
  `carlavst2::SubPluginFeatures` (`plugins/CarlaVst2/CarlaVst2SubPluginFeatures.h`) lists the synths for `carlavst2`
  and everything else for `carlavst2effect`.
- **Catalogue** (`src/core/ControlDeviceVst2.cpp`): `plugin.list` format `vst2` now has kind `effect` entries, appended
  after the VST2 instruments (so no `dev-<n>` that stage 1 handed out moves); `plugin.load` resolves them to
  `carlavst2effect`. The device picker (Add device, Add effect, Insert, Replace) shows them with format `VST2`;
  `MissingDevices` names a saved VST2 effect by its key.
- **Fixture** (`tests/data/vst2-test-effect`): a plain-C VST2 effect on the same clean-room ABI restatement as the
  stage-1 instrument (`zene_vst2_abi.h`, which gains `zvPlugCategoryEffect`), built natively and with
  `winegcc -b x86_64-w64-mingw32` as a Windows PE `.dll`. Output = (2·Left·inL, 2·Right·inR); it counts the blocks it
  heard sound in its chunk only; its chunk reports whether its editor is open; `ZENE_VST2_FIXTURE_STALL_MS` makes
  every process call sleep.

## Realtime

- **Carla never runs on the audio thread.** `CarlaVst2Effect::processImpl` (audio thread) calls
  `carlavst2::Renderer::process`: it copies the period's input into a preallocated input ring (release store), drops
  any late frames it owes (below), and copies out the frames processed two periods earlier, or silence (counted) if
  the worker has not finished them. Atomics and copies only - no lock, allocation, system call, Carla call or Qt
  signal. The worker thread takes input (up to one engine period, the buffer size Carla was told), pushes changed
  parameter values to Carla (`setParameterValueRT`), runs Carla's process in place, mixes wet/dry against the same
  input (so the dry signal stays aligned with the delayed wet one), and publishes into the output ring.
- **Latency is fixed and reported.** The output ring starts with two periods of silence; `latencyFrames()` reports
  them, so the chain's delay compensation lines the effect up; `tailFrames()` is the same, so auto-quit does not cut
  the delayed output. A period the worker missed is silence, and the frames it delivers late are dropped once they
  arrive (`m_late`, audio-thread only), so the delay stays what was reported rather than growing.
- **An export waits BETWEEN periods, never inside one** (review r1). The render path never waits, not even while a
  project is exported (`renderNextPeriod` runs in a `RealtimeScope`). Each VST2 renderer - the effect's and the stage-1
  instrument's - is an `offlinerender::Participant` (`include/OfflineRenderBarrier.h`, `src/core/OfflineRenderBarrier.cpp`);
  `ProjectRenderer::run` calls `offlinerender::waitForAll()` before each period, outside the render period, and each
  renderer returns once the frames the next period takes are ready (Process: every queued input processed; Generate:
  `latencyFrames()` rendered ahead), at most 2 s per period. An export without a VST2 device is unchanged (empty
  registry). While exporting, the effect's Carla rack also reports itself offline (`is_offline`), so Carla blocks for
  its plug-in and the Wine bridge on the worker rather than passing a block through.
- **No parameter signal on the render thread.** The effect's parameter models defer render-thread change signals; the
  worker hands each changed value to Carla before its next period; the effect's 30 ms GUI timer emits the deferred
  signals, and only then is Carla's UI told (`ui_set_parameter_value`, GUI thread). A value the plug-in's editor
  changed comes back on the GUI thread (queued there if Carla calls from elsewhere) without an echo.
- **The worker holds still** (between two periods, nested pauses counted) while Carla's plug-in or parameter list
  changes: state/preset load, parameter refresh, sample-rate change, and while the chunk is read for a save.
- Declared to the static sweep: `CarlaVst2Effect::processImpl`, `Renderer::process`, `Renderer::take`, `Renderer::read`
  (`tests/rt-safety-scope.txt`, reasons updated: none of them waits; `RtSafetySweep` PASS).
- Still on the GUI/control thread: discovery (`QProcess`), `carla_add_plugin`, state and preset I/O, editor calls and
  `ui_idle`. Carla's engine callback stores two relaxed atomics.
- Local TSan does not run on this box: the rings' ordering (one producer and one consumer each; release on publish,
  acquire on read), the late-frame accounting and the pause handshake were reasoned, not measured.

## Known limits

- **Latency**: two engine periods per VST2 effect (compensated by the chain). A Wine-bridged effect's first blocks
  after its bridge starts may be silence.
- **Wine bridge parameter lag**: after a long silence a Wine-bridged plug-in applies a parameter change one or two
  blocks late (measured during review r2, with or without a stall: the first sounding blocks at the old value). The
  export test plays the note once before exporting so this does not hide what it checks.
- **An export waits up to 2 s per period per VST2 device** for a worker that does not catch up (a hung plug-in), then
  goes on; that period of the device is silence in the file.
- **Bypass/sleep**: while the effect is bypassed or asleep (auto-quit) its rings are not fed; when it resumes, the
  first two periods are the output it had queued before (normally the tail of the signal that put it to sleep).
- **A Carla runtime is required.** Without one (an ordinary build links the weak stand-in) no VST2 effect is listed and
  a project that used one keeps it as a placeholder. Hosted CI has no runtime: there `CarlaVst2EffectHostingTest`
  reports Skipped; it fails, not skips, whenever the runtime and the fixtures exist and the host does not work.
- **Bridged chunk restore is unproven here** (as in stage 1): Carla hands a chunk to its bridge through a file in
  `/var/tmp`, which this lane's sandbox cannot write. The test checks it wherever that directory is writable and says
  so otherwise; bridged parameters, processing and the project round trip of parameters and output are checked.
- **The Wine-bridged editor** opens in Carla's own Wine window; not exercised by the test (no display).
- **Presets** live in the `carlavst2effect` preset folder, shared by every VST2 effect; a preset or state file carries
  its plug-in, so loading one made with another VST2 effect switches the device to that plug-in.
- **Mono/multi-bus**: the effect gets the chain's stereo pair; side-chain inputs and extra output buses of a VST2
  effect are not routed.
- 32-bit Windows binaries need Carla's 32-bit bridge, which `tools/build-carla-runtime.sh` does not build; untested.
- Converting VeSTige / VST-effect projects is stage 3; Q050-477's legacy corpus does not exist yet, so this stage adds
  no legacy-project fixtures.
