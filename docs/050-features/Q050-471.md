# Q050-471 Per-clip effect-chain storage

Branch `feat/050-Q050-471-oc`. The feature itself (per-clip realtime effects: the model, the render path, the agent
surface, the clip UI and the `<fxchain>` format) shipped under **Q050-111**; see `docs/050-features/Q050-111.md`.
This unit adds an independent storage regression for that chain and changes no product code.

## What this unit adds

- `ClipEffectsTest::theStorageRoundTripsAndOmitsEmptyChains` (tests/src/core/ClipEffectsTest.cpp), headless. It
  pins the storage contract that Q050-111 described but did not test end to end on its own.
- No product, command, snapshot or manual change. The storage code it covers already exists in
  `SampleClip::saveClipEffects` / `loadClipEffects` (src/core/SampleClipEffects.cpp:59-80).

## Format (`<fxchain>`)

Additive, on the `<sampleclip>` element:

- A clip whose chain holds at least one device writes one `<fxchain>` child: the same element and content a track's
  chain writes (`enabled`, `numofeffects`, one `<effect>` per device with its plug-in key, settings and on/off state).
- A clip whose chain is empty writes **no** `<fxchain>` child, so existing projects serialise as before.
- Reading: a clip element without the child loads with no effects (reset on absence). A restore over a clip that has
  since gained devices takes them off.
- A SampleTrack's own chain is a separate element. Its `<fxchain>` is a child of the track, not of a clip, and the
  storage test does not count it.

## Revert method

The single behaviour line that writes the chain on save is `saveClipEffects(_doc, _this);` in the clip's save path
(src/core/SampleClip.cpp, line 1072). It was commented out in the tree, the test executables
were rebuilt (log 005-build-red-1, built), and ClipEffectsTest was run (log 006-test-red-1). Then the line was
restored from a copy, the executables rebuilt, and the three tests re-run (log 008-test-green-1, 3/3 passed).

Under the revert, the new slot fails at its save-and-count check (line 362) and the pre-existing
`theChainSurvivesSaveAndReopen` also fails (line 265). So the new test catches the same defect the older one does,
from the headless side, and the revert is not a no-op.

## Known limits

These are unchanged from Q050-111; see `docs/050-features/Q050-111.md` ("Known limits"):

- Audio clips only. MIDI, pattern, automation and launcher-cell clips have no clip effects (typed refusal).
- An effect's tail stops when the clip's play handle ends; it is not rendered past the clip.
- A clip effect's latency is not compensated (PDC covers track and channel chains only).
