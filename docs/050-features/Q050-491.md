# Q050-491 - Host Audio Unit (AUv2) plug-ins on macOS

Queue unit (P1, L, feature, area L10): macOS builds list, load, play, automate, save and restore Audio Unit v2
instruments and effects, with their own Cocoa views. Branch `feat/050-Q050-491-oc`, cut from `050/m0-train-21`
(`37eaf07557`).

**Status: the code is written; the macOS half has not been compiled or run.** This lane runs on Linux, cannot reach a
macOS toolchain, and is never pushed, so no hosted macOS job has built it. What was proved on Linux, and how, is in the
table; every row that depends on the macOS job says so.

## What was built

- **Format-neutral rules, every build** (`include/AuComponent.h`, `src/core/AuComponent.cpp`):
  - a component is named by its three four-character codes, and stored in a project as `type:subtype:manufacturer`
    (`aufx:bpas:appl`; a non-printable code is written as eight hex digits);
  - `scanCachePath()` gives each component its own absolute scan-cache path, `/AudioUnits/<type>/<subtype>/<maker>`.
    An AU component has no file of its own (all of Apple's are in one bundle), and the quarantine list only takes
    absolute paths;
  - `recordScan()` applies the scan-cache rules a plug-in file gets: a quarantined component is left out and reported;
    every other one is recorded (name, maker, version, kind); only `aufx`/`aumf` (effects) and `aumu` (instruments)
    are listed; any other type is recorded as "not a plug-in". An unchanged registry writes nothing;
  - `instantiationError()` / `statusName()`: the typed refusal names the component, the step that failed and the
    OSStatus with its name.
- **The catalogue** (`src/core/ControlDeviceAu.cpp`): the `au` half of `plugin.list` / `plugin.load`, after CLAP so no
  existing `dev-<n>` moves. Entries carry `component` and `scan_cache_path`. Off macOS it is a no-op, and a hand-made `au`
  entry is refused (`Refused`, "AU hosting is built on macOS only").
  - `plugin.list` offers the `au` filter only where it is built (`controlAuHostingBuilt()`); so does the organiser's
    preferred-format list.
  - `plugin.load` of an instrument now adds the host's instantiation reason, as an effect's load already did.
  - `MissingDevices` names a saved AU device by its name and component.
  - The device picker labels the format "Audio Unit".
- **The macOS host modules** (`plugins/AuEffect` -> `aueffect`, `plugins/AuInstrument` -> `auinstrument`; each
  `CMakeLists.txt` returns early unless `LMMS_BUILD_APPLE`, and `-DWANT_AU=OFF` turns them off):
  - `AuSubPluginFeatures`: the registry (`AudioComponentFindNext`) through `recordScan()` into the factory's scan cache,
    saved when it is persistent; the maker goes to `pluginvendors` for `plugin.list`'s `vendor`.
  - `AuHost` (Objective-C++, no ARC; `-xobjective-c++` on that one file):
    - loads with `AudioComponentInstanceNew`;
    - `prepare()` sets stereo non-interleaved float on the output (and on the input for an effect), the maximum
      frames, and `AudioUnitInitialize`;
    - the effect's input arrives through a render callback that copies the pointers `process()` set;
    - `process()` applies pending parameter values (atomics), hands queued MIDI to `MusicDeviceMIDIEvent` at its
      frame, and calls `AudioUnitRender` into the caller's buffers;
    - state is `kAudioUnitProperty_ClassInfo` as a binary plist;
    - latency and tail come from their properties;
    - the editor is the unit's `kAudioUnitProperty_CocoaUI` view, else CoreAudioKit's `AUGenericView`, added to the
      editor window's NSView. Under any Qt platform but `cocoa` it is refused by name, because the window id is then
      not an NSView.
  - `AuEffect` / `AuEffectControls` / `AuEffectControlDialog`: the same device and chain model as the CLAP effect (wet/dry,
    bypass, latency/tail to the chain, the native editor through `PluginNativeEditor`), knobs plus "Show plugin editor".
  - `AuInstrument` / `AuInstrumentView`: MIDI-based and single-streamed like the CLAP instrument. Note on/off, key and
    channel pressure, CC, pitch bend and program change go into the VST3 host's bounded lock-free MPSC queue
    (`Vst3MidiQueue.h`, header-only, no SDK type).
  - `AuParameter`: each parameter is a `FloatModel` (`au-<id>`) under the device, so `plugin.param_get` / `param_set`,
    automation, controllers and modulators find it as any device's. It is saved with `AutomatableModel::saveSettings`,
    which keeps automation links, beside `<state>`.
    - **The handoff to the unit is per block (review round 1).** No `dataChanged()` connection sends values to the
      unit. The device's `processImpl` calls `AuParamModelList::pushChangedValues()` before it renders: it reads each
      model's value and hands a changed one to the unit through `ParamTarget::setParam`, an atomic store the same
      block applies.
    - Each model defers its render-thread signal (`setDeferChangeSignalOnRenderThread`), so an automation tick emits
      nothing on the render thread. The GUI poll emits the held-back signals (`flushDeferred()`).
    - The poll does not pull a unit value over a host change the audio path has not handed over yet.
    - `AuParamModelList` works on `au::ParamTarget` (`HostedUnit` is one), so the handoff is tested on every build.
  - `AuState.cpp` (the `<state>` save and load) and `AuCocoaView.cpp` (the unit's CocoaUI view, Objective-C++) were
    split out of `AuHost.cpp` for the file-length gate (review round 2).

## Format changes

- An AU device is saved as the effect/instrument key `component` + `name`. Its settings are saved under `<au>` (effect)
  or `<auinstrument>`: `<state>` (base64 binary plist of ClassInfo) and `<parameters>` (each `au-<id>` model with its
  automation link).
- Old projects are untouched: no existing element changes.
- A project with an AU device opened off macOS keeps it as a placeholder that writes its state back, the same rule as
  any missing module. `MissingDevices` names it as format `au`.

## Realtime

- The audio thread calls only `AudioUnitSetParameter`, `MusicDeviceMIDIEvent` and `AudioUnitRender`, plus pops from the
  preallocated MPSC ring and reads the parameter models (`AuParamModelList::pushChangedValues`).
- No Qt signal is emitted on the render thread for an AU parameter (review round 1): automation's change is deferred by
  the model and emitted by the GUI poll; the value reaches the unit through atomics. Proved by `AuParameterHandoffTest`. Buffers, the `AudioBufferList`, the scratch blocks and the parameter atomics are all
  allocated in `prepare()` / `load()` on the GUI thread, with the engine held for a re-prepare.
- The render callback copies from pointers set by the same thread.
- What a third-party unit does inside `AudioUnitRender` is its own; Apple's API contract makes those three calls the
  realtime path.
- TSan does not run on this box. The race reasoning:
  - parameter values: release store / acq-rel exchange per index;
  - MIDI: the VST3 queue's sequence-number ring;
  - `prepare` / `loadState`: only under `requestChangeInModel` (a recursive mutex, so nesting inside a project load is
    safe).

## Known limits

- Stereo only. No side-chain bus, extra output buses, factory presets or AUv3.
- SysEx is not passed.
- The editor needs Qt's `cocoa` platform.
- The macOS code is compile-checked here only by syntax: GCC with real headers for the plain C++ files, clang with stub
  SDK headers for `AuHost.cpp` and `AuCocoaView.cpp`. The first hosted macOS run is its build proof.
