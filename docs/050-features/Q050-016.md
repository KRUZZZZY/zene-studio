# Q050-016 — MPE expression event streams

Unit: capture, edit through commands, save, and play **time-varying** pitch, pressure and timbre
points on individual notes. The merged model stored one scalar `MpeNoteExpression` snapshot per
note (task #601); this unit adds per-axis ordered `(tick from the note's start, value)` streams on
top of it, the agent commands that read and write them, backwards-compatible serialization, a
playback path that delivers each point at its own frame offset, and the piano roll's GUI path to
the same commands (round 2). The full GUI curve editor stays the dependent unit Q050-137 (see
Known limits).

## Built
- **Model** — `MpeExpressionPoint` and `MpeExpressionStream` in `include/MpeExpression.h:79`/`:106`
  (three axes, `MaxPoints = 256`, points sorted by tick, each holding until the next);
  `MpeExpressionStream::setPitch/setPressure/setTimbre/clear` and `valueAt()` in
  `src/core/midi/MpeExpression.cpp:115`/`:152` clamp and order the points (stable sort, so a
  round trip never reorders a user's points). `MpeExpression::bendForPitchCents()`
  (`src/core/midi/MpeExpression.cpp:219`) is the inverse of the existing bend→cents mapping, used
  to turn a streamed pitch point into a MIDI bend.
- **Note storage** — `Note::hasMpeStream()/mpeStream()/mpeStreamForEdit()/setMpeStream()/
  clearMpeStream()` (`include/Note.h:242`) backed by a `std::shared_ptr<MpeExpressionStream>`
  (round 2: shared, never mutated in place — copies, including the `NotePlayHandle` the audio
  thread builds by copying the note, share the same immutable snapshot, so starting a streamed
  note allocates nothing on the audio thread; every mutation goes through `mpeStreamForEdit()`/
  `setMpeStream()`, which detach — copy-on-write — on the calling UI/control thread, so the audio
  thread never observes a half-written vector; the same sharing shape as the detuning helper).
  Serialized as three **optional attributes** —
  `mpepitchpts` / `mpepressurepts` / `mpetimbrepts`, `tick:value,tick:value,...` — written only
  when an axis is non-empty (`src/core/Note.cpp:568`) and parsed with per-token validation,
  clamping and re-sorting (`src/core/Note.cpp:682`). An attribute, not a child element, because
  `Note::loadSettings` treats any child of a note element as detuning.
- **Playback** — `src/core/MpeExpressionStreamPlayback.cpp` (new): `NotePlayHandle::
  scheduleMpeExpressionStream()` is called from `NotePlayHandle::play()`
  (`src/core/NotePlayHandle.cpp`) right after the note-on. For every stream axis it emits the
  points whose tick falls in the current period, each at its own frame offset
  (`sendMpeExpressionAxisEvent`: pitch → MIDI bend on the note's channel, pressure →
  channel pressure, timbre → CC74). `effectiveMpePitchCents()` feeds
  `updateFrequency()`, so a streamed pitch curve retunes the
  built-in synthesisers from period to period while the bend event reaches a MIDI consumer
  sample-accurately. `sendMpeExpressionMidi()` skips an axis a stream schedules, so no snapshot is
  sent first. A note with no stream runs none of this: nothing changes for every project saved
  before this feature. Round 2: the point-offset math (`NotePlayHandle::mpeStreamPointOffset`,
  now a public static pure function) is 64-bit throughout (`std::llround`/`std::int64_t`) —
  frame positions past 2^31 are real (`f_cnt_t` is 64-bit) and on LLP64 (Windows) `long` is
  32 bits, so the old `std::lround`/`long` spelling truncated them.
- **Commands** (both on the agent surface, one registered `ControlRegistry` command each) —
  `note.expression_stream_get` (`src/core/ControlCommandsNoteExpression.cpp:268`) and
  `note.expression_stream_set` (line 297, `replaceStreamAxis` line 249). The set command replaces
  the axes the call names (an empty array clears one axis; omitting an axis keeps it; all empty

- **GUI path** (round 2) — the piano roll's note-tools menu (`makeNoteTransformActions`,
  `src/gui/NoteTransformActions.cpp`): **MPE pitch ramp...** asks the bend at the note's end in

  (into cents) and records each axis's last value and period offset; `tests/src/plugins/

## Known limits
- **No GUI curve editor.** The piano roll's note-tools menu edits streams (MPE pitch ramp...,
  Clear MPE expression streams — round 2); drawing/dragging them is Q050-137, which depends on
  this unit. The existing note-editor expression
  lane edits the scalar timbre/pressure values (`note.expression_set`), not the streams.
- **Point resolution is a tick**, and the pitch axis retunes the built-in synthesisers from period
  to period (a note's frequency is computed once per block); the MIDI bend event is the
  sample-accurate part a hosted instrument or MIDI output sees.
- **No interpolation**: a point holds until the next (step), where `note.pitch_curve` interpolates
  linearly. The two are different stores on purpose — the pitch curve is the note's detuning
  automation, the stream is the MPE gesture log.
- **A DSP consumer of pressure/timbre is still the in-tree test fixture**; no built-in synthesiser
  reads those axes (unchanged from #649).
- TSan does not run on this box, so the realtime race argument is by design: streams are written on
  the UI/control thread with copy-on-write detach, and a playing handle shares the note's immutable
  snapshot (one lock-free reference count), so the audio thread never observes a half-written vector.

audio-thread note copies (an unsynchronised write of a `std::shared_ptr` object while the audio

### Design and memory-ordering argument (TSan cannot run here)
Writers (the UI/control thread: commands, the piano-roll actions, `operator=`, loading) never
change a published snapshot: they build a complete new one and publish it with a `seq_cst`
`exchange`, whose release half makes the snapshot's contents visible with the pointer. The audio
thread only (a) copies notes - `acquire()` - and (b) destroys its handles - `release()`/`retire()`.
Why a copy can never touch a freed snapshot (`include/MpeStreamSnapshot.h:58`):
1. `acquire()` raises the global `s_copiesInFlight` (`seq_cst`) before it loads the slot
   (`seq_cst`), takes its reference with an increment that refuses a zero count (so a snapshot on
   its way to reclamation is never revived; a zero count means the slot swapped it out, so the
   slot is re-read), then lowers the counter (`release`). An empty slot read first returns at once:
   a note without a stream costs one atomic load and touches no shared counter.
2. A count reaches zero only after every slot that held the snapshot swapped it out; each slot's
   swap is sequenced before its own decrement, and the `acq_rel` decrements form one release
   sequence to the final one - so every swap happens-before the freeing thread's `seq_cst` read of
   `s_copiesInFlight`.
3. If that read sees 0, any copy that loaded the snapshot had already lowered the counter (its
   decrement is in the value read: its reference-count reads happen-before the free), and any copy
   that raises the counter later is after the swap in the single `seq_cst` order, so its slot load
   returns the new pointer. If the read sees a copy in flight, the snapshot is retired and
   `reclaimRetired()` repeats the same check (splicing the list back if a copy is still in flight).
Frees happen only in `destroy()`, reached from `release()` when no `RealtimeScope` is active, the
caller did not ask to defer, and no copy is in flight - or from `reclaimRetired()`, which refuses
inside a `RealtimeScope`. A `NotePlayHandle` always defers. Publication never blocks the audio
thread: there is no lock anywhere on the path (the track lock `play()` already takes with `tryLock`
is untouched and is not relied on).

### What was not measured / open
- **Locks are not counted at run time on this box.** The lock-freedom claim rests on: no mutex,
  condition variable or wait on the path (code; rt-safety sweep finds none in the declared
  functions), `static_assert(is_always_lock_free)` on every atomic used, and the hosted RTSan job,
  to which `MpeStreamSnapshotTest` is now added (it runs on dispatch/schedule; not run by this lane).
  Allocations and frees ARE counted absolutely (AllocationProbe, now with frees).
- The whole `NotePlayHandleManager::acquire`/`release` path is still not allocation-free for any
  note (upstream: `new BaseDetuning`, `m_processHandles` growth, `s_mutex`, `lock()`); the stream
  adds nothing to it (the stream's own operations measure 0/0). `MpePlaybackTest::
  streamedHandleAcquisitionAllocatesNothingExtra` stays as the comparison it always was.
- `Note`'s other fields (key, position, ...) are still plain members written by the editor without
  synchronisation against the audio thread's copy (upstream design); only the stream pointer is
  covered here.
- **Live capture is still not built**: an MPE controller's changes during recording are not yet
  written into the recorded note's stream (the brief's outcome bullet 1); acceptance (a)-(c) does
  not test it and the REWORK did not ask for it, but a reviewer should know it is missing.
