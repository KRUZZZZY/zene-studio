# Q050-227.1 - Persistent mixer docks (stage 1/2: persistent mixer zones)

**Unit.** The mixer's body becomes a dockable arrangement of four regions whose separators resize them, and the
arrangement and the widths are saved with the project's window layout and restored when the project reopens.
Stage 1 of cluster Q050-227; stage 2 adds pinned strips (`pinned_channels`), which this stage deliberately does
not build and does not design against.

**Goal.** "Users can dock mixer regions, resize their separators, and restore those choices with the saved
project layout."

**Design.**

- **Four regions, one splitter.** `MixerView`'s body was a fixed `QHBoxLayout` chain (master, scrolling
  channels, add buttons, VCA strips, effect rack). It is now one horizontal `QSplitter` of *dock hosts*:
  `master`, `channels`, `vca`, `rack`. The channels' host keeps the scrolling area **and** the add buttons
  together, so a separator can never land between the strips and their New/Return buttons. Master-first and the
  rack stack's index order are preserved (`m_mixerChannelViews[0]` is still a child of nothing but its host),
  which the strip code and `EffectRackView` parenting depend on.
- **A portable layout, not a Qt blob.** `include/MixerZones.h` defines `mixerzones::Layout` as
  `docks` (region id -> `left`/`middle`/`right`) plus `sizes` (region id -> logical pixels). Serialization is
  `{"zones": {id: dock}, "sizes": {id: pixels}}` with `fromJson` tolerant by construction: unknown ids are
  ignored, an unusable dock or size falls back to that region's default, `channels` refuses to leave `middle`,
  and a document with no object at all is `defaultLayout()`. No `QByteArray` of `saveState()` crosses a version.
- **One live state.** `mixerzones::MixerZoneState` (a process-wide `QObject`) holds the one `Layout`; the view
  renders it in `relayoutZones()`; a separator drag reports the new widths through `zoneSizesJson()` to the
  registered `window.mixer_zones` command (`live: true`), which writes them through `setSizes()` without
  re-laying the splitter mid-gesture. A layout change emits `changed()`, so the view re-lays itself
  immediately; `m_applyingZones` keeps a programmatic `setSizes()` from being mistaken for a user drag.
- **Persisted with the layout the project already keeps.** The shell's `snapshot()` gains one key,
  `mixer_zones`, and `restoreSnapshot()` reads it (absent -> `reset()`, i.e. the default arrangement). That
  means the arrangement travels with `ui/shell.layout` (personal layouts, `window.layout_save`) and with the
  project's own layout (`window.layout_project_save` / `window.layout_project_apply`), through the one
  existing undoable layout step - no second project section, no second format, and a project from before the
  feature opens with the default arrangement because its snapshot simply has no such key.
- **The undo step is now honest on screen.** `window.layout_project_save` was already `true_inverse` through
  `uistore::writeProject`, but its `apply` was empty: undoing put the *project* layout back without putting the
  window back. Its `apply` now restores the stored layout onto the live shell, which is what the mechanism's
  own transaction text claims, and it is what makes the zones' undo visible.
- **Realtime untouched.** All of this is GUI-thread widget code. Nothing is added to `updateFaders()`, the
  audio thread or any model notification path; a separator drag is a Qt mouse event on the GUI thread.

Commands (group `window`):

| Command | Mutating | Reversibility |
| --- | --- | --- |
| `window.mixer_zones` | no (writes no project data of its own - the arrangement lives in the layout, whose save is the step) | `not_mutating`, with the row stating where the data lives and how to put it back |

Its arguments: `dock` (`"rack=left"`, or just `"rack"` for the side it is not on), `zones` (the whole
`{region: dock}` object), `sizes` (`{region: pixels}`, 24..4000), `reset`, and `live`. Its answer: `zones`,
`sizes` and `mixer_zones` (the object the shell snapshot keeps). Every argument is validated by
`mixerzones::parse()` before anything is applied, so a refusal is typed `InvalidArgs` and changes nothing.

**A separator drag IS a command call.** `QSplitter::splitterMoved` does not write `MixerZoneState`; it
invokes the registered `window.mixer_zones` with `live: true` and the widths the splitter now has, so a drag
and an agent's `sizes` argument are one path into one handler with two callers. `live` exists because the
splitter already shows those widths: the handler's live branch writes them through the state's sizes-only
path and never re-lays the splitter, which is what makes it safe in the middle of a gesture. `live` refuses
`dock`, `zones` and `reset` (typed `InvalidArgs`), because a dock during a drag would re-parent the widget
under the mouse and would also mean the gesture was asking for something it never showed.

The GUI entry is the mode bar's **Zones** chip: one submenu per side region with **Left**/**Right** (the one in
force checked), then **Reset the Layout**. Every entry is an action with `controlCommand = window.mixer_zones`
that runs the command through `runCommand`, so the menu and an agent take the identical path.

Format changes. `ui/shell.layout` and a project's `<workspace>` layout part gain one optional object,
`mixer_zones: {"zones": {...}, "sizes": {...}}`. It is additive: nothing reads it unless it is there, an old
document is the default arrangement, and a new document opened by an older build ignores the key (the layout
model itself tolerates unknown keys). No project XML node and no other format changes.

Known limits.

- The widths are logical pixels, not proportions, so a mixer docked on a very different DPI opens at the same
  pixel widths it was saved with. That is deliberate (a strip is a pixel-sized thing), but it is not a
  percentage layout.
- A region hidden because it has nothing to show - the VCA area with no groups - keeps its stored width and
  comes back at it; it cannot be *docked away* by the user, because every region always has a side.
- This stage docks the four regions the mixer already had. Stage 2's pinned strips are not built here, and no
  `pinned_channels` argument exists yet.
