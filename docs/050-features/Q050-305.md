# Q050-305 - Verify and synchronize live pin edits (L09, priority 40)

**Unit.** Change audio pins and channel counts during playback without a data race, a stale routing cache or audio on the
wrong channel.

**Verdict: the synchronization is already in the product, and it is now verified and guarded.** The finding
(`R-mixing-13`) says `Matrix::setPin` writes the shared pin matrices and the routing caches from control and GUI callers
"without visible engine synchronization", and that the race is unreproduced. The write side was synchronized by the
accepted cluster-23 fix (`e814e57e3e`, on this train). This unit supplies what was missing: a test that drives the real
mutators against a real render period, a stress run that checks the caches and the routed audio period by period, and a
measured red state that shows what the missing guard does. No product change was needed, which is the second acceptance
criterion's "measured refutation without an unnecessary code change"; the reasons are below, with file and line.

## What the code does today (measured on this branch)

Every mutator of the routing state takes `AudioEngine`'s model-change guard, the `std::recursive_mutex m_changeMutex`
(`include/AudioEngine.h:888`) that `AudioEngine::renderNextPeriod()` holds for a whole period
(`src/core/AudioEngine.cpp:1220`):

| mutator | `takeRoutingEditGuard()` at |
| --- | --- |
| `AudioPortsModel::setAllChannelCounts` | `src/core/AudioPortsModel.cpp:153` |
| `AudioPortsModel::setTrackChannelCount` (and `growTrackChannels`) | `:196` |
| `AudioPortsModel::setChannelCounts` (`setChannelCountIn`/`Out` delegate to it) | `:227` |
| `AudioPortsModel::setPins` (batch) | `:313` |
| `AudioPortsModel::loadSettings` (project load) | `:350` |
| `Matrix::setPin` (a pin click, `port.set_pin`) | `:518` |
| `Matrix::setPinBatch` (batch, project load) | `:535` |
| `Matrix::setTrackChannelCount` | `:541` |
| `Matrix::setChannelCount` | `:562` |
| `Matrix::loadSettings` | `:686` |

`takeRoutingEditGuard()` (`:64`) returns that guard except in the three documented cases: no engine (a model built before
`Engine::init`), the calling thread is already inside a `RealtimeScope` (the render thread and the render workers own the
data), and a model created inside `DetachedBuildScope` (a device that is in no chain, so the render thread cannot see it).
`RealtimeScope`'s depth is `thread_local` (`include/RealtimeScope.h:74`), so a realtime worker cannot make a control-thread
edit skip the guard.

The readers of the same state are:

- the router and the bus inside a render period: `directRouting()`, `trackChannelsUpperBound()`,
  `in()/out().enabled()`, `out().usedTrackChannels()` (`include/AudioPorts.h:186`, `:431`, `:447`, `:600`;
  `src/core/AudioBus.cpp:91`, `:99`, `:100`, `:276`, `:286`, `:291`) and `Effect::processAudioBuffer`
  (`src/core/Effect.cpp:362`). All of them run inside the period that holds `m_changeMutex`;
- the control thread: `PinConnector`'s paint and click handling (`src/gui/PinConnector.cpp:345`, `:363`, `:397`, `:581`)
  and the ports commands (`src/core/ControlCommandsPorts.cpp:136`, `:139`, `:170`, `:174`, `:306`, `:383`, `:416`).
  `ControlRegistry::dispatch()` runs every handler on the UI thread (`src/core/ControlRegistry.cpp:274` →
  `runOnUiThread`, `:219`, a `Qt::BlockingQueuedConnection` into the application object), which is the same thread that
  paints the Pin Connector.

So the writers are serialized against the render period by the guard, and the readers on the control side are the writer's
own thread. There is no remaining unsynchronized pair in the pin path, which is why this unit makes no product change.

## ThreadSanitizer: what was measured, and why this lane has no TSan number

- TSan itself works on this box: a two-thread probe compiled with `g++ -fsanitize=thread` reported its race
  (`SUMMARY: ThreadSanitizer: data race /tmp/tsan_probe.cpp:2`, exit 66). The instrumented runtime starts here.
- A TSan build of the product is refused. This lane may not configure a build tree:
  `cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug -DWANT_DEBUG_TSAN=ON ...` →
  `bunny-guard: configuring is the parent's job; the lane build tree is already configured. Use 'cmake --build build
  --target <t>'.` (exit 97). The configured tree has `WANT_DEBUG_TSAN:BOOL=OFF`, and the TSan switch is a compile flag, so
  the test cannot be instrumented without a configure.
- The two fallbacks are unavailable: `valgrind` is not installed, and `vm.mmap_rnd_bits` (the ASLR entropy the
  `setarch -R` note in `tests/run-mixer-concurrency-tsan.sh` is about) is not readable by this user
  (`cat /proc/sys/vm/mmap_rnd_bits` → `Permission denied`).

So the race argument is made from the design, the ordering measurement and the red state, not from a sanitizer report, as
the lane brief allows. The deterministic slot is what a TSan run would have had to agree with: while the period is open the
edit is parked on the same mutex the period holds, and `modelChangeWaiters()` says so.

## Commands, formats, limits

- **No command was added or changed.** The two user-facing paths already existed and both reach the now-verified code: the
  Pin Connector's click (`src/gui/PinConnector.cpp:581`) and the agent commands `port.set_pin` / `port.set_pins`
  (`src/core/ControlCommandsPorts.cpp:306`, `:383`, `:416`), the latter through `AudioPortsModel::setPins`. Undo is
  unchanged: `port.set_pin` still records its one inverse from the value it read before the write, `port.set_pins` is one
  snapshot step, a bare `Matrix::setPin` from the view journals nothing (reversibility classes `true_inverse` and
  `snapshot` in `ControlReversibilityTableRouting.cpp`, both unchanged). No snapshot or A16 row changes, because no command
  metadata changed.
- **No format change.** Pins, channel counts and the `track_channels` attribute are written exactly as before; the save and
  load in the test is the existing format. Old projects load and render as before: the only product files this unit touches
  are the two test manifests.
- **Limits.** (1) The stress half checks the routing of one stereo bus pair; pins on track channels past the pair are
  created and removed by the script and are covered by the cache checks and by the save/load, but a bus with more than one
  pair is not rendered here. (2) `Matrix::setPin`'s and `AudioPortsModel::setPins`'s own parameter ranges are not validated
  by the model (the callers validate), which is unchanged behaviour and not this unit's finding. (3) The measured
  observation of "parked" is `modelChangeWaiters()`, so the slot proves the guard is taken at the mutator; it does not
  re-prove the guard's own correctness, which `AudioEngineNullRenderTest` and the mixer concurrency suite cover.
