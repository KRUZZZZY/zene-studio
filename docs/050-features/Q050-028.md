# Q050-028 - Wake the ALSA MIDI output thread on queued events

Type: fix (P0, size S). Member: R-performance-4. Area: L15.

## What was built
- The wake path was already in place before this unit: `MidiAlsaSeq::processOutEvent()` writes the wake pipe on the
  first push after a drain (`MidiOutQueue::pushAndRequestWake`), and `run()` consumes the wake byte (`src/core/midi/MidiAlsaSeq.cpp`).
- This unit adds the proof: a test-build-only marker `MidiAlsaSeq::pollWaitActiveForTesting()` (`include/MidiAlsaSeq.h`),
  set around the worker's `poll()` call (`src/core/midi/MidiAlsaSeq.cpp`, guarded by `LMMS_TESTING`). Production builds
  carry no extra code or behaviour.
- `tests/src/core/MidiOutQueueTest.cpp`: `queuedEventReachesAnAlsaSequencerClientPromptly` opens an ALSA capture client
  (`default`), routes Zene's output port to it, waits until the worker is inside `poll()`, queues one NOTE_ON and
  measures arrival. It fails if arrival is at or over 150 ms (the old poll timeout is 250 ms). The helpers
  `openReceiver`, `waitForNoteOn`, `waitForPollWait` keep the function under the complexity ratchet (CCN 10).
  If the ALSA sequencer cannot be opened, the test QSKIPs with the reason, so hosted CI without `/dev/snd/seq` stays green.
- `tests/upstream-modifications.txt`: two lines record the test-only marker in `include/MidiAlsaSeq.h` and `src/core/midi/MidiAlsaSeq.cpp`.
  `MidiOutQueueTest` now uses `QTEST_GUILESS_MAIN` (it needs an Engine for the ALSA case).

## Known limits
- The ALSA end-to-end test depends on an ALSA sequencer device. On a machine without one it skips; it does not prove
  delivery there. The arrival bound (150 ms) is measured on one Linux host; it does not measure hardware MIDI latency.
- Not run under ThreadSanitizer (the TSan evidence is for Q050-043).
