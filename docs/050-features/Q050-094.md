# Q050-094 - Make audio record modes honor history

Unit: P1, M, completion (area L03; WF-082, R-recording-5). Goal: users choose overdub, replace or
keep-history behaviour for audio recording, with each kept pass preserved as a take lane.

Starting claim, verified: `transport.record_options` offered only `overdub` / `replace` and the Record Mode
menu was titled "Record Mode (MIDI)"; an audio pass always replaced the clip's audio (the first take of an
arming went through `SampleClip::setSampleBuffer`, `src/core/SampleClip.cpp`, without looking at the mode).

## What was built

- **One mode list for MIDI and audio** (`include/RecordOptions.h`, `src/core/RecordOptions.cpp`):
  `Mode::KeepHistory = 2` joins `Overdub = 0` and `Replace = 1` (the numbers stored in the config file are
  unchanged; a number no build knows reads as Overdub). `modeNames()` is `overdub`, `replace`,
  `keep_history` and drives the command schema, the Record Mode menu and the Rec mode readout.
  `midiScope()` / `audioScope()` / `modeScope()` / `modeChoice()` / `modeLabel()` state what each mode does
  to each medium; the reply of `transport.record_options` carries `mode`, `mode_label`, `mode_scope`,
  `midi_scope`, `audio_scope` and `modes` (the old keys, `replace_erases` and `replace_keeps` included,
  are unchanged).
- **The audio pass lands according to the mode** (`src/core/SampleClip.cpp`, `include/SampleClip.h`,
  main-thread completion path only - `acceptRecordedTake` -> `installFirstPass`):
  - *Replace*: as before - the pass is the clip's audio; the arm's track checkpoint makes one undo bring
    the earlier audio back.
  - *Overdub*: when the clip has audio, the pass is mixed into it sample for sample from the first frame
    (`recordoptions::overdubMix`, resampled to the clip's rate when they differ; as long as the longer),
    so the old audio stays audible beside the new. A clip that does not play as recorded (trimmed window,
    reversed, warped, frame-led or offset) is left untouched and the pass is added over it as a clip of its
    own on the same track - never thrown away. A clip with no audio takes the pass as its content, as it
    always did.
  - *Keep History*: every pass is a take lane of the clip's group. When the clip already holds audio, a
    copy of it (its window, fades and how it plays) becomes a lane first; the pass becomes the next lane and
    the active take (`TakeLaneModel::recordTake(..., overrideChoice=true)`: the newest pass is active even
    over a take the user chose earlier; `comp.take_select` / Next Take Here choose another). The armed clip
    stays as the empty shell the lanes hang from (as after a loop recording) and keeps its length.
  - A loop recording's passes (a wrap while the transport still records) are lanes in every mode, as they
    were; the loop policy is a separate unit.
- **Take lanes are now saved and survive later checkpoints.** The lane clips of a recording were created
  with journalling switched off and left off, and `JournallingObject::saveState` writes nothing for such a
  clip: the lane list was in the project (`<z:lanes>`) but the lane clips were not, and a later track
  checkpoint (a take choice, its undo) would have dropped them. Journalling now comes back on once the
  clip is placed (the placement is still not an undo step of its own - the arm's step covers it). This also
  repairs loop-recording lanes (the same code path).
- **GUI**: `src/gui/RecordLaunchMenus.cpp` - the submenu is "Record Mode" and lists all three choices, each
  with its scope as the tooltip, the one in use checked, each running `transport.record_options`.
  `src/gui/shell/TransportReadouts.cpp` / `include/TransportReadouts.h` - the Rec mode readout offers the
  same three (right-click) and takes typed `overdub`, `replace` or `keep`; `recordMode()` exposes the field
  for its test. `src/gui/editors/PianoRoll.cpp` - the record buttons' tooltip states the MIDI scope.
- **Agent**: `transport.record_options` (`src/core/ControlCommandsRecordingPass.cpp`) - the same three
  `mode` values; description updated. Reversibility is unchanged: `true_inverse`, one undo step per real
  change, a preference in the config file. No new command; the command snapshot
  (`tools/mcp-zene-control/zene_control/commands_snapshot.json`) was regenerated from a live instance (833
  ids / 76 groups, unchanged; only this command's enum and description moved), `doc-figures-gate` PASS.
- **Manual**: `data/manual/index.html` (Recording) describes the three modes for MIDI and audio.
- Registration: `tests/CMakeLists.txt` (`RecordModeMenuTest` with the offscreen environment),
  `tests/fork-sources.txt`, `tests/all-sources.txt`.

## Commands

`transport.record_options` (changed): `mode` now `overdub` | `replace` | `keep_history`; the reply gained
`mode_label`, `midi_scope`, `audio_scope`, `modes`. Reversibility class unchanged (`true_inverse`, the
preference restored by the undo step); A16 histogram unchanged (`ReversibilityContractTest` passes).

## Format changes

None to the project format: take lanes and take-group choices are the existing additive `<z:lanes>` section
and the clips' `lane` / `takegroup` attributes. The config file's `recording/mode` gains the value 2.
Old projects and configs load as before (a project from before has no lanes; a config with 0 or 1 reads the
same). Lane clips of a recording are now written to the project (they were lost on save before).

## Known limits

- **MIDI Keep History keeps the notes as Overdub does.** MIDI take lanes do not gate playback (the
  instrument track plays every clip unless a composite names its lane), so a MIDI pass cannot be kept as a
  lane that is silent until chosen without a playback change that is outside this unit; the scope text and
  the manual say so. MIDI Overdub and Replace are untouched (Replace still erases overlapped notes only).
- Overdub mixes in place only for a clip that plays as recorded (whole buffer, forwards, no warp or lead);
  other clips get the pass as a layered clip. The layer is a plain clip: later passes do not silence it.
- Keep History leaves the armed clip as an empty shell (auto-resize off, length kept), as a loop recording
  does; choose the earlier audio with `comp.take_select`, Next Take Here, or the take-lanes view.
- A loop recording's passes are lanes in every mode (unchanged; the loop-recording mute / advance policy is
  a separate unit).
- Local TSan does not run on this box. No audio-thread code changed: the mode decision, the mix, the lane
  creation and the clip edits all run on the existing main-thread completion path
  (`SampleClip::acceptRecordedTake`), under the same engine change lock the previous lane code took.
