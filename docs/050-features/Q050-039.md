# Q050-039 - MPE release-velocity capture fix (P0, fix, L07 note editor)

**Unit.** Preserve the incoming MPE note-off velocity on the released note and send it through playback.

**Finding that shaped the work** (`R-instruments-4`). The MPE capture in
`InstrumentTrack::trackMpeInputEvent` tracked a note-off only to drop the note's expression state
(`m_mpeExpression.noteOff`) and never looked at `event.velocity()`. The note model could already store a
release velocity (`Note::setReleaseVelocity`, `relvel` on disk) and playback already sent it back
(`NotePlayHandle::noteOff` → `MidiEvent( MidiNoteOff, ..., midiReleaseVelocity( base ) )`), but live MPE
input was the one path that threw the velocity away, so the value was lost for both playback and a record
pass.

**Review r1 finding (this rework).** The capture stored the velocity with `MidiEvent::volume()`'s
truncating conversion and playback truncated back: at the port's default base velocity (63) an incoming 96
landed on note-volume 152 and read back as 95, and the tests hid that by pinning the base velocity to 100
(where the scales agree). The capture and the playback emission are now an exact inverse pair
(`Note::releaseVelocityFromMidi` / `Note::midiReleaseVelocity`), both converting with rounding, and the
tests prove exactness at the default base velocity as well as at 100.

Why rounding: on the note volume scale (0..200, 100 = the base velocity) one velocity step at base 63 is
1.587 units. Truncation loses a unit on the way in and again on the way out (96 → 152 → 95); round-half-up
on both sides makes the pair exact inverses for every velocity the scale can name (96 → 152 → 96). A
note-on's velocity keeps `MidiEvent::volume()`'s truncating conversion - the non-MPE path is untouched.

## Format changes

None. A captured release velocity is written with the existing optional `relvel` attribute
(`src/core/Note.cpp:479`, already shipped with the L07 release-velocity feature); a note that captures
nothing still saves without it. Old projects load and render unchanged; a stored value that converts
exactly (e.g. `relvel` 150 at base 64) emits the same velocity as before (load at `:568`).

## Realtime note

The capture runs on the MIDI-input thread (`processInEvent`), not the audio thread: it reads
`midiPort()->baseVelocity()`, indexes the fixed `m_notes` array and writes one plain `int` on a live note
handle - no allocation, lock, wait, I/O or signal. `Note::releaseVelocityFromMidi` is pure integer
arithmetic. The test fixture keeps its realtime contract (fixed arrays, int writes).

## Known limits

- The note volume scale (0..200) names velocities up to twice the base velocity, so at the default base 63
  MIDI's 127 saturates to 126 (a property of the shared volume scale, exact for 0..126); bases above 100
  have coarser resolution than one velocity step and are not exact - the port's default is 63.
- Only member channels are captured. A note-off on the master channel, or one that does not match the
  sounding note's channel, is left alone on purpose (the pre-existing MPE channel rule).
