# Q050-211 - Step input and recording in the new editor (completion, M, L07)

**Unit.** Record MIDI notes and enter notes one step at a time from a MIDI keyboard or computer keys in the new note
editor.

## Measured first (base `3436a808b6`)

The new note editor (`docs/NOTE-EDITOR.md`, the shell's detail panel) had no recording and no step input: `§8 Not done`
said "MIDI recording, step input, chord stamping and detuning automation. Use the classic piano roll", and `§7` said the
classic roll still existed for "recording from a MIDI keyboard, step input". Nothing in `src/gui/noteeditor/` listened
to `InstrumentTrack::midiNoteOn`, and no command put a note down for a key press: the note commands are all "change the
notes the arguments name" (`note.add`, `note.edit`, `note.add_many`), none of them keeps a cursor. A phrase therefore
had to be played in time (classic roll only) or clicked in note by note.

## What changed

- **`note.step_input`** (new, `src/core/ControlCommandsNoteStepInput.cpp`) is one step of step entry: `key` (one MIDI
  pitch) or `keys` (a chord of up to 32 distinct pitches), `position` (default: the clip's step cursor), `length`
  (default: the step), `step` (default 12 ticks, a sixteenth), `velocity`, `select` (default true). The reply carries the
  new notes' ids, `position`, `length`, `step`, the new `cursor`, `velocity`, `selected`, `note_count` and the clip id.
  The notes are added under **one MidiClip journal checkpoint**, so one `control.undo` takes the whole step back; the
  step's notes become the selection (`note.select`'s rule: the flags of the notes it does not name go off).
- **The step cursor is core edit state** (`include/ControlStepInput.h`, `src/core/ControlStepInput.cpp`): a per-clip
  `int`, shared by the command and the editor, never saved and never journalled, so `control.undo` does not move it and
  an old project opens exactly as before.
- **The editor's Step input mode** (`src/gui/noteeditor/NoteStepInput.cpp`, `NoteEditor`, `NoteEditorToolbar`): a
  checkable **Step input** button in the editor's header (icon `step`, the lucide `footprints` glyph) runs the same
  registered `window.note_editor_set {step_input}` the agent calls, and the button follows the state when a command
  moves it. Armed, the editor
  - takes the clip track's **`midiNoteOn`** on a `Qt::QueuedConnection` (the same signal and hop the classic roll's
    record pass uses) and turns it into one `note.step_input`;
  - turns the **computer keys** the instrument window's piano plays (Z S X D C V G B H N J M `,` L `.` `;` `/`, and
    Q 2 W 3 E R 5 T 6 Y 7 U I O P 9 0 an octave above) into the same command, from `keyPressEvent` before the tool
    letters;
  - reads its **grid** and its **note length** from the editor's own view state (`grid` ticks; `new_length` when set,
    else the last note's length), so both entry sources use the same two settings and an agent's call cannot drift from
    them;
  - puts the cursor at the playhead snapped down to the grid when it is armed, and drops the MIDI connection on disarm,
    on a clip change and when the panel is reset - a key held across a transport stop writes nothing (the note is
    written on note-on) and a key pressed afterwards cannot reach a clip the editor no longer holds.
- **`window.note_editor_set`** gained `step_input` (bool) and `step_cursor` (ticks, 0..1919808) and reports both in its
  reply; `window.get_state.note_editor` gains `step_input` and `step_cursor` (`NoteEditor::describe`).

## Format changes

None. The step cursor is edit state, not project state: no project field, no value file, no new file. Old projects open
and render exactly as before (no code that reads a project was touched), and a project saved from this build holds only
the notes the steps wrote - ordinary `Note`s, which every older build reads.

## Realtime

Nothing on the audio thread. The command runs on the control/GUI thread through `ControlRegistry::invoke`; the cursor is
a `QHash` touched only there; the editor's MIDI path is the instrument track's own `midiNoteOn` signal received on a
`Qt::QueuedConnection` (the hop the classic roll's record pass already uses), so the emitting audio thread only appends
to Qt's queued-connection event, as it already does for that signal. No allocation, lock, wait, I/O or signal emission
was added to `process`, `renderPeriod`, `processAudioBuffer` or any other audio-thread function. Local TSan does not run
on this box; the reasoning above is by design and by the existing signal's own contract.

## Known limits

- While Step input is armed the piano keys win over the tool letters (P B D T C E Y and 1..7 play a note); the tools are
  one click or one disarm away, and the mode is not saved across sessions.
- The on-screen key column still only auditions; it plays through the piano model, not through the track's MIDI input, so
  it enters no step.
- Live (transport-time) recording is still the classic piano roll's; this unit is step input and a MIDI-key entry path.
- A step is one undo step per call: a chord is one step, four keys are four.
