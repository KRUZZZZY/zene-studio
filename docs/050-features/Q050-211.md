# Q050-211 - Step input and recording in the new editor (completion, M, L07)

**Unit.** Record MIDI notes and enter notes one step at a time from a MIDI keyboard or computer keys in the new note
editor.

## Measured first (base `3436a808b6`)

The new note editor (`docs/NOTE-EDITOR.md`, the shell's detail panel) had no recording and no step input: `§8 Not done`
said "MIDI recording, step input, chord stamping and detuning automation. Use the classic piano roll", and `§7` said the
classic roll still existed for "recording from a MIDI keyboard, step input". Nothing in `src/gui/noteeditor/` listened
to `InstrumentTrack::midiNoteOn`, and no command put a note down for a key press: the note commands are all "change the
notes the arguments name" (`note.add`, `note.edit`, `note.add_many`), none of them keeps a cursor or a held key. A
phrase therefore had to be played in time (classic roll only) or clicked in note by note.

## What changed

### Step input

- **`note.step_input`** (new, `src/core/ControlCommandsNoteStepInput.cpp`) is one step of step entry: `key` (one MIDI
  pitch) or `keys` (a chord of up to 32 distinct pitches), `position` (default: the clip's step cursor), `length`
  (default: the step), `step` (default 12 ticks, a sixteenth), `velocity`, `select` (default true). The reply carries the
  new notes' ids, `position`, `length`, `step`, the new `cursor`, `velocity`, `selected`, `note_count` and the clip id.
  The notes are added under **one MidiClip journal checkpoint**, so one `control.undo` takes the whole step back; the
  step's notes become the selection (`note.select`'s rule: the flags of the notes it does not name go off).
- **The step cursor is core edit state** (`include/ControlStepInput.h`, `src/core/ControlStepInput.cpp`): a per-clip
  `int`, shared by the command and the editor, never saved and never journalled, so `control.undo` does not move it and
  an old project opens exactly as before.
- **The editor's Step input mode** (`src/gui/noteeditor/NoteStepInput.cpp`, `NoteEditor`, `NoteEditorToolbar`): a
  checkable **Step input** button in the editor's header (icon `step`, the lucide `footprints` glyph) runs the same
  registered `window.note_editor_set {step_input}` the agent calls, and the button follows the state when a command
  moves it. Armed, the editor
  - takes the clip track's **`midiNoteOn`** on a `Qt::QueuedConnection` (the same signal and hop the classic roll's
    record pass uses) and turns it into one `note.step_input`;
  - turns the **computer keys** the instrument window's piano plays (Z S X D C V G B H N J M `,` L `.` `;` `/`, and
    Q 2 W 3 E R 5 T 6 Y 7 U I O P 9 0 an octave above) into the same command, from `keyPressEvent` before the tool
    letters;
  - reads its **grid** and its **note length** from the editor's own view state (`grid` ticks; `new_length` when set,
    else the last note's length), so both entry sources use the same two settings and an agent's call cannot drift from
    them;
  - puts the cursor at the playhead snapped down to the grid when it is armed, and drops the MIDI connection on disarm,
    on a clip change and when the panel is reset - a key held across a transport stop writes nothing (the note is
    written on note-on) and a key pressed afterwards cannot reach a clip the editor no longer holds.

### Recording

- **`note.record_on`** (new, `src/core/ControlCommandsNoteRecord.cpp`) opens one note **where the playhead is**,
  snapped down to the `step` the editor sends, with the editor's draw velocity, and remembers it as the clip's held
  note for that pitch. The take's **first** `note.record_on` takes the clip's MidiClip journal checkpoint - so the whole
  take is **one undo step** - and installs the song's `stopped` listener; every later call of the same take reports
  `take_started: false` and `applies: journal_later`, so `control.undo` unwinds the take instead of refusing with "no
  journal step".
- **`note.record_off`** closes the held note of that pitch where the playhead is **then**: the length is what was
  played, at least one step. A key-up with nothing open writes nothing and answers `closed: false`.
- **`note.record_end`** (`not_mutating`) ends the take: the notes stay, the checkpoint is closed, and a key still held
  keeps the one step it had written. `Song::stopped` ends an open take on its own (one `QPointer<Song>` listener, no
  hook in the GUI), and `control.undo` / `control.redo` end every open take first so no checkpoint is unwound under a
  held key.
- **The editor's Record button** (`NoteStepInput.cpp`: `recordEnter`, `onMidiNoteOff`, `followRecord`, `dropRecord`,
  `finishRecordTake`, `setRecord`): a checkable **Record** button beside Step input (icon `record`, the lucide
  `circle-dot` glyph) runs `window.note_editor_set {record}`, the same command an agent calls. Armed, it takes **both**
  MIDI edges on queued connections and calls `note.record_on` on the key's note-on and `note.record_off` on its
  note-off with the same grid step; the editor follows the playhead so notes arrive as they are written. Step input and
  Record are mutually exclusive, and a clip change or a reset drops both connections.
- **`window.note_editor_set`** gained `step_input` (bool), `step_cursor` (ticks, 0..1919808) and `record` (bool) and
  reports all three in its reply; `window.get_state.note_editor` gains the same three (`NoteEditor::describe`), so both
  the toolbar and the socket read one state.

## New and changed commands

| Command | Class | What it does |
| --- | --- | --- |
| `note.step_input` (new) | `true_inverse` | One step of step entry: one note (or a chord) at the step cursor, the cursor advanced by the step. One MidiClip journal checkpoint per step |
| `note.record_on` (new) | `true_inverse` | Opens one held note at the playhead, snapped to the step; the take's first call takes the clip's ONE journal checkpoint |
| `note.record_off` (new) | `true_inverse` | Closes the held note of a pitch where the playhead is: its length is what was played |
| `note.record_end` (new) | `not_mutating` | Ends the take (the notes stay, the checkpoint closes); the transport's stop calls the same thing |
| `window.note_editor_set` (changed) | `not_mutating` | New args `step_input` (bool), `step_cursor` (ticks) and `record` (bool); all three are echoed in the reply. Still view/edit state, not journalled |

## Format changes

None. The step cursor and the held notes are edit state, not project state: no project field, no value file, no new
file. Old projects open and render exactly as before (no code that reads a project was touched), and a project saved
from this build holds only the notes the steps and the take wrote - ordinary `Note`s, which every older build reads
(`ClipSerialisationTest` passes at HEAD, `test-7.log`).

## Realtime

Nothing on the audio thread. The commands run on the control/GUI thread through `ControlRegistry::invoke`; the cursor
and the held notes are a `QHash` touched only there; the editor's MIDI path is the instrument track's own
`midiNoteOn` / `midiNoteOff` signals received on `Qt::QueuedConnection` (the hop the classic roll's record pass already
uses), so the emitting thread only appends to Qt's queued-connection event, as it already does for that signal. No
allocation, lock, wait, I/O or signal emission was added to `process`, `renderPeriod`, `processAudioBuffer` or any other
audio-thread function. Local TSan does not run on this box; the reasoning above is by design and by the existing
signals' own contract.

## Known limits

- While Step input is armed the piano keys win over the tool letters (P B D T C E Y and 1..7 play a note); the tools are
  one click or one disarm away, and neither mode is saved across sessions.
- The on-screen key column still only auditions; it plays through the piano model, not through the track's MIDI input,
  so it enters no step and records nothing.
- Recording is one take at the playhead: no punch region, no loop-pass take lanes and no count-in of its own - those are
  the classic roll's (`docs/NOTE-EDITOR.md` §3b, §7).
- A key shorter than one grid step is recorded one grid step long, and a key still held at the transport's stop keeps
  the step it had rather than running on.
- A step is one undo step per call: a chord is one step, four keys are four. A whole recorded take is one undo step.

## Portability

No Qt-6-only API was used: `QMetaObject::Connection`, `QPointer`, `QJsonObject`, `QTest::keyClick` and the
`connect(sender, &Class::signal, ...)` form are all Qt 5.15. No `std::filesystem`, no POSIX-only call, and no identifier
named `small`, `near`, `far`, `interface`, `min` or `max`.
