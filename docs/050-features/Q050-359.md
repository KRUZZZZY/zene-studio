# Q050-359 - Carla Rack VST3 opening stability

Unit: fix, size S, priority 60, area L10. Branch `feat/050-Q050-359-oc`, cut from `050/m0-train-35`.
Goal: users can open a VST3 inside Carla Rack without crashing Zene.

## What was found, and what was built

The load sequence the finding describes is: put **Carla Rack** on an instrument track (that is how a plug-in gets inside
Carla), open Carla's window, load a VST3 in it. On this product the first step was the crash.

`CMakeLists.txt:545-558` sets `LMMS_HAVE_CARLA` only when `pkg-config` finds `carla-native-plugin`; otherwise the build
sets `LMMS_HAVE_WEAKCARLA` and links `plugins/CarlaBase/DummyCarla.cpp`, whose
`carla_get_native_rack_plugin()` / `carla_get_native_patchbay_plugin()` **answer nullptr** (`DummyCarla.cpp:11-12`).
`CarlaInstrument`'s public constructor passed that pointer straight to the descriptor constructor, which calls
`fDescriptor->instantiate(&fHost)` (`plugins/CarlaBase/Carla.cpp:203`) with no null check - so the first step died with
`SIGSEGV` at fault address `0x48`, `call *0x48(%rax)`, inside `lmms::CarlaInstrument::CarlaInstrument(...)`.

Reproduced twice, from both sides of the product:

- **the real binary over its control socket**: `plugin.list` offers `carlarack` (`dev-1`, format `builtin`,
  `loadable: true`), `track.add` then `plugin.load` of it kills the process; the crash reporter writes
  `signal=SIGSEGV(11)` / `fault_addr=0x48` (`logs/repro-2.log`).
- **the regression test** with the product hunks reversed: `ctest -R '^CarlaRackNoRuntimeTest$'` names
  `lmms::CarlaInstrument::CarlaInstrument(...)` at `call *0x48(%rax)` in round 1's run; in round 2 the same reversed run
  fails on the data-loss assertions instead (the guard is in the branch, so the crash is gone and what is left to prove
  is that a refusal changes nothing - see Acceptance).

Two things were fixed, in the two layers where the null descriptor and the destroyed instrument entered.

### 1. The modules decline instead of crashing

The guard `plugins/CarlaVst2` and `plugins/CarlaVst2Effect` already carry (`CarlaVst2.cpp:81`): the two host modules
decline when the runtime is absent, and note the reason through `pluginload::noteInstantiationFailure`
(`include/PluginInstantiationFailure.h`, the mechanism `Vst3Effect`, `AuEffect` and `ClapEffect` use):

- `plugins/CarlaRack/CarlaRack.cpp:52-71` - `lmms_plugin_main` returns nullptr for a null Rack descriptor.
- `plugins/CarlaPatchbay/CarlaPatchbay.cpp:52-69` - the same for the Patchbay descriptor (same host path, same null).

### 2. `InstrumentTrack::loadInstrument` is trial-then-swap

`src/tracks/InstrumentTrack.cpp:1445` used to destroy the track's instrument *before* instantiating the requested
module, so a refusal still cost the musician the device, its settings and - on the next save - the project's only copy
of them: the socket probe in round 1 saw the saved instrument go from `tripleoscillator` to `dummy` with no undo entry.
It now instantiates the candidate with the track as parent **first**, and judges it the way `ControlCommandsPlugin.cpp`
and `ControlCommandsAudioSlice.cpp` already read a refusal (no descriptor, a descriptor name other than the one asked
for, or a non-empty `unavailableReason()`):

- **refused**: the candidate is deleted and the call returns `nullptr` with the previous instrument, its state, the
  track's name and `m_preservedInstrument` untouched - no notes silenced, no model change, no undo step. A track that
  held no instrument at all keeps the `DummyInstrument` placeholder every reader can dereference.
- **accepted**: the original sequence unchanged - silence notes, `requestChangeInModel`, `destroyInstrument`, clear the
  preserved XML, adopt the candidate, `setName`, `instrumentChanged`.

The callers that dereferenced the result unconditionally now handle the refusal: `TrackContainerView.cpp`
(`InstrumentLoaderThread::run`, whose new `refused(plugin, reason)` signal the arranger drop path forwards to
`arrangerdrop::reportRefusedInstrument`, and which removes the track a dropped file just created), `FileBrowser.cpp`,
`instrument/InstrumentTrackWindow.cpp` and `PresetPreviewPlayHandle.cpp`. The remaining call sites ignore the result
instead of dereferencing it - `ControlCommandsClipImportFile.cpp:247`, `ControlCommandsDocuments.cpp:116`,
`ControlCommandsTrackRole.cpp:342`, `ControlTrackRouting.cpp:104` and `Song.cpp:1934/1937` - so they need no guard: a
refused load there leaves the new track with the placeholder, which is what it held before this change too.

What the user gets instead of a crash:

- `plugin.load` answers a typed `refused` naming the cause and the way out: *"this build has no Carla runtime, so Carla
  Rack cannot host anything: the module links the weak stand-in. Install a Carla runtime (or build one with
  tools/build-carla-runtime.sh) to load plug-ins inside Carla Rack; a VST3 loads through Zene's own VST3 host instead
  (plugin.list format vst3, then plugin.load its dev-&lt;n&gt;)"*. That is the "route the VST3 to the native host" half of
  acceptance 2, said where the user meets it.
- The device card's **Replace Instrument...** runs the same registered command (`src/gui/shell/DeviceActionMenu.cpp:131`),
  so the GUI meets the same refusal and the message floats over the panel instead of the app dying.
- **A refused load changes nothing.** The track keeps the instrument it had, its parameter values, its name and its
  journal: a save taken afterwards is canon-identical to the one taken before, which is what
  `pluginLoadRefusalKeepsTheInstrument`, `theDeviceCardRefusalKeepsTheInstrument` and `carlaPatchbayRefusalKeepsTheInstrument`
  assert.
- **A project that names Carla Rack opens with the placeholder** the product already uses for an unavailable instrument
  (Q050-018: `DummyInstrument`, `InstrumentTrack::capturePlaceholder`), which writes the file's own
  `<instrument name="carlarack">` XML back on save, so the device comes back when a runtime is installed. A `plugin.load`
  of Carla Rack onto such a track is refused and leaves the placeholder and the saved XML as they were.

`plugin.list` still offers both modules: the entry is honest (the module is in this build), and the refusal - not a hidden
row - is what tells a user why it hosts nothing.

## Commands, undo and format

- **No new command, no changed schema, no changed description.** `plugin.load` keeps its class (`snapshot`) and its
  `refused` answer for an instrument it cannot create; a refused command journals nothing, which the test checks
  (`control.transactions` / `journalledSteps()` is the same count before and after the refusal, in every case).
- The committed command snapshot still matches a live instance: `ctest -R '^ControlCommandsSnapshot$'` exit 0. The
  brief's `research/reviews/m1-session-2026-10-12/scratch/m0/snapshot_live.py` does not exist in this checkout
  (`research/` is not present), so no snapshot was regenerated - none was needed.
- **Format: none.** A project that names Carla Rack is unchanged on disk; the placeholder writes the file's own
  `<instrument name="carlarack">` element back verbatim, and `aSavedCarlaRackProjectKeepsItsPlaceholder` compares the
  element canonically before the open, after the open + save, and again after a refused `plugin.load`.

## Realtime

Nothing on the audio thread changed: the guard runs in the module's `lmms_plugin_main`, i.e. once, on the thread that
instantiates the device (GUI thread, or the project loader), before any `CarlaInstrument` exists. The seam runs on the
same thread and only on an explicit load, and the accepted path is the sequence that was there before
(`requestChangeInModel` / `destroyInstrument` hold the render off while the old instrument goes).
`CarlaInstrument::playImpl` and the MIDI hand-off are untouched.

## Portability

Plain `nullptr` comparisons, `QStringLiteral` and one signal/slot connection; no Qt-6-only API, no new POSIX call, no
`std::filesystem`, no identifier from the reserved list (`small`, `near`, `far`, `interface`, `min`, `max`). The test uses
`QLibrary::resolve` through `PluginFactory::PluginInfo`, which exists in Qt 5.15, and drives the device card through its
real action menu rather than a Qt-6-only widget API.

## Known limits

- The step *inside* Carla - opening Carla's window and loading a VST3 in it - is not reachable in this session, and this is
  the bounded not-reproduced half: this build has **no Carla runtime** (`pkg-config carla-native-plugin` finds nothing, so
  `LMMS_HAVE_WEAKCARLA` and the stand-in are used), and a real runtime has to be built first
  (`tools/build-carla-runtime.sh <build>/carla-runtime`, a separate heavy build). Even with one, Carla's Rack shows its own
  native window for adding plug-ins, which a headless QtTest cannot drive; the host API Zene itself uses
  (`carla_add_plugin`, what `plugins/CarlaVst2` drives) would be the automated equivalent, and that is a new test surface,
  not this fix.
- The test reports **Skipped** in a build that does link a real Carla runtime (it asks the module itself:
  `carla_get_native_rack_plugin()`), because then the refusal is not the path under test - the same convention
  `CarlaVst2HostingTest` uses from the other side.
- Carla Rack still hosts nothing at all in a build without a Carla runtime; the guard only makes that honest instead of
  fatal.
- A refused load is reported, not offered as a choice: there is no "install Carla now" button, and the reason is only as
  good as the module's own message.
