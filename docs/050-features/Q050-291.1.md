# Q050-291.1 - Convert MIDI CC lanes and device automation, stage 1/2: the reversible commands (P2, feature, L06)

**Unit.** An agent can convert a MIDI clip's `cc:<n>` lane to the automation of a device parameter on the clip's owning
track, and a parameter's automation to a CC lane, read the result back through the existing read commands, undo it in one
step, and save and reload the project with the converted data intact. Stage 2 (the note editor's lane chooser and the GUI
prompt for the target) is a separate unit.

## Design

- **Commands** (`src/core/ControlCommandsControllerConvert.cpp`, group `clip`, registered next to `clip.controllers_*`):
  - `clip.controllers_to_automation {clip, lane, parameter?}` copies the lane onto the parameter's automation clip.
  - `clip.controllers_from_automation {clip, lane, parameter?}` copies the parameter's automation that lies inside the
    clip into the lane (replacing it).
  - `lane` is `cc:<0..127>`; `parameter` is the `<plugin>/<index>` id `automation.get_state` lists for the clip's **owning**
    track (instrument and effects on its chain).
- **Target.** `parameter` may be left out only when it names exactly one candidate (to: the track has one parameter; from:
  one parameter of the track carries automation). Otherwise the call is `invalid_args` and lists up to eight candidates.
- **Value.** CC 0..127 spans the parameter's `min..max` linearly, in the model's own unit (the `value` automation.get_state
  reports). Going back rounds to the nearest CC step and clamps. The clip stores `inverseScaledValue(value)`, as
  `automation.add_point` does.
- **Time.** Lane tick `t` is song tick `clip.start + clip.startTimeOffset + t` (the mapping `InstrumentTrack::play` uses).
  An automation node at local tick `n` is song tick `automationClip.start + n`. So a MIDI clip at song 192 and an automation
  clip that starts at 96 land every point at the right place; the automation clip's own position is respected.
- **Copy, not move.** The source stays. `to_automation` replaces the target clip's nodes from the first to the last
  converted tick and keeps the rest; `from_automation` replaces the whole lane. Where the clip cuts through the curve,
  `from_automation` adds the curve's value at the cut (lane tick `-startTimeOffset` and the clip's end) so the lane plays
  what the automation played.
- **Linear.** A CC lane is linear between points, so `to_automation` makes the target clip linear. It refuses instead when
  the clip is not linear and has nodes outside the replaced span (that would change how they play). A clip the call creates
  is made linear and starts with only the converted points.
- **Refusals** are decided before the first write, so a refusal changes nothing and records no undo step: a non-`cc` lane
  (pitch bend, aftertouch, program), a lane with no points, an unknown or ambiguous parameter, a parameter that is a
  switch / list of choices / has no range, a trim (relative) automation clip, a point that would land before the
  automation clip, more than 4096 points, a non-linear clip with nodes outside the span, no automation inside the clip.
- **Undo.** One call is one undo step: the MidiClip or AutomationClip checkpoint (or, for an automation track the call
  created, the action step that removes it) is merged by the registry into one step. Both commands are `true_inverse`.
- **Reads.** Nothing new: `clip.controllers_get` shows the lane, `automation.get_state` the points.

## A defect found on the way: project files dropped every CC lane

`MidiClipControllers::save` writes the lanes as `<controllers metadata="1">` inside the clip, but `DataFile::write` calls
`cleanMetaNodes`, which deletes every `metadata="1"` child from a project file. So a lane survived undo and clip copies and
was lost on save. `cleanMetaNodes` now spares a `midiclip`'s `<controllers>`. The element keeps its `metadata="1"` flag, so
older builds still skip it when they read a clip's notes; old files (no element) load as before.

## Commands, formats, limits

- **Commands.** `clip.controllers_to_automation`, `clip.controllers_from_automation`: both mutating, both `true_inverse`
  (the table rows are in `ControlReversibilityTableArranger.cpp`). Snapshot: 878 -> 880 ids, 77 groups.
- **GUI.** None in this unit. The note-editor lane chooser and the conversion prompt are stage 2 and will call these same
  commands. Until then the conversions are available to agents (control socket, MCP, Lua `zene.command`) and the command
  palette.
- **Formats.** A project file now carries a MIDI clip's `<controllers metadata="1">` lanes (see the defect above). The
  lane format is unchanged; old projects load and render as before; older builds skip the element.
- **Realtime.** Both commands run on the control thread. `setControllerPoints` takes the instrument track lock as
  `clip.controllers_set` does; nothing runs on the audio thread. No race beyond the existing lane-write protocol
  (TSan does not run on this box: reasoned, not measured).
- **Known limits.**
  - Linear mapping across `min..max` in the parameter's unit: a logarithmic parameter is mapped linearly in its own unit,
    and integer parameters round on playback.
  - Before its first converted point the parameter keeps its own value (automation semantics); the CC lane would hold its
    first value there. No anchor point is invented, so the points stay 1:1.
  - A Discrete or cubic automation clip converts to a linear lane through its points; `source_progression` reports it.
  - Switches (`BoolModel`) and choice lists (`ComboBoxModel`) are refused through the same branch as a parameter with no
    range. tripleoscillator exposes neither, so the test proves that branch with a collapsed range; the type check itself
    is not exercised by a test.
  - A point hidden by a left trim (lane tick below `-startTimeOffset`) is converted like any other.
  - Pitch bend, aftertouch and program lanes are refused (out of scope per the brief).
