# Q050-217.2 - MIDI bindings for saved workflows (stage 2/4)

**Unit.** Bind a MIDI note and a MIDI control change to a **saved workflow**, and run it through the existing
workflow command path. Stage 2 of cluster Q050-217; stage 1 already bound a note or CC to a built-in command, and
stages 3-4 add scripts and workflow header buttons. Nothing here is designed so those must undo it: the store, the
decoder, the drain and the dispatch are stage 1's, and this stage only widens what a binding may NAME.

**Goal.** "Bind MIDI notes and CCs to saved workflows and run each through the existing workflow command path."

**Design.** The binding surface is stage 1's, extended rather than duplicated: one port, one 15 ms UI-thread
drain, one config store, one channel-specificity rule. What changes is that a stored binding has one of two
targets instead of only a command id.

- **One target key, two kinds.** A binding in `midi/commandbindings` carries `command` (stage 1) **or**
  `workflow` (this stage), and never both:
  `{trigger:"note", key:60, channel:0, workflow:"Bounce stems"}`. The store's format is additive - an old config's
  command bindings have no `workflow` key and keep their exact meaning; `LaunchBindings::targetKey()` is the one
  place that reads which kind a binding is.
- **The workflow is named, not copied.** A binding stores the workflow's NAME and runs it through
  `workflow.run` - the command the Workflows menu and the socket already call. So an activation is acknowledged
  at once and the steps run on the next event loop turn exactly as a menu run does, each step recording and
  undoing as itself, and a run that stops reporting where in the interface's report as usual. The binding is not a
  second workflow engine.
- **Resolved from the library in use, when it fires.** `workflow.run` itself reads the library in use (shared in
  `ui/workflows`, or the project's `<workspace>` when `workflow.set_scope` says so). The binding therefore
  answers with whatever that library holds NOW: editing a workflow is followed, keeping workflows with the
  project is followed, and a shared workflow and a project workflow of the same name resolve to whichever library
  is active. The name is checked when the binding is made (so a typo is a typed `not_found` where the user can
  see it, naming the workflows there are), and **again** when it fires - a name the library no longer holds is a
  no-op, not a failed dispatch into the MIDI drain, because the binding is the user's config and the workflow may
  come back (an undo, a project reopened, a scope switched back).
- **Activation is stage 1's, unchanged.** A note fires once on its press and rearms on its release (a note-on at
  velocity 0 is a release); a control change fires when it goes from 0 to a positive value and rearms at 0, so one
  sweep of a knob is one activation. The CC **value is not passed on** - a workflow takes no activation
  arguments, which is exactly why a binding can be a fixed target at all. The more specific channel wins; at
  equal specificity a binding wins over a launcher binding, and a note moved between a command and a workflow
  target is one undo step across both stores.
- **Readback says what it is.** `session.command_bindings` still answers the raw `bindings` array (unchanged
  shape), and adds `targets`: each binding with its `target` kind, its `name`, whether it `resolved` against the
  library in use right now, and - when it does not - the `reason`. It also names the active `workflow_scope` and
  the `workflows` in that library, so a reader can see where a name came from without a second call.

Commands (no new ids; the stage 1 ids gained a target):

| Command | What changed | Mutating | Reversibility |
| --- | --- | --- | --- |
| `session.bind_command` | `workflow` is now accepted as the binding's target (exactly one of `command`/`workflow` is required) | yes | `true_inverse` (unchanged) - one recorded undo step writes both previous config lists back |
| `session.unbind_command` | removes a note's or CC's binding whichever target it names | yes | `true_inverse` (unchanged) |
| `session.command_bindings` | `targets` (with `target`, `name`, `resolved`, `reason`), `workflows`, `workflow_scope` added beside `bindings` | no | `not_mutating` (unchanged) |

The GUI entry is **Launcher > Controller > Bind a Workflow**: one submenu per workflow in the library in use,
each with *Bind a Note...* and *Bind a Control Change...*, and *Workflow and Command Bindings* to read them back.
Each entry is an action declaring `session.bind_command` and fixing the workflow's name and the trigger kind, so
the menu and an agent take the identical path through `ControlRegistry`, and the schema-built form asks only for
the number and channel. The submenu is rebuilt from the library each time it opens, so a workflow saved, renamed
or kept with the project is offered as the library is now; with none saved it says so and points at
*Workflows > Record a Workflow...*.

## New commands

None. `session.bind_command`, `session.unbind_command` and `session.command_bindings` already existed; this stage
widens the first two's target and the third's reply, additively:

- `session.bind_command` takes `workflow` (a saved workflow's name) as an alternative to `command`. Exactly one
  target is required. The trigger (`trigger` note|cc, `key`/`controller`, `channel`) and the one-undo-step rule are
  unchanged.
- `session.unbind_command` removes the binding on that note/CC whichever target it names.
- `session.command_bindings` adds `targets` (each binding's `target`, `name`, `resolved`, `reason`), `workflows`
  (the names in the library in use) and `workflow_scope` (`shared`/`project`) beside the unchanged `bindings`.

## Format changes

None to the project. One **config** addition, additive inside the existing `midi/commandbindings` array: a
binding may carry `workflow` (a string name) instead of `command`. An old config's bindings have no such key and
keep their meaning; a new binding round-trips as a plain JSON array. Old projects load and render exactly as
before - a project-scoped workflow the binding names lives in the project's own `<workspace>`, which stage 19
already saves and which is unchanged here.

## Realtime

Nothing on the audio or MIDI thread allocates, locks, waits, does I/O or emits a signal. `decode()` is untouched
and still fills a plain `LaunchTrigger` into a fixed `MpscQueue<LaunchTrigger, 256>`; the only new work is on the
UI thread in `applyTrigger`, where `dispatchTarget` reads the binding's target name and calls
`ControlRegistry::invoke("workflow.run", {name})` - a QString copy and one registry call on the drain, exactly
where a command binding already dispatched. Workflow steps run later, on the event loop, by `WorkflowRun`'s own
timer. The MIDI thread never sees a QString, the registry or the project. Races were reasoned about, not measured
(local TSan does not run on this box): the latch sets are UI-thread only, and the config array is read on the UI
thread as the launcher's already was.

## Known limits

- A binding targets one workflow by name. Renaming a workflow therefore leaves the binding naming the old name;
  it is kept and reported `resolved: false` (not silently deleted), and it works again if a workflow of that name
  comes back.
- Only argument-free targets are bindable: a workflow takes no activation arguments, and the CC value (or the
  note's velocity) is not passed to its steps. That is the stage's scope.
- The workflow is run through `workflow.run`, so one workflow runs at a time: a binding fired while another run
  is under way is a no-op (the registry refuses it, and nothing reports into the drain). This is the same rule the
  menu follows.
- Scripts are stage 3 and workflow header buttons are stage 4; neither is offered here.
- As in stage 1, the bindings are per machine and per user (the config file), and a CC or note bound to a
  workflow is replaced by a later binding on the same control whichever target it names.
