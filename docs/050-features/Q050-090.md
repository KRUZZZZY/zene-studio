## Commands and format

New: `plugin.scan_start` (irreversible, `pace_ms` 0..1000), `plugin.scan_status` (not_mutating),
`plugin.scan_cancel` (not_mutating; `cancelling:true`, effect at the next file boundary).
Changed surface: `plugin.list` entries gain `vendor` (empty when the format reports none); the A16 histogram moves
to `rows=840 true_inverse=417 snapshot=42 irreversible=23 not_mutating=358` (`docs/RELEASE-NOTES-v0.3.0-alpha.md`);
the commands snapshot to 831 ids / 76 groups (`tools/mcp-zene-control/zene_control/commands_snapshot.json`,
`README.md` canary). No project format change: the cache file keeps format version 1, old caches load as before,
new per-file outcomes are the same records the synchronous scan stores.

## Known limits

- The quarantine list is snapshotted when a background run starts; an edit made mid-run takes effect on the next
  run (a synchronous scan re-reads the file). Stated in the command notes and `docs/PLUGIN-SCAN-CACHE.md` §2.6.
- Records are stored live as they are taken, so a cancelled run's measurements stay cached for the next run to
  serve; only the catalogue commit is atomic. Stated in `PluginFactory.h` and the cancel note.
- `pace_ms` delays chunk to chunk on the main thread; with pace 0 a small scan can finish between two status
  polls (the transcript cancels a paced run, deterministically pre-first-chunk).
- TSan does not run on this box (runtime crash at thread creation): the no-races argument is by construction
  (single-thread confinement, no atomics, no locks) and stated in `PluginFactoryBackgroundScan.cpp`, not measured.
- Races were reasoned, not executed, for the same reason; the synchronous transcript (`ControlPluginScanCommands`)
  still passes unchanged against the refactored stages.
