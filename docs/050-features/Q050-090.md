`plugin.scan_cancel` (not_mutating; `cancelling:true`, effect at the next file boundary).

`README.md` canary). No project format change: the cache file keeps format version 1, old caches load as before,
new per-file outcomes are the same records the synchronous scan stores.

## Known limits

- The quarantine list is snapshotted when a background run PLANS (its first turn, after the start returns);
  an edit made before that takes effect, one made later waits for the NEXT run (a synchronous scan re-reads
  the file). Stated in the command notes and `docs/PLUGIN-SCAN-CACHE.md` §2.6.
- Records are stored live as they are taken, so a cancelled run's measurements stay cached for the next run
  to serve; only the catalogue commit is atomic. Stated in `PluginFactory.h` and the cancel note.
- `pace_ms` delays turn to turn on the main thread; with pace 0 a small scan can finish between two status
  polls (the transcript paces the run and waits for the first completed file before cancelling).
- TSan does not run on this box (runtime crash at thread creation): the no-races argument is by construction
  (single-thread confinement, no atomics, no locks) and stated in `PluginFactoryBackgroundScan.cpp`, not measured.
- Races were reasoned, not executed, for the same reason; the synchronous transcript (`ControlPluginScanCommands`)
  still passes unchanged against the refactored stages.
