# Q050-040 - Unmute note-chase fix

Unit: P0, S, L07 (note editor / MIDI). Goal: with chase enabled, start a note that is already under
the playhead as soon as its track or its clip is unmuted during playback.
Branch: `feat/050-Q050-040-oc`, based on train 5 `de5a85a96`; review round 2 reworked (below).

## What was built

Chase used to fire only on a start, a jump or a loop (`MidiPlayback::chasingNow`). An unmute is
none of those, so a muted track/clip stayed silent until the next note began. The fix adds the
unmute as a chase trigger and makes it safe to fire:

- `include/InstrumentTrack.h:432` + `src/tracks/InstrumentTrack.cpp:834-858`: `play()` keeps the
  track's mute as the render thread saw it one pass back (`m_mutedLastPlay`). The one-pass
  `muted -> unmuted` edge is `trackUnmutedNow`, a chase trigger. With chase on, a muted track now
  schedules nothing at all: a silent handle left under the playhead used to block the unmute chase
  (and doubled the note on a seek into it).
- `include/Clip.h:309-314,386` + `src/tracks/InstrumentTrack.cpp:905-924`: each clip remembers, on
  the render thread, whether it was muted on the previous pass (`playbackWasMuted`). The
  `muted -> unmuted` edge is `clipUnmutedNow`, a chase trigger scoped to that clip. The per-clip
  pass is the same thread that already reads `clip->isMuted()` there, so the flag is a plain bool.
- `src/tracks/InstrumentTrack.cpp:924`: the per-clip chase is `chasingNow() || trackUnmutedNow ||
  clipUnmutedNow`, gated on the `chase` preference.
- `src/tracks/InstrumentTrackNotes.cpp:135-163`: `noteStartsNow` takes `chaseNow` and, on a chase
  tick, will not start a note a live handle already covers (`noteIsAlreadySounding`, same file;
  the handle's clip, key and clip-relative position against `Engine::audioEngine()->playHandles()`;
  a released handle is a release tail, not the note). This is what keeps a seek/loop from doubling
  a note that is still ringing.
- `src/core/ControlCommandsNotePlayback.cpp:288-291`: the `transport.midi_options` description now
  names the unmute; `data/manual/index.html:83-84` says the same.

No new command. `transport.midi_options` is the existing GUI (Project menu `Chase Notes`) and
agent surface; its reversibility class is unchanged (`RC::TrueInverse`, one undo step).

## Review round 2 rework

The round-2 review (REWORK) found two defects and one process issue; all are addressed:

- **Clip-owned deduplication.** `noteIsAlreadySounding` used to match track, key and note position
  only, and a note play handle carries its clip-relative position - so the same-key note of
  another overlapping clip could suppress the unmuted clip's valid note. A handle now records
  the originating clip instance: `include/NotePlayHandle.h:228-242,395-399` (`clip()`, `setClip()`,
  `m_clip`), set in `InstrumentTrack::triggerNote`
  (`src/tracks/InstrumentTrackNotes.cpp:234`). The check requires the handle's clip to be the clip
  being played (`src/tracks/InstrumentTrackNotes.cpp:152-153`). Regression:
  `UnmuteChaseTest::overlappingClipsEachChaseTheirOwnNote`.
- **The mute edge survived a failed lock.** `play()` wrote `m_mutedLastPlay` before `tryLock()`, so a
  pass that could not take the processing lock consumed the unmute edge and the next pass no longer
  saw it. The flag is now written only on a pass that holds the lock (or on the frozen-take pass,
  which locks nothing): `src/tracks/InstrumentTrack.cpp:845-858`. A failed tryLock is a pass that
  never happened, so the edge waits for the pass that can act. Regression:
  `UnmuteChaseTest::unmuteEdgeSurvivesAContendedLock` (a second thread holds `m_processingLock`
  across the unmute passes; the note starts once on the release).
- **The tests moved out of `NotePlaybackTest.cpp`.** That inherited file grew from 624 to 699 code
  lines. The Q050-040 slots now live in a new fork-owned source, `tests/src/core/UnmuteChaseTest.cpp`
  (225 code lines), registered in `tests/CMakeLists.txt` (ENABLE_EXPORTS block + tripleoscillator
  dependency) and `tests/fork-sources.txt`; `tests/all-sources.txt` was re-derived from its header
  recipe. `tests/src/core/NotePlaybackTest.cpp` is back at its train-5 state (624).

## Realtime and portability

- The audio thread adds no lock, no allocation, no I/O and no Qt signal: two plain flags written
  by the one scheduler thread (`Song::processNextBuffer`), a pointer store on the handle at
  trigger time, and a read-only walk of the play-handle list on chase ticks only. The mute reads go
  through the model's published atomic value, as the existing `processAudioBuffer` already does.
- `noteIsAlreadySounding` is O(play handles) on a chase tick; chase is rare and opt-in, so this is
  bounded work with no allocation. Recorded as a limit below.
- No Qt-6-only API, no `findChild<T>` without `Q_OBJECT`, no new reserved identifiers, no
  `std::filesystem`; `NotePlayHandle`'s new `MidiClip*` member is a forward-declared pointer.

## Known limits

- `noteIsAlreadySounding` mirrors the clip transpose but not a chord-follow re-keying: on a track
  that follows the chord track, a chase may start a note whose handle is already ringing.
- The dedup compares the clip instance, key and position - not velocity or length - because those
  do not identify a note-on to an instrument; two genuinely identical overlapping clips sound as
  two notes, which is what the user asked for.
- On a loop shorter than a note, the note is neither cut at the loop end nor retriggered (the fix
  blocks the retrigger so the note is not doubled). Only an unlocked improvement would cut and
  retrigger it.
- The contended-lock regression exercises a same-track mutex held by another thread; it is a
  scheduling proof, not a stress test (local TSan does not run on this box).
