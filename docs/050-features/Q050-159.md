# Q050-159 - Explain patterns, arrangement clips, launcher cells, and mixer routing

**Unit.** A musician could read about the arranger, the note editor, the launcher and the mixer separately, but
nothing connected their models: what a pattern stores, what a timeline clip stores, what a launcher cell points
at, and which track owns the mixer channel a sound reaches. This is an S documentation unit (L14): one manual
section and one "Your first beat" tour step, no playback, model, routing or format change.

track's column uses that track's devices, fader, pan and mixer channel.

## New commands and reversibility

None. The section names existing commands only: `track.overview`, `mixer.get_state`,
`arrangement.get_state`, `session.pattern_list` and `session.get_state` are `not_mutating`;
`track.set_mixer_channel` and `session.set_slot` are `true_inverse`. No command metadata, snapshot or
reversibility histogram changed.

## Format changes

None. No project serialization changed; old projects load and render exactly as before.

## Known limits

- The unit explains the models; it does not change playback, the pattern/clip/slot models, routing or project
  formats.
- The trace tests the channel assignment and its undo, not an audio render: the manual's claim about an audio
  cell's devices/fader/pan/channel is the existing `SessionCellPlayHandle` path (`include/SessionAudioCells.h`),
  outside a docs unit.
- A channel added by `mixer.add_channel` after a track exists is outside the track's current mixer-channel model
  range, so the transcript adds the destination channel before the sample track (the same order as Add Channel
  then Add Track in the GUI). This is pre-existing routing behavior, not changed here.
- Nested PatternStore tracks are not addressable by `track.overview` / `track.set_mixer_channel`; the manual says
  so rather than implying they are song tracks.
