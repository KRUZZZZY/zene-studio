# Q050-231.3 - Masking Report musician workflow (stage 3 of 3, L08, R-mixing-7)

Stages 1-2 already provide the report (`mixer.masking_report`) and the apply command
(`mixer.apply_masking_proposal`). This stage hardens the workflow: the report's cached rows are invalidated on any
input change, so a stale row can never be applied, and in-dialog Ctrl+Z is proven against the real application-wide
Undo action of `MainWindow`.

## What changed

- **`src/gui/MixerMaskingReport.cpp`.**
  - An `m_reported` guard: a row exists only after a Report has run, and `invalidateReport()` returns early when
    there is nothing to clear.
  - `itemChanged` (ticking or unticking a channel) and `currentIndexChanged` (a priority combo) both call
    `invalidateReport()`. It clears the clash rows, disables Apply through `updateApplyEnabled()`, and shows
    "Channel selection or priorities changed. Press Report again."
  - `runReport()` clears `m_reported` first and sets it only after the clash rows are listed, so Apply is enabled
    again only for rows of a fresh report.
- **Tests.** `MixerMaskingReportWindowTest` gains `changingChannelsOrPrioritiesClearsTheStaleReport`,
  `untickingAChannelClearsTheStaleReport` and `ctrlZInTheReportWindowUndoesTheAppliedProposal`. Commit `e2f2ee06fb`
  adds the 16/17-channel boundary and ten-second clip coverage to `MixerMaskingReportTest`. Commit `683cb9934d` adds
  the playback-active scenario to `tests/control-masking-report.py`. Commit `503208f22b` splits the invalidation
  regression into two slots so the function stays under the complexity target.

## Realtime and threads

Apply and Report run on the control (main) thread. The invalidation handlers touch only widget state and the
`m_reported` flag, which are GUI-thread-only. No audio-thread code was added and no mixer period buffer is touched.
The undo checkpoint is still taken in the apply handler. Local TSan is not available on this box, so the race
argument is by design only.

## Known limits

- The proposal's `strip_eq` values are absolute, not deltas. A row applied after the report has been refreshed still
  writes the values recorded when it was produced. Stale rows are therefore cleared on input change, and Report must
  be pressed again.
- Only one mid bell per channel exists. Two proposals that need the mid band on the same target overwrite each
  other, and the last applied wins (each is its own undo step).
- Priorities are arguments only and are not saved in the project.
- Instrument tracks are not analysed yet (they appear in `unanalysed_tracks`).
