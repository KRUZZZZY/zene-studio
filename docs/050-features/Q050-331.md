# Q050-331 - Persist controller bindings with presets

Type: feature (P2, size M). Member: R-workflow-177. Area: L15.

## What was built
- The binding itself already travelled inside a preset: each parameter writes its own MIDI controller connection next
  to its value (`AutomatableModel::saveSettings`, `MidiController::saveSettings`: channel, CC, soft takeover,
  feedback), and a load reads it back onto that parameter of the device the preset just created. The tests below
  prove that round trip; nothing re-binds by name, so a binding cannot land on another parameter.
- `include/PresetBindings.h`, `src/core/PresetBindings.cpp` - the binding MANIFEST: at save, a `<zenebindings>` list of
  every binding, named from its device (`instrument>Osc 1 volume`, `effect 1>Volume`, a track parameter by its own
  name - the instrument and the effect chain are not object children of the track, so `fullDisplayName()` could not
  be cut at the track); at load, a reconciliation against what the loaded devices carry: `restored`, or `skipped`
  with target, channel, CC and the reason. An older preset has no manifest and loads exactly as before.
- `track.preset_save` writes the manifest and answers `bindings` (how many); `track.preset_load` answers
  `bindings: {saved, restored[], skipped[], summary}` and `bindings_summary`
  (`src/core/ControlCommandsTrackPresets.cpp`).
- `chain.save` stores a manifest per device beside its state (`<device><zenepluginstate/><zenebindings/></device>`;
  the reader still takes the first child as the state); `chain.apply` answers `bindings` reconciled per device against
  the instance it just created, each entry carrying that effect's `fx-<n>` id (`ControlChainPresetSupport.cpp`,
  `ControlCommandsChain.cpp`, `ControlCommandsChainEdit.cpp`).
- Undo: `include/ConnectionRestoreScope.h` + `AutomatableModel::loadSettings` + `JournallingObject::restoreState`. A
  journal restore now states each model's controller connection in full: a connection the checkpoint's element does
  not carry is removed. Before, undoing a preset load left the preset's binding on any parameter the checkpoint reused
  (the track's own Volume, measured). Outside a restore a load still only adds, so loading a preset onto a mapped knob
  keeps the mapping.
- GUI: track menu > Track Preset > Load Preset... now keeps its form open with the answer ("Bindings summary: 1 of 1
  controller bindings restored: ..."); track menu > Effect chain presets > Apply <name> shows the same summary after
  the apply when the preset carried bindings (`src/gui/ChainPresetMenu.cpp`, a test seam `setChainPresetNotice`).
- Manual: "Presets keep their controller bindings" in Devices.

## New commands / reversibility / format changes
- No new command. `track.preset_load`, `chain.apply` (both `true_inverse`, unchanged) and `track.preset_save`
  (`not_mutating`) carry the new result fields; their descriptions say so.
- Format: an optional `<zenebindings><binding target channel controller soft_takeover feedback/></zenebindings>` in a
  track preset (after the track element) and in a chain preset's `<device>` (after the state). Absent = older preset,
  loaded unchanged; an older Zene ignores it.

## Known limits
- A binding is matched by its device-relative name, channel and CC; two parameters of one device with the same
  display name would be indistinguishable in the report (the binding itself still lands on its own parameter).
- Pre-existing, not changed here: undoing a track preset load onto an instrument track that had NO instrument leaves
  the preset's instrument (the checkpoint has no instrument to put back). With an instrument the undo is exact.
- Instrument presets saved from the instrument window (not `track.preset_save`) carry inline bindings but no manifest,
  so their loads report nothing.
