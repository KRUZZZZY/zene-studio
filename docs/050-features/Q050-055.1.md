# Q050-055.1 - Panel-scoped shortcuts (stage 1 of 2)

Unit Q050-055.1, cluster "Context-aware shortcuts and plug-in actions", stage 1 of 2: the arranger, the
note editor, the automation editor and Perform each get their own shortcut context, with scoped conflict
resolution and restart persistence. Stage 2 (keys bound to plug-in actions) is deliberately NOT started:
nothing here has to be undone for it, because a panel action is declared as `{scope, id, command, args}`
and the command is any registered id, so a plug-in action only has to be added to that table later.

## What was built

| piece | file |
| --- | --- |
| the four scopes, the bindable action table, the store access, the application-wide key router | `include/PanelShortcuts.h`, `src/gui/PanelShortcuts.cpp` |
| a binding now knows its scope; a clash is two bindings of ONE scope | `include/ShortcutMap.h` (`Binding::scope`), `src/gui/ShortcutMap.cpp` (`conflicts`) |
| `shortcuts.list/set/reset/export/import` learn `scope`, `panels` and same-scope clash resolution | `src/gui/ControlCommandsShortcuts.cpp` |
| the automation editor's edit modes as a command (the toolbar's own actions, so the checked button follows) | `src/gui/ControlCommandsAutomationMode.cpp`, `AutomationEditorWindow::editorMode/setEditorMode` |
| the shortcuts page shows the context and passes it to every row action | `src/gui/CommandLists.cpp` (`CommandLists::shortcuts`) |
| the router is installed once the shell's menus exist | `src/gui/shell/Shell.cpp` (`showEvent`) |

**Store layout.** `ui/shortcuts` now holds `{"overrides": {menuId: keys}, "panels": {scope: {actionId: keys}}}`.
A panel map nested by scope rather than flattened under a separator character: the store is a config XML
attribute, and a control character in it makes the next start's whole config parse fail - which the restart
transcript caught, so the first draft was replaced before this record was written. Only a STRING is an
override (a hand-edited `42` still keeps the action's key, cluster 5373); `""` is a deliberate unbind.

**Scope semantics.** The same key in two scopes is the point, not a clash. `shortcuts.set` refuses a
same-scope clash, typed `refused`, unless `force` is given; force moves the key there and unbinds the other
action OF THAT SCOPE only. `shortcuts.reset` with no `id` resets one context, or with no `scope` argument at
all every menu AND panel binding.

**No panel action has a default key.** A user who never opens the shortcuts page keeps every existing key
(P/B/D/T/C/E/Y in the note editor, Shift+D/E/C/T in the automation editor, the digits/Escape/Space in
Perform, the arranger's mode keys), and a bound scoped key wins over both a window menu shortcut and the
panel's built-in table because the router claims it in Qt's `ShortcutOverride` phase.

## Format changes

None to projects. `ui/shortcuts` gains an optional `panels` object; an existing config (only `overrides`)
loads unchanged and keeps working, and a build that never writes `panels` keeps writing only `overrides`.

## Known limits

- Stage 2 (plug-in actions as bindable targets) is not implemented.
- A panel scope is decided by widget ancestry: a panel popped out into its own window, and any dialog, has
  no scope, so its scoped keys do nothing until it is docked again.
- Perform's Up/Down, Enter, Page Up/Down and digits past 2 have no scoped action yet (Stop All, Start/Stop
  Transport and Launch Scene 1-2 do), so those meanings cannot be rebound - stated in `docs/KNOWN-LIMITATIONS.md`.
- The arranger scope exposes zoom, fit and the three editor tools; the overlay tools (range, audition, zoom,
  smart) are reachable through `arrangement.set_tool` but have no declared panel action yet.
- Scoped keys are matched on the focused widget's panel, so a key pressed while the focus is on a window's
  menu bar (or on a toolbar outside every panel) is not scoped.
