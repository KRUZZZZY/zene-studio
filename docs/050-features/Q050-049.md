# Q050-049 - Crash-aware plug-in quarantine

Unit: P0, M. Goal: offer quarantine for the third-party plug-in named by a crash marker.
Branch: `feat/050-Q050-049-crash-quarantine`, based on train 2 `190242990`.

## What was built

- `include/SafeStart.h:233`, `src/core/SafeStart.cpp:284,338`: the first `beginSession()` reads the previous marker and
  latches its suspect. The later GUI `install()` / `beginSession()` pair for the same directory and process preserves
  that read instead of interpreting this session's fresh marker as the previous crash. The core-only path reports
  its offer early; GUI startup makes its one offer after `GuiApplication` exists (`src/core/main.cpp:1235` and `1508`).
- `include/SafeStart.h:244`, `src/core/SafeStart.cpp:452`: `ActivePluginScope` pops only when its matching entry was
  pushed. A nested engine-owned module therefore cannot remove an enclosing third-party entry. The scan and
  instantiation call sites remain `src/core/PluginFactory.cpp:179` and `src/core/Plugin.cpp:281`; the real-load test
  observes both call sites (`tests/src/core/SafeStartLoadPathTest.cpp:143`).
- `src/core/ControlCommandsPluginScan.cpp:349`, `src/core/ControlCommandsPluginScanEdit.cpp:348,379,411`: scan-cache
  state, quarantine add/remove and rescan commands do not require the registry's project-edit readiness flag. They still
  use `PluginFactory` and its file-backed cache; the GUI test initializes the engine but leaves `startupComplete()`
  false and does not call `setReady(true)` (`tests/src/gui/PluginQuarantineMenuTest.cpp:83`).
- `src/gui/PluginQuarantineMenu.cpp:168`: an accepted offer reports a failed cache write or refusal in a warning
  box instead of returning false silently. The test seam captures this notice and verifies duplicate-entry refusal.
- `tests/src/core/SafeStartTest.cpp:378`: POSIX signal rows are guarded. Windows gets a placeholder row that the test
  body skips, so the test source does not reference `SIGSEGV` or `SIGKILL` on MSVC.

## Commands and format

No new commands. `safestart.get_state` keeps its additive `crash_suspect` and `offer.quarantine` fields. The existing
`plugin.scan_cache_quarantine_add` / `plugin.scan_cache_quarantine_remove` snapshot pair remains reversible; the
existing `plugin.rescan` command remains irreversible. These cache operations now work while the registry's
engine-ready flag is false. No project serialization changed. Four optional marker lines were added; old markers still parse
and report no suspect.

## Known limits

- Only in-process `lmms-module` scanning and instantiation are instrumented. LADSPA's constructor-time scan,
  out-of-process hosts, and VST3/CLAP editor opens are not covered; a crash there has no plug-in suspect.
- The crash test raises a real signal inside the instrumented scope over a test-local placeholder path; it does not
  load a deliberately crashing shared library. The real-load test separately verifies both production scope
  call sites with the built `midiexport` module.
- The GUI prompt and warning are exercised offscreen through the real menu/command path, not through an interactive
  screenshot run. The test host is Linux/Qt 6.4.2; Windows portability is covered by the guarded source and focused
  `Q_OS_WIN` compile probe, not an MSVC build on this host.
- Marker writes are on plug-in loader paths, never audio callbacks. Their startup I/O cost has not been benchmarked.
