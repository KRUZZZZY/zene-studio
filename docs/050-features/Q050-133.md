# Q050-133 - Add file URLs to browser and sample-clip drags (P1, feature, L11)

**Unit.** A drag from the file browser or a file-backed browser search result publishes its file as a
`text/uri-list` URL beside the private StringPair payload, so a plug-in editor (VST, CLAP, LV2) or a file
manager / the desktop that accepts file URLs receives the source file, while every drop target inside Zene
keeps decoding the unchanged StringPair payload. Research: R-workflow-183 ("Drag samples directly from the
browser to plugins", four DAWs cited, medium demand).

**Finding that shaped the work.** `StringPairDrag` published only `application/x-zene-stringpair`, so an
external recipient saw a drag with no recognisable file format. The honest seam is the drag helper itself:
both browser drag sources (the file lists and the search results) build their payload through it, and every
consumer of the browser's file keys already treats the value as a filesystem path. So the URL publishing is
keyed on exactly those browser file keys in one testable place (`StringPairDrag::createMimeData`), and no
call site, no internal target and no other StringPair producer (serialized clips, embedded sample data,
model ids, float values) changes at all.

## New command and reversibility

None. This unit adds no `ControlRegistry` command, no agent surface entry and no undo step: a drag publishes
a second MIME format and mutates no project state. An agent's part is unchanged (`browser.query` reports a
sample's path; the musician drags the browser row).

## Format changes

None. Projects save and load byte-for-byte as before; the change is outgoing GUI drag MIME only.

## Known limits

- Arrangement clip drags (`clip_*` serialized clips) and `sampledata` (embedded audio) deliberately publish
  no URL - the unit's out-of-scope list; a file manager receiving a clip's source file would need a real
  file on disk, which an embedded clip has not got.
- External receivers vary; the tests model the file-manager / plug-in-editor MIME contract
  (`text/uri-list` with a local file). A manual GUI smoke check against a concrete file manager and a
  hosted plug-in editor remains a manual step - offscreen CI cannot drive an OS-level drag.
- The change is GUI-thread only (drag construction); no audio-thread path is touched. TSan does not run on
  this box (runtime crash at thread creation), and none is needed: no shared state is introduced.
