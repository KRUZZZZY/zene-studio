# Q050-103 - Sampler envelopes and released-voice policy

Queue unit (P1, M, feature, area L10, members `R-instruments-20`, `R-instruments-75`): the Audio File Processor had a
fixed 3 ms release and no way to fade a note in, and every note took a fresh playback state on the audio thread with no
rule for what happens when many notes sound at once. Built on branch `feat/050-Q050-484-oc` together with Q050-484,
Q050-087 and Q050-071 (a feature batch; each unit has its own commits).

## What was built

- **Attack and Release models** (`plugins/AudioFileProcessor/AudioFileProcessor.h`, `.cpp`): two `FloatModel`s in
  milliseconds - Attack 0..2000 (default 0), Release 0..5000 (default **3**, the value the sampler always used). The
  release feeds `Instrument::desiredReleaseTimeMs()`, so the engine keeps the note alive for exactly that long after
  note-off and `Instrument::applyRelease` fades it linearly. The attack is a linear ramp from silence, counted from the
  note's own first frame (`NotePlayHandle::totalFramesPlayed()`), so a note that starts while others are sounding ramps
  on its own. With Attack 0 the ramp is skipped entirely, so the output of an unchanged project is bit-identical.
- **Voice limit and voice-reuse policy** (`plugins/AudioFileProcessor/SamplerVoicePool.h`): an `IntModel` "Voice limit"
  (1..64, default 64). The sampler now owns a fixed pool of 64 + 16 voices built when the instrument is created; a note
  start claims one with atomics only - **no allocation on the audio thread** (the old code did
  `new Sample::PlaybackState` on every note's first period). At the limit the pool picks, deterministically:
  1. the voice whose note was **released the longest ago**; else
  2. the voice whose note **started the longest ago**.
  The chosen note is not cut: it is marked, fades to silence over 3 ms on its own render, then frees its voice. The new note
  takes one of the 16 spare voices, starts from a reset playback state and its own envelope position. Notes that were not
  chosen are untouched. Ties cannot occur (strictly increasing order numbers).
- **Persistence** (`saveSettings` / `loadSettings`): `atk`, `rel`, `voices` attributes. A project without them loads the
  defaults (Attack 0, Release 3 ms, limit 64), i.e. plays as it always did; the existing loop-point compatibility rule
  (`lframe` absent -> `sframe`) is unchanged.
- **GUI** (`AudioFileProcessorView.cpp`): two knobs (Attack, Release) and an LCD box (Voice limit) in the strip between
  the title and the file name, bound to the same models the agent reads.
- **Agent**: no new command. The three models are named, appended after the eight existing ones (parameter indices 8, 9,
  10 - the earlier indices are unchanged), so `plugin.param_get` / `plugin.param_set` on `inst` and the automation commands
  (`automation.add_point` ... on `inst/8`, `inst/9`, `inst/10`) see them.

## Commands and reversibility

No new or changed command: `plugin.param_set` stays `true_inverse` (one `control.undo` step per set - exercised in
`automationDrivesTheEnvelope`), `plugin.param_get` and `plugin.list` stay `not_mutating`. No snapshot, canary or A16
change.

## Format

New optional attributes `atk`, `rel`, `voices` on the `<audiofileprocessor>` element. Old projects load without them (see
above); a project saved now and opened in an older build ignores them and plays with the old fixed 3 ms release.

## Known limits

- The voice limit is a count of sounding notes per sampler instance, default 64. A project that sounded more than 64 notes
  at once on one sampler (it had no cap before) now has the oldest/released ones faded out at the 65th. 16 further voices exist
  only for the notes being faded out; a burst of more than 16 reuses inside 3 ms drops the surplus new notes.
- The sampler's "Interpolation mode" selector still has no effect on the converter: `Sample::play` asks for the render's
  SRC quality (`ExportRenderSettings`) and the voice pool is built for that mode. That is how it behaved before this unit.
  If an export selects a different SRC quality, the first note of each voice re-creates its converter (the existing
  behaviour; exports are not realtime).
- Envelope hold, a sample-gain envelope and drum-kit fades are not part of this unit (they were not in its acceptance).
- The race-freedom of the voice pool is argued, not measured: ThreadSanitizer does not run on this machine. Notes of one
  instrument render on several engine threads; one note's voice is written only by that note, and everything the pool shares
  between notes is a `std::atomic` (the stolen mark carries the victim's token, so it cannot hit a voice that was handed on).
