# Q050-055.2 - Keyboard plug-in actions (stage 2 of 2)

Unit Q050-055.2, cluster "Context-aware shortcuts and plug-in actions", stage 2 of 2, on the panel scopes of stage 1
(`docs/050-features/Q050-055.1.md`). A key can open the selected track's device editor, and a key can load a chosen
plug-in onto the selected track or mixer channel.

## What was built

**Selection.** The commands read `ShellSelection` when they run, and nothing is remembered, so a key cannot act on a stale
track. They then run `plugin.editor_open` / `plugin.load` with the explicit target. No fallback picks another target:
nothing selected, or no such device on the selection, is refused.

**Which device.** The shell has a selected track, not a selected device, so `plugin.selected_editor_open` opens the track's
instrument, or on a track with none (and on a selected mixer channel) its first effect; `device: effect` asks for the first
effect. The plug-in's own window when it can open one, else the host's view, as the device card does; `surface` says which.

**The binding.** Stored as a normal scoped override, `panels.<scope>["<Panel> ▸ Load Plug-in ▸ <key>"]`, where `<key>` is
`pluginorganiser::keyOf` (module + sub-plugin attributes), not `dev-<n>`, which moves when a plug-in is installed. Export,
import, undo, clash rules and restart therefore need no new store. Setting its keys to empty removes the row.

## New commands

| id | args | class | notes |
| --- | --- | --- | --- |
| `plugin.selected_editor_open` | `device`: main, effect (optional) | `not_mutating` | Needs a display, as `plugin.editor_open` does. Interface state. |
| `plugin.selected_load` | `device`: dev-<n> or stable key | `not_mutating` wrapper | Runs `plugin.load`, which records itself as `snapshot`: an effect is one undo step, an instrument replacement `reversible:false`. Needs the interface, because the selection is interface state; `plugin.load` itself stays headless-safe. |
| `shortcuts.bind_plugin` | `scope`, `device`, `keys`, `force` | `not_mutating` wrapper | Runs `shortcuts.set`, which records one `true_inverse` undo step. |

**Why wrappers are classed `not_mutating`.** It is the `arrangement.nudge` / `range.consolidate` pattern: the wrapper writes
nothing, and the nested command keeps its own class and record. A mutating wrapper would also forward the bare
`plugin.selected_load` to a collaboration host, where it would act on the HOST's selection; this way the explicit `plugin.load`
is what travels.

## Format changes

None to projects. `ui/shortcuts` `panels` holds one more kind of id; older builds report it `unknown` on import and keep it.

## Known limits

- The hosted native-editor path is not driven here: the test platform cannot embed one, so the keys are proven against the
  host's view, and the native branch is the unchanged `plugin.editor_open` that `PluginNativeEditorTest` owns.
- There is no "selected device" in the shell, so a key opens the main device or the first effect, not an arbitrary one.
- An instrument track with no instrument loaded has no device card, so its editor action refuses with `plugin.editor_open`'s reason.
- A binding's row shows the stable key, not the display name (`Arranger ▸ Load Plug-in ▸ amplifier`).
- Scoped keys work only with the focus in one of the four panels (stage 1's rule). The two editor actions and Load a Plug-in...
  also exist as menu actions for a window-wide key; a chosen plug-in has no window-wide key.
- A bound plug-in that has since been uninstalled keeps its row; pressing it reports that the device is not in the catalogue.
