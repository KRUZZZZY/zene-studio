# Q050-481.1 - Host VST2 instruments through Carla (stage 1 of 4)

Queue unit (P1, L, modernisation, area L10). Branch `feat/050-Q050-481.1-oc`, cut from `050/m0-train-24` (`2a7fd9f9c7`).
Goal: musicians and agents load native and Wine-bridged VST2 instruments through Carla. Stages 2-4 (VST2 effects,
converting VeSTige/VST-effect projects, removing `VstBase`/`Vestige`/`VstEffect`) are later units; nothing here has
to be undone for them.

## What was built

- **`plugins/CarlaVst2` -> module `carlavst2`** (instrument, built wherever Carla Rack is built):
  - `CarlaVst2Instrument` is a `CarlaInstrument` (a Carla Rack instance) holding exactly one VST2 plug-in, added with
    Carla's host API (`carla_add_plugin` through `carla_create_native_plugin_host_handle`, from the runtime's
    `libcarla_host-plugin`). Native binaries run in Carla; 64-bit (and, where installed, 32-bit) Windows `.dll`s run in
    Carla's Wine bridge. No VST2 header is compiled anywhere in the product (AGENTS.md rule 8).
  - Inherited unchanged from the Rack: the audio/MIDI path (`CarlaInstrument::playImpl` and its lock-free MIDI
    hand-off), the parameter models (one automatable `CarlaParamFloatModel` per plug-in parameter), the Params window,
    and the state (Carla's project XML: binary, unique id, parameter values, and the plug-in's chunk, base64).
  - The plug-in's own editor: `openNativeEditor` embeds it in Zene's editor window through `carla_embed_custom_ui`
    (effEditOpen with the window, size from Carla's `ENGINE_CALLBACK_EMBED_UI_RESIZED`); a Windows plug-in's editor is
    shown by Carla in a window of its own.
  - A GUI-thread timer calls Carla's `ui_idle` (embedded-editor idle, deferred plug-in deletion).
  - `CarlaVst2Discovery`: search folders (`ZENE_VST2_PATH` replaces the list; otherwise `VST_PATH`, the VST folder
    setting, `~/.vst`, `~/.lxvst`, `/usr/lib/vst`, `/usr/local/lib/vst`, `/usr/lib/lxvst`); each `.so`/`.dll` is
    classified by its own ELF/PE header and read by Carla's discovery tool **in a separate process**
    (`carla-discovery-native`, or `carla-discovery-win64.exe` through Wine); results cached per file (size + mtime)
    for the session; a run that could not start or timed out is not cached.
  - `lmms_plugin_main` declines (placeholder, Q050-018) when there is no Carla runtime (the weak stand-in has no Rack)
    or the key names no binary, or Carla cannot load it.
- **`plugins/CarlaBase`**: `CarlaInstrument` takes an optional key (becomes `Plugin::key()`, which the project stores),
  can leave the Rack's unused/disabled parameter slots unnamed (so `parameterCount()` and `plugin.param_*` see only
  the plug-in's parameters), and has `hostsSinglePlugin()`; its view then shows "Show plugin editor" instead of
  Carla's own GUI button. All three default off: Carla Rack and Carla Patchbay are unchanged. `DummyCarla.cpp` gains
  the two host-handle symbols the module links.
- **Catalogue** (`src/core/ControlDeviceVst2.cpp`): `plugin.list` format `vst2`, appended after every other format so no
  existing `dev-<n>` moves; entries carry `file`, `unique_id`, `binary` (`native`/`win64`/`win32`) and `bridged`;
  `plugin.load` resolves them to the `carlavst2` key. Vendor from the discovery's maker; the device picker labels the
  format `VST2`; the instrument browser recognises the host; `MissingDevices` names a saved VST2 device by name/file.
- **Fixture** (`tests/data/vst2-test-instrument`): a plain-C VST2 instrument (clean-room ABI restated from the tree's
  VeSTige layout, `zene_vst2_abi.h`) built natively and, with `winegcc -b x86_64-w64-mingw32`, as a Windows PE `.dll`.
  While a key is held it outputs (L, R) = (Level, Tone); it counts note-ons in its chunk only; its chunk reports
  whether its editor is open.
- **`tools/build-carla-runtime.sh`**: builds a real Carla runtime from the pinned submodule (`plugins/CarlaBase/carla`)
  into `<build>/carla-runtime/lib`, optionally with the Wine bridge (needs a C++ PE toolchain such as llvm-mingw).

## Realtime (reworked after review round 1)

Round 1 was sent back for two realtime faults: the render period called Carla's process, which for a Wine-bridged
plug-in waits on the bridge's semaphore every block; and automation changed the parameter models on the render
thread, whose `dataChanged` (connected `Qt::DirectConnection`) ran `paramModelChanged` there and reached Carla's
mutex-taking `uiParameterChange` for a plug-in with its own editor. Both are fixed for every VST2 instance:

- **Carla never runs on the audio thread.** `carlavst2::Renderer` (`plugins/CarlaVst2/CarlaVst2Renderer.*`) owns a
  worker thread that calls Carla (`CarlaInstrument::playImpl`: time info, the queued MIDI from the lock-free
  hand-off, Carla's process) two periods ahead of the audio thread into a preallocated single-producer/single-consumer
  frame ring (32768 frames). `CarlaVst2Instrument::playImpl` - the audio thread - only copies finished frames out
  with two atomics, or outputs silence for a period that is not ready (counted). No lock, allocation, system call or
  Carla call. The two periods are reported to the track (`reportLatency`), so plug-in delay compensation lines the
  instrument up with the rest of the project.
- **While a project is exported** (`Song::isExporting()`) there is no realtime deadline and a dropped period would be
  silence in the file, so `Renderer::read` waits for the worker, at most 2 s per period - the rule the VeSTige host
  already applies while exporting (`plugins/Vestige/Vestige.cpp:434`, `tryLock(-1)` when exporting).
- **No parameter signal on the render thread.** Every Rack parameter model of a VST2 instance defers render-thread
  change signals (`setDeferChangeSignalOnRenderThread`). The worker hands each changed value to Carla before each
  period (`pushParameters`, `set_parameter_value`); the instrument's 30 ms GUI timer emits the deferred signals
  (`flushDeferredChange`), so `paramModelChanged` and Carla's UI updates run on the GUI thread only.
- **Never played half-built or half-destroyed.** `CarlaInstrument` can leave the play-handle registration to its
  subclass (`playNow` flag, `startPlaying()`); the VST2 instrument registers once fully built and removes its play
  handles first in its destructor, then stops the worker, before the Rack is torn down.
- Declared to the static sweep: `CarlaVst2Instrument::playImpl` and `carlavst2::Renderer::read` in
  `tests/rt-safety-scope.txt` (`RtSafetySweep` PASS).
- Still on the GUI/control thread: discovery (`QProcess`), `carla_add_plugin`, state and preset I/O (the worker is
  paused around `loadSettings`), the editor calls and `ui_idle`. `engineCallback` stores two relaxed atomics.
- Carla Rack and Carla Patchbay are unchanged (they still call Carla from the render path, as before this unit).
- Local TSan does not run on this box: the ring's ordering (release on publish, acquire on read, one producer, one
  consumer) and the pause handshake were reasoned, not measured.

## Known limits

- **Latency**: Carla runs two periods ahead of the audio thread; the instrument reports that to the track (plug-in
  delay compensation). During live playback, a period the worker has not finished in time is silence (counted), not a
  wait. Offline export waits for the worker, bounded to two seconds per period.
- **A Wine bridge that has just started can drop the MIDI of its first blocks** (measured in round 1: a note-on in the
  bridge's first ~200 ms was lost, a re-sent one sounded). The test re-sends its note while nothing sounds.

- **A Carla runtime is required.** Without one (an ordinary build links the weak stand-in) no VST2 is listed and a
  project that used one keeps it as a placeholder. Hosted CI has no runtime, so `CarlaVst2HostingTest` reports
  Skipped there; it fails, not skips, whenever the runtime and fixture exist but the host does not work.
- **Bridged chunk restore is unproven here.** Carla hands a chunk to its bridge through a file in `/var/tmp`
  (water's `tempDirectory`, hard-coded); this lane's sandbox cannot write `/var/tmp`, so the bridge never receives
  it. The test checks it whenever that directory is writable and says so otherwise. Native chunk restore is proven.
- **Wine-bridged editor** opens in Carla's own Wine window; not exercised by the test (no display in the test run).
- **Carla's water `removeEllipsis` bug** (upstream, in the submodule): if the directory the loader used for
  `libcarla_native-plugin` contains `..`, creating any Carla Rack corrupts the heap (measured: SIGSEGV under glibc's
  malloc checker with such a path, clean without). This affects Carla Rack too; keep that path normalised.
- **Build-tree stand-in shadowing**: `build/plugins/libcarla_native-plugin.so` (the weak stand-in) is a module
  candidate in the build tree, and once loaded the Carla modules bind to it by soname. The test uses its own plug-in
  directory without it; an installed product keeps the stand-in in `optional/`, which is not scanned.
- Discovery runs when the plug-in factory first lists modules, once per binary per session; a large VST2 folder makes
  that first listing slower (Windows binaries cost a Wine start each).
- Presets live in the `carlavst2` preset folder, shared by every VST2 instrument; a preset carries its plug-in, so
  loading one made with another plug-in switches to that plug-in.
- 32-bit Windows binaries need Carla's 32-bit bridge, which `tools/build-carla-runtime.sh` does not build; untested.
- Q050-477's legacy corpus does not exist yet; this stage adds no legacy-project fixtures (stage 3 does).
