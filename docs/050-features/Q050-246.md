# Q050-246 - Measure and correct external MIDI output timing

Type: completion (P2, size M). Member: R-recording-56. Area: L15.

## What was measured, and the fix
- The baseline is over 1 ms. On ALSA, every note was scheduled at its whole song tick
  (`snd_seq_ev_schedule_tick(TimePos)`); a note's offset inside the audio period is far below one tick (a 256-frame
  period is 5.8 ms, a tick 10.4 ms at 120 BPM), so every note of a period left when the sequencer thread drained the
  period. Measured: 4.5-4.7 ms max interval error on a 1/32-note line (three runs).
- Fix (sub-tick scheduling): `MidiAlsaSeq::processOutEventAt()` (the frame-offset entry `MidiPort` already calls,
  0.5.0 W4) turns the offset into a real-time due point - the period's start (`RenderPeriodClock`, now readable from
  the render thread's workers too: `inPeriod()`) plus offset / sample rate - and pushes it with the event
  (`MidiOutQueue::Command::dueNs`). The sequencer thread schedules the event on the ALSA queue in real time, relative
  to now, at that point (a point already passed goes at 0 on the same queue, keeping order). The output queue's timer
  asks for 4 kHz (`MidiAlsaSeq::QueueTimerHz`): at the default 1 ms tick the same fixture measured 1.50 ms.
  Clock messages (direct) and events with no frame position keep their old scheduling.
- Realtime: on the audio path the override adds one atomic read, one clock read and integer arithmetic before the
  existing lock-free, allocation-free push; nothing allocates, locks or waits (the wake-pipe write is the existing one).

## Acceptance
| Criterion | Test | What it proves | Exit |
|---|---|---|---|
| A MIDI loopback test measures repeated 1/32-note output timing and reports jitter in milliseconds. | `MidiOutTimingTest::thirtySecondNotesKeepTheirSpacingThroughAnAlsaLoopback` | a render-period driver (256 frames, 120 BPM, 33 notes 62.5 ms apart) sends through a real `MidiAlsaSeq` port to a second ALSA client subscribed with real-time queue stamps; each run prints `Q050_246_MIDI_JITTER` lines: target, mean interval, max and mean |interval - 62.5 ms|, the same against the requested intervals, period, rate, tempo and setup | ctest `MidiOutTimingTest` 0 |
| If measured jitter exceeds 1 ms, the regression test proves sub-tick scheduling fixes it; otherwise the measured pass and hardware setup are recorded. | same test | the whole-tick path (the pre-fix behaviour, driven the way `MidiClient::processOutEventAt`'s default sent it) must measure > 1 ms; the product path must measure <= 1 ms | ctest 0 |

Measured on this host (three consecutive runs, max |error|): whole-tick 4.57 / 4.46 / 4.61 ms; frame-offset
0.252 / 0.251 / 0.251 ms (against 62.5 ms) and 0.255 / 0.266 / 0.256 ms (against the requested intervals). With the
override reverted to drop the offset the test FAILS: "1/32-note output jitter 4.638 ms > 1 ms" (exit 1).

Setup recorded: Linux (CachyOS), ALSA sequencer kernel loopback client-to-client, 44.1 kHz Dummy engine, HR timer;
no hardware MIDI interface is attached to this host, so no cable loopback was measured.

The assertion uses the delivered-versus-requested interval: on a loaded 4-core host the simulated render loop itself
wakes late now and then (one run at load 4 measured 26 ms raw), and that lateness belongs to the audio device's
callback in the product, not to the MIDI output. The raw 62.5 ms figure is printed beside it.

## New commands / reversibility / format changes
None. No project data; `track.midi_out` unchanged.

## Known limits
- ALSA only. JACK already places output at frames (0.5.0 W4); raw MIDI, Windows and macOS clients still send at
  enqueue time.
- The due point is the render period's start: MIDI leaves when the period is rendered, ahead of its audio by the
  output latency (no latency compensation - out of scope).
- A note whose due point passed before the sequencer thread woke goes out at once (late by the wake-up).
- Not measured through a hardware interface.
