# Q050-321.1 — Touch keyboard: multi-touch input

Unit: P2, size L, area L14. Branch `feat/050-Q050-321.1-oc`, base `050/m0-train-24` (`2a7fd9f9c7`).
Stage 1 of 3 of Q050-321. Stage 2 (independent multi-touch drum pads) and stage 3 (accessible
surfaces and the two-finger double-tap record gesture) are deliberately left out; nothing here
has to be undone for them.

## What was built

- **Each finger its own note.** `PianoView` (the instrument window's keyboard) now takes Qt touch
  events and gives every contact its own note. A contact's note lasts until *that* contact lifts:
  releasing or cancelling one contact leaves every other contact's note sounding. Two fingers on
  the same key sound one note and get one note-off when the last of them lifts, because
  `InstrumentTrack` keeps one live voice per pitch (`m_notes[key]`).
- **The bookkeeping is a reusable model, not keyboard code.** `TouchContacts`
  (`include/TouchContacts.h`, `src/gui/TouchContacts.cpp`) is a small surface-independent
  contact tracker: a `KeyAt` / `VelocityAt` surface, a `NoteOn` / `NoteOff` sink, a map of
  contact → note and a count of contacts per note. Stage 2's drum pads reuse it with a pad grid
  as the surface — that is the seam it exists for.
- **Through the existing MIDI input path.** The sink calls exactly what the mouse handler calls:
  `piano->midiEventProcessor()->processInEvent(MidiEvent(MidiNoteOn/MidiNoteOff, ...))` plus
  `Piano::setKeyState`, so the track's monitoring, MIDI recording, input transform, MPE capture
  and layer/part routing all see touch notes with no new path. Live contacts are transient MIDI
  input: no project data, no undo step.
- **Mouse and computer keyboard unchanged.** `PianoView`'s mouse handlers and its
  `keyPressEvent` / `keyReleaseEvent` are untouched; Qt-synthesized mouse events
  (`Qt::MouseEventSynthesizedByQt`) are ignored by the touch path, so a finger can never sound
  twice. Two tests drive the real mouse and the real key event and assert the note still
  starts and ends.
- **No stuck notes.** A whole-sequence `QEvent::TouchCancel` releases every contact; a
  `QEvent::TouchEnd` releases every contact the platform did not report lifting; a focus loss
  releases every contact. A per-contact `TouchContacts::cancel(id)` releases exactly one.
- **Qt 5.15 / Qt 6 across the seam.** The touch-point spelling
  (`QTouchEvent::touchPoints()` + `screenPos()` vs `QEvent::points()` + `globalPosition()`) and
  the touch-point state enum (`Qt::TouchPointState` vs `QEventPoint::State`) are behind the same
  `QT_VERSION` guards `CompSwipeStrip.cpp` and `TouchInput.cpp` already use; the test's
  `commit()` return value is guarded like `TakeLanesPanelTest`'s.

## New commands and reversibility

None. q050-321.1 adds no agent command: a touch contact is transient live MIDI input, not a
project edit, so there is no action to register, no undo step and no reversibility row. The
notes reach the instrument through the same `InstrumentTrack::processInEvent` path a mouse click
uses, and an agent prepares MIDI with the existing `note.add` / `note.edit` and plays it back with
the existing transport actions. `window.appearance`'s workspace field is untouched (Q050-235.1
already carries it).

## Format changes

None. No project field, no `.mmp`/`.mmpz` change: live touch contacts are never saved, and a
project saved before or after this change loads and renders exactly as before.

## Known limits

- Stage 1 only: the drum pads (stage 2) and the accessible surface + two-finger double-tap record
  gesture (stage 3) are not part of this unit. `TouchContacts` is the seam the pads build on.
- The keyboard's hit rectangles are its drawn key widths — a black key is 8 logical pixels wide and
  a white key 10, so the keyboard is separately hit-testable but does *not* meet the 44-pixel
  discrete-target minimum. That minimum is stage 3's acceptance for the touch workspace; the keys
  are deliberately left at their musical geometry rather than widened into a different instrument.
- The surface does not implement per-key accessibility roles and pressed-state announcements; that
  is stage 3's acceptance too.
- Touch is taken from the platform's own `QTouchEvent` stream. A platform that only synthesizes
  mouse events from touches behaves as before (one note, the mouse path).
- Only the instrument window's keyboard gets touch in this unit; the piano roll's keyboard column
  keeps its existing mouse and computer-keyboard input.
