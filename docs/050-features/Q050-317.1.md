# Q050-317.1 - Persist and edit mastering song sequences

Stage 1 of 3 of cluster **Q050-317** (`R-workflow-152`, P2, L, area L12). The other two stages are rendering the
songs/full release and the GUI release page's richer editing; this stage is the state and its agent surface.

Branch `feat/050-Q050-317.1-oc`, cut from `050/m0-train-24`. Goal: create a mastering release sequence through
`project.new_document` and agent commands, with ordered audio-file sources, per-song processing, gaps and fades,
and have that survive save and reopen.

## What was built

- **`include/MasteringSequence.h` / `src/core/MasteringSequence.cpp`** (new): `MasteringSequence`, a `ProjectSection`
  holding an ordered `QVector<MasteringSong>`. A `MasteringSong` is `{id, source, title, processing, fadeInMs,
  fadeOutMs, gapMs}`. `processing` is the *name* of one of `MasteringJob::defaultCandidates()` (or `"none"`), never a
  copy of its numbers - so a saved song cannot carry a loudness target that disagrees with the candidate it names, and
  a change to the candidate set moves every song that names it. The gap is the silence *after* the song; the last
  song's gap is kept but is not heard between songs (the list reports `gap_applies: false` for it). Saved as
  `<mastering-sequence>` only when it holds a song (absent element loads as empty: the reset-on-absence rule), with
  one `<song>` child per song and the fields as attributes. The load pass is defensive: a missing/duplicate/malformed
  id is re-assigned, a negative fade or gap clamps to 0, an over-bound one clamps to the page's limit, and a child
  without a `source` is not a song.
- **`src/core/ControlCommandsMasteringSequence.cpp`** (new): the registered command group.
  - reads: `mastering.sequence_list` (songs in release order with `song-<n>`, `source`, `title`, `processing`,
    `fade_in_ms`, `fade_out_ms`, `gap_ms`, `exists`, `file_name`, `index`, `gap_applies`; plus `processing_names`,
    `document_type`, `count`, `max_songs`);
  - edits: `mastering.song_add`, `mastering.song_set`, `mastering.song_move`, `mastering.song_remove`. Each is one
    undo step that puts the whole previous list back (`control::addUndoStep`, the mechanism `section.*` uses for the
    same kind of state); an edit that changes nothing records no step; a refusal changes nothing and records no step.
  - Every source must be an existing file the build decodes; the stored path is absolute. `processing` is validated
    against the engine's own candidate names, fades/gaps against `MaxFadeMs` / `MaxGapMs`.
- **Reversibility**: `mastering.sequence_list` is `not_mutating`; the four edits are `true_inverse` (a recorded action
  checkpoint - a `ProjectSection` is not a `JournallingObject`, so no live checkpoint can reach it), in
  `src/core/ControlReversibilityTableMastering.cpp`.
- **GUI**: `CommandLists::masteringSequence()` (`src/gui/CommandLists.cpp`, declared in `include/CommandLists.h`) is a
  `CommandListDialog` over `mastering.sequence_list`, and Project Tools gets a **Mastering Release...** entry
  (`src/gui/shell/ShellCommandMenus.cpp`) whose `controlCommand` property is that list id. Row actions are
  Edit..., Move to Top, Move to Bottom, Move to Position..., Remove, and the Add Song extra - every one a
  `mastering.song_*` command, so the page and an agent edit the same list.
- **Project wiring**: `MasteringSequence::instance()` is registered in `ProjectSectionRegistry::registerAll()` (so a
  `--render`/headless run loads it too) and the group is registered in `ControlRegistryRegistrations.cpp`.
- **Pre-existing crash the acceptance path hits, fixed**: `project.new_document` for *mastering* or *live* killed the
  GUI instance (measured: SIGSEGV in `TrackView::updateFolderIndent` immediately after the command answered, both on
  this branch and on the base tree `zene-cachyos` at `00fc19d6b3`). Two deferred readers outlived their tracks: the
  zero-delay `TrackView` callback (`src/gui/tracks/TrackView.cpp`) now checks the track is still in the container's
  live list before reading it (pointer compare, never a dereference), and `InstrumentTrackView::~InstrumentTrackView`
  no longer dereferences a null `model()` when its track was deleted first. This is what makes the acceptance path
  (create a mastering document, then edit its release) survive in the real application at all.

Out of scope, left for stages 2 and 3: rendering a song with its processing/fades and the full release with gaps,
and any editing affordance beyond the shared list.

## Format

New project element `<mastering-sequence>` with one `<song id source title processing fade-in-ms fade-out-ms gap-ms>`
child per song, written only when the sequence holds one. Defaults are omitted, so a song with no processing, no fades
and no gap writes only `id` and `source`. Old projects have no element and load as an empty release; a project that
never uses the feature re-saves byte for byte.

## Known limits

- Rendering each song with its processing/fades and the whole release with the gaps is the next stage; this stage
  stores and edits the state only.
- `processing` names a candidate from `MasteringJob::defaultCandidates()`; there is no per-song chain editor yet.
  The name is deliberately not resolved to numbers until a render derives them, so a song always reflects the current
  candidate set.
- The last song's `gap_ms` is kept (it is part of the release's shape) but `gap_applies` is false and a render will not
  insert it; that fact is reported rather than silently ignored.
- The page is the shared list dialog: editing a song's fields is the command's form (all fields, blank keeps the
  current value), not a bespoke page. Layout/naming were left open by the scoping brief.
- The pre-existing `project.new_document` GUI crash is fixed for mastering/live documents; the fix is two deferred-
  lifetime guards, not a redesign of the document-replacement sequence.
