# Q050-313: Zyn MIDI during a preset load

Users can send MIDI to ZynAddSubFX without waiting behind a preset load.

## What was already there, and what changed

`handleMidiEvent()` already pushed to `MidiHandoffQueue<256>` without taking `m_pluginMutex`, and the audio path already used a zero-wait try-lock (`plugins/ZynAddSubFx/ZynAddSubFx.cpp`). That behaviour had no direct test, so this unit adds one.

Reading the overflow path found these defects in its promise that a refused event's channel is cut after the events queued before the refusal. Each left a note stuck:

| Defect | Fix |
| --- | --- |
| A refused note-off left the key's running count behind. All-notes-off released the note but kept the count, so the key's next note-off was swallowed and that note never ended. | `LocalZynAddSubFx::applyMidiEvent` clears the addressed channel's counts on CC 123 and CC 120. |
| The cut was applied at once, ahead of accepted events waiting at a later frame of the period, so it ended nothing and those notes then started. | `forwardQueuedMidi()` places the cut at the latest frame forwarded in the drain. |
| Clearing every channel's counts on one channel's cut would swallow the note-off of a note still running on another channel. This came from the first version of this unit's own fix. | The counts are per MIDI channel, and a cut clears only its own channel. |
| A full drain filled the 256-entry scheduled list. One channel's cuts can also repeat at different queue positions, so 256 + 16 entries were not enough either. A cut that found the list full was applied at once, with the same result. | The list holds 256 + 16 × 257 = 4368 entries: one drain plus one cut per channel at each of its 257 queue boundaries. |

## Commands and project format

No command, GUI action, undo step or reversibility entry was added or changed. The existing routes are the instrument view's preset drop (`ZynAddSubFxView::dropEvent`, which calls `loadFile()`) and `plugin.preset_load`, which restores the device state. Submitting MIDI takes no plug-in lock on either route. The queue is runtime-only, so the project format is unchanged.

## Known limits

- The slow preset is simulated: the hook holds a real `loadFile()` open, with a preset path that does not exist. No large preset was timed.
- The agent route was read in the code, not driven by these tests.
- The overflow cases run on the in-process synth. The separate-process client uses the same `LocalZynAddSubFx` code and receives the cut's offset, but overflow was not driven through it. `ZynSeparateProcessTest` passes as a regression check only.
- The instrument is silent while a load holds the mutex, and notes queued meanwhile start late, when it finishes.
- Drop counts are internal: nothing shows them to the user.
- A flood at a later frame still applies each event in queue order, so an offset-0 event that follows a later-frame event is applied first. That ordering predates this unit and is unchanged.
- The same key on two channels now counts separately. Before, the two channels shared one count for that key, so such a project can render differently. Single-channel playing is unchanged.
- The 4368-entry bound is the worst case. It adds about 52 KB per Zyn instance if an entry is 12 bytes (not measured); the array never grows and nothing allocates on the audio thread.
- TSan does not run on this box. By design, the sender only touches the atomic queue and overflow state, and the test's other variables are read only after the semaphore or the join.
