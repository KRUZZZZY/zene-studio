# Q050-131 - Benchmark real-model stem separation speed

Unit: docs, S, L05. Goal: users can see reproducible real-model throughput figures before
deciding to separate a clip.

## What was built

A new section `doc/STEM-SPLIT.md` "End-to-end §4. Real-model benchmark (Q050-131,
2026-10-17/18/19)" (doc/STEM-SPLIT.md:149). It is the document's only real-model section;
sections 1–3 keep every stub-model figure, explicitly labelled. It records:

- **Model revision:** the pinned spec of owner decision 14 — commit
  `d54ed9eb60e258ea82131c6ee14578628816456a` of `StemSplitio/htdemucs-onnx`
  (`htdemucs_fp16weights.onnx`, 165,612,636 bytes, sha256
  `d05c269d0178d2a72ad484b10b11dd370193fc923201c3b27a99f848745db70a`). The file was
  downloaded from that pinned commit on 2026-10-17; its sha256 was re-verified with
  `sha256sum` (exit 0) immediately before each later measurement day (2026-10-18,
  2026-10-19).
- **Inference path:** the exact path the GUI drives (`ExternalProcessStemSeparator`
  spawns `/usr/bin/python3 tools/stem_split_cli.py`): Python 3.14.8, `onnxruntime`
  1.28.0 (`CPUExecutionProvider`), numpy 2.5.4.
- **Hardware:** Intel Core Ultra 7 255HX (20 cores, 1 thread per core, NUMA 1),
  30.7 GiB RAM, kernel `7.2.9-2-cachyos`.
- **Reference audio:** deterministic synthetic mix — 30.0 s stereo 44.1 kHz float32,
  1,323,000 frames, 10,584,000 bytes (110 Hz sine + 220 Hz sine + seeded gaussian
  noise, PCG64 seed 20261017, right channel delayed 100 frames), sha256
  `548aab6c6fc07424d9ed752a084eb18a9bde7a37a2d004d11be8b9c6eb47d2ad`. The generator
  command is printed verbatim in the doc; regenerating it on 2026-10-18 and 2026-10-19
  reproduced the same sha256 byte-for-byte (exit 0).
- **Exact command:** the per-run `python3 tools/stem_split_cli.py --model
  htdemucs_fp16weights.onnx --input ref-mix-30s.f32 --in-format f32 --in-rate 44100
  --out-dir stems-out-N --out-format f32 --progress-json` line, printed in the doc.
- **Results:** three runs per measurement day over the 11 chunks the model's fixed
  343,980-frame segment (7.8 s) yields for 30 s. Canonical table = 2026-10-19
  (every cell captured, lightly loaded box); the 2026-10-18 and 2026-10-17
  measurements are kept in the same table for cross-day reproducibility:

  The user-facing rule recorded in the doc: a 30 s clip separates in about 42–47 s of
  wall time (RTF ≈ 1.13–1.30) on a lightly loaded box and 60–77 s (RTF ≈ 1.86–2.25)
  under heavy concurrent load, plus ~8–11 s of model/session load per CLI process.
  The doc states the load condition per run plainly, that real time stays impossible
  by design (7.8 s receptive field), and that an idle run can only be faster than
  the contended figures.

- **Output sanity:** each run wrote four stems of exactly 10,584,000 bytes
  (1,323,000 frames × 2 ch × 4 B), every sample finite, per-stem RMS
  drums 0.221 / bass 0.231 / other 0.257 / vocals 0.005 — identical on all three
  measurement days (the mix has no vocal content; a sanity check of the I/O path,
  not a quality claim; also evidence the pipeline is deterministic).

(item 1 reworded to cover quality only), and longest-exercised audio is now the 30 s
benchmark clip (item 5).

## Known limits

- Quality is not measured (SDR or listening); the benchmark is throughput only, and
  the audio is synthetic by construction (deterministic, hash-checkable).
- Load varies between measurement days: the 2026-10-17/18 runs were under heavy
  concurrent load (1-min loadavg up to 50) and are labelled contended upper bounds;
  the 2026-10-19 runs ran on a lightly loaded box (loadavg 7–21). All rows record
  their loadavg so users can compare like with like.
