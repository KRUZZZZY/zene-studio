# Q050-081 - Controller scripting and a mapping editor

Type: feature (P1, size L). Members: R-workflow-36, R-workflow-195, R-workflow-211. Area: L15.

## What was built
- `include/ControllerScript.h`, `src/core/ControllerScript.cpp` - a control-surface script: a Lua file bound to one
  MIDI input and one MIDI output of the MIDI client, through its own `MidiPort` ("Zene script: <name>"). Every event the
  input delivers calls the script's `on_midi(event)` (`type` note_on / note_off / cc / pitch_bend / program /
  channel_pressure / key_pressure, `channel` 1-16, `key`/`velocity` or `controller`/`value`); `on_start()` runs once.
  The script calls `zene.command(id, args)` - `ControlRegistry::invoke`, so schemas, typed refusals, undo and the
  transaction record are the registry's; the refusals Lua scripts already have (`ScriptCommandBridge::refusalFor`) plus
  any file argument and starting or stopping a controller script - and sends feedback to the output with
  `surface.send_cc(channel, cc, value)` / `surface.send_note(channel, key, velocity)`, at most 64 per call.
  `surface.log(text)` writes to the script's log.
- Threads and bounds. `processInEvent()` runs on whatever thread the MIDI client delivers on (the audio thread with
  JACK): it copies the event into a fixed 256-slot lock-free ring and counts; a full ring drops and counts. Nothing
  there allocates, locks, waits or signals. The script runs on the UI thread from a 5 ms timer, at most 64 events per
  turn, in a sandboxed Lua state (base, table, string, math; no io/os/require/load/dofile) with 1,000,000 instructions
  per call (a count hook) and 8 MiB of Lua heap (the existing `ScriptMemoryState` allocator). An error is counted,
  logged (512 characters max) and reported; 8 in a row fault the script, which then drops and counts its events until
  it is started again. A one-second watch compares the bound input with the client's port list: a lost input is
  reported (`port_lost`, `port_losses`), and when it returns the port is subscribed again (`reconnects`).
- Commands (`src/core/ControlCommandsControllerScripts.cpp`): `controller.script_start` {name, path, input, output},
  `controller.script_stop` {name}, `controller.script_state` {name?} - all `not_mutating` (device state, the
  `surface.mcu_connect` precedent; what the script runs records as itself).
- GUI: Customise > Controller Scripts > Start Script... (the command's form), Script State, Stop Script...
  (`src/gui/shell/ShellCommandMenus.cpp`). The mapping editor is the existing Customise > MIDI Mappings... list
  (`CommandLists::controllerMappings`): its rows are `controller.surface_state`, its actions `controller.soft_takeover`,
  `controller.feedback`, `controller.unmap` and its extras `controller.map` / `controller.template_save`; this unit
  proves it lists, edits and persists (below) rather than adding a second editor.
- Example: `data/scripts/controller-surface.lua` - CC 7 drives the master fader (`mixer.set_volume`, the master's id
  read from `mixer.get_state`) and is echoed back; note 94 / 93 run `transport.play` / `transport.stop` and light /
  clear the Play LED.
- `ScriptCommandBridge` exports its Lua <-> JSON conversions (`tableToObject`, `pushJsonObject`) for reuse, and its
  refusal list names `controller.script_start/stop`; the OSC bridge refuses `controller.script_*` too.
- Manual: "Controller scripts" in Scripts, agents and controllers.

## New commands / reversibility / format changes
- `controller.script_start`, `controller.script_stop`, `controller.script_state`: `not_mutating`.
- No project format change: scripts are session state; bindings keep their existing project serialisation.

## Known limits
- Scripts are not saved with the project or restarted at launch.
- A script runs on the UI thread: a call is bounded by its instruction budget (about 1-10 ms of Lua), but a heavy
  script can still make the interface stutter; it never touches the audio thread.
- With a raw MIDI client (no named ports) the input/output names are not checked and port loss is not watched.
- Feedback is CC and notes only (no SysEx, so no Mackie strip LCD).
- Not run under ThreadSanitizer (not available on this box). Race reasoning: the ring has one producer (the client's
  delivery thread) and one consumer (the UI thread), with acquire/release on the two indices; the counters are atomics.
