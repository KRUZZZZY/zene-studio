# Q050-161 - Remove per-period automation ramp locking

Type: fix (P1, size S). Member: R-performance-43. Area: L15.

## What was built
- The lock-free read was already the product's: since cluster 2647 (`c28751cef`, `8c837f075`) the render-time
  `AutomatableModel::valueBuffer()` answers a request inside a `RealtimeScope` from the period's prepared buffer, and the
  serial prepass (`AudioEngine::prepareAutomatableModelBuffers()` -> `prepareValueBufferForRender()`) is the only place a
  ramp or a control write is turned into that buffer. `m_valueBufferMutex` survives only as a test sentinel. What was
  missing was the proof the unit asks for; this unit adds it, and documents at the hit why it takes no lock
  (`src/core/AutomatableModel.cpp`, the `RealtimeScope` branch of `valueBuffer()`).
- `AutomatableModel::setValueBufferCacheHitProbeForTest()` (`include/AutomatableModel.h`, `LMMS_TESTING` only, null in
  the product): a probe called on every cache hit, so a test counts hits on the reading thread.
- `tests/src/core/PhaseDSidechainTest.cpp`, two cases:
  - `cachedRampHitsTakeNoLockAndRecomputeAfterConcurrentUpdates` - four periods on a mixer fader. Period 1: ramp A is
    prepared; a realtime worker reads `valueBuffer()` 256 times while another thread holds the legacy mutex and a
    control thread is blocked writing two values (it waits on the engine's change lock, the render period's owner).
    Every read must be a cache hit (probe count 256, all inside a `RealtimeScope`), return within 2 s and carry ramp A's
    exact bits; the write must not land inside the period. Period 2: the write lands at the boundary and the prepass
    interpolates old -> new bit-exactly as the legacy algorithm. Period 3: a newly published ramp B replaces the
    cache. Period 4: no ramp and no write - the buffer is null and the static value is the last write.
  - `instrumentedRampRenderHitsCacheWithoutLockAndMatchesReference` - the full-mixer ramp render from
    `AutomationPrepassProofTest` (fader 0.75, ramp 0.125 -> 0.875, DC 0.25), rendered on a thread while the mutex is
    held, with the hit probe on: it completes, allocates nothing, the fader is answered from the cache (10 hits), and
    the master output's SHA-256 equals the reference pinned there (`a7348883...5a69`).

## Acceptance
| Criterion | Test | What it proves | Exit |
|---|---|---|---|
| A concurrent ramp test proves cache hits avoid the mutex while recomputation remains correct under updates. | `PhaseDSidechainTest::cachedRampHitsTakeNoLockAndRecomputeAfterConcurrentUpdates` | 256 realtime reads under a held mutex and a blocked concurrent writer are all hits with ramp A's bits; the next periods recompute from the write (bit-exact legacy interpolation) and from a new ramp | ctest `PhaseDSidechainTest` 0 |
| An audio-thread instrumentation test confirms no lock is taken on a cache hit and automation output matches the existing render. | `PhaseDSidechainTest::instrumentedRampRenderHitsCacheWithoutLockAndMatchesReference` | the instrumented render completes under the held mutex with 0 allocations and >0 counted hits, and its SHA-256 equals `AutomationPrepassProofTest`'s reference | ctest `PhaseDSidechainTest` 0 |

The tests fail when the property breaks (mutation runs, logs in the run folder):
- a `QMutexLocker` on `m_valueBufferMutex` added to the cache-hit return: both cases FAIL ("a cache-hit valueBuffer()
  read waited on a lock", "the ramp render waited on m_valueBufferMutex"), exit 1 each;
- `consumePublishedValuePair()` removed from the prepass (updates not recomputed): the concurrent case FAILS at the
  period-2 comparison, exit 1.
Restored: `PhaseDSidechainTest` passes, exit 0. The probe seam itself is the only product-side change, so "reverting the
product change" removes the API the tests call (they do not build); the mutations above are the meaningful negative
controls.

## Known limits
- Not run under ThreadSanitizer (it does not run on this box). Race reasoning: worker reads touch only render-owned
  state that the serial prepass wrote before the workers were woken; control writes take the engine's change lock, which
  the render owner holds for the whole period, so they cannot interleave with a period's reads (the test shows the
  writer blocked there).
- The 2 s bound detects a wait, not its length; a lock taken and released uncontended would not be seen by the
  held-mutex probe - it is seen by code review of the hit path, which is three lines.
