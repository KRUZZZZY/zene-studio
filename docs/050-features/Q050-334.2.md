# Q050-334.2 - Versioned public TypeScript session SDK

Unit: feature, size L, priority P2, area L17, stage 2 of 2 of Q050-334 (stage 1, the event protocol, is
`docs/050-features/Q050-334.1.md`). Branch `feat/050-Q050-334.2-oc`, base `050/m0-train-26` (`af010bc3cc`). Goal:
third-party TypeScript clients connect to an open Zene session, read and edit it through existing commands, and
consume the change-event protocol.

## What was built

The package `@zene-studio/session-sdk` **0.1.0** is in `tools/zene-session-sdk/`. It runs outside the DAW process,
and this unit changes no C++.

- **`ZeneClient`** (`src/client.ts`) opens the local control socket (`net.connect({path})`). On Windows that call
  takes a `\\.\pipe\` name. The client checks `control.version` (protocol 1). `call(cmd, args)` runs any registered
  command; `KnownCommands` types the common reads and edits (`src/protocol.ts`). Replies are matched by `id`, event
  lines (`event`, no `id`) are routed to their subscription, and a reply or event never blocks the other.
- **`Subscription`** (`src/subscription.ts`) offers `onEvent`, `onEnd`, an async iterator and `unsubscribe()`. It
  checks that `seq` rises by exactly one in one `session`, and a break ends it with reason `gap`. It ends with
  `unsubscribed`, `overflow` (carrying the `events_overflow` notice), `disconnected` or `gap`.
- **`ZeneClient.resync(read, {since})`** is the protocol's recovery: subscribe first, then reread. It reports
  `missed` (null when unknown or when the session changed).
- **`LiveSession`** (`src/live-session.ts`) is a self-recovering view. After an overflow it resyncs on the same
  connection. After a lost connection it reconnects with back-off until `stop()`. It fires
  `onStale`/`onSync`/`onChange`/`onError`.
- **Typed errors** (`src/errors.ts`): `ZeneCommandError` (`kind` from the closed set), `ZeneConnectionError`,
  `ZeneTimeoutError` and `ZeneProtocolError`, all of them `ZeneError` with a `code`.
- **Versioned package:** `package.json` version with `SDK_VERSION` (`src/version.ts`; the test checks they agree),
  `CHANGELOG.md`, and `exports` for the built `dist/` (JS + `.d.ts`, `npm run build`). A `zene-source` condition
  maps the package name to its TypeScript sources. `README.md` documents connection, read/edit calls,
  subscriptions, errors and resync. The pinned dev tools (`typescript` 5.9.3, `@types/node` 22) are in the
  committed `package-lock.json`. There are no runtime dependencies.
- **Example:** `examples/live-view.ts` imports the package by its published name.

## New commands

None. The SDK uses the existing registered commands, including stage 1's `events.subscribe`/`unsubscribe`/`get_state`,
so no snapshot changed.

## Format changes

None. Nothing is saved in a project.

## GUI

None. The brief puts a GUI panel out of scope, and the package is for external programs. Every edit it makes is an
existing registered command, the same one Zene's menus use. The manual's `#session-sdk` paragraph describes it.

## Known limits

- **Windows named pipe not run here.** The connection is the same `net.connect({path})` call, which takes
  `\\.\pipe\` names on Windows. The ctest is registered with the UNIX control suite only (`CONTROL_SUITE_AVAILABLE`),
  like `ControlProjectEvents`, because the harness launches over AF_UNIX. Stage 1's `ControlNamedPipeSmoke` covers
  the pipe's event delivery on hosted CI.
- **Toolchain on CI.** `ControlSessionSdk` needs Node >= 22.6, because it runs the TypeScript sources by type
  stripping; an older node reports Skipped (77), and the test is not registered without node. The typecheck needs
  `npm ci` in `tools/zene-session-sdk` (or `$ZENE_TSC`). A test must not install anything, so without it the
  typecheck reports Skipped (77) and does not pass.
- Not published to a registry; the brief makes publication out of scope.
- Changes that arrive before the first listener are held for it, up to 8192 (`MAX_HELD_EVENTS`, `MAX_HELD_CHANGES`). Past that, a subscription ends `overflow`, and a `LiveSession` with no `onChange` listener stops holding.
- Events after a resync can describe changes that the reread state already shows, because the read runs after the
  subscription starts. The README says to apply them idempotently.
- Thread safety: the SDK is single-threaded Node and does nothing on Zene's threads; the DAW side is stage 1's,
  unchanged.
- **The SDK's named-pipe path is CI-only.** `ControlSessionSdkPipeSmoke` is registered on Windows only (`WIN32`); this host ran the same assertions over the POSIX socket with `tests/session-sdk-pipe-smoke.py`, which proves the file's logic but not the Windows half. The Windows half runs only on hosted CI.
