# Q050-283.1 - Create and persist neutral arrangement tracks (stage 1 of 3)

Unit (L04, R-workflow-286, P2): SongEditor offered separate instrument, sample and
automation creation; a musician could not add a row before choosing what it carries.
Stage 1 adds a **neutral arrangement row** and keeps it through save/load. Stage 2
(assign an instrument) and stage 3 (audio input, switching roles without loss) are
separate units; nothing here has to be undone by them.

## What was built

- `include/Track.h` (`Track::Type::Neutral`): value 8, after `Folder`, before `Count`.
  Every earlier value keeps its persisted integer; only `Count` moves (in-process use only).
- `include/NeutralTrack.h`, `src/tracks/NeutralTrack.cpp`: the `NeutralTrack` class. It is one
  more row of the same flat track list, so its stable `trk-<n>` id, arrangement position, name,
  mute/solo, colour, height and folder membership are `Track`'s own and are persisted by
  `Track::saveTrack` (id/name at `src/core/Track.cpp` `saveTrack`). `play()` returns false, it owns
  no clips (`createClip()` is null, like `TrackFolder`) and no mixer channel. Its only own data is an
  empty `<neutraltrack/>` element.
- `src/core/Track.cpp` (`Track::create`): `case Type::Neutral`. Both the creation path and the
  project loader (`Track::create(element, tc)`) go through it, so a saved row reloads as a `NeutralTrack`.
- `include/NeutralTrackView.h`, `src/gui/tracks/NeutralTrackView.cpp`: the row's header (standard
  track header with a name button and an icon drawn at runtime - no theme file added).
- `src/core/ControlCommandsArrangement.cpp`: `track.add` accepts `type: "neutral"` (same command,
  same undo step, same reply with `track`, `index`, `type`).
- `src/gui/editors/SongEditor.cpp`: the "Add neutral track" toolbar action (`addNeutralTrackAction`)
  calls `ControlRegistry::invoke("track.add", {type: neutral})` - the same command an agent uses.
- Type name `"neutral"` in the five `trackTypeName` switches (`ControlCommandsAutomation`,
  `ControlCommandsTransport`, `ControlDeviceSupport`, `ControlEditSupport`,
  `ControlCommandsSessionRecordLand`), `LuaTrack::type()` and the DAWproject import name mapping, so
  every read reports it and nothing mislabels it as an instrument.
- `clip.add` refuses a neutral track (`refused`, before the undo checkpoint, like a folder), and the
  arranger's clip-paste skips a track that returns no clip (`TrackContentWidget.cpp`) instead of
  dereferencing null.

## Commands and reversibility

No new command. `track.add` gained `neutral` in its `type` enum: still **true_inverse** (the inverse is the
operation, `ControlReversibilityTableStructure.cpp`); `track.list`, `track.get_state` still `not_mutating`.
The snapshot was regenerated from a live instance (878 ids / 77 groups, unchanged; only `track.add`'s schema and
description differ); `doc-figures-gate.py` PASS. `ReversibilityContractTest` needed no histogram change.

## Format changes

- `<track type="8" ...><neutraltrack/></track>`. Everything else is the existing track attributes. A
  project that has no neutral row saves exactly the bytes it did before.
- A build older than this one has `Count == 8`, does not know type 8 and opens the project without the row.

## Known limits

- Stage 1 gives the row no role: it holds no clips, plays nothing and has no mixer channel. Instrument and
  audio-input roles, and switching between them, are stages 2 and 3.
- A neutral row has no `role` field in state readback yet; `type: "neutral"` is the marker.
- Pasting clips over a neutral/folder row skips them.
- No audio-thread code was added: `NeutralTrack::play` is a constant `false`; creation, saving and view
  work run on the control/GUI thread. TSan does not run on this box.
