# Q050-167 — Keep legacy macOS audio wakeups lock-free

Queue unit (P1, S, fix, area L15, member `R-platform-53`): on Apple deployment targets below
macOS 11 the audio worker wake was a process-global `std::mutex` plus
`std::condition_variable`, and its first call lazily allocated both with `new`. The mutex was
taken on the **render thread every period**. The wake is now a compare-and-wait on the
generation word itself, so the render-side post neither locks nor allocates.

## What changed

- `include/AudioWorkerWake.h`, `src/core/AudioWorkerWake.cpp` (new): the platform half of the
  wake. One selection macro (`LMMS_WORKER_WAKE_WAIT_ON_ADDRESS`) picks the primitive:
  - **Apple** — `__ulock_wait` / `__ulock_wake` on the generation word (the compare-and-wait
    trait libc++ itself uses under `std::atomic::wait`; available since macOS 10.12, below the
    10.13 floor). Not gated on the deployment target, so the macOS x86_64 CI job runs the code a
    legacy macOS user runs instead of a second path only they would exercise.
  - **Linux** — the same protocol on the same word with `FUTEX_WAIT_PRIVATE` /
    `FUTEX_WAKE_PRIVATE`. This is what makes the tests on the development box drive the shipping
    code rather than a stand-in: only the two-syscall shim differs.
  - **Windows / POSIX without those calls** — `std::atomic::wait` / `notify_all`, unchanged.
  - Static assertions require the wake word to be 32 bits and `is_always_lock_free`; an Apple
    build whose primitive is not the wait-on-address path fails to compile.
- `src/core/AudioEngineWorkerThread.cpp`: `notifyWorkers()` is `workerwake::notify(...)`,
  `waitForWake()` is `workerwake::wait(...)`. The `LMMS_WORKER_WAKE_CONDVAR` branch, its mutex
  and condition variable, and their lazy `new`s are deleted. `wakeWorkers()` (the increment
  plus post), the no-lost-wake guarantee, the deterministic-render handshake and the shutdown
  path are unchanged.
- `include/AudioEngineWorkerThread.h`: the wake comment now names the primitive, not the
  removed condition variable.
- `CMakeLists.txt`: states the supported macOS floor (`10.13`, Qt 5.15's own minimum
  deployment target) in the configure summary and warns if `MACOSX_DEPLOYMENT_TARGET` is set
  below it. The floor is documented in the user-facing README too.
- `README.md`, `data/manual/index.html`: the user-visible behaviour (Play wakes the worker pool
  without a lock or allocation) and the supported macOS floor.
- `tests/rt-safety-scope.txt`: declares `AudioEngineWorkerThread::notifyWorkers` and
  `workerwake::notify` as render-side paths for the whole-tree real-time sweep.

primitive; the failure is therefore behavioural, not a compile error.

## Commands and project format

No user-facing command, GUI action, control registration, undo step or reversibility entry was
added or changed: this unit changes how an existing internal wake is implemented, and Play and
`transport.play` keep using the same `AudioEngineWorkerThread::startAndWaitForJobs()` path they
already used. Project serialization is unchanged; no format migration or new persisted data is
involved.

## Realtime and portability notes

- The render-side post (`wakeWorkers` → `notifyWorkers` → `workerwake::notify`) does one relaxed
  counter increment (test builds only), one `RealtimeExemption`, and one wake syscall. It does not
  lock, allocate, free, wait or do I/O. The `RealtimeExemption` documents the syscall because
  RealtimeSanitizer reports every syscall; a wake with no waiter returns immediately.
- The wait side re-reads the generation before parking and after every return, so a wake that
  arrives first is never lost — the same guarantee the condition variable provided, without its
  mutex.
- Local TSan does not run on this box; the race reasoning is in the header and in this file rather
  than a sanitizer transcript.
- `__ulock_wait` / `__ulock_wake` are declared in the one Apple translation unit; they are the
  same declarations libc++'s `__threading_support` uses. The Apple path is guarded by
  `#if defined(__APPLE__)`; Linux includes remain inside the Linux guard; Windows keeps
  `std::atomic::wait`.

## Known limits

- The macOS x86_64 job was not run from this Linux worktree. What is proved here is the protocol
  and the two syscall shims' contract on Linux, plus a compile-time assertion that the Apple
  build must select the wait-on-address path; the Apple run is the hosted job's to confirm.
- The runtime mutex interposer is glibc-only. On a macOS runner the case prints a warning instead
  of a pass, and the source scan plus the primitive assertion carry the mutex half there — stated
  rather than hidden.
