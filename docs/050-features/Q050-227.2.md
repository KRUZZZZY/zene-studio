# Q050-227.2 - Pinned mixer strips (stage 2/2 of persistent mixer docks)

**Unit.** A channel strip can be pinned beside the scrolling channels, so it stays on screen while the channel
area scrolls. Pins are part of the mixer's persistent layout (the same `mixer_zones` layout that Q050-227.1 saves
with the window layout and the project), so they are saved with the project and come back when it reopens.
Stage 2 of cluster Q050-227; it builds on the zones of stage 1.

**Goal.** "Users can pin mixer strips so they stay visible while the channel area scrolls, read the pinned channel
IDs through `window.mixer_view`, and restore pins from the saved project layout."

**Design.**

- **Pins live in the layout.** `mixerzones::Layout` gains `pinned`, a list of `ch-<n>` ids in pin order. The master
  is never pinned. `MixerZoneState` holds it beside the dock and size data and emits `pinsChanged()`; the view
  re-lays itself when that signal fires.
- **Strip menu.** The channel strip menu has Pin Strip / Unpin Strip. A pinned strip is moved to a fixed area
  left of the scrolling channels; an unpinned strip returns to its place in mixer order.
- **Agent surface.** `window.mixer_view` takes `pin`, `unpin` and `pinned_channels` (see below) and reports the
  result as `pinned_channels`. The same handler serves the menu and agents.
- **Persistence.** The shell's `mixer_zones` snapshot key carries `pinned`, so the existing undoable layout step
  (`window.layout_project_save` / `window.layout_project_apply`) saves and restores pins with the rest of the
  layout. No second project section and no second format.
- **Realtime untouched.** Pins are GUI-thread widget state. Nothing is added to `updateFaders()`, the audio thread
  or any model notification path.

**Commands changed.**

| Command | Change |
| --- | --- |
| `window.mixer_view` args | `pinned_channels` (an array of `ch-<n>` ids; replaces the list in the order given, each id once), then `pin` (one `ch-<n>` id; appended), then `unpin` (one `ch-<n>` id; removed). A non-array `pinned_channels` is `InvalidArgs`. A pin or unpin of an unknown id is `NotFound`. A refused call changes nothing. |
| `window.mixer_view` result | `pinned_channels`: the pinned `ch-<n>` ids in pin order. |
| `window.mixer_zones` object | gains `pinned`: the same list, as the layout keeps it. |

**Format change.** `mixer_zones` gains `pinned`, an array of `ch-<n>` ids:
`{"zones": {...}, "sizes": {...}, "pinned": ["ch-3", ...]}`. Layouts saved before this feature lack the key, so
nothing is pinned when they open. The reader ignores unknown ids and never fails on a missing `pinned`.

**Known limits.**

- Pins live in the window layout, not the song undo stack. Undo of a pin change is the layout undo step, not a
  song-level undo entry.
- A pin of a channel that has since been deleted is not reported in `pinned_channels`.
- An unknown id given to `pin`, `unpin` or `pinned_channels` is refused as `NotFound`, and nothing changes.
- The master is never pinned: it has its own dock and is not in the pin list.

**Portability.** Qt5/Qt6-safe APIs only: `QStringList`, `QObject` signals and `QJsonObject`, with no version-specific
calls.

**Realtime.** GUI thread only. No engine code, audio thread or `updateFaders()` change. A pin change is a Qt
event on the GUI thread, and the layout is written through the existing layout save.
