# Q050-267.1 - Zene Rack plug-in module and state bridge, stage 1/3: VST3 Rack processor and documented chain loading (P2, feature, L10)

**Unit.** Build an installable VST3 Rack module that loads and processes one documented supported effect chain.
This stage ships the product bundle and its chain report; stage 2 (Q050-267.2) adds host-state recall, and stage 3
(Q050-267.3) adds the standalone-project state bridge. Nothing here has to be undone for either.

**Before.** The tree had two VST3 *host* modules (`plugins/Vst3Effect`, `plugins/Vst3Instrument`) that load other
vendors' plug-ins into Zene. No target shipped Zene itself as a VST3 effect, so another DAW could not load a Zene
Rack. Existing standalone effect chains serialise to project XML, but there was no bundle to receive them.

## What was built

| Piece | Where |
| --- | --- |
| `zenerack` product target: a VST3 bundle (`ZeneRack.vst3`) with the SDK's per-platform entry point and loader layout. It is not a `BUILD_PLUGIN` module and does not link `zene`. `install()` puts it under `<libdir>/vst3/ZeneRack.vst3` | `plugins/ZeneRack/CMakeLists.txt`, wired from `plugins/CMakeLists.txt` |
| The effect: one documented chain, fixed order, stereo in/out. Stage 1 `Amplifier` (linear gain), stage 2 `BassBooster` (the `FastBassBoost` recurrence, frequency 100 × sampleRate/44100, ratio 2.0), stage 3 `WaveShaper` (input drive then hard clip at ±1). Per-stage gains are the `RangeParameter`s `1 Amplifier Gain`, `2 BassBooster Gain`, `3 WaveShaper Drive` | `plugins/ZeneRack/ZeneRack.cpp` |
| Chain report (no Zene API needed): the ordered parameter names, a read-only `Chain` parameter whose string value is the descriptor, an `IUnitInfo` program list with the same one program, and the component state text | `plugins/ZeneRack/ZeneRack.cpp` |
| Real-time path: atomics for the three normalized values (static-asserted lock-free), two `double` filter states reset in `setActive`, direct buffer walk. No allocation, free, lock, wait, I/O or signal | `plugins/ZeneRack/ZeneRack.cpp` (`process`) |
| State text (report only in this stage): `ZENERACK-STATE 1`, `chain=...`, `gain=...`, `bass=...`, `drive=...`, written off the audio thread. Restoring a fresh instance from host state is stage 2 | `plugins/ZeneRack/ZeneRack.cpp` (`writeState`) |

The bundle is deliberately self-contained: it compiles the documented DSP stages itself and links only the pinned MIT
VST3 SDK's plug-in/bundle side. It does not call Zene's module loader and does not require `zene` to be running.

## New and changed commands

None. This stage is a plug-in loaded by another DAW; its controls are the VST3 parameter surface and its reports are
the VST3 parameter/program/state surfaces, not `ControlRegistry`. The control-surface bridge (`rack.*`) belongs to
stage 3, where it has a real command to expose.

## Realtime

`process()` is the only audio-thread function added. It reads three `std::atomic<float>` shadows with
`memory_order_relaxed` (the class static-asserts `std::atomic<float>::is_always_lock_free`), reads two `double`
filter states that `setActive(true)` resets, walks the host's buffers and writes every output frame. It does not
allocate, free, lock, wait, do I/O or emit a signal. The parameter queues are folded in with a fixed switch and a
`setNormalized` on the parameter objects is never called from `process`; the host-facing parameter objects are
updated only from `setParamNormalized`/`setState` (off the audio thread). There is no TSan run on this box (it does
not work here); the cross-thread values are the atomics described above, and the DSP state is owned by the plug-in
instance.

## Format

No project-file change. The new data is the plug-in's own VST3 component state text (`ZENERACK-STATE 1`), stored by
the hosting DAW, never inside a `.mmp`/`.mmpz`. Old projects load and render exactly as before because no Zene
serializer, model, engine or render path changed. The stage-3 bridge will define the standalone-project conversion;
stage 1 does not write project data.

## Known limits (stage 1)

- One fixed chain, in one fixed order. There is no rack editor, no reordering, no parallel/nested chains, no zones or
  macros in the plug-in.
- The chain is the Rack's own implementations of the three documented stages, not instances of Zene's plug-in modules
  (the bundle must not depend on Zene's executable or module loader). Values follow the built-in defaults documented
  above; the BassBooster frequency/ratio are fixed.
- Stereo in, stereo out, 32-bit float samples at any sample rate. Other bus layouts and 64-bit processing are refused.
- Stage 2 (host-state recall into a fresh instance) and stage 3 (standalone-project ↔ Rack state bridge) are later
  units. The state text written here is already self-contained, but this stage only asserts that it reports the chain.
- The bundle is only built when the pinned VST3 SDK is configured (`WANT_VST3`), the same condition as the existing
  VST3 host modules.
