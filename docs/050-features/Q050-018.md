# Q050-018 - Preserve missing-instrument data and report placeholders (P0, M)

Branch `feat/050-Q050-018-missing-instruments`, based on train 2's `190242990`.

## The unit

Goal: save and reopen projects with unavailable instruments without discarding the original plug-in XML, and tell
users which devices could not load.

The defect it fixes (measured, `build-3` control run): a project whose instrument module is absent loaded with a
`DummyInstrument`, and the next save wrote `<instrument name="dummy"><dummyinstrument/></instrument>` - the plug-in
identity and its whole state were gone. The same loss happened for the hosted formats: a VST3 / CLAP wrapper whose
plug-in binary is missing kept loading as an empty host and saved no state, and VeSTige kept only the path.

## What was built

- `include/MissingDevices.h`, `src/core/MissingDevices.cpp` - the `MissingDevice` record (kind, name, format, vendor,
  track, reason, identity), `describe()` (reads them from the original XML), `detachedCopy()`, `collect(Song*)` (live
  list: instrument tracks' instruments, track and mixer-channel effect chains) and `noticeText()`.
- `include/Instrument.h:219`, `include/Effect.h:114` - `virtual unavailableReason()` (empty = the real device).
  Overrides: `DummyInstrument` (module missing), `Vst3Instrument`, `ClapInstrument`, `VestigeInstrument`, `Vst3Effect`,
  `ClapEffect`, `VstEffect` (hosted binary missing). LV2: a missing URI throws in the constructor, so it falls to the
  dummy path.
- `src/tracks/InstrumentTrack.cpp` - `capturePlaceholder()` keeps a detached copy of the file's `<instrument>` element
  (also the old compat form, where the element is named after the module); `saveTrackSpecificSettings` writes it back
  verbatim while the instrument is a placeholder; `loadInstrument` drops it (the user chose a new instrument). The
  vendor, which is deliberately not in the plug-in key, is saved as an attribute beside the name for later opens.
- `src/core/EffectChain.cpp` - `DummyEffect` already re-emitted its XML (module missing); a hosted effect whose binary is
  missing now does the same through `Effect::preservedPluginData`. Effects share the path, so they are covered and
  reported with kind `effect`.
- `src/core/ControlCommandsProjectFiles.cpp` - `project.open` and `project.get_state` carry
  `missing_device_count` / `missing_devices`. A placeholder is not a load error (`loaded_with_errors` is unchanged).
- `src/core/Plugin.cpp` - while a project loads, the per-plug-in "Plugin not found" `QMessageBox` is not raised (it was
  modal and one per plug-in); the reason still goes to the log.
- `src/gui/MissingDevicesNotice.cpp`, `src/gui/MainWindow.cpp` - on `Song::projectLoaded` one non-modal
  `QMessageBox` lists every placeholder (name, format, vendor); skipped in an unattended run.

## Vendor, honestly

The sub-plug-in key holds the device's identity and is saved in projects; the maker is not part of it
(`PluginVendors.h`). So the vendor shown is, in order: the `vendor` attribute a build that knew it wrote on the element;
what this session's scan recorded for that VST3/CLAP class; "LMMS" for a native module; the host of an LV2 URI (an
inference, not a declared maker); else `unknown` (CLAP and VeSTige projects saved by an older build).

## New commands and reversibility

None. `project.open` / `project.get_state` gain result fields only; reversibility classes are unchanged
(`project.open` stays documented-not-reversible).

## Format changes

Additive only: an optional `vendor` attribute on `<instrument>` / `<effect>`. Older builds ignore it; old projects load
and render unchanged.

## Known limits

- The notice is shown by `MainWindow` on `projectLoaded`; there is no GUI-driven test of the main window itself, only of
  the box (the helper is the same function).
- Parallel rack chains and post-fader inserts are now collected and round-trip (round 2 below).
- VeSTige (`vst`) is not covered by a test: its module is not built in this tree, so the round-1 row was removed.
- The GUI notice test uses a mixer-channel-only project. A GUI `project.open` of a project that holds an instrument track,
  followed by a second open, crashed in `InstrumentTrackView::~InstrumentTrackView` (`model()` null: the view was deleted
  after its track). Measured with the round-2 test under gdb; not fixed here (pre-existing track-view teardown, outside
  this unit).
- `ControlHeadlessProjectOpen` first segfaulted at start-up here because the plug-in modules outside the target list were
  stale against the changed `Effect` / `Instrument` layout; after `make -C build/plugins` it passes. Rebuild all plug-ins
  with this change.
- A placeholder stays unavailable for the session: installing the plug-in needs a reopen (stated in the notice).
- The vendor of a CLAP/VeSTige device is `unknown` unless the file or the scan knows it.
