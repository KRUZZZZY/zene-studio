# Q050-111 Per-clip realtime effects

Branch `feat/050-Q050-111-oc` (cut from `050/m0-train-21`). An audio arrangement clip carries an ordered chain
of realtime effects of its own; it processes that clip alone, live and non-destructively, before the track sums
its clips.

## How it works

- **Model.** `SampleClip` owns one `EffectChain` (`SampleClip::clipEffects()`, include/SampleClip.h). It is built
  with the clip, empty and switched off, and lives as long as the clip. Edits go through the chain's own
  model-change guard (`EffectChain::appendEffect/removeEffect/moveUp/moveDown/loadSettings`), the same guard a
  track's chain uses, so an edit never lands during a render period.
- **Processing.** `SampleTrack::play` gives each live play handle its clip (`SamplePlayHandle::setClipEffects`);
  `SamplePlayHandle::play` calls `SampleClip::processClipEffects` on the handle's own buffer after the fades, gain
  and take gating. `AudioBusHandle` sums the track's handles only after that, and runs the track's chain on the sum,
  so a clip effect never touches a sibling clip, overlapping or not. `processClipEffects` (src/core/SampleClipEffects.cpp)
  returns at once for a clip without effects; otherwise it wraps the buffer in a stack `AudioBus` and calls
  `EffectChain::processAudioBuffer` - no allocation, no lock, no wait, no I/O, no signal. A non-blocking atomic
  flag makes a second handle of the same clip in the same period (the live schedule never makes one) play dry
  rather than share the chain's state across two workers.
- **Agent surface.** `resolveControlTarget` (src/core/ControlDeviceSupport.cpp) accepts `clip-<n>` for an audio clip
  and resolves its chain, so every device command takes it: `plugin.load` (add, optional `position`), `plugin.move`
  (reorder), `plugin.bypass`, `plugin.param_set` / `plugin.param_get`, `plugin.unload`, and `dsp.get_state` reads it.
  A MIDI/pattern clip is a typed `refused`. The undo steps find the chain again by the clip's persistent id
  (`chainArgs` in src/core/ControlStructuralSupport.cpp), so they survive the clip's own undo rebuild.
- **GUI.** The audio clip's context menu has **Clip effects...** (with the count once it has any), opening
  `ClipEffectsDialog` (src/gui/ClipEffectsDialog.cpp): the chain in order with On/Bypassed and every parameter's
  value, read through `dsp.get_state`; Add effect... / Move up / Move down / Bypass (Turn on) / Remove buttons and a
  double-clicked parameter row each run the registered command above with the clip as the target - the same command
  an agent sends. The clip view paints an **FX** badge (with the count past one) while the clip carries effects.

## Commands

No new command ids (871 ids / 76 groups unchanged). Changed metadata: the descriptions of `plugin.load`,
`plugin.unload` and `dsp.get_state` name the `clip-<n>` target; the snapshot was regenerated from a live instance.
Reversibility classes are those of the existing rows and hold for a clip target unchanged: `plugin.load` snapshot
(the recorded step unloads it), `plugin.unload` true_inverse (structural re-instantiation), `plugin.bypass` and
`plugin.param_set` true_inverse (model checkpoint), `plugin.move` true_inverse, `dsp.get_state` not_mutating.

## Format

Additive: a sample clip with at least one effect writes an `<fxchain>` child (the same element and content a
track's chain writes: `enabled`, `numofeffects`, each `<effect>` with its plug-in key and settings, including each
device's on/off). A clip without effects writes nothing, so every existing project serialises byte for byte as
before; a clip element without the child loads with no effects (reset on absence).

## Known limits

- Audio clips only: MIDI, pattern, automation and launcher-cell clips have no clip effects (typed refusal).
- An effect's tail (a reverb or delay) stops when the clip's play handle ends; it is not rendered past the clip.
- A clip effect's latency is not compensated (PDC covers track and channel chains only).
- `clip.consolidate` renders the clips' source audio without their clip effects and the consolidated clip has none;
  one undo brings the originals back with their effects. `clip.process` changes the source; the clip effects stay
  and run on the result.
- Automation of a clip effect's parameters is whatever the existing automation path gives a model (not tested here).
- Local TSan does not run on this box. The race argument: the chain pointer is set at clip construction and never
  reset; every edit to the effect list or the graph takes the engine's model-change guard (as a track chain's edits
  do), which excludes render periods; a clip's handle is removed under the same guard before the clip is destroyed
  (`SampleClip::~SampleClip` -> `SampleTrack::updateClips`); two handles of one clip in one period are kept off the
  shared chain state by the non-blocking busy flag.
