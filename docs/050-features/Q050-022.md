# Q050-022 - Show automation lanes as track children

Unit (L06, R-workflow-197, P0): expand an arrangement track to see and edit its
automation lanes directly beneath it. Before this change `automation.lane_add`
already placed an automation track right under the owner and set
`AutomationTrack::followsTrack()`, and the arranger drew it as one more peer row
- never indented, never hidden with its owner, and `automation.get_state` did not
report the relation. The gap is exactly what R-workflow-197 names: lanes "do not
fold with or nest inside the owning track".

## What was built

- `include/Track.h:346` / `src/core/Track.cpp:592,874`: a per-owner `autolanes`
  fold flag (`Track::automationLanesCollapsed()`/`setAutomationLanesCollapsed()`),
  saved on the owner's own `<track>` element only when folded, reset on absence
  (`TRACK_RESTORE_SCHEMA`, `src/core/Track.cpp:89`) - so a project that never
  folded a track re-saves its old bytes.
- `include/Track.h:358,576` (signal `automationLanesCollapsedChanged`): the fold
  flag is OBSERVABLE. `Track::setAutomationLanesCollapsed` emits it on a real
  change, and `Track::loadTrack` (`src/core/Track.cpp:878`) emits it when a
  checkpoint restore reads a different `autolanes` value (an undo/redo of the
  command lands there).
- `src/gui/editors/TrackContainerView.cpp:213`: `addTrackView` connects every
  track's `automationLanesCollapsedChanged` to `realignTracks` (queued), so a fold
  from the agent surface, from the menu, or from an undo/redo re-lays the rows
  with no `realignTracks()` call by the caller. The menu/button handlers no longer
  realign by hand.
- `include/Track.h:366` / `src/core/Track.cpp:419`: `Track::automationLaneChildren()`
  and `hasAutomationLaneChildren()` - the lanes whose `followsTrack()` is this
  track's stable id, derived in container order, never stored twice. The walk
  takes the container's read lock (`m_tracksMutex`), which excludes the two
  writers that also take it (`TrackContainer::addTrack`/`removeTrack`) but NOT
  `TrackContainer::moveTrack`/`clearAllTracks`, which mutate `m_tracks` without
  it; the real barrier is that every caller and mutator is GUI/control-thread
  code (commands are marshalled to the UI thread), and nothing on the audio
  thread calls it, and by the realtime rule nothing may, because the lock can
  wait.
- `src/gui/editors/TrackContainerView.cpp:331` (`hiddenUnderOwner`),
  `:345` (`groupedWithLaneChildren`), `:370` (`realignTracks`): a lane row is
  hidden when its owner is hidden (`Track::isVisible`) or folded, or sits under a
  collapsed folder; and the rows are ordered so an owner is immediately followed
  by its lane rows however the flat track list was reordered (`realignTracks`
  is at `:409`). A lane met BEFORE
  its owner is deferred until the owner is emitted, so a downward move of the
  owner (which leaves the lane earlier in the flat list) still draws the lane
  beneath it; a lane whose owner is not in the container keeps its own row, and
  unrelated tracks keep their relative order.
- `src/gui/tracks/TrackView.cpp:174` (`updateFolderIndent`): a lane's settings
  column is indented one level under its owner (inheriting the owner's own folder
  depth) and its accessible description names the owner.
- `src/gui/tracks/TrackOperationsWidget.cpp:159,313,397`: the owner's row gains a
  fold button (`btn-automation-lanes`, visible only when the track owns a lane)
  and a context-menu action, both through the registered
  `automation.lanes_set_collapsed`; the GUI delete path removes the child lanes
  with the owner as one undo step.
- `src/core/ControlCommandsAutomationLanes.cpp:242,318`:
  `automation.lanes_set_collapsed` - folds/unfolds a track's child lanes as one
  undoable Track checkpoint.
- `src/core/ControlCommandsAutomation.cpp:105-114`: `automation.get_state` now
  reports each lane's owner (`follows`), each track's `automation_lane_count` and
  `lanes_collapsed`, from the fields the arranger renders.
- `src/core/ControlStructuralSupport.cpp:310` (`journalTrackRemovalWithLanes`),
  `src/core/ControlCommandsArrangement.cpp:102` (`trackRemovalTransaction`) and
  `:338`: deleting an owner removes its child lanes too, captured as ONE
  structural step. The transaction text names the owner AND its child lanes, and
  the all-or-nothing failure case (a member over the cap or unindexable) is
  described, with no inverse recorded.

## New commands and reversibility

- `automation.lanes_set_collapsed` (group `automation`, args `track`, `collapsed`):
  fold/unfold a track's child automation lanes. Reversibility: **TrueInverse** -
  a live `Track` checkpoint; the owner's own `<track>` element carries `autolanes`
  and `Track::loadTrack` resets it on absence. A16 row in
  `src/core/ControlReversibilityTableArranger.cpp:131`.
- `automation.get_state` gained read-only fields (`follows`,
  `automation_lane_count`, `lanes_collapsed`); still `NotMutating`.

## Format changes

- New per-owner attribute `autolanes` on `<track>` (only written when folded;
  reset on absence). Old projects load and render exactly as before (default:
  lanes shown). New data round-trips (proved by the save/load test).
- No change to the lane's own serialisation (`follows` already existed, ED-181).

## Known limits

- The arranger ORDER is a projection: an owner's lane rows are drawn directly
  beneath it in `realignTracks` (derived from `followsTrack`), while the flat
  container order a `track.list`/save round-trip sees is unchanged. A `track.move`
  therefore moves the owner's row and the lane is regrouped under it visually,
  without rewriting the flat list.
- Folding is a view flag with no audio meaning (like `visible`): a folded lane
  still plays.
- Moving the owner's clips carries its lane's points only when
  `arrangement.modes` `automation_follows_clips` is on (the pre-existing ED-190
  behaviour, unchanged).
- TSan does not run on this box; the new code is control/GUI-thread only
  (`automationLaneChildren` walks the container's track list under its read
  lock `m_tracksMutex` - the same lock `addTrack`/`removeTrack` take; `moveTrack`
  and `clearAllTracks` do NOT take it, so the lock is not a complete barrier and
  the serialization that makes the walk safe is the GUI/control thread itself;
  callers never hold the lock already, and the audio thread calls none of it) and
  adds nothing to the audio thread.
- A point inside a lane is edited on the lane's own editing surface (the
  automation editor the child lane's clip opens with a double-click); the
  arranger's clip view itself has never edited points, before or after this unit.
- `anUncapturableLaneRefusesTheInverseHonestly` triggers the all-or-nothing
  capture failure with a synthetic lane over the 64 KB cap, because no ordinary
  project reaches that bound; the production path is the same one it exercises.
- The fold signal is queued, so a caller that changes the flag and inspects the
  rows in the same call still needs an event-loop turn; every product path
  (button, menu, command, undo) returns to the loop before the user sees it.
