# Q050-074.1 - Track synthesis CPU and overload history (stage 1 of 2 of Q050-074)

Unit: P1, L (split), feature, area L15. Goal: musicians and agents can identify expensive instrument
tracks and locate engine deadline misses in song time (B-WF-104, R-performance-71/48/78).

Stage 2 (backend xruns, negotiated device rates, period/buffer frames and device latency, unavailable
device readings) is NOT in this unit; nothing here would have to be undone for it: late periods are
named the engine's deadline misses everywhere (not xruns), so a backend xrun counter can sit beside them.

## What was built

- `include/RenderDiagnostics.h`, `src/core/RenderDiagnostics.cpp` (new):
  - `SynthesisLoad` - one per instrument track (`InstrumentTrack::synthesisLoad()`). Its `Probe` times a
    scope with two steady-clock reads and adds the nanoseconds with one relaxed `fetch_add` (render
    workers run play handles concurrently). `fold(period, periodSeconds)` runs once per period on the
    render thread after STAGE 1 and folds the period's time into a smoothed percent (the same 0.1 weight
    as `DspLoadProbe`); a track without a handle in some periods decays on its next fold, and
    `percent(currentPeriod)` decays it for a reader in between, so a stopped track falls to zero rather
    than holding its last reading.
  - `LatePeriodLog` - a fixed ring of the newest 64 late periods plus a running count; single writer
    (the render thread), each slot under its own sequence number, so an off-thread reader never takes
    half a mark. A mark holds the song tick its period started at, whether the arrangement was rolling,
    how long the render took and how long the period lasts (microseconds).
- `src/core/NotePlayHandle.cpp` / `src/core/InstrumentPlayHandle.cpp`: each play handle times its own
  rendering into its track's `SynthesisLoad` (`PlayHandle::synthesisLoad()`, a new virtual, nullptr for
  sample/preview/monitor handles). The instrument handle times only the instrument's own stream, after
  the notes it waits for (which time themselves), so nothing counts twice.
- `src/core/AudioEngine.cpp` `renderNextPeriod()`: numbers the period (`renderedPeriods()`), calls
  `foldSynthesisLoads()` right after `renderStageInstruments()` (a pass over the engine's own play-handle
  list), and after `m_profiler.finishPeriod()` calls `noteLatePeriod()`: when the period's measured render
  time (`AudioEngineProfiler::lastPeriodMicros()`, the figure engine_percent is made of) exceeds the
  period's duration, the mark is recorded at `m_periodStartTick`, taken in `renderStageNoteSetup()` before
  the song advances. An export (offline render) records nothing.
- `src/core/ControlCommandsTrackLooks.cpp`:
  - `mixer.cpu_load` gains `tracks` (per instrument track - arrangement and pattern editor: `track` id,
    `name`, `instrument`, `synthesis_percent`), `synthesis_total_percent`, and `late_periods`
    (`count`, `held` = 64, `marks` oldest first: `serial`, `tick`, `position` "bar.beat", `playing`,
    `took_us`, `period_us`, `percent`). Existing keys (`channels`, `total_percent`, `engine_percent`) are
    unchanged in meaning.
  - `track.overview` gains `synthesis_cpu_percent` on instrument tracks only (a sample, pattern or
    automation track synthesises nothing and carries no figure); `cpu_percent` stays the channel's.
- GUI: `include/CpuDiagnosticsDialog.h`, `src/gui/shell/CpuDiagnosticsDialog.cpp` (new). The header's
  **CPU** readout (`TransportReadouts`) gets a right-click action **CPU diagnostics...**
  (`controlCommand` = `mixer.cpu_load`), opening a window with a summary line (engine / instruments /
  mixer / late-period count), the instrument synthesis table, and the late-period table (newest first,
  bar.beat, took, period, load, playing/stopped). Every value comes from invoking `mixer.cpu_load` through
  `ControlRegistry`, twice a second while shown, so the window and the agent read the same state.
- Manual: `data/manual/index.html` (The window > Header) describes the window, both commands' new fields,
  and that a late period is not a device xrun.

## Commands

None added. `mixer.cpu_load` and `track.overview` keep their empty argument schemas, `mutating: false`
and their `not_mutating` reversibility rows; only their descriptions and reply fields grew (snapshot
regenerated live: 871 ids / 76 groups, unchanged).

## Format changes

None. The readings are runtime telemetry: nothing is serialised, so old projects load and render exactly
as before and there is nothing to round-trip.

## Known limits

- Synthesis is CPU time: play handles of different tracks (and notes of one track) render on several
  workers at once, so a track's or the total's figure can pass 100 on a multi-core machine.
- The late-period threshold is the engine's own render time against the period length. A period can be
  late without the device dropping audio (its buffer absorbs it) and the device can xrun for its own
  reasons; backend xruns are stage 2 (Q050-074.2).
- Pattern-editor and MIDI-clip playback mark `playing: false`; the tick is the arrangement position.
- The fold reads its period count once per read and the smoothed value separately, so a read racing a
  fold can be one period stale (a meter, not an accounting figure). TSan does not run on this box; every
  shared field is a std::atomic and the ring uses per-slot sequence numbers (the reasoning, not a run).
- A track whose instrument plays through no play handle (none in-tree) would show 0.
