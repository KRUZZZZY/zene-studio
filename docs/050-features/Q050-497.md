# Q050-497 Earcons: monitoring tones for edits, refusals, recording and loop wraps

Starting state (verified): the editor had no audible feedback of its own. A refused command, a recorded take starting or
stopping, and a song loop wrap were announced only in speech or not at all; a blind user working with monitoring on had
to listen to the transport to know whether an edit applied. Nothing in the engine mixed an editor-owned signal into the
device output, and nothing could do so without disturbing the render or a recorded take.

## Built
- **`lmms::earcons`** (`include/Earcons.h`, `src/core/Earcons.cpp`): a fixed set of short tones, one per event
  (`SelectionBoundary`, `EditApplied`, `Refused`, `RecordStart`, `RecordStop`, `LoopWrap`), grouped into five categories
  (`selection`, `edit`, `refused`, `record`, `loop`). `Category categoryOf(Sound)`, `categoryNames()`,
  `setEnabled` / `enabled`, `setLevel` / `level`, `prepare(sample_rate_t)`, `play(Sound)`, `beginBuffer()`,
  `nextSample()`.
- **Playback path**: `AudioEngine::renderNextBuffer` (`include/AudioEngine.h`) calls `earcons::beginBuffer()` and
  `earcons::nextSample()` and adds the result to the device output channels. `renderNextPeriod` (which feeds export and
  the recorder taps) never calls them, so an earcon is monitored, never rendered or recorded. The regression
  `EarconsRenderTest::theDeviceOutputCarriesTheEarcon` measures the actual device-output buffer.
- **Synthesis**: `earcons::prepare()` fills one of two preallocated banks, then publishes it with an atomic active-bank
  index. It runs on the control thread at `AudioEngine.cpp:807/1414/1443`, only while processing is stopped. The buffer
  length is clamped to 192 kHz (`kMaxFrames`) so no index can overrun even above that rate.
- **Hooks**: `ControlRegistry::dispatch` queues `EditApplied` after any successful mutating command, regardless of
  dispatch route (`NoteEditor::run`, automation point command, form, palette or socket); the unaddressable in-place
  automation edit also queues it directly (`src/gui/editors/AutomationPointEdit.cpp:83`). A refused transition and
  record start/stop queue their tones from `src/gui/AccessibleAnnouncements.cpp:199-201`; an automation selection at
  the first/last point queues `SelectionBoundary`; a song loop wrap queues `LoopWrap` (`src/core/Song.cpp:707`, on the
  audio thread with only an atomic counter update before `earcons::play`).

## New command `view.earcons`
- Args: `category` (enum `selection` | `edit` | `refused` | `record` | `loop`, required), `enabled` (bool), `level`
  (number, 0..1). At least one of `enabled` / `level` must be given; an unknown category, a missing category, a
  non-boolean `enabled`, or a level that is non-finite or outside 0..1 is `InvalidArgs` and changes nothing.
- Result: the command's `category`, the `enabled` / `level` now in force and a `previous` object with the values it
  replaced.
- Reversibility: `TrueInverse` (`src/core/ControlReversibilityTableW3Custom.cpp:136`), reversibility flag `true` - one
  action checkpoint, one `control.undo` step, which writes the previous `ui/earcons` object back and re-applies it.
- Settings live in the UI config (`gui::uistore` `earcons`), never in the project. `uistore::applyStoredEarcons`
  (`src/gui/UiConfigStore.cpp:99-106`) re-applies them at startup; an out-of-range stored level is ignored.
- GUI: **View > Earcons** (`src/gui/MenuBarExtras.cpp`, `addEarconsMenu`), one submenu per category with a checkable
  *Enabled* entry and checkable 25 / 50 / 75 / 100 % level entries. Each entry runs the registered `view.earcons`
  through the ControlRegistry - the command an agent calls on the socket / MCP - so the menu and the agent path are the
  same command, one journal checkpoint, one undo step. The menus re-read the stored state on `aboutToShow`, so an edit
  made over the socket or undone is reflected when they open.

No project-format change: the settings are UI config, so old projects load and render exactly as before. Rendering
identity is shown by `renderOutputIsIdenticalWithEarconsOn`. Every category is off by default and every category has its
own level, so a user who turns nothing on hears nothing.

## Known limits
- The device-output test above proves the mix with a runtime RED; tests that depend on the new earcon API also cannot
  compile if the new header is removed.
- The tones are fixed: frequency, length and shape are compiled in; only the per-category on/off and level are settable.
  The GUI offers four level steps (25/50/75/100 %); the socket accepts any value in 0..1.
- Overlapping sounds of the same category all play (up to one voice per sound); a rapid burst of the same sound retriggers
  rather than mixing a second copy.
- The settings are per user, not per project: two projects share them, by design (they are UI config `ui/earcons`).
- The audio-thread safety argument is a design argument plus the allocation probe in `EarconsTest`. TSan is not runnable on
  this box, so the single-consumer claim is not machine-checked here.
- No Qt 5.15, Windows/MSVC, macOS 10.15 or clang windows-arm64 build was available on this Linux host; the changed code
  was inspected for those APIs and platform constraints.
