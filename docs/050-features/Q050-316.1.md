# Q050-316.1 — Filter local browser results by tempo and key

Unit: in the Search view a musician narrows the library by a **tempo range** and a **key**
beside Kind, Where to look and Category; the same filter answers the walked search
(`browser.query`), the indexed search (`browser.index_query`) and a saved collection, and
both searches return **the same files** for the same facets. A file whose tempo or key is
unknown never matches an active tempo or key filter. Everything is local and offline.
(0.5.0 L11, stage 1/2 of Q050-316; the optional asset pack is stage 2.)

## How the two searches are kept equal

There is ONE measurement: the library index's import detection
(`BrowserFeatures::analyse`, `ImportDetectionDsp.h`), stored per file as `bpm` and
`keyPitchClass`. Both searches read that same record and apply the same predicate,
`browserItemMatchesFilters()`:

- `browser.query` copies the measured table once for a filtered walk and attaches each
  candidate's record by canonical path; an item it did not measure stays unmeasured.
- `browser.index_query` walks the index's own entries, so each item carries the record it
  was filtered on.

A file with no record, and a record whose detector found nothing (`bpm == 0`,
`keyPitchClass == -1`), do not match an active range or key in either engine. That is the
only rule that can make the two answers equal, and it is why "unknown" is reported
separately from "0 BPM": the wire form has `tempo_known` for exactly that distinction.

## Format changes

- **No project-format change.** The measurement lives in the library index (a config
  cache), the filters are query arguments, and a collection is the browser's own store.
- `browser-index.json` is unchanged: the `f` record it already carried for `browser.similar`
  (`dur`/`db`/`cent`/`zcr`/`bpm`/`key`) is the measurement this unit filters on. An index
  built with `features:false` has no `f` records; it loads exactly as before and simply
  matches no active tempo or key facet.
- `browser-collections.json` entries may now carry `tempo_min`, `tempo_max`, `key` inside
  `query`; an older collection without them runs as "any tempo, any key".

## Known limits

- The key is a **pitch class** only (0 = C .. 11 = B): the measurement stores no octave and
  no mode, so "C" is the same filter as "C#3"-less "C", and a major/minor distinction is out
  of scope. A name carrying an octave (`C#3`) is refused rather than reinterpreted.
- The measurement is the library index's: a file the index has not measured (no
  `browser.reindex` with features, or past its `MaxAnalysed` budget) carries no tempo or key
  and so matches no active facet. The filter never measures on the fly — a search is a read.
- The GUI offers whole-BPM bounds (0-400); an agent may send a fractional `tempo_min` /
  `tempo_max`.
- A searched range whose minimum is above its maximum is refused (typed `invalid_args`)
  rather than silently matching nothing.
- As with the category facet, the filter is library/query state, not project state: it does
  not travel inside a project file. A saved collection does keep it.
