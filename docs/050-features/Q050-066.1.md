# Q050-066.1 - Drum-rack pad workflow, stage 1/4: sampler-side pad state and commands (P1, feature, L10)

**Unit.** Expose sample-backed pad creation and complete state read-back on the sampler side, using a shared state
contract suitable for later transfer. Members: B-MX-111, R-instruments-55, R-instruments-66, R-instruments-73,
R-instruments-77. Stages 2-4 (per-pad chain editing, pad links and one-shot slots, the launcher transfer) are later units.

**What was there (base `5c1c6715d`).** `track.drum_rack` built a folder of sampler tracks (AudioFileProcessor), each into
a channel of its own sending to a bus channel, as one undo step. It answered ids only; nothing read a rack back, added a
pad to one or edited a pad. Building it surfaced three defects in that command, fixed here because the new commands
build pads the same way:

| Defect on the base | Cause | Fix |
| --- | --- | --- |
| The first pad played straight into the bus, not its own channel | the pad's track was made before its channel, and a track's channel model takes its range when it is made, so the new channel's index was clamped to the bus (headless; the mixer view widens the range only when it exists) | the channel is made first (`buildPad`, `src/core/ControlCommandsDrumRack.cpp`) |
| A pad's given `name` was replaced by the file's name | AudioFileProcessor renames a track after the first file it loads, and the name was set before the file | the file is loaded, then the name set |
| A step recorded after the rack (a pad added to it) could not be redone after the rack's undo and redo | the rebuild wrote models with the journal on (its own steps emptied the redo stack), and it made new track/channel ids | the build runs with the journal muted, and a redo gives every track and channel back its first id (`Track::setId` / `MixerChannel::setId`) |

## What was built

| Piece | Where |
| --- | --- |
| Shared pad-state contract `DrumPadState` (+ `DrumPadPlayback`): `track`, `name`, `sample` (absolute; empty when embedded), `key` (trigger key = the base note: the note that plays the sample at its own pitch), `channel` (the pad's chain), `sends_to` (the bus), `playback {amp, start, end, loop_start, loop, reversed, stutter, interpolation, attack (ms), release (ms), voice_limit}` - every setting the sampler saves except the sample data itself. Every field is read from the track, its sampler (through the sampler's own `saveState`, the serialisation the project file uses) and its channel - nothing is stored twice | `include/DrumPadState.h`, `src/core/DrumPadState.cpp` |
| `track.drum_rack_get_state {track: folder}` - the folder, its name, the bus (when every pad sends to one) and the pads | `src/core/ControlCommandsDrumRack.cpp` |
| `track.drum_rack_pad_add {track: folder, sample, name?, key?}` - a sampler track in the folder, a channel of its own sending to the rack's bus; key defaults to the next after 36 | same |
| `track.drum_rack_pad_set {track: pad, name?, key?, sample?}` - one Track checkpoint covers all three | same |
| GUI: the folder's track menu, Folder > Drum Rack Pads..., opens `DrumRackPanel`: a row per pad (name field, trigger-key box, sample, Sample...) and Add Pad.... Every control runs the commands above and every redraw reads `track.drum_rack_get_state` | `include/DrumRackPanel.h`, `src/gui/DrumRackPanel.cpp`, `src/gui/TrackFolderMenu.cpp` |

## New commands and reversibility

| Command | Class | Mechanism |
| --- | --- | --- |
| `track.drum_rack_get_state` | `not_mutating` | reads only |
| `track.drum_rack_pad_add` | `true_inverse` | action checkpoint: undo removes the pad's track and channel; redo builds it again under the same ids |
| `track.drum_rack_pad_set` | `true_inverse` | ProjectJournal Track checkpoint: name, base note and the sampler (sample and settings) |

## Format changes

None. A pad is still an instrument track with a sampler in a folder, a mixer channel and a send - all data the project
format already carried. A rack saved before this unit reads back through `track.drum_rack_get_state` unchanged.
`ControlDrumRackPads` checks that the saved project carries no XML element the old-style project lacked (opening this
build's file in the base build was not run separately).

## Realtime

All new code runs on the UI/control thread: the read-back serialises the sampler's settings there, the edits are the
same `Instrument::loadFile` / model writes the sampler's own view and `plugin.open_file` make, and the journal mute is
UI-thread state. Nothing new runs on the audio thread. (TSan does not run on this box; this is by reading.)

## Known limits

- The trigger key is the pad's base note. A pad still plays any note its own clips hold (pitched relative to the key);
  routing one MIDI clip or controller across pads by key is not part of this stage.
- Renaming a pad does not rename its mixer channel.
- There is no pad-remove command; `track.remove` removes a pad's track (its channel stays).
- A rack is any folder: `track.drum_rack_get_state` lists the folder's sampler children as pads (other children are left
  out), and reports `bus` only when every pad sends to the same channel. No rack marker is saved (no format change).
- The panel's Sample... and Add Pad... use a file dialog; the GUI test answers it through `DrumRackPanel::setSampleChooser`.
