# Q050-002 - Move recorder setup off the audio thread

Unit: P0, size M, area L03 (recording, takes, comping, inputs), type fix.
Branch `feat/050-Q050-002-oc`, base `de5a85a96` (train 5, `050/m0-train-5`).

Goal: starting an armed recording does not allocate memory or create its drain thread from the audio
render callback.

## Result: already implemented on train 5; verified and now pinned by a regression

This queue unit was authored against the pre-train-2 tree. The behaviour it asks for is the fix that
the merged lane `alloc-probe-fix` / `docs/m0-blocker-fixes-2026-10-08` (clusters 3508/4411/5308)
already landed, and `plans/P0-RECONCILE-2026-10-09.md` records it as **DONE**. On train 5 the
recorder's accumulator and its drain thread are built by `SampleClip::prepareRecordTake()` on the
main thread (`src/core/SampleClip.cpp:183`), and `SampleTrack::play()` only *claims* the prepared
take (`src/tracks/SampleTrack.cpp:268`) - no `new SampleRecordHandle` and no `std::thread` on the
render path. This lane did not re-implement that product code; it verified the exact acceptance on
train 5 and added the recorder-start regression the second criterion asks for.

Where the acceptance lives now:

- `SampleRecordHandle::SampleRecordHandle` (`src/core/SampleRecordHandle.cpp:95`) builds the
  `SampleRecordAccumulator` (`include/SampleRecordAccumulator.h:174`, which allocates the ring and
  starts `m_drainThread`). It is called only from `SampleClip::prepareRecordTake()`
  (`src/core/SampleClip.cpp:202`), on the main thread.
- `SampleClip::claimRecordHandle()` (`src/core/SampleClip.cpp:174`) is the audio-thread side: it
  moves the two prepared slots and marks the take claimed, and allocates nothing.
- The stale R2.2 comment in `SampleRecordHandle.cpp` that claimed the constructor runs on the audio
  thread was corrected to say the main thread (comment only; no code change).

## What this lane changed

- `tests/src/core/RecordingRealtimeTest.cpp:421`
  `recorderStartIsPreparedBeforeTheCallbackPath()`: arms a clip and asserts both prepared takes
  (the accumulator and its drain thread, `recordTakesReady() == 2`) **before** `playAndRecord()`
  starts the transport, so the setup provably happens before playback (the r1 review's rework
  point); the probe then runs the callback entry point `Song::processNextBuffer()` eight times
  inside a `RealtimeScope` with `AllocationProbe.h` armed - the first probed period is the one
  that starts the pass (the claim) - and asserts **zero allocations**, and finally drives real
  periods and asserts the take is non-empty. This is the "recorder-start regression" of
  acceptance criterion 2.
- `src/core/SampleRecordHandle.cpp:105`: the R2.2 comment no longer says the constructor runs on the
  audio thread (it has run on the main thread since cluster 5308).
- `tests/upstream-modifications.txt`: the reason for the comment-only change.

No new files, no new commands, no format change.
