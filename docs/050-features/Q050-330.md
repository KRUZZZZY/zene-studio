# Q050-330 - Add Windows ASIO device selection

Status: **BLOCKED** (no code on this branch; the unit goes back to the queue).

## Why
- Every acceptance criterion needs Windows: "Windows CI builds the chosen low-latency backend and enumerates its
  drivers before port setup", "a device-selection test starts and stops an ASIO or WASAPI device and reports its ports
  and latency". This lane runs on Linux only; it cannot build the MSVC configuration, cannot run a WASAPI or ASIO
  device, and may not push to hosted CI (the lane brief and AGENTS.md rule 11). A backend written blind could not be
  shown to compile, start, stop or report latency, and the review rule is a test that fails without the change and
  passes with it.
- ASIO itself is a licensing decision first: the SDK is GPLv3 and must not be bundled
  (`research/plugin-hosting/VST3-LICENSING.md`), so the realistic path is WASAPI (through PortAudio's WASAPI host API or
  a native backend), which still needs a Windows build and a device to prove.

## What a lane with a Windows host needs to do
- Build PortAudio with WASAPI in the `msvc-x64` job (or add a native `AudioWasapi` device), expose its devices before
  port setup through `audio.device_list`/a new not_mutating driver list, select one for the next start through the
  existing `audio.device_set` (true_inverse), and prove start/stop, ports and latency in a Windows-only QtTest.
- Write the Windows audio setup guide (supported choices, the Dummy fallback and its failure messages).
