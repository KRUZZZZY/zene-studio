# Q050-010 - Move long-running jobs off the interface thread

Branch `feat/050-Q050-010-oc`, cut from `050/m0-train-24` (`2a7fd9f9c`). The earlier attempts (`feat/050-Q050-010-oc-pre-v2`,
`feat/050-Q050-010-jobs-off-gui`) sit on older trains; their peak and stem ideas were re-implemented here, their plug-in
worker-plus-wait was not.

## What was built

| Job | Before | Now |
|---|---|---|
| Plug-in scan | `plugin.scan_start` (Q050-090) ran every `dlopen` on the UI thread | each library's load runs on a pool worker that gets a path only; a queued report names its run, so a stale one is dropped (`src/core/PluginFactoryBackgroundScan.cpp`). A cancel during a load ends the run at once. Staging and atomic commit are Q050-090's, unchanged. |
| Browser peaks | `browser.peaks` read the file on the UI thread, and the waveform view used it | new `browser.peaks_start` / `PeakJobs`: one worker fills a private entry, the UI thread adopts it after re-checking the cancel (`src/core/PeakJobs.cpp`). The view uses it for files over 1 MiB. |
| Stem separation | `stem.job_start` decoded and resampled on the caller; Split to Stems wrote an in-memory clip's WAV on the GUI thread | `StemJobManager::submitFrom`: decode (a `.ds` synthesis included) and resample run on the worker; the caller reads the header only (`src/core/ControlStemSource.cpp`). An in-memory clip's WAV is written on a pool worker, listed as `stem_prepare` (`stem-prepare-<id>` in `app.tasks`) with Cancel, before the same `stem.job_start` (`src/gui/StemSplitController.cpp`). |
| Render | already in the queue | `task` in its start reply; lifecycle and responsiveness now tested. |

`app.tasks` / `app.task_cancel` cover all four. Every start reply carries `task`, the exact `app.tasks` id: `plugin-scan-<TaskCenter id>`,
`peak-<TaskCenter id>`, `render-<job>`, `stem-<job>`. Scan and peak rows are read from `TaskCenter`, including ended ones
(at most `TaskCenter::MaxFinished` are kept). `app.tasks` no longer wakes the stem engine when no stem job was ever started.

GUI: the browser's waveform view (selecting another sample cancels the read), Edit > Plugin Quarantine > Rescan Plugins and
the Plug-in lists' Rescan now use the background routes; the status bar's Tasks list shows each with progress and Cancel.

## New commands

`browser.peaks_start` (`not_mutating`: fills only the memory-resident derived cache). `task` added to replies of
`plugin.scan_start`, `render.queue_add`, `render.queue_bounce`, `stem.job_start`, `stem.job_cancel`, `stem.job_status`.
Snapshot regenerated live: 879 ids / 77 groups; A16 `rows=888 ... not_mutating=387`. Nothing here edits a project, so no undo step is added.

## Known limits

- Synchronous compatibility routes remain and hold the interface while they run: `plugin.rescan`, `browser.peaks` on an
  uncached file, `render.render`, `render.stems`, `bounce.in_place`, `freeze.*`, `bounce.land`, `track.flatten`, `range.bounce`.
  These were not moved in this unit.
- A scan resolves descriptors on the UI thread, one file per turn. Only the `dlopen` moved. A plug-in's static initialiser
  now runs on a worker when the background scan is first to load it; a plug-in whose initialiser needs the GUI thread
  would misbehave there. None was found by a grep of `plugins/`, but third-party modules were not tested.
- `stem.job_start` reads only the header on the caller. A `.ds` or `.ogg` source, whose header gives no length, is accepted and
  decoded by the job's worker; its reply's `frames` is 0 until then, and a broken one fails the job rather than the start.
  Any other file libsndfile cannot open is refused at once.
- `SampleBuffer::fromFile` and the resampler cannot be interrupted, so a stem cancel takes effect when they return.
- The waveform view reads files up to 1 MiB where selected, with no task, as `TaskCenter.h` asks of short operations.
