# Q050-059.1 - Modular instrument graph, stage 1/3: playable modular instrument core and starter modules

Queue unit (P1, L, feature, area L10, members R-effects-25, R-effects-30, R-instruments-22, R-instruments-79): the
patcher modelled effect chains only; several requests describe a modular *instrument* graph. This stage adds the
instrument, its starter modules and its saved state. Stage 2 (agent graph commands, preset round-trip) and stage 3 (GUI
graph editor) build on it. Branch `feat/050-Q050-059.1-oc`, cut from `050/m0-train-21` (`37eaf0755`).

## What was built

- **The Modular Synth** (`plugins/ModularSynth/`, module `modularsynth`, "Modular Synth" in the instrument list): an
  instrument whose sound is a graph of modules. Five kinds, each with its parameters and input ports
  (`plugins/ModularSynth/ModularGraph.cpp`):

  | Kind | Output | Inputs | Parameters |
  | --- | --- | --- | --- |
  | Oscillator (`oscillator`) | audio | `pitch` (control, octaves), `amp` (control; 1 when unwired) | Wave (0 sine, 1 saw, 2 square, 3 triangle; saw and square PolyBLEP band-limited), Coarse (st), Fine (ct), Level |
  | Envelope (`envelope`) | control 0..1 | - | Attack, Decay (ms), Sustain, Release (ms); gated by the note |
  | Filter (`filter`) | audio | `in` (audio), `cutoff` (control) | Mode (0 low-pass, 1 high-pass, 2 band-pass), Cutoff (Hz, log knob), Resonance, Mod depth (octaves per unit of `cutoff`) |
  | LFO (`lfo`) - the modulation module | control -1..1 | - | Wave (0 sine, 1 triangle, 2 saw, 3 square), Rate (Hz, log knob), Depth |
  | Output (`output`) | - | `in` (audio), `amp` (control; 1 when unwired) | Gain |

  Several wires into one port add up. A graph is playable when it has 1..16 modules with unique ids, exactly one output,
  at most 64 wires, every wire between existing modules into a port of the matching signal, no wire twice and no cycle
  (`Graph::isValid`).
- **The starter graph** (what a new instrument holds): `osc1 -> filter1.in`, `filter1 -> out.in`, `env1 -> out.amp`,
  `lfo1 -> filter1.cutoff` - a saw through a low-pass at 1200 Hz with the LFO moving the cutoff and the envelope shaping the
  level. A note through it sounds.
- **Real-time design.** The graph is compiled on the control thread (`modular::compile`) into a `Program` of fixed arrays
  in processing order, wiring as indices, parameter model pointers. Each note's state (`modular::Voice`, 264 bytes: phases,
  envelope stage, filter memories) is constructed in the `NotePlayHandle`'s inline plug-in storage (static_assert on its
  size). `ModularSynth::playNoteImpl` loads the program pointer (one atomic acquire), reads each parameter once per block
  and renders per sample from stack arrays - no allocation, free, lock, wait, I/O or signal. A new program (a state restore,
  a project load) is published by swapping that pointer while `AudioEngine::requestChangesGuard()` holds the render period
  off - the publication the oscillator instruments use - and the old program and its parameter models are freed on the
  control thread afterwards, after the window has rebound. A voice whose program changed under it restarts its modules.
  Every parameter holds its change signal back on the render thread (`setDeferChangeSignalOnRenderThread`) and a 100 ms
  timer on the instrument's thread emits it, as the SFZ Player does.
- **Release.** `desiredReleaseTimeMs()` is the longest envelope release (at least 3 ms). When an envelope drives the
  output's `amp`, the envelope is the note's release; otherwise the note fades over the release time
  (`Instrument::applyRelease`). Notes held by the sustain pedal keep their envelope until the pedal lets the release start.
- **State** (`saveSettings` / `loadSettings`): `<modularsynth version="1"><graph>` with `<module id type ...params/>` and
  `<wire from to port/>`; each module's parameters are saved on its `<module>` element by `AutomatableModel::saveSettings`
  (so automation and controller links travel with them). A state **without `<graph>`** loads the starter graph at its
  defaults, silently. A graph that **cannot be played** (unknown type, missing or second output, unknown port, wrong signal,
  a wire to a missing module, a cycle) is never installed half-wired: the starter graph is, and the reason goes to
  `Song::collectError` (the project-open error report) and `loadProblem()`.
- **Parameters for agents and automation.** Every module parameter is a named `FloatModel` ("Osc 1 Wave", "Filter 1 Cutoff",
  ...): `plugin.param_get` / `plugin.param_set` on `inst` read and write them by name or index, and they are automatable.
- **The window** (`ModularSynthView`): a row per module with a knob for each parameter (object names `<id>.<key>`,
  property `parameter` = the parameter's name), and the wiring listed under them. It is rebuilt when the graph is replaced.
- **A knob edit is the agent's command** (review round 1). Each knob shows a stand-in `FloatModel` owned by the window (not
  a child of the instrument, not journalled, saves nothing). What the knob does to it is dispatched as `plugin.param_set`
  `{target, plugin: "inst", name, value}` through `ControlRegistry::invoke` - the same handler, range check, journal
  checkpoint and transaction an agent gets; a drag or a run of wheel steps on one parameter coalesces into one undo step
  (the command's coalescing key `target,plugin,name,index`). The parameter's own changes (an agent, automation, undo, a
  load) are copied back to the stand-in. If the surface cannot address the instrument (an instrument layered on another
  track, or the surface not up yet) the knob falls back to a plain journalled edit of the parameter.

## Commands and reversibility

No new command and no changed command; the window's knobs dispatch the existing `plugin.param_set`. The instrument uses the existing surface: `plugin.list` / `plugin.param_get`
(`not_mutating`), `plugin.load` (`snapshot`), `plugin.param_set` (`true_inverse`, one `control.undo` step - proven above).
A knob turn is a `plugin.param_set` run (one undo step, proven by the GUI test). The snapshot is unchanged (871 ids).

## Format

New element `<modularsynth version="1"><graph><module id type [param attributes]/>...<wire from to port/>...</graph>`
inside an instrument track's `<instrument name="modularsynth">`. Nothing existing changes: no loader, engine or other
plug-in code was touched, so projects without this instrument load and render as before.

## Known limits

- The window's knobs have no right-click automation/controller menu and no Ctrl-drag: they show a stand-in model, and those
  links would be made on it. Automation is made on the parameter (automation editor, agent automation commands). A knob on
  an instrument the control surface cannot address (a rack layer) falls back to a plain journalled edit.
- **Stage 1 plays the graph it is given.** Adding, removing and wiring modules is stage 2 (agent commands) and stage 3
  (GUI editor); until then a graph other than the starter one comes from a saved state or project.
- Instrument presets (`.xpf`, `plugin.preset_save`/`preset_load`) carry the same `saveSettings` state, but their round-trip
  is stage 2's acceptance and was not tested here.
- Wires have no amount: a control signal into `pitch` is octaves per unit, into a filter's `cutoff` it is scaled by the
  filter's Mod depth, into `amp` it multiplies. Wave and mode are whole-number knobs. Synthesis is mono (both channels
  equal; the track pans it); the graph has no velocity input (the track applies note volume).
- Parameters are read once per period (automation is block-rate). The LFO restarts with every note.
- A graph replaced under a sounding note restarts that note's modules (phase, envelope from its attack).
- `desiredReleaseTimeMs()` reads the published program; it is called from the render thread and the control thread. A
  third thread calling it while a load replaces the graph could read a program being freed; no such caller exists.
- **Only Linux / GCC / Qt 6 was built and run.** Qt 5.15, MSVC, mingw, macOS < 10.15 are covered by construction: no
  Qt-6-only API, no `std::filesystem`, no `min`/`max`/`small`/`near`/`far`/`interface` identifiers, C++20 features already
  used across the tree. The race-freedom of the program hand-over is argued (the render side takes no lock; the swap
  happens under the engine's change guard), not measured: ThreadSanitizer does not run on this machine.
