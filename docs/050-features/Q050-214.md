# Q050-214 - Plug-in editor gesture undo

Branch `feat/050-Q050-214-oc`, base `2a7fd9f9c` (`050/m0-train-24`). Unit (P2, feature, M, L10): a complete VST3 or CLAP
editor gesture is one project-history step, shared by GUI and agent.

## What changed

- **The plug-in reports.** VST3 `beginEdit`/`endEdit` (`plugins/Vst3Effect/Vst3ComponentHandler.h`) and CLAP
  `CLAP_EVENT_PARAM_GESTURE_BEGIN`/`END` from `process()` (`plugins/ClapEffect/ClapHostInternals.h`, `markGesture`) only
  increment a per-parameter atomic pair, `PluginParamGesture` (`include/PluginParamGesture.h`).
- **The GUI poll groups.** Each 100 ms poll reads the value and the marks together and hands them to the model's
  `PluginGestureHistory` (`include/PluginGestureHistory.h`). A gesture's first change takes the journal checkpoint while the
  model still holds the value from before it; later changes of that gesture write with `setValue(value, false, false)`. A
  change outside a gesture takes its own checkpoint, as before.
- **Same stack.** Nothing new is added to the history: the checkpoint is the model's own, on `ProjectJournal`, which Edit > Undo,
  the Undo History panel and `control.undo` all unwind.
- **A shared-history defect fixed on the way.** `control.undo` refused with "EVICTED" when the last agent record's step had
  merely been undone: `plugin.param_set`, then Edit > Undo, then an editor gesture, then `control.undo`. `step < oldest` was
  true for both. `ProjectJournal::newestEvictedSerial()` now tells them apart. A record from a previous document is still refused.

## New commands and reversibility

None, and no command's metadata changed, so the snapshot is untouched. `control.undo`'s behaviour changes in the one case above:
a refusal becomes the undo of the journal's top step, reported as `unrecorded edit` with its `step_serial`, the existing label
for a top the record does not match. `plugin.param_set` stays `true_inverse`. A gesture is one journal step.

## Realtime

The CLAP path runs on the audio thread: `markGesture` does a binary search and an atomic increment, with no allocation, lock, journal,
model or Qt work. All of that stays on the GUI poll. `begin()` publishes with a release fence before the first value, `end()` with
release after the last, and `read()` loads end, value, acquire fence, begin, so a seen end implies its last value and a seen value
implies its begin. Reasoned, not run: local TSan does not run on this box. The counters are relaxed-order atomics, so there is no
data race to report in any case; the ordering only decides which step a racing value lands in.

## Format changes

None. Nothing new is written to a project file, so old projects load and render as before: a gesture changes only what a poll does
with a journal checkpoint, and no render path is touched.

## Portability

No Qt-6-only API (`qMax`, `QMetaObject::invokeMethod` by name). `std::atomic_thread_fence`, `std::span` as neighbours use it. The test's VST3
half is compiled only when the opt-in fixture is (`WANT_VST3_TEST_INSTRUMENT`), and each half SKIPs without its fixture.

## Known limits

See `docs/KNOWN-LIMITATIONS.md` ("Plug-in editor gesture undo"). In short: the 100 ms poll is the resolution, so two gestures inside one poll
merge; one step per parameter, so an XY pad is two; changes a plug-in does not report as parameters are outside the history; a plug-in that
never ends a gesture merges until its next begin; a gesture has no row in the Undo History list, only its buttons.
