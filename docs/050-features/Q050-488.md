## Stage 2 - the ALSA raw-MIDI worker (reproduced and fixed)

**Reproduction.** Open a raw device that receives no input. The worker sits in `poll()` with a 10 s timeout,
and the destructor's 1 s `wait()` always expires first. So every close of an idle device took 1000 ms and
ended in `QThread::terminate()` while the worker was inside ALSA/poll code. `MidiAlsaRawShutdownTest`
reproduces this hermetically. The "device" is a pipe behind faked `snd_rawmidi_*` entry points, using the
same technique as `MidiOutQueueTest` and `AudioAlsaPollDescriptorTest`. Measured on the old behaviour:
`close took 1000 ms`.

**Design** (`src/core/midi/MidiAlsaRaw.cpp:43-52` documents it):

- **Ownership.** The `MidiAlsaRaw` object owns the device handles, the poll array, the wake pipe and the
  worker. The worker borrows them and never releases them.
- **Stop request.** `stopWorker()` (`:128`) stores the `std::atomic_bool m_quit` with release ordering,
  writes one byte to the non-blocking wake pipe, and joins. It is idempotent: a second call finds nothing
  running, and a full pipe already holds a wake-up.
- **Blocking-I/O wakeup (Linux).** The wake pipe's read end is the last entry of the poll set
  (`m_npfds + 1`, `:95`, `:216`). After `poll()` returns the worker checks `m_quit` before touching ALSA.
  The device is non-blocking, so nothing else in the loop can block.
- **Join order.** The worker is joined first, then the device handles are closed, then the poll array is
  freed, then the wake pipe is closed (`~MidiAlsaRaw`, `:116`). There is no `terminate()`. If the join
  takes more than 2 s, a warning is printed and the join continues.
- **Bound.** After the stop request the worker finishes at most its 5 ms pacing sleep, plus one
  128-byte parse, before it sees the flag.
- **Partial startup failure.** After a successful open, a non-positive descriptor count, a pipe failure or
  a short descriptor retrieval closes both handles at once and starts no worker. `AudioEngine::tryMidiClients`
  then treats the client like a failed open. Before this change, a zero count started a worker that polled
  nothing.
- **Unchanged.** The 10 s poll timeout, the 5 ms pacing sleep, the EINTR/error exits, input parsing and
  `sendByte`. `sendByte` gains only a null check for a device that never opened; previously that case
  handed ALSA a null handle.
- **Realtime.** The audio-thread entry point is `MidiClientRaw::processOutEvent` -> `sendByte`. It still
  writes the byte straight to ALSA, exactly as before, with no allocation, free, lock or wake-pipe traffic
  (proven below). Joins and resource release happen only in the destructor, which runs on the thread that
  deletes the MIDI client (`AudioEngine::~AudioEngine`, main thread), never on the audio thread.

## Shutdown order with the engine (review round 1)

The raw worker dispatches parsed input to `m_midiPorts` (`MidiClient.cpp`, `processParsedEvent`). Tracks own
those ports, and `~MidiPort` erases itself from the list. `Engine::destroy()` used to clear the project
first and stop the worker only in `~AudioEngine`, so an incoming event could walk the list while it shrank,
or reach a destroyed port. Now:
- `MidiClient::stopInput()` is a virtual, a no-op in the base. Its contract: when it returns, no dispatch is
  in flight and none can start.
- `MidiAlsaRaw::stopInput()` is `stopWorker()`.
- `Engine::destroy()` calls it right after `stopProcessing()`, before `clearProject()`.

The resulting order: stop audio, stop MIDI input, destroy the tracks and their ports, delete the
AudioEngine, which closes the device.

A lock held across dispatch was rejected because it deadlocks. A note-off dispatch takes
`requestChangeInModel()`, which the main thread holds while it destroys tracks.

Held by `stopInputWaitsForAnInFlightDispatch` and `engineShutdownStopsRawInputBeforePortsAreDestroyed`.

**Not covered: runtime track deletion.** Deleting a track at runtime, while input arrives, still has the
pre-existing unsynchronised port-list removal. It affects every raw client, and MidiAlsaSeq's snapshot
dispatch too. This is stage-4 callback-ownership work: it needs deferred removal that cannot deadlock
against `requestChangeInModel()`.

## Commands, formats, GUI

No command, schema, project format or GUI control changes. The behaviour is reached through the existing
paths that close the MIDI client: File > Quit and `control.quit`. The MIDI interface is chosen in
Settings. The manual (`data/manual/index.html`, "Closing a MIDI device") describes it.
