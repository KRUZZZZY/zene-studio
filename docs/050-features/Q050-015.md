# Q050-015 Articulation map editor

Unit: P0, L07 note editing. Create and edit named articulation maps, assign keyswitches, programs and
controllers, and manage the map from the interface. Base `de5a85a96` (train 5), branch `feat/050-Q050-015-oc`.

## What was built

- `src/gui/noteeditor/ArticulationMapEditor.cpp`, `include/ArticulationMapEditor.h`: the editor dialog
  (table of number, name, keyswitch, program, controller, value; New, Duplicate, Move Up, Move Down,
  Remove; cells editable). Every edit is one `track.articulations_set` through `ControlRegistry` (`commit`,
  ArticulationMapEditor.cpp:264); the table is re-read from `track.articulations`.
- Entry points: Track menu "Articulations..." (`src/gui/shell/ShellCommandMenus.cpp:266`) and the note
  editor's Articulation > "Edit Articulations..." (`src/gui/noteeditor/NoteEditorMenus.cpp:148`); both declare
  `track.articulations_set` as their command.
- `src/core/ArticulationRemap.cpp`, `include/ArticulationRemap.h`: `track.articulations_set` takes an optional
  `from` (old 1-based position of each new entry, 0 = new) so notes follow a moved entry and ask for none when
  theirs is removed. `applyArticulationEdit` replaces the map and moves the notes under ONE InstrumentTrack
  lock and returns the clips whose notes changed; the caller emits their `dataChanged` after unlocking
  (`ControlCommandsNotePlayback.cpp:174`). Playback (`InstrumentTrack::play`, `tryLock`) can therefore only
  read the old map with the old indices or the new map with the new ones, never the new map with the old
  indices. Undo and redo go through the same one-lock call. Reply gains `notes_remapped`.
- Order fix found by the playback test (round 1; replaced in round 2, below): the keyswitch's play handle was
  added before the note's, and the engine takes new handles newest first, so its note-on arrived after the note's.
- `tests/src/plugins/MpeTestConsumer.cpp`: the test instrument also logs note-ons, program changes and control
  changes in order (read through `saveState`, reset through `restoreState` with `clearlog`).
- `docs/NOTE-EDITOR.md` section 5a.

## Commands and reversibility

No new command, but one registered command's schema changed: `track.articulations_set` (true inverse,
unchanged class) gains the optional array argument `from`, its description says what `from` does, and its
reply gains `notes_remapped`. The commands snapshot (`tools/mcp-zene-control/zene_control/commands_snapshot.json`)
was regenerated from a live instance for that change (round 1: the `from` property and the new description);
the command COUNT is unchanged at 828 ids / 76 groups, and the canary figures pass
(`tests/doc-figures-gate.py` exit 0). Undo covers the map and the notes `from` moved. (Corrected in round 4:
earlier text said no schema changed.)

## Format

None. The `articulations` attribute of the track element is as before (written only when non-empty);
a note's `articulation` index is as before.

## Known limits

- Without `from`, notes keep their numbers (the previous behaviour). Linked clips on other tracks are not
  re-mapped (they index their own track's map).
- Names are unique case-insensitively in the editor; the command itself still accepts duplicates.
- No per-articulation lead time, colour or note-head.
- The hosted Windows test host cannot load the test instrument module, so `ArticulationPlaybackTest` skips there
  (same as `MpePlaybackTest`).

## Round 4 (Opus lane, 2026-10-19)

Rework of the r2 code-verifier REWORK: articulation events were lost on arpeggiator-generated (and,
through them, chord-stacked) child handles; the feature record misstated the schema change and
pointed the UI/command-equivalence evidence at the wrong test.

### What changed (file:line)
- **`src/core/NotePlayHandle.cpp:110`** (constructor, the `hasParent()` branch): a handle whose
  origin is `Origin::Arpeggio` copies its parent's `m_articulation` (a four-`int` POD - no
  allocation, no lock, no signal; it runs where `acquire()` already runs, in the parent's `play()`).
  Why only arpeggio steps: `play()` sends the articulation inside the note-on block
  (`NotePlayHandle.cpp:288`), and an arpeggio BASE note never enters that block
  (`hasParent() || !isArpeggioEnabled()` is false for it), so before this change nothing was sent
  for an arpeggiated note at all - each step now sends it just before its own note-on, at the step's
  own frame offset, and lets the keyswitch go a period later or at the step's `noteOff`. A
  chord-stacking sub-note is created by `InstrumentFunctionNoteStacking::processNote` inside its
  parent's `play()` -> `InstrumentTrack::playNote`, i.e. AFTER that parent (the played note, or an
  arpeggio step) sent the articulation and its own note-on at the same offset; giving every voice
  its own copy would only repeat the program change, controller and keyswitch once per voice.
- **Tests** (`tests/src/core/ArticulationPlaybackTest.cpp`): helper `setFunctionsAndMap` (`:209`,
  the arpeggiator and chord stacking through `loadTrackSpecificSettings`, the same element a project
  load reads, then a map entry sending keyswitch 25, program 7 and CC 11=90) and
  `isArticulatedMajorChord` (`:230`); three playback slots below. Each renders the song through the
  real engine into the logging instrument.
- **Docs:** this record's "Commands and reversibility" now states the schema change (`from`) truthfully;
  `docs/qwen-fixes-2026-10/cluster-Q050-015.md` points acceptance 3 at `ArticulationMapEditorTest`
  (`theEditorAndTheCommandLeaveTheSameMap`, `everyEditIsOneUndoStep`, `notesFollowTheirArticulation`)
  instead of `NotePlaybackTest`; `docs/NOTE-EDITOR.md:173` (section 5a) describes arpeggio and
  chord-stacking playback; `tests/upstream-modifications.txt` records the constructor change.
