# Q050-484 - SFZ instrument

Queue unit (P1, M, modernisation, area L10, member `HOTSPOT-Q050-484`): Zene had no SFZ support while it shipped two
legacy sampler formats (Gravis `.pat`, GigaStudio `.gig`). Built on branch `feat/050-Q050-484-oc` together with
Q050-103, Q050-087 and Q050-071 (a feature batch; each unit has its own commits).

## What was built

- **The SFZ Player** (`plugins/SfzPlayer/`, module `sfzplayer`, "SFZ Player" in the browser). It loads an `.sfz` with
  **sfizz 1.2.3** (BSD-2-Clause) - samples, velocity layers (`lovel`/`hivel`), round robins (`seq_length`/`seq_position`),
  key switches (`sw_*`) and the rest of what sfizz plays - and renders it as one stereo instrument (MIDI based, single
  streamed, like the VST3/LV2 instruments).
- **sfizz is vendored and built into the module on every platform** (`plugins/SfzPlayer/sfizz/`, see `LICENSE-NOTICE.md`
  there for the inventory, licences and what was left out): sfizz, Abseil (Apache-2.0), ghc::filesystem, SIMDe,
  atomic_queue, kissfft, pugixml, tunings, cpuid and the rest of sfizz's own dependencies. The only external dependency
  is libsndfile, which Zene already requires everywhere (sfizz reads samples through it: wav, flac, ogg, aiff, ...). There is
  **no `if(LMMS_HAVE_...)`** around the module and no system sfizz: it is in `PLUGIN_LIST` unconditionally, so it ships
  wherever the other built-in instruments do. The vendored targets are static, position independent, C++17, hidden
  symbols and marked third-party for the warning flags; per-file `-mavx` is applied only on x86 GNU/Clang. Windows
  (`NOMINMAX`, `_USE_MATH_DEFINES`, `/utf-8`, `/Zc:__cplusplus`, `/fp:fast`), the macOS aligned-new fallback for
  deployment targets below 10.14 and `-ffast-math` follow sfizz's own build. **Only the Linux/GCC build was run here** -
  the other platforms are by construction and by sfizz's own CI, not measured (see Known limits).
- **Real-time safety.** `SfzPlayer::handleMidiEvent` (any thread) pushes a trivially-copyable `SfzEvent` into the existing
  lock-free `MpscQueue`; `playImpl` (render thread) drains it into a fixed array, orders it by frame offset (insertion
  sort, stable, no allocation), plays each event at its offset and renders in 1024-frame pieces through sfizz. A load or a
  change of polyphony / oversampling / sample rate builds a **complete new `SfzSynth` on the control thread** (sfizz forbids
  reloading a synth the render thread is playing) and hands it over with `RtPublished` (`plugins/SfzPlayer/RtPublished.h`):
  the render path takes two atomic increments and one atomic load around its use of the synth - no lock, no allocation,
  no wait - and only the control thread's `replace()` waits (until no render is inside the old synth). Sample streaming runs
  on sfizz's own worker threads. **Two things sfizz's `renderBlock` does were taken out of the render callback** (the one
  change to the vendored sources, `ZENE_SFIZZ_NO_RENDER_THREAD_WAITS`, see `plugins/SfzPlayer/LICENSE-NOTICE.md`): the periodic
  file-pool garbage collection (a spin mutex and a walk that moves sample data) and, when freewheeling, waiting for the background
  loaders. The player never enables freewheeling. An **export** instead loads every sample whole before it starts:
  `ProjectRenderer::startProcessing` (main thread) emits the new `Song::exportPreparing`, the player rebuilds its synth with a
  whole-sample preload, and `Song::exportFinished` (main thread, queued from the render thread's end) takes it back to
  streaming. The `SfzRenderThreadGate` ctest reads the built library's symbol table and fails if `Synth.cpp` references the
  collection again.
- **No signals on the render thread.** An automation tick sets the four models on the render thread; they hold their change
  signal back there (`AutomatableModel::setDeferChangeSignalOnRenderThread`), and a 100 ms timer on the player's own thread emits
  it (`flushDeferredChange`) - that is what knobs follow and what triggers the rebuild for polyphony / oversampling. A change
  from the socket or the window emits at once as before.
- **State.** `saveSettings` writes `src` (`PathUtil::toShortestRelative`, so a project is portable), `volume`, `quality`,
  `polyphony`, `oversampling`; `loadSettings` loads the settings first, then the file once. A file that is missing keeps its
  reference (so a later save does not forget it), the player is silent and `Song::collectError` reports it. The `.sfz`
  is a project asset (`sfzplayer@src` in `ControlProjectAssets`: missing-asset reports and relink know it); the samples it
  names are read by the SFZ itself and are not tracked separately.
- **Parameters** (agent-visible through `plugin.param_get` / `plugin.param_set` on `inst`, automatable): Volume (dB),
  Sample quality (1-10), Polyphony (1-256) and Oversampling (1x/2x/4x/8x). Polyphony and oversampling are fixed when a synth
  is built, so changing them rebuilds the loaded file (on the instrument's own thread, within about 100 ms of an automation
  tick); Volume and quality apply live.
- **Reaching it.** `plugin.list` lists it (builtin, instrument, `.sfz`), `plugin.load` puts it on a track, `browser.load`
  with an `.sfz` makes a track holding it (`.sfz` is a `preset` kind in the browser catalogue), the file browser lists `.sfz`
  files and loads them on double-click, and the instrument window has an **Open SFZ...** button.
- **New command `plugin.open_file`** (`{target, path}`): opens a file in the instrument a track already carries - what the
  window's Open button runs, so the window and an agent cannot disagree. The instrument must be the one that opens the file's
  extension; a file it cannot load is refused (the instrument keeps what it had) and records no step; success is one
  `control.undo` step restoring the previous file and settings. Class `true_inverse` (action checkpoint, the same mechanism
  as `plugin.state_load`).

## Commands and reversibility

One new command, `plugin.open_file` - `true_inverse` (row in `ControlReversibilityTableAction.cpp`; A16 histogram
`rows=850 true_inverse=423` in `docs/RELEASE-NOTES-v0.3.0-alpha.md`). No other command changed: `plugin.load` (instrument
branch: `snapshot`, not reversible), `plugin.param_set` (`true_inverse`), `plugin.list`/`plugin.param_get`
(`not_mutating`), `browser.load` (`true_inverse`). `commands_snapshot.json` regenerated live: 841 ids / 76 groups.

## Format

New element `<sfzplayer src volume quality polyphony oversampling>` inside an instrument track. Nothing existing changes;
projects that name the legacy Patman / GigPlayer modules load exactly as before (those modules are untouched - hiding them
from new-instrument lists is Q050-485).

## Known limits

- **Only Linux / GCC was built and run here.** Windows (MSVC, mingw, clang arm64), macOS and the Qt 5.15 / Qt 6.8 matrix
  are covered by construction: the sfizz build is its own upstream recipe, the CMake is conditional only on compiler and
  processor, the player's sources use no Qt-6-only API and no `std::filesystem`. The hosted CI jobs are the first real
  measurement.
- sfizz reads samples through libsndfile, so the formats are libsndfile's (wav, flac, ogg, aiff, ...); sfizz's own
  WavPack/DecentSampler support is not built in.
- A region whose sample file is missing is dropped by sfizz without an error: the file loads, the region is silent. The
  status line shows the regions that exist.
- Polyphony, oversampling and a sample-rate change reload the file (the load blocks the instrument's thread for as long as
  sfizz takes to parse and preload the SFZ; audio meanwhile keeps playing the previous synth). Do not automate them.
- MIDI reaches the instrument through its queue, so a note-on posted after the instrument rendered in a period sounds in
  the next one (the same period of latency the VST3 and LV2 instruments have). A full queue (1024 events) drops events.
- The instrument does not apply the track's microtuner, pitch-bend range, or Scala tuning (sfizz supports Scala files; there
  is no control for it yet). Editing SFZ zones, bundling or relocating sample libraries are out of scope.
- **No sample garbage collection while a synth lives**: a sample that was streamed to its end stays in memory until the synth
  is rebuilt (a reload, an export, closing the project). The memory is bounded by the samples the instrument has played.
- An export holds every sample of the instrument in memory for its duration.
- The race-freedom of the synth hand-over is argued in the code and in this page, not measured (ThreadSanitizer does not run
  on this machine). sfizz still takes its own try-lock inside `renderBlock` for control calls the player does not make on a
  live synth.
