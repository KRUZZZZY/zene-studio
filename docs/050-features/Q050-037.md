# Q050-037 - Define the automation value before its first point

**Unit.** An automation clip whose first node sits later than the clip's start used
to read `0` before that node (`AutomationClip::valueAt` and the sample-accurate
ramp), so starting at the beginning - and every return to it - slammed the
controlled parameter to its minimum. The clip now holds the authored parameter's
initial value there; a point drawn at clip-relative tick 0 remains the explicit
clip-start value.

**What was built**
- `AutomationClip::valueAt(TimePos, bool *beforeFirst)` reports the pre-first read
  in the same lock it already takes; the value is the first object's
  inverse-scaled authored initial value. An empty map keeps answering `0`.
- `AutomationClip::rampValueAt()` returns the same pre-first value, so the map
  read and the audio ramp cannot disagree. A point at tick 0 is simply the first
  node, so it wins and interpolation at/after it is untouched.
- `writeBlockRamp()` takes an optional `target` (whose initial value the pre-first
  knots hold) and reports `firstNodeFrame`. It still takes the clip mutex exactly
  once per block.
- `TrackContainer::collectAutomatedValues()` (per-tick apply) uses the flag from
  `valueAt()` and applies each target's own initial value. No second clip lock.
- `Song::buildAutomationRamps()` builds the curve once per clip and gives a target
  whose initial value differs a **copy** of the fixed-capacity ramp with only the
  pre-first prefix overridden (`AutomationRamp::setValueBefore`). It does not
  rebuild a ramp per target under another clip lock.
- No new command, no serialized field: nodes and target ids are saved exactly as
  before; the initial value is derived from the model.

**Review r1 finding (this rework).** The earlier attempt added mutex acquisitions
to the audio path (`preFirstValue()` via `firstObject()`, a per-tick
`isBeforeFirstNode()` lookup, and a per-target `writeBlockRamp()` rebuild). Those
are gone. The pre-first flag now travels out of the existing `valueAt()` lock,
the target initial values are plain model scalars, and a differing target gets a
stack copy of the already-built ramp. `Song::buildAutomationRamps` and
`TrackContainer::collectAutomatedValues` are declared in
`tests/rt-safety-scope.txt`; the sweep stays green with no new allowlist line.

## Format changes

None. Nodes (`<time pos=... value=...>`) and target ids (`<object id=...>`) are
saved and loaded exactly as before. The pre-first value is derived from the
target model's existing authored initial value, so old projects need no migration
and a project that saves no new field round-trips byte-for-byte.

## Realtime note

`Song::buildAutomationRamps` runs on the audio thread. It adds no allocation and
no new lock: the clip mutex is the same single lock `writeBlockRamp` already took,
the per-target initial values are scalar model reads, and a differing target
copies the fixed-capacity `AutomationRamp` (528 bytes, no heap) and rewrites its
pre-first knots in place. `TrackContainer::collectAutomatedValues` keeps its
single `valueAt()` lock and only adds the out-flag and scalar per-target reads.
The static sweep measures both declared paths (exit 0, no new allowlist entry);
the runtime allocation probe in `SampleAccurateAutomationTest` stays green. Local
TSan does not run on this box; the race argument is by design (the clip state is
read under its existing recursive mutex, model initial values are plain scalars
read the same way playback already reads model ranges).

## Known limits

- A direct `valueAt(TimePos)` read without a target (the editor, transforms, note
  detuning) answers with the clip's **first** object's initial value; a clip with
  no object still answers `0`. Multi-target playback uses each target's own value.
- Relative (trim) clips are deliberately **unchanged** (review r2): their value is
  an offset from the range midpoint, so before the first node they still read `0`
  (an offset of -0.5 on a 0..1 range) in `valueAt()` and in the ramp. The
  initial-value hold applies to absolute clips only.
- An empty node map keeps the old `0`: there is no curve and no start value to
  define.
