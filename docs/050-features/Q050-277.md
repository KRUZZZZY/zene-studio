# Q050-277 - Capture an exact number of externally clocked bars

Unit: P2, size M, area L03 (recording, takes, comping, inputs), type feature.
Branch `feat/050-Q050-277-oc`, base train 24 (`050/m0-train-24`, `2a7fd9f9c7`).

Goal: a user starts an external synth and captures exactly the chosen number of bars or steps.

## What was built

`session.record_slot` (the launcher-cell audio capture) gained two arguments:

- `steps` (1-1024): the take's length in sixteenth notes (`TicksPerMidiBeat` = 12 ticks, MIDI Clock's own beat), beside
  `bars`. Exactly one of the two; both is `invalid_args`. The reply and `session.record_slot_status` say which unit was
  chosen (`length_unit`: `bars` / `steps` / `none`).
- `clock_sync` (boolean): the MIDI clock master (set up with `clock.master_set`) sends START when the take starts and STOP
  at its end, with exactly `length / 2` clock pulses between (`MidiClock::captureStarted/captureStopped`, driven from the
  session scheduler's launch and stop events through `SessionAudioRecorder`). The audio thread only QUEUES them (a fixed
  lock-free ring); a sender thread (`src/core/MidiClockCapture.cpp`) delivers them to the MIDI client, so no client I/O runs
  on the audio thread. Master turned off mid-capture: the span ends there with one STOP, no catch-up, the take continues. Refused (`refused`) while the master is off
  or has no destination; the message names `clock.master_set`. While the span is open the clock pulses on its own time
  (the song's transport may be stopped) and does not send the transport's own edges; a cancel mid-span sends STOP.
  `session.record_slot_status` reports `clock_sync` and `clock` (`active`, `start_tick`, `stop_tick`, `length_ticks`,
  `pulses`, `starts`, `stops`).

GUI: an empty launcher cell's menu has Record Audio for Steps..., Record Bars with MIDI Clock Start/Stop... and Record
Steps with MIDI Clock Start/Stop... beside Record Audio for Bars... - each a `session.record_slot` form
(`src/gui/SessionGridMenus.cpp`), landed by the grid like the existing entries. Manual: `data/manual/index.html`
("Capturing an external synth for an exact length"). Design record: `docs/SESSION-AUDIO-RECORD.md`.

## Realtime and output ownership

The audio-thread additions (`captureStarted`, `captureStopped`, `emitCapturePulses`) are atomics and a store into a fixed
SPSC ring (`queueOut`): no allocation, lock, wait, logging, MIDI-client call, I/O or Qt signal. Work per callback is bounded: a
period queues the pulses its frames cross; a stop queues at most `MaxTopUpPulses` (64) then STOP; nothing scales with the
capture's length. The sender thread (made by `captureArm()` on the control thread) delivers the ring in order. Local TSan does
not run on this box: the ring has one producer (the audio thread; `captureAbort` from a cancel holds the engine so no period
renders) and one consumer, head/tail with release/acquire; the span's counters are atomics read by the control thread.
Round 3: the sender delivers through `MidiClient::sendFromNonAudioThread()` (a mutex the audio thread never takes), never
`processOutEvent()` - on ALSA that feeds `MidiOutQueue`, single-producer, whose producer is the audio thread. `MidiAlsaSeq`
gives the off-audio path its own `MidiOutQueue` (one producer: the mutex holder) and its sequencer thread drains both (one
consumer). Raw clients accept only one-byte System Real-Time messages from it (legal anywhere in a MIDI stream; one atomic
pipe write / `snd_rawmidi_write` / multi-producer JACK queue push); Core MIDI and WinMM use their thread-safe system calls via
`processOutEvent` (not run here). A refused message stays at the ring's tail and is retried. Admission: a span opens only when
START and STOP both fit; pulses keep one slot free for the open span's STOP; otherwise the span is refused before START.
Proofs (round 2): `theCallbacksOnlyQueueAndTheSenderThreadDelivers` (sender held: a whole capture runs and the audio thread
delivers nothing), `aFullRingRefusesPulsesButStillDeliversStartAndStop` (a 6-bar capture against a held sender: bounded queue,
drops counted, START/STOP delivered), `theMasterTurnedOffMidCaptureEndsTheSpanWithoutCatchUp`.

## Known limits

- Period-granular: START is queued in the period the cell starts (delivered about a millisecond later by the sender); the stop queues at most 64 catch-up pulses for its own period.
- If the sender is starved so long the ring fills, pulses are refused and counted (`captureOutputDropped`); a new capture whose START and STOP do not both fit is refused before START (`clock.refused`) and records unclocked.
- macOS (Core MIDI) and Windows (WinMM) off-audio delivery is reasoned, not run on this Linux host; no hosted CI run.
- The fixture is what the engine handed its MIDI client (the bound in `docs/KNOWN-LIMITATIONS.md`), not bytes a device received.
- The synth's own latency is not compensated beyond the recording round trip the take already drops.
- After a span ends, a running transport re-sends its own SPP/CONTINUE (the device was stopped).
- One take, one cell, empty cells only (unchanged).
