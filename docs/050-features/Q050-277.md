# Q050-277 - Capture an exact number of externally clocked bars

Unit: P2, size M, area L03 (recording, takes, comping, inputs), type feature.
Branch `feat/050-Q050-277-oc`, base train 24 (`050/m0-train-24`, `2a7fd9f9c7`).

Goal: a user starts an external synth and captures exactly the chosen number of bars or steps.

## What was built

`session.record_slot` (the launcher-cell audio capture) gained two arguments:

- `steps` (1-1024): the take's length in sixteenth notes (`TicksPerMidiBeat` = 12 ticks, MIDI Clock's own beat), beside
  `bars`. Exactly one of the two; both is `invalid_args`. The reply and `session.record_slot_status` say which unit was
  chosen (`length_unit`: `bars` / `steps` / `none`).
- `clock_sync` (boolean): the MIDI clock master (set up with `clock.master_set`) sends START when the take starts and STOP
  at its end, with exactly `length / 2` clock pulses between (`MidiClock::captureStarted/captureStopped`, driven from the
  session scheduler's launch and stop events through `SessionAudioRecorder`). Refused (`refused`) while the master is off
  or has no destination; the message names `clock.master_set`. While the span is open the clock pulses on its own time
  (the song's transport may be stopped) and does not send the transport's own edges; a cancel mid-span sends STOP.
  `session.record_slot_status` reports `clock_sync` and `clock` (`active`, `start_tick`, `stop_tick`, `length_ticks`,
  `pulses`, `starts`, `stops`).

GUI: an empty launcher cell's menu has Record Audio for Steps..., Record Bars with MIDI Clock Start/Stop... and Record
Steps with MIDI Clock Start/Stop... beside Record Audio for Bars... - each a `session.record_slot` form
(`src/gui/SessionGridMenus.cpp`), landed by the grid like the existing entries. Manual: `data/manual/index.html`
("Capturing an external synth for an exact length"). Design record: `docs/SESSION-AUDIO-RECORD.md`.

## New commands and reversibility

No new command ids (878 ids / 77 groups unchanged, A16 histogram unchanged). `session.record_slot` stays `not_mutating`
(arming and recording are a launch); `session.record_slot_land` stays `true_inverse`. The snapshot
(`tools/mcp-zene-control/zene_control/commands_snapshot.json`) was regenerated from a live instance for the new args.

## Format changes

None. A saved project references the take's WAV exactly as before; `bars`/`steps`/`clock_sync` are not persisted.

## Realtime

The audio-thread additions (`MidiClock::captureStarted/Stopped`, `emitCapturePulses`) are atomics plus the existing
`emitMessage` -> MIDI client output path the clock already uses from the audio thread; nothing allocates, locks or emits
Qt signals. `captureAbort` runs only under the engine-held cancel. Local TSan does not run on this box: the span state is
written by the audio thread only (the scheduler and the clock run in the same `processNextBuffer`), read as atomics by
the control thread.

## Known limits

- Period-granular: START goes out in the period the cell starts; the last period's pulses are topped up just before STOP.
- The fixture is what the engine handed its MIDI client (the bound in `docs/KNOWN-LIMITATIONS.md`), not bytes a device received.
- The synth's own latency is not compensated beyond the recording round trip the take already drops.
- After a span ends, a running transport re-sends its own SPP/CONTINUE (the device was stopped).
- One take, one cell, empty cells only (unchanged).
