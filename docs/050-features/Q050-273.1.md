# Q050-273.1 Save and reuse audio launcher cells in the shared library

Stage 1 of 2 of Q050-273. Arrangement clips already had **Save to Library...**; a launcher cell did not. A
cell is not an arrangement `Clip` - an audio cell stores a source **path** - so `browser.save_clip` now
takes a launcher-cell address as well as a clip address.

## What was built

- **One command, two addresses** (`src/core/ControlCommandsLibraryClips.cpp`): `browser.save_clip`
  accepts either `clip` (an arrangement clip) or the pair `track` + `scene` (a populated launcher cell),
  exactly one of the two. Everything after the address - the folder (default `<user samples>/Clips`, which
  the browser's Samples root lists), the `name` default, `tags`, the duplicate refusal, `overwrite` and
  the one undo step - is shared code, so the two routes cannot drift apart.
  - An audio cell is saved as the audio its source file holds: a stereo 32-bit float WAV at the source's
    own rate and its own frames. The cell's `gain_db`, `transpose`, `detune`, `loop_start`/`loop_length`
    and `warp` are playback settings of that cell and are **not** baked into the entry.
  - A MIDI cell is refused by name (its PatternStore notes are stage 2 of Q050-273); so are an empty
    cell, an address outside the grid, and one coordinate without the other.
- **The decoded-size bound, not the input size** (`include/LibraryCellAudio.h`,
  `src/core/LibraryCellAudio.cpp`): the previous draft refused a source file larger than 512 MiB and then
  called `SampleDecoder::decode()`, which allocates the whole decoded buffer and then a second full
  interleaved copy. That was no memory bound: a compressed file that is 20 KB on disk can decode to
  gigabytes. The save now has a bound on **decoded** stereo float PCM (256 MiB, the same figure the WAV
  payload costs), checked from the source's header before anything is decoded, and libsndfile-readable
  sources are **streamed block by block** (8 192 frames) with no full-size buffer and no second copy at
  all. A source only the built-in decoder reads (Ogg without libsndfile support, DrumSynth) gets a
  one-second bounded length probe first, so an over-limit file is refused before its full decode.
- **Atomic writes**: the target is a `QSaveFile`; libsndfile encodes through its `handle()` (with
  `close_desc = SF_FALSE`) and the destination is replaced only by a complete, closed file's `commit()`.
  Any failure - decode error, short write, failed close, failed commit - cancels the write, so a refused
  save leaves no partial file, never replaces the bytes already there, and leaves no `QSaveFile`
  temporary behind.
- **Deterministic failure seams** (compiled only under `LMMS_TESTING`; the `DataFile` `ZENE_TEST_SAVE_FAULT`
  style). Each is read per call and has no effect in a release build:
  - `ZENE_TEST_LIBRARY_SAVE_MAX_DECODED_BYTES` lowers the decoded-size budget, so the exhaustion boundary
    is measured with a small file;
  - `ZENE_TEST_LIBRARY_SAVE_ALLOC_FAULT` drives the out-of-memory refusal;
  - `ZENE_TEST_LIBRARY_SAVE_WRITE_FAULT=short-write` or `=before-commit` drives the failed-write cleanup.
- **The GUI route** (`src/gui/SessionGridMenus.cpp`): a populated **audio** cell's right-click menu has
  **Save to Library...**, which runs `browser.save_clip` with `track` + `scene` fixed and the cell's name
  pre-filled in the shared command form. An empty cell and a MIDI cell do not offer it (the command
  refuses both by name; an entry that always refused would be a dead item).
- **The agent route**: the same registered command over the control socket / MCP, with the `track` and
  `scene` arguments and no window at all.

No new command id was added; `browser.save_clip`'s `argsSchema` and description changed, so
`tools/mcp-zene-control/zene_control/commands_snapshot.json` was regenerated from a live instance
(`snapshot_live.py`). The id count and group count are unchanged (878 ids / 77 groups), so the README
canary and the A16 histogram are unchanged. `browser.save_clip` keeps its `true_inverse` class (its undo
removes the file and the tags it added; redo writes the subject again - a clip by id, a cell from the
source path it captured).

No project-format change: the cell's source is already persisted in `<z:scenes>`, and the library entry is
a file outside the project. Nothing was added to the audio thread: the save is a command handler on the
control/UI thread; the renderer is untouched.

## Known limits

- Stage 1 is audio only. A MIDI cell is refused by name; saving its PatternStore notes and inserting the
  saved MIDI in another launcher cell is stage 2 of Q050-273.
- The library entry is the source audio, not a render of the cell: `gain_db`, `transpose`, `detune`, loop
  and warp are not baked in. That is the stated scope ("reusable media content only"), and it is why the
  frames compare exactly.
- A source libsndfile does not read and that only the built-in decoder handles (Ogg where libsndfile lacks
  it, DrumSynth) is decoded whole once past the bounded length probe; the probe is what keeps that inside
  the decoded-size bound, but the peak there is one decoded copy plus the block-sized output scratch, not
  the streaming path's bounded working set.
- The 256 MiB decoded budget is fixed in the product; the test seam only lowers it.
- The undoing of a cell save writes the captured source file again on redo; if that source has been
  deleted in the meantime there is nothing to redo from (the redo is then a no-op and the undo step stays
  consumed).
- Saving a cell to `dir`/`name` that resolves to the cell's **own** source file is refused: the write
  would rename a new file over the one it is reading (and on Windows could not open the temporary at all).
  The refusal names the collision and suggests another `name` or `dir`.
