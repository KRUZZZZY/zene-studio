# Q050-062.1 Stem-separation quality, stage 1/4: expose quality settings to stem jobs

**Unit.** R-ai-2, R-performance-55, R-workflow-102 (`L05`). Agents can choose a fast or a
higher-quality separation for `stem.job_start` and read the setting a job actually uses from job
state. Callers that do not choose get exactly the behaviour they had before.

## What the setting is

The quality is the **overlap between consecutive model segments**. Both C++ backends and
`tools/stem_split_cli.py` run HTDemucs over overlapping segments and average the Hann-windowed
predictions (overlap-add). Before this change the overlap was always 50%.

| quality | overlap | hop | inference passes vs standard |
| --- | --- | --- | --- |
| `fast` | 25% | `floor(segment * 3 / 4)` | about 2/3 |
| `standard` (default) | 50% | `floor(segment * 2 / 4)` = `segment / 2`, the old hop | 1 |
| `high` | 75% | `floor(segment * 1 / 4)` | about 2x |

The hop is never below 1. `segment_frames` is not used as a quality control: it changes the model's
context, and HTDemucs was trained on its own 343,980-frame segment (the brief's "most likely mistake 1").

## Known limits

- **No GUI choice yet.** The sample clip's **Split to stems** still submits `stem.job_start` without
  `quality`, so it splits at `standard`, unchanged. The menu choice and showing the setting in the job
  UI are stage 2 (Q050-062.2), per the scoping split.
- **SDR is not measured.** No figure here says `high` separates better. Measuring real-model SDR and time
  for each setting is stage 3 (Q050-062.3). More overlap means more predictions averaged per frame
  (Demucs's own `--overlap` works the same way), at the cost of the passes in the table above.
- `hop_frames` in job state comes from the same `stemHopFrames()` the in-process backend calls. It is
  not a count read back from the backend; the tests above check the run counts directly.
  `inference_quality` is the value the worker passed to `separate()`; what each backend then does with
  it is proven by the backend tests, not over the socket.
- In this build the socket transcript runs the in-process ONNX backend (`LMMS_HAVE_ONNXRUNTIME`). The
  external-process route is covered by `StemSplitPipelineTest`.
- From before this change, and left alone: `segment_frames <= 1` makes the ONNX backend use the
  model's own segment, while the CLI takes `--segment 1` literally.

## Format changes

None. The project format is unchanged, and quality is not stored in projects.
