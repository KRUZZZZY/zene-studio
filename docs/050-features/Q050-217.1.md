# Q050-217.1 - MIDI bindings for built-in commands (stage 1/4)

**Unit.** Bind a MIDI note and a MIDI control change to a built-in command that needs no arguments, and run
that command through the control registry from the controller. Stage 1 of cluster Q050-217; the later stages
add workflows, scripts and workflow header buttons, and nothing here is designed so that they must undo it.

**Goal.** "Bind MIDI notes and CCs to built-in commands that require no arguments."

**Design.** The binding surface is the one the launcher already had, extended rather than duplicated, because
two MIDI ports on one controller would both see every event and there would be two answers to "what does this
note do".

- **One surface, one drain.** `LaunchBindings` still derives `MidiSurfaceInput` and is still the single port
  `session.bindings_connect` opens. Its MIDI-thread `decode()` now also accepts control changes; the item it
  queues (`LaunchTrigger`) is four plain numbers and a bool, so the MIDI thread still allocates nothing and
  takes no lock, and the 15 ms UI-thread timer still does all the work. `drainPending()` is the seam a harness
  uses to apply the queue synchronously instead of waiting for a tick.
- **A second store, not a second format.** Command bindings live in `midi/commandbindings` (their own config
  section, a JSON array); the launcher's `launcher/bindings` keeps its format, its meaning and every binding
  an old config already holds:
  `{trigger:"note", key:60, channel:0, command:"mixer.add_channel"}` /
  `{trigger:"cc", controller:74, channel:-1, command:"transport.stop"}`.
- **Activation.** A note fires once on its press and rearms on its release; a note-on at velocity 0 is a
  release, as every MIDI source spells one. A control change fires when it goes from 0 to a positive value and
  rearms at 0, so one sweep of a knob is one activation. The CC **value is not passed on as an argument** -
  that is exactly why a bound command must require none.
- **Argument-free only.** `session.bind_command` refuses a command whose `argsSchema` has any required
  property, with the reason, at the moment the binding is made - the same rule `window.header_set` already
  applies to a header button (a click runs its command with no arguments either).
- **Note collisions.** Binding a command to any channel (-1) removes every launcher binding for that note;
  binding it to one channel removes the launcher binding for that channel, leaving a wildcard launcher for
  the other channels. `session.bind` and `session.bind_learn` can add an exact launcher binding beside a
  wildcard command binding.
- **Specificity.** The more specific channel binding wins across both stores: an exact-channel binding beats
  an any-channel one. At equal specificity a command wins. A CC never launched anything, so a CC binding
  leaves the launcher's store alone.

Commands (group `session`, beside the launcher's own five):

| Command | Mutating | Reversibility |
| --- | --- | --- |
| `session.bind_command` | yes | `true_inverse` - one recorded undo step writes both previous config lists back |
| `session.unbind_command` | yes | `true_inverse` - one recorded undo step writes the previous list back |
| `session.command_bindings` | no | `not_mutating` - a read |

The GUI entry is **Launcher > Controller**: *Bind a Command to a Note or Control Change...*,
*Unbind a Command...* and *Command Bindings*, each an action declaring the command it runs, so the menu and an
agent take the identical path through `ControlRegistry`.

## New commands

- `session.bind_command` - bind a note (`trigger:"note"`, `key` 0..127) or a control change (`trigger:"cc"`,
  `controller` 0..127) on `channel` 0..15 or -1 (any) to `command`, a registered command that requires no
  arguments. Replaces a binding on the same control; one undo step, which also takes the note off the
  launcher.
- `session.unbind_command` - remove that binding. One undo step.
- `session.command_bindings` - read them back, plus whether a controller is connected.

## Format changes

None to the project. Two **config** additions: `midi/commandbindings` (a new array; nothing wrote that
section before, so an old config simply has no command bindings) and, only when a note moves between the two
kinds of binding, the launcher's existing `launcher/bindings`. Old projects load and render exactly as
before, and a new binding round-trips through the config as a plain JSON array.

## Realtime

Nothing on the audio or MIDI thread allocates, locks, waits, does I/O or emits a signal: `decode()` fills a
`LaunchTrigger` of four ints and a bool into a fixed `MpscQueue<LaunchTrigger, 256>` and returns; the
`ControlRegistry` call, the config write and the undo step all happen in `applyTrigger`, on the UI thread,
from the 15 ms timer (or from `drainPending()` in a harness). The MIDI thread never touches the registry,
the project or a QString. Races were reasoned about rather than measured - local TSan does not run on this
machine: the queue is the existing single-producer/single-consumer one, the latch sets (`m_controlsHigh`,
`m_commandNotesHeld`) are only ever read and written on the UI thread, and the config arrays are read on the
UI thread like the launcher's already were.

## Known limits

- Only commands whose schema requires **no** arguments are bindable. That is the stage's scope; passing a CC
  value (or a note's velocity) as an argument is a later stage, and nothing here prevents it.
- The controller is the one `session.bindings_connect` opens. Opening a second one for command bindings would
  subscribe two ports to the same events, so the two kinds of binding share the connection deliberately.
- A note or CC can be bound to one command. Two commands on one control is not offered; the closest binding
  (exact channel before any-channel) is the one that answers.
- No MIDI learn for command bindings: the binding form asks for the note or CC number. (The launcher's learn
  is unchanged and still binds launcher actions.)
- Bindings are preferences in the config file, not project data: they are per machine and per user, as the
  launcher's already were.
- The whole-tree manifest (`tests/all-sources.txt`) was re-derived with its own recipe, which also cleared the
  1,148 vendored `plugins/SfzPlayer/sfizz` entries train-12 had left in it; `tests/fork-sources-gate.sh` and
  `feature_check.py` are green.
