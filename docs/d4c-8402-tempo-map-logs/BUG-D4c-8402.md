# BUG-D4c-8402 — an ACTIVATED tempo map was written, then dropped by the reader, so it vanished one save later

Lane: certification-wave-4 fix lane, train worktree `zene-040`, branch `0.4.0/train-w1`.
Base `4b677e20a` (frozen baseline 239/239, 8 gates green). Raw run logs are not landed as `.log`
(Gate 11 refuses them anywhere in the tree); the commands, their unpiped exit codes and the exact
printed lines are recorded here, the shape `docs/bug-fix-2026-09-24-logs/BUG-CTL-4.md` already uses.

## The defect (certification wave 4, seed 8402, `D4c-8402-tempo-map`, reproduced 2/2)

Step 44 of run 8402 called `transport.tempo_map_set_active {"active":true}` — the documented way to
put the timeline under the tempo map WITHOUT editing its events. The saved document then carried

```
<tempo-map max-events="128" active="1" events="0"/>
```

and one `project.open` -> `project.save` later the element was GONE. The delta is outside the
documented per-save strips (`docs/SAVE-CANONICAL-STABILITY.md` section 3/4 cover the `<z:provenance>`
block and its index digest only), so this was silent project-state loss — the BUG-A4-3 class: session
state must survive load -> save -> load.

Evidence, decoded from the sweep's own files under `/tmp/zene-cert-w4-rw/`
(`qCompress` = 4-byte length + zlib):

```
run-8402/tmp/workspace/checkpoint-080.mmpz  -> ['<tempo-map max-events="128" active="1" events="0"/>']
run-8402/tmp/workspace/loadstable-080.mmpz  -> []            # after open -> save
run-8402/failure.json  checkpoint 80: "load_save_load": {"ok": false, first_sha256 927ffadf…, second_sha256 3387001e…}
```

## Root cause: the READER reset the flag the WRITER had just been asked to keep

The writer is right. `TempoMap::saveSettings` (`src/core/TempoMap.cpp:285`) writes the element
unconditionally, and it is called only when the map says it must be:

```
include/TempoMap.h:178   bool shouldPersist() const { return m_active || m_count > 0; }
src/core/Song.cpp:1850   if( m_tempoMap.map().shouldPersist() )          // the only write site
```

So an empty-but-active map IS written — that is the half the sweep saw succeed.

The reader dropped the very state that made the write happen. `TempoMap::loadSettings`
(`src/core/TempoMap.cpp:310`) read the `active` attribute, then undid it for any element whose event
set came back empty:

```
setActive(element.attribute(QStringLiteral("active"), QStringLiteral("0")).toInt() != 0);
…
if (!any) { clear(); }        // <-- clear() also sets m_active = false
```

`clear()` is `m_count = 0; m_active = false` (`include/TempoMap.h:180`). Nothing here is a
"don't serialize empty" optimisation and nothing is in the session/document restore path: the load
goes through `Song::restorePublisherBackedSection` (`src/core/Song.cpp:2363`; the tempo-map branch is
2369-2375), which hands the element straight to `loadSettings`. So the sequence was: load -> map
emptied AND switched off ->
`shouldPersist()` false -> the next save wrote nothing -> the document lost the state for good.
There is exactly one reader and no upconverter for this element.

## The contract the code was breaking

* `docs/TEMPO-MAP.md` section 3: "**the map writes nothing into a project that does not use it.**
  `TempoMap::shouldPersist()` is `active || size() > 0`, and it gates the only write site in
  `Song::saveProjectFile()`."
* `transport.tempo_map_set_active`'s own description
  (`src/core/ControlCommandsTransportMap.cpp:437`): "Switch the tempo map's authority on or off
  WITHOUT editing its events: off, every tick answers the global tempo again and **the stored events
  are still saved with the project**; on, the timeline obeys them. A call that sets the state it
  already has is `invalid_args`." — the same sentence is the row in `docs/CAPABILITIES-0.3.0.md:1266`.
* SPEC A16 (`src/core/ControlReversibilityTableAction.cpp:136`,
  `R("transport.tempo_map_set_active", RC::TrueInverse, true, …)`): the flag is engine-read project
  state, and the recorded undo step "restores the map captured before the switch, so the flag comes
  back with the events" — a flag that does not survive a save is not state an inverse can be honest
  about.

A state the writer persists by contract, and the reader refuses to read back, is exactly the
`shouldPersist()` negation. The fix makes the reader agree with the writer.

## The fix

`src/core/TempoMap.cpp` — `clear()` at the top of `loadSettings` has already emptied the event set,
so an element carrying no event this build accepts degrades to "no events" (the timing path's
global-tempo answer, `docs/TEMPO-MAP.md` section 3) WITHOUT the reader also discarding the authority
the element declares. `shouldPersist()` is the rule for both directions. Behaviour-preserving
otherwise: a map with any event loads exactly as before, and an inactive map stays inactive. No
serialization shape changed, so no golden had to rotate.

## Secondary — the interrupted seed-8403 "D4a candidate": adjudicated a CHECK ARTIFACT

`run-8403` stopped at `code: D4a, "undo did not restore captured pre-mutation state at checkpoint 60"`.
From the recorded steps the only successful mutation since the previous checkpoint is step 58,
`project.save {"path": …/outputs/grammar-current.mmpz}` — the run's FIRST save, to a path that did not
exist (its own reply says `revisions: {count: 0}`). `project.save` is a **file-level snapshot** command
(`src/core/ControlReversibilityTableSnapshot.cpp:73`, `RC::Snapshot`), so the D4a premise — "the latest
mutation moved session state, its undo restores that state" — does not hold for it.

Reproduced directly against the binary (probe: `mixer.add_channel`; snapshot; first `project.save`;
`control.undo`; snapshot):

```
BEFORE: {"file": "", "modified": true, "revisions": {"count": 0, …}, "tempo": 140, "track_count": 4, …}
AFTER : {"file": "", "modified": true, "revisions": {"count": 0, …}, "tempo": 140, "track_count": 4, …}
TOP TX: {"class":"snapshot","command":"project.save","reversible":true,
         "inverse":{"applies":"command","args":{"path":"…/fresh.mmpz","revision":0},"op":"project.restore_revision"},
         "mechanism":"file revision: the replaced file is kept as revision 0 …"}
UNDO  : {"ok": false, "error": {"kind": "not_found",
         "message": "no revision 0 of …/fresh.mmpz (the retained set is reported by project.get_state's revisions)"}}
```

`project.get_state` is IDENTICAL before the save and after the refused undo — no session state was
lost or changed, so the D4a RED is an artifact of the walk reaching a checkpoint whose latest success
was a file-level command.

The probe does expose one narrow REAL finding, reported rather than fixed here (out of this lane's
scope, and it is a single `!refused` flag, not a state-loss bug): `rotateProjectRevision`
(`src/core/ProjectRevisions.cpp:81`) returns early and keeps nothing when the target file does not
exist ("A first save has no previous revision"), but its caller still records
`reversible: true`, `revision_kept: true` and a named inverse `project.restore_revision {revision: 0}`
(`src/core/ControlCommandsProjectFiles.cpp:94-134`) — an inverse that cannot exist on a first save, so
`control.undo` answers the typed `not_found` above. The same `!refused` shortcut drives both fields.
