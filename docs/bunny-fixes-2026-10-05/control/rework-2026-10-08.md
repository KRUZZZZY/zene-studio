## The two-element case (round 6)

On the 0.4.0/train-w1 line, a v="2" section is refused at the version check (train-w1 src/core/ProvenanceSection.cpp:198)
and kept unclaimed (train-w1 src/core/Song.cpp:2301, then the unclaimed walk at Song.cpp:1656, re-emitted at Song.cpp:2009).
If that 0.4 build then records a change and saves, its writeTo emits a NEW v="1" provenance element holding only its own
entries, and the re-emitted v="2" element follows it. The file has two `<z:provenance>` elements, in either order.

On this build, before round 6, both were claimed: Section::load clears and replaces, so the second claim overwrote the
first's entries in memory, and the next save lost them. The fix (702dfd695): the load walk (Song.cpp, the provenance branch
of restoreNamedSection) adopts the first provenance element only; a further one is kept verbatim as unclaimed and re-emitted
byte-for-byte on save. Both chains survive a save and a reload.

Why not a merge: each chain numbers its entries from seq 1, so interleaving them either collides on seq or renumbers
entries, and renumbering changes the identity of each recorded change. Keeping the second element verbatim needs neither.

Limit: the second element is re-emitted unchanged, not appended to. A later save of this build writes its own section
(from the first element's entries and any new ones) next to the unclaimed one, so the file keeps two elements, each with its
own seq chain. That is lossless, not a single chain.

## Round-5 residuals and limits

- **Step-less record residual (traced by the review, not reproduced).** A recorded call that pushes NO journal step
  (a Snapshot-class command with a descriptor, step 0) does not break a coalescing run, because coalescing is only called
  for calls that produced a step. A later press then joins the run's journal step, and `extendForMergedStep` extends the
  newest record, which is the step-less one (its class and reversibility are rewritten, the run's own record is not), so
  control.undo sees a top record with step 0 and refuses. The same class of defect exists for top-level coalesced drags,
  since recordTransactionOf also extends the top record. Fix options: break the run (ProjectJournal/UndoCoalescer breakRun)
  when a recorded call pushes no step, or extend the record whose step equals the run's serial. Not done this round.
- **Burst granularity.** The journal result matches the base burst (one step per burst). The record side is new: one record
  per burst, extended per press (base wrote no record for a burst). "The same journal step, plus a record" is the accurate

## Round-4 decisions and limits

- **Burst granularity (item 1).** A nudge is one wrapper call with one nested clip.move. The wrapper joins that
  call's coalescing run (the clip.move row's key: the clip). A press on a different clip starts a new run, because the
  key differs. Selection changes that do not change the clip do not split a run (the same as the direct clip.move rule).
  A wrapper whose nested calls are two or more never joins a run. A run's record is extended per press (`commands`
  counts presses); its `inverse.children` lists only the first press's children (the journal step covers all presses).
- **Coalescing a nested call (guard).** `mayCoalesce` (ControlRegistry.h / ControlRegistryRecords.cpp) refuses a call a
  wrapper runs, a call a mutating call runs, and a wrapper that joins its nested call's run instead. The guard term for
  mutating calls is not reachable by a current command (no coalescing command is nested in a mutating handler today);
  the test drives it with mixer.set_volume (a coalescing row) inside a test mutating command.
- **Extension of a run.** A merged press extends the previous record's `after` digest and `commands`, and lowers its
  reversibility (and class) if the new press is not reversible. A press with no previous record writes a new record.
- **Provenance (item 3), corrected in round 5.** `<z:change nested="...">` is written only for an aggregate or a merged
  run, and such a section is `<z:provenance v="2">`; a section without nested ids stays v="1". An older build refuses a
  v="2" section at its version check and keeps the element verbatim as unclaimed. The earlier claim here, that an older
  build "refuses the entry" (the strict attribute check, hasOnlySupportedAttributes), holds only for builds that have that
  check. The 0.4.0/train-w1 line does NOT: its loader accepts v="1" entries with any attribute set and rewrote them on
  save, which would have silently dropped `nested`. Round 5 closes that by the version bump, with the evidence lines in
  the round-5 table. No 0.4 build exists here, so the 0.4 side is source-reading only.
- **Contract refinement (item 2 and the test).** The ReversibilityContract test required every coalescing declaration to
  be true_inverse. It now accepts a declaration on a non-mutating wrapper that carries `coalescesWrapped`. This is a
  refinement, with the old assertion still applied to every other row; flagged for owner review.
- **Snapshot (item 4).** The committed tools/mcp-zene-control/zene_control/commands_snapshot.json carries generator
  metadata from the instance it was taken from: `captured_at`, the `lane` path (a worktree path), and `source_socket`
  (a /tmp path). These are the generator's own output, committed as written, and they change on each regeneration.
- **revisions.compare on a zlib-less build (item 4).** Every compressed (.mmpz) revision is reported as unreadable
  (`readable: false`). The projectDocumentText path refuses without zlib (RevisionTimelineCompare.cpp, via
  inflateQtCompressedWithinCap). RevisionTimelineTest's compressed case fails on such a build, by design.
- **revisions.compare tests are output guards, not allocation guards (item 4).** The lying-header case returns empty both
  before and after the change, because the previous code's own post-check also refused it. The small-cap seam checks the
  bound's output. Neither observes the allocation. An allocation regression test would need a counter in the inflate loop
  or a memory measurement; that is the owner's call.
- **R3 (round 3) remains an undoability loss**: the three-level chain's innermost inverse is not composed, and control.undo
  refuses that step. Unchanged.
- **Inherited, unchanged.** src/core/DataFile.cpp decompressesAsRecoverableDocument has the same header-as-bound premise.
- **Windows and macOS.** Unverified until hosted CI prints `zlib found`.

## Decisions and limits (round 3)

- **R2 status.** Round 2 said R2 was fixed on the direct path only. Round 3 closes the held path with a test. Both paths
  now flag the outer or held record reversible:false with the reason. The round-2 claim "R1-R4 closed" is withdrawn in
  favour of the table above; R2 is FIXED on both paths, pending independent review.
- **R3 is an undoability loss, not a fix.** A three-level chain (mutating outer -> non-mutating -> mutating inner) gives ONE
  journal step and ONE record. The innermost change's own inverse is not composed into that record. The record is flagged
  reversible:false, so `control.undo` REFUSES this step (typed irreversible) even though the journal holds the change. An
  agent must use the journal or the GUI undo for it. The mechanism text names the reason but not the nested command's id.
- **R1 undo granularity change.** A mutating call run by a non-mutating wrapper no longer coalesces into an earlier step (a
  drag of the same command on the same target inside a wrapper is now one step per call, merged by the wrapper into one
  step). Calls outside wrappers coalesce as before.
- **R1 aggregate and provenance.** The aggregate writes one `<z:change>` for the wrapper's step; the per-child provenance
  entries are no longer written. Owner to confirm (the aggregate itself was the orchestrator's decision).
- **Snapshot metadata.** Regenerating commands_snapshot.json also rewrote its capture time, version string and `lane` path
  (the generator's own output; the committed file pointed at zene-survey).
- **Z-residual test is not a red.** The pre-change code also returned empty for the over-cap body, because its own
  post-check refused it, so the test passes on both. The change bounds the allocation (the loop stops at the cap); the
  test does not observe memory. Reachability: revisions.compare is a registered NotMutating control verb and reaches
  projectDocumentText (src/core/ControlCommandsRevisions.cpp:224).
- **zlib-less builds are red by design.** With ZENE_HAVE_ZLIB undefined, `ControlProjectArchiveTest` fails its bomb and relink
  cases, and `RevisionTimelineTest` fails its compressed-document case. That is the fail-closed refusal, observed in a
  simulated build (round 2). A configure without zlib shows these reds in ctest, and the configure prints a WARNING.
- **Windows and macOS.** Unverified until hosted CI prints `zlib found`.
- **Inherited, unchanged.** src/core/DataFile.cpp decompressesAsRecoverableDocument has the same header-as-bound premise
  (about lines 240-258). Not changed here.
- **Residual, not demonstrated.** A command-applies inverse that pushes a journal step would have no record. None was
  found in this lane.

## Decisions and limits (round 2)

- **R1 (aggregate record).** Chosen option (a) from the coordinator's brief: one record for the merged step, named for the
  wrapper. Owner to confirm. Side effects, all deliberate:
  - The per-child `provenance` change is no longer written; the wrapper's one `<z:change>` stands for the step.
  - `control.transactions` shows one record for `range.consolidate` over two tracks, not one per track. The
    `ReversibilityTable` row for `range.consolidate` still says "undo each track's clip.consolidate". That text
    is now wrong for multi-track runs; it is NOT changed here (the table is snapshot-sensitive). A docs follow-up.
  - A single nested call keeps its own record, as before.
- **R2 and R3.** A folded nested change is not composed into an outer descriptor. When it is folded, the outer
  record is marked `reversible:false` with the reason. That is conservative: it may hide a reversibility an outer
  command really has. Composition is not implemented.
- **R3 has no separate innermost record.** One journal step gives one record. The innermost change is reported by the flag on the
  outer record, not by its own record.
- **R4.** `control.undo` runs a command-applies inverse through `ControlRegistry::invokeUnrecorded`. Any
  command run from inside that inverse also records nothing.
- **Z2 (fail closed).** Without zlib, `.mmpz` reads are refused before any compressed byte is read. Side effect, not
  fixed here: on a zlib-less build the `relink` of a compressed project is refused too (the round-2
  simulation showed `relinkKeepsTheCompressedFormat` failing). That is the intended fail-closed behaviour.
- **Z3.** `src/CMakeLists.txt` prints STATUS when zlib is found and WARNING when it is not. Windows (MSVC via
  vcpkg, MinGW via `libz-mingw-w64-dev`, MSYS2 clangarm64 via `mingw-w64-clang-aarch64-zlib`) and macOS (SDK zlib, Brewfile
  unchanged) are UNVERIFIED until hosted CI runs. The `Found ZLIB` line must be checked on each job.
- **Cap during inflation.** The zlib loop refuses at the first chunk past the cap (1 MiB scratch). The test proves the
  refusal comes from the loop (the message) and goes red when the loop cap is disabled. It does not measure memory.
- **Growth race.** Both bodies are read through `readBoundedBody` (cap+1 bytes). There is no deterministic test for a file
  that grows during the read.
- **Engine recovery (not changed here).** `src/core/DataFile.cpp` `decompressesAsRecoverableDocument` (about lines 240-258)
  has the same header-as-bound premise. It checks the size only after `qUncompress` returns. This is inherited and outside
  this lane; not changed.
- **Not run.** The full ctest suite. Hosted CI for Windows and macOS.

  unresolved list.
