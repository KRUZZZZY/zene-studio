## Per-item notes

1. **Master guard (`2fa142d5b`).** Round 1 kept master loading and refused negative numbers.
   Round 2 found that `toInt()` without a success flag returns 0 for a missing or non-numeric
   `num`, which then overwrote the master. The main load pass now skips any element whose `num`
   does not parse or is negative. The bus pre-pass still rejects zero. The round 2 test
   covers a missing `num`, a word `num`, an empty `num`, and a bus marker on the malformed element.

2. **Solo walks (`4d50f628b`).** Each walk direction has its own visited set
   (`include/Mixer.h`, `src/core/Mixer.cpp`). Independent review traced the counterexample through
   the new code and found it correct. Related: `MixerStripTest` exit 0.

3. **Sidechain amount (`f1a74cc54`, `0cfcbfa14`).** Round 1 replaced the sidechain read with a
   lock-free `publishedValueAt()` that served only a published ramp. Review found this changed
   behaviour for controller-driven and manually changed amounts, which the original
   `valueBuffer()` read honoured. Round 2 restored the `valueBuffer()` read exactly as at
   `4218c1e30` and removed `publishedValueAt`.
   **Status: BLOCKED-ON-2647.** The lock in `valueBuffer()` (`src/core/AutomatableModel.cpp`,
   `QMutexLocker` on `m_valueBufferMutex`) is called on the audio thread from the sidechain read and
   from the regular-send paths at `src/core/Mixer.cpp:526` (volume), `:624` (send) and `:784` (pan).
   It is pre-existing and mixer-wide, and it is tracked as cluster 2647. It is not fixed here.
   The two behaviour tests pin the per-frame behaviour: the controller-driven test uses an
   `LfoController` attached through `ControllerConnection`, and it ends a period first
   (`Controller::triggerFrameCounter()` and `AutomatableModel::incrementPeriodCounter()`), because
   the LFO fills its buffer once per period. Without that, the buffer stays at its constructor fill
   of 0.5 and the test is a false red.

4. **Batch-07 report (`480fd367e`).** Corrected in `eac373106` and then `bfbdc0bdd`: the 4288
   fix now includes the round 2 guard, and 5156 states that no lock fix is on the tree.

5. **Snapshot recall boundary (`1e1ccd541`).** `applySends()` writes each send inside
   `requestChangesGuard()`, the boundary `Mixer::createChannelSend()` uses for an existing route.
   Recall and undo/redo both reach it. Independent review: no nested guard or deadlock found.
   Related: `ProjectStateTest` exit 0.
   Open note: `applyChannel()` writes volume, pan, mute and solo with plain `setValue` and no
   guard. Those are model writes, not plain render-read fields, so this item leaves them as they are.

6. **Batch-09 report (`2e3ee5581`).** Corrected in `d810b6ff3`: recall lacked the boundary until
   `2ef8d233c`.

7. **Content table churn (`390ec761c`).** `SessionSlotContentTable::install()` removes an entry
   when its cell loses its pattern. The last entry moves into the hole, and the count drops. This
   is a bounded move over fixed storage, on the audio thread, with no allocation and no lock. The
   header and the thread comment are corrected. Independent review: ACCEPT.
   Related: `SessionPlaybackRenderTest`, `SessionModelTest` exit 0.

8. **Linked clip trim and split (`4218c1e30`).** **Status: BLOCKED-OWNER-DECISION.**
   `clearNotesOutOfBounds()` and `destructiveSplitClip()` build their clones under
   `ClipLinks::MirroringSuspension`, so the group's other members keep their notes. The
   original loss of notes is therefore fixed. The clone still keeps the source's `linkId` and
   joins the group, which the `ClipLinks.h` invariant does not allow. An owner decision is
   needed on whether a trimmed or split half should unlink, or propagate to the group.
   - Invariant: `include/ClipLinks.h:138-141` states that members are written in sync.
   - Trim: `src/gui/clips/MidiClipView.cpp:394-416`. The trimmed clone stays in the group. Any
     trim that removes or shortens a note leaves the peers untrimmed, so the group disagrees.
   - Split: `src/gui/clips/MidiClipView.cpp:907-944`. Both halves join the group with different
     notes. The peers keep the whole, unsplit notes.
   - Test: `tests/src/gui/MidiClipLinkedEditTest.cpp` uses only in-bounds notes (both inside the
     one-bar clip), so the trim changes nothing and the test cannot detect the divergence. The
     test covers the note loss, not the group invariant.
   - Split: `destructiveSplitClip` is private and reached only through a knife-mode mouse
     release. No test drives it.
   Related: `ClipLinkTest`, `ClipLinkPersistenceTest` exit 0.
