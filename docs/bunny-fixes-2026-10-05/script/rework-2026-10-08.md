## 51e7da51f — FIXED

The original test could only SKIP, because this build loaded no effect module. The fix does three things:

1. `applyRemoveEffect` (`src/core/ScriptDawEdit.cpp`) journals the removal with `control::journalEffectRemoval`
   before the removal, as `plugin.unload` does. If the device cannot be captured, the device is still removed (as
   the script asked), and the log says the removal is not undoable. No undo step is claimed in that case.
2. The first version of the fix did not pass. Emptying a chain runs `m_enabledModel.setValue(false)`
   (`src/core/EffectChain.cpp`, `removeEffect`), which pushes a checkpoint after the structural step. One
   `journal->undo()` only reverted the enabled flag. The fix now folds the removal's checkpoints into one step with
   `mark = undoDepth()` and `mergeCheckpointsFrom(mark)`, the same mechanism the control registry uses.
3. The test loads the build's BassBooster module: `tests/src/core/ScriptDawBindingTest.cpp` sets
   `LMMS_PLUGIN_DIR` from `LMMS_TEST_PLUGIN_DIR` (as `RackMenuTest` does), and `tests/CMakeLists.txt` adds the
   test to the list that defines that directory. The test now runs (verified with `./ScriptDawBindingTest -v2`:
   PASS, 8 passed, 1 skipped for an unrelated amplifier case).

## Round 7 — the device load runs outside the audio change lock

**Relabel.** The round-5 entry "Restore of a disabled chain's flag outside the audio change lock: FIXED (source-derived,
not measured)" is wrong in two ways. The round-5 undo took the change lock before the device was built, so the plug-in
load ran under the lock. The render thread takes the same lock every period, so rendering stalled for the whole load.
That is a realtime-rule violation. The label now reads: REWORK in review (round 6), FIXED in round 7 (below), with the
load proven outside the lock by a timing test.

| Item | Verdict | Commit | Evidence |
| --- | --- | --- | --- |
| The recorded device's plug-in load ran under the audio change lock (undo closure) | FIXED | b8e3ad07e | `aRecordedDeviceIsBuiltWithoutTheAudioChangeLock`: red 8 (building the device waited 2999 ms for the lock, limit 1500), green 0 |
| The undo closure's order: device built before the lock | FIXED, structural | b8e3ad07e | the closure calls `instantiateRecordedDevice`, then takes `requestChangesGuard`, then `attachRecordedDevice` and `setEnabledUnjournalled`. The timing test covers the function the closure calls first; the closure's order is read from the code, since no hook observes the closure itself |

**What changed.** `recreateEffectFromState` is split. `instantiateRecordedDevice` validates the recorded document and
loads the device, and it takes no lock. `attachRecordedDevice` appends the device, restores its position and settings,
and cleans up on failure. `recreateEffectFromState` is the composition of the two, for its other callers in
`ControlDeviceMoves.cpp`; those callers take no lock of their own, so their load already ran outside it. They now take
the lock for the attach. The undo closure builds the device first, then takes the change lock once for the attach and
the enabled-flag restore. The attach stays under the lock, so the lock covers the append, the placement, the settings
restore and the flag. I did not add a separate `EffectChain` method; the lock bracket in the closure does the same job
and nests with `appendEffect`'s own lock, which is recursive.

**Test.** Another thread holds the change lock for three seconds, and the test builds a recorded device on its own
thread. The build must return in under 1.5 seconds. The timing test proves the load does not wait for the lock. It
does not observe the closure directly, because no hook in the product reports whether the lock is held.
