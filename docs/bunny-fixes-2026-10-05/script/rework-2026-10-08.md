## 51e7da51f — FIXED

The original test could only SKIP, because this build loaded no effect module. The fix does three things:

1. `applyRemoveEffect` (`src/core/ScriptDawEdit.cpp`) journals the removal with `control::journalEffectRemoval`
   before the removal, as `plugin.unload` does. If the device cannot be captured, the device is still removed (as
   the script asked), and the log says the removal is not undoable. No undo step is claimed in that case.
2. The first version of the fix did not pass. Emptying a chain runs `m_enabledModel.setValue(false)`
   (`src/core/EffectChain.cpp`, `removeEffect`), which pushes a checkpoint after the structural step. One
   `journal->undo()` only reverted the enabled flag. The fix now folds the removal's checkpoints into one step with
   `mark = undoDepth()` and `mergeCheckpointsFrom(mark)`, the same mechanism the control registry uses.
3. The test loads the build's BassBooster module: `tests/src/core/ScriptDawBindingTest.cpp` sets
   `LMMS_PLUGIN_DIR` from `LMMS_TEST_PLUGIN_DIR` (as `RackMenuTest` does), and `tests/CMakeLists.txt` adds the
   test to the list that defines that directory. The test now runs (verified with `./ScriptDawBindingTest -v2`:
   PASS, 8 passed, 1 skipped for an unrelated amplifier case).

**1 (committed, 82146d0c4).** `ProjectJournal::mergeCheckpointsSince(serial)` names the window by serial. It folds
every step pushed after the newest step whose serial was taken before the removal. `applyRemoveEffect` uses this
with `topStepSerial()`. The test fills the undo stack to a cap of 8 with a sentinel step on top, runs a script that
loads and removes a device, and checks that one undo restores the device and the enabled flag while the sentinel
stays at 0. Red with the index mark: exit 8, actual 0, expected 1. Green with the serial mark: exit 0.

**2 (BLOCKED).** Refusing a removal when `journalEffectRemoval` fails is the behaviour the reviewer asked for. It
has no test in this build: no loaded device can produce a state over `StructuralSnapshotLimit` (65536 bytes), and
the test seam would be a product change. Because the brief forbids committing a code change without a red/green
test, it is not committed. The committed code still removes the device and logs "not undoable". If the chain is not
emptied, Ctrl+Z then reverts the previous, unrelated step. The owner needs to decide on the refusal.

**3a (BLOCKED on red proof, not committed).** The fix uses `control::recordedChainFinder` for `LuaEffect` (the
wrapper stores a finder, not a raw `EffectChain*`), so a removed channel makes the wrapper read as gone. The fixed
tree is green (`ScriptDawBindingTest` exit 0, 10 passed, the new case PASS). Without the fix the case also exits 0.
The reason: `Mixer::deleteChannel` frees the channel with `delete ch` (src/core/Mixer.cpp, near line 1195). The stale
read then finds nothing in freed memory, so the assertions pass by accident. No valgrind is installed, and an
ASan build is not practical on this disk. The patch is saved outside the repository. A deterministic red needs a
sanitizer build, or a test seam that keeps the freed chain readable.

**3 scope left open.** The same raw-pointer pattern remains in `LuaEffectChain` (`ScriptDawBindings.h:176`,
`ScriptDawEffects.cpp:81-91`), `LuaMixerChannel` and `LuaTrack`. Queued commands still hold raw `object0` pointers.

**Index-mark pattern in the registry (not changed, to track).** `src/core/ControlRegistry.cpp:323` and `:337` take
`mergeCheckpointsFrom(mark)` with an index-based mark. The same eviction defect as finding 1 applies there.
`mergeCheckpointsSince` is the fix to adopt. The registry is outside this lane.

**4 (REAL-UNTESTED, no code change in this lane).** The local fix is to re-read the memory base after `callProcess`
and before the output read, in both `processSlot` (`src/wasm/WasmWorker.cpp`, the pointer cached near 213 and read

**Residual (FIXED, 63f8844d2).** The emptied chain's enabled flag used to be journalled as its own checkpoint,
pushed after the structural step. Under a cap of one step that checkpoint evicted the structural step. The flag
write is now not journalled during the removal, so the removal pushes exactly one checkpoint. The undo re-appends
the device, and appending switches the chain on again (`EffectChain::appendEffect`, `src/core/EffectChain.cpp:207`).
The cap-8 test still passes.

**Known residual of that fix (read from the code, not run).** A chain that was switched off before the removal comes
back switched on after the undo, because the restore re-appends the device. The plugin path has the same restore;
it avoids the difference only because it journals the flag as a second checkpoint.

**Capture refusal: OWNER-DECISION.** Refusing a script's removal when `journalEffectRemoval` fails is the
behaviour the reviewer recommended. It is a behaviour change: a script that removes a device whose saved state is
over 64 KB (`StructuralSnapshotLimit`, `include/ControlStructuralSupport.h:83`) would be refused. Until the owner
decides, the committed code removes the device and logs "not undoable", so Ctrl+Z can still revert the previous
unrelated step when the chain is not emptied. A test is possible in one of two ways: a device whose saved state
exceeds the limit (none is loadable in this build), or a minimal test seam that lets a test set the limit. Either
needs a decision before code is written.

**LuaEffect raw chain pointer: REAL-UNTESTED.** The fix (the wrapper stores `control::recordedChainFinder` instead of
a raw `EffectChain*`) is parked in `research/reviews/m0-2026-10-08/` in the program root, not in this worktree. It is
green with the fix. Without the fix the test also exits 0, because `Mixer::deleteChannel` frees the chain with
`delete ch` (`src/core/Mixer.cpp`) and the stale read happens to find nothing. A deterministic red needs an ASan
build, which this machine cannot run in practice. The same raw-pointer pattern is in `LuaEffectChain`
(`include/ScriptDawBindings.h:176`, `src/core/ScriptDawEffects.cpp:81-91`), which the parked patch does not touch.
