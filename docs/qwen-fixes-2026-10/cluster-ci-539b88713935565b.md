Evidence (untrusted log, read as data only):
`/home/kruzzzzy/.local/share/zene-bunny-fix/qwen/train-ci/c20ef591b571e3c3dc7b108107d166497f1b34be/run-43611324689-job-132496796731.log:5134,5138,5142`.

Classification: **product/test portability defect** — a fork-new test used a Qt factory that the
platform's Qt is configured without. Not infrastructure (the job's configure, dependency install
and the other ~1,800 compiled objects were clean) and not a flaky/skipped test (this job runs no
tests; the build is the gate).

## Cause (file:line)

`.github/workflows/deps-ubuntu-24.04-mingw.txt` installs `qt5base-mingw-w64` from the pinned
tobydox PPA, and the `mingw64` job in `.github/workflows/build.yml:829` configures with
`cmake/toolchains/x64-mingw-vcpkg.cmake` (no `-DWANT_QT6`, so Qt 5 — `CMakeLists.txt:363-365`).
The PPA package is **Qt 5.15.6** and its `QtCore/qtcore-config.h:15` carries

```
#define QT_FEATURE_cxx11_future -1
```

so Qt's own `qthread.h` compiles its factory out (`QThread` has no `create`):

* `qthread.h:50` `#if QT_CONFIG(cxx11_future)` — the `<future>`/`<functional>` includes
* `qthread.h:120-128` — the only declarations of `static QThread *create(...)`
* `qthread.h:161` and `:169-237` — `createThreadImpl` and the definitions

That is the whole of the diagnostic: on that Qt the name does not exist, on the Qt 6 build used
here it does, so only the cross job sees it. The PPA `Packages.gz` (fetched 2026-11-14) states
`qt5base-mingw-w64 5.15.6-1`; the package's `qtcore-config.h` was extracted and read. The feature
value was also reproduced directly: a two-line probe with `QThread::create()` compiles against
this box's Qt 5.15.19 (`QT_FEATURE_cxx11_future 1`) and fails with the job's exact message against
the PPA header (exit 1).

Sources at HEAD, all four in test code:

* `tests/src/gui/Warp/SampleClipWarpEditTest.cpp:433,463,551` (the job's three errors). This file
  is fork-NEW (`tests/fork-sources.txt:2343`).
* `tests/src/core/WarpMarkersTest.cpp:131` — the same defect one target away. That TU had only
  reached its autogen step when the job died (`run-...log:4367`, `Built target
  WarpMarkersTest_autogen`); its source was never compiled, and compiling it here against the
  PPA-configured Qt 5 fails identically (row 2). It is an inherited file the fork already declared
  in the divergence ledger (`tests/upstream-modifications.txt:5779`).

`grep -rn 'QThread::create' src include plugins` finds no product use (only the commented-out
workaround in `plugins/SpectrumAnalyzer/{Analyzer.h,DataprocLauncher.h}`, which exists for exactly
this reason: "QThread::create() workaround for older Qt version"). The defect is in the two tests.

## Fix (at the cause)

1. **`tests/src/core/TestWorkerThread.h` (new, 65 lines).** A `QThread` subclass whose `run()`
   calls a `std::function<void()>` — what `QThread::create()` is, minus the `std::async` plumbing.
   `start()` and `wait()` are unchanged, so call sites keep their shape and their assertions.
   Registered in `tests/fork-sources.txt` and `tests/all-sources.txt`.
2. **`tests/src/core/WarpMarkersTest.cpp:55,132`** and
   **`tests/src/gui/Warp/SampleClipWarpEditTest.cpp:68,434,464,552`** use it:
   `std::unique_ptr<test::TestWorkerThread> x = std::make_unique<test::TestWorkerThread>([&] { ... });`
   No behaviour change: the body still runs on its own thread, `start()`/`wait()` still bracket it.
3. **`tests/qt5-worker-thread-check.py` (new, ctest `Qt5WorkerThreadCheck`,
   `tests/CMakeLists.txt:9155-9175`).** Two deterministic halves:
   * it scans every tracked first-party source for `QThread::create`, so it is **red on this Qt 6
     host too** (comment/literal-stripped, self-tested against a flagged fixture and an unflagged
     subclass);
   * when `pkg-config` finds a Qt 5 tree it takes the affected translation units' own command
     lines from `compile_commands.json`, strips the Qt 6 include paths, prepends a **shadow**
     `QtCore/qtcore-config.h` with `QT_FEATURE_cxx11_future -1`, and compiles them with Qt 5's
     `moc` — the hosted job's own configuration, which is what makes the failure reproducible
     without a Windows cross toolchain.
   Three controls keep the simulation honest: the shadow must reject a `static_assert`
   on `QT_CONFIG(cxx11_future)` (so the feature really is off), the old spelling must **not**
   compile under the shadow (so the fixture can fail), and the old spelling **must** compile on
   the host Qt where the feature is on (so the shadow, not the fixture, is the cause). Where the
   host has no Qt 5 tree at all the compile half reports SKIP and never PASS, and the scan still
   runs.

Callers and siblings checked: `QThread::create` appears nowhere else in `src/`, `include/`,
`plugins/` or `tests/src/` (7 hits in the tree: the 4 fixed, 2 comments and one comment-only
reference in `tests/reference/`, which is a frozen upstream copy and outside every scope).
`Tests/src/core/WarpMarkersTest.cpp`'s only other thread API is `QThread::msleep`, which is not
feature-gated. The other features the PPA's Qt disables (`gestures`, `statemachine`,
`qeventtransition`) were audited: `QGesture`/`QPinchGesture` occur only in `src/gui/ArrangerAids.cpp`
(already guarded, cluster ci-017caf2edd434b66) and no `QStateMachine`/`QEventTransition` occurs in
first-party code. Both affected TUs also compile under a shadow with all four features off.

## Self-check

* **The regression FAILS with the product change reverted and PASSES restored.** Reverted (row 2):
  ctest `Qt5WorkerThreadCheck` EXIT=8, the hosted diagnostic reproduced at all four sites. Restored
  (row 4): EXIT=0, 1/1 passed. The revert/apply commands and their exit codes are rows 2-3.
* **The test is deterministic.** No wall clock, no sleep, no race. The seam is Qt's own
  configuration file: the shadow `qtcore-config.h` sets `QT_FEATURE_cxx11_future -1`, exactly what
  the PPA package ships, and the compiled translation units are the checked-in sources with their
  recorded flags. Nothing in the check depends on timing; `compiled` vs `not compiled` is the whole
  verdict, and the three controls make a "passes for the wrong reason" visible.
* **The fix is at the cause and complete.** Every `QThread::create` occurrence in the tree was
  enumerated (4 real, 3 comments), all four are fixed; the product has none. The portable header is
  used by both TUs, and its own positive compile is asserted under the shadow. The other features
  the hosted Qt disables were audited (gestures already guarded; no state-machine use) and both TUs
  also compile with all four features off.
* **No collateral damage.** No product source, no command, no serialisation and no audio path is
  touched — only two test files (their assertions and thread bodies are unchanged), a new test
  helper, a new ctest and the two manifests. Old projects and saved data are not read or written by
  anything here. The new check adds no limit that any other caller must satisfy.
* **Realtime / undo / commands.** Nothing in this diff runs on the audio thread: it is test code
  (two QTest binaries, a Python source-and-compile check) and registration. No `ControlCommands*`
  file changed, no new command, no reversibility row, so the command snapshot and canary are
  unchanged. The warp suites' existing single-undo-step assertions still pass (row 6).
* **The GUI test still drives the real view.** Unchanged: `SampleClipWarpEditTest` keeps its
  `QTest::mousePress`/`mouseRelease` path and its `warp.move` assertions; this fix only changed how
  its helper thread is started.
* **Portability direction.** The fix removes the only Qt-5-feature-gated API from first-party test
  code; nothing new was added that needs a guard. MSVC/macOS are not affected by
  `QT_FEATURE_cxx11_future` (their Qt ships with the feature on) and the portable header is plain
  `QThread` + `std::function`, which both compile.
* **Log folder.** The designated folder is not writable in this session (see the evidence table);
  the logs are in `build/qwen-logs/` and mirrored to the harness-writable
  `/home/kruzzzzy/.local/share/zene-bunny-fix/dsh/home/ci-539b88713935565b-logs/`.
