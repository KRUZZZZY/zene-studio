## The regression test

`tests/Qt5QFileInfoDateCheck.py`, registered as CTest `Qt5QFileInfoDateCheck`
(`tests/CMakeLists.txt`, beside the other Qt 5 portability checks), registered in
`tests/fork-sources.txt`.

The defect is invisible on a Qt 6.12 host, so the test does not trust this box's
headers. It compiles each candidate translation unit through its **own**
`build/compile_commands.json` command line against a QtCore/qfileinfo.h (and
qdirlisting.h, which `<QDir>` reaches on Qt 6) in the failing shape: the two
QDateTime/QTimeZone includes removed, `QDateTime` forward-declared and the accessors
declared out of line — the exact Qt 5 header shape, derived from the real header so it
cannot drift. On a Qt whose real header already has that shape (the hosted Qt 5 jobs)
it uses the real header and builds no shadow. Test translation units get their own
`.moc` from the build's moc, as automoc does.

Three properties keep it from being a tautology:

* a known-bad fixture (date accessor, no `<QDateTime>`) must be **rejected with the
  CI's own QDateTime diagnostic** before any product file is judged — the run prints
  whether it was;
* a known-good fixture (same code with the include) must compile;
* a translation unit that does not build on this host for an unrelated reason is
  reported SKIP; a baseline compile whose diagnostic is the CI's own - an **incomplete
  QDateTime** - is FAIL, never SKIP. On the failing Qt 5 / macOS Qt 6 header shape
  nothing supplies QDateTime, so that error is raised by the *baseline* compile: the
  sweep would have passed while the hosted job was red, which is the hole the first
  review found (`tests/Qt5QFileInfoDateCheck.py:288-290` at `035e3bcae9`). The
  classifier is proved by a self-test on synthetic compiler output both ways: the two
  spellings of the incomplete-type error (clang's "calling 'lastModified' with
  incomplete return type" and gcc's "invalid use of incomplete type") are FAIL, while an
  unrelated compiler error, a missing-header error and a different QDateTime error
  (e.g. no matching `QDateTime::fromString`) remain skippable.

The registered test sweeps **twice** where a Qt 5 development tree exists: once through
this build's Qt 6 headers with the shadow shape, and once against the real Qt 5 root
(`pkg-config --variable=includedir Qt5Core`, overridable with `--qt5-root`), with every
recorded Qt 6 include root rewritten to its Qt 5 counterpart. The second sweep is the
hosted configuration itself: there the failing translation unit's BASELINE compile says
`invalid use of incomplete type 'class QDateTime'`, and the test now fails on it.

It needs no second toolchain, no network, no clock: the only inputs are the recorded
compile commands, the real Qt headers and the fixtures.

## Rework after the round-1 review

The review's one blocking item was `test-proves-nothing`: at `035e3bcae9` the harness
returned SKIP on **any** failed baseline compile
(`tests/Qt5QFileInfoDateCheck.py:288-290`), so on the hosted Qt 5 header shape —
where the incomplete-QDateTime error is raised by the baseline compile itself — the
affected translation unit would have been skipped and the test would have passed while
the CI job failed. Fixed here:

* `baseline_verdict()` (`tests/Qt5QFileInfoDateCheck.py:315`) classifies a baseline
  diagnostic that is the CI's own (an **incomplete QDateTime**, either compiler
  spelling) as FAIL and keeps every other baseline failure non-fatal. `date_diagnostic()`
  (`:189`) is the single classifier used for both the baseline and the strict compile.
* `self_test()` (`:329`) proves both directions on synthetic compiler output before the
  sweep: clang's and gcc's incomplete-QDateTime spellings FAIL, while a missing-header
  error and an unrelated QDateTime error stay skippable. A failure there exits 2 without
  touching a single product file.
* The registered test now also sweeps through a **real Qt 5** tree when one is installed
  (`toolchains()` at `:450`; `--qt5-root`, `QT5_INCLUDE_DIR`, or `pkg-config
  --variable=includedir Qt5Core`), rewriting every recorded Qt 6 include root to its
  Qt 5 counterpart. On this box that second sweep goes through `/usr/include/qt`; with
  the product include reversed its BASELINE compile says `invalid use of incomplete type
  'class QDateTime'` and the test fails on it (proof below). On a host with no Qt 5 tree
  the second sweep is simply absent and the shadow sweep remains the check — the same
  conditional form the Qt 5 signal-overload checks use.

## Rework after the round-2 review

Two blocking items, both in the test harness rather than the product:

1. **`ci-compile` — the check could not run under MSVC.** `.github/workflows/build.yml`
   runs CTest on `msvc-x64`, and the harness hardcoded `-fsyntax-only` for both the
   translation-unit and the fixture compiles. Every compile now uses the configured
   compiler's own switch through `switch(compiler, msvc, other)`:
   `-fsyntax-only` for gcc/clang, **`/Zs`** for `cl.exe` and `clang-cl`, with `/I` and
   `/std:c++20` alongside. `tests/CMakeLists.txt` passes `--cxx ${CMAKE_CXX_COMPILER}`,
   so the registered test builds with the job's own compiler rather than a `c++` from
   PATH. Windows support is no longer incidental: `split_command()` parses a recorded
   MSVC line with quoted `C:/Program Files/...` paths and escaped quotes,
   `substitute_paths()` rebases `\`-separated include roots case-insensitively (and
   `include_dirs()` reads `/I path`, `/Ipath` and `/external:I`), and `errors_of()` reads
   MSVC's **stdout** diagnostics, not only stderr. The classifier accepts all three
   spellings of the CI's error (clang "incomplete return type", gcc "invalid use of
   incomplete type", MSVC `C2027 use of undefined type`).
2. **Red proof lost — the QA negative control could not find the test.** `negctl.prove()`
   pairs a changed `tests/` file with the CTest test of the **same stem**
   (`tests/<stem>.py` → `<stem>`). The script was `qt5-qfileinfo-date-check.py` while the
   test was `Qt5QFileInfoDateCheck`, so the control reported "no ctest test matched the
   changed tests (qt5-qfileinfo-date-check)" and the whole verification was discarded.
   The script is now **`tests/Qt5QFileInfoDateCheck.py`**, the same stem as the
   registration (which is unchanged: `add_test(NAME Qt5QFileInfoDateCheck ...)`), and the
   report names the test in its `ctest -R` evidence. Running `negctl.prove()` on the
   committed branch with **no report text** now resolves the test by stem
   (`"tests": ["Qt5QFileInfoDateCheck"]`), which is what the control asks it to do.

`self_test()` proves the new paths before any product file is judged, on every host:
the Windows parse (quoted paths, escaped quotes), the include rebase, the `/Zs`,
`/I`, `/std:c++20` switches for `cl.exe` and `clang-cl` versus `-fsyntax-only` for
gcc/clang, an MSVC compile line losing `/Fo` and `/c` and gaining `/Zs` and a Qt 5
include root, the MSVC fixture command line, and all three diagnostic spellings plus the
