FIXED - cluster ci-b5ac4280f3e4b317: `ImportTrackIoTest.cpp` assigned a brace list to a `QStringList`, which Qt 5 rejects as ambiguous

Verdict: **FIXED (REAL, test-source portability defect)**. The hosted
`build / macos-arm64` job builds against Homebrew Qt 5.15
(`/opt/homebrew/opt/qt@5/lib/QtCore.framework/Headers/qstringlist.h:111-127`), whose
`QStringList` declares `operator=(const QList<QString> &)` and
`operator=(QList<QString> &&)` beside its own copy/move assignments. A
brace-enclosed list can initialise either `QStringList` or its `QList<QString>`
base, so all four candidates are viable and overload resolution is ambiguous.
The failure is in a first-party test source, not in CI infrastructure and not a
product runtime bug: `zene` itself never assigns a brace list to a `QStringList`.

`tests/src/core/ImportTrackIoTest.cpp:344` is

overloads, so this box's Qt 6 build compiles the identical line - which is why
only the Qt 5 job failed.

## The fix

`tests/src/core/ImportTrackIoTest.cpp:344`, one line - name the type the list
initialises, which is the portable spelling on both Qt versions:

```cpp
plan.documents = QStringList{UnparsableTrack, trackDocument(Lead)};
```

The value and the behaviour are identical; the test still builds the same plan
and asserts the same thing. No product code, command, undo path, audio-thread
path or save format changes.

**Completeness.** Every ambiguous form was searched tree-wide with the new
scanner (which resolves the assigned name to its declared type, not just its
name): exactly one occurrence, this line (`scan-2-tree-red.log`). As an
independent second check, every first-party translation unit that contains a
brace initialiser (`= {`) - 820 of them - was compiled against the real Qt 5.15
headers through its own recorded command line; none of the 820 produces the
ambiguous-assignment diagnostic (`sweep-2-qt5-all-brace-files.log`,
`DONE ambiguous 0 of 820`). Other occurrences of `= {` in the tree are
declarations that already name the type (`const QStringList names = {...}` -
these construct, they do not assign), or `QList<QString>`/other container
assignments, which have no extra overloads on Qt 5 and are covered by that
sweep. The one exception the sweep cannot judge -
`plugins/CarlaBase/carla/.../qsafesettings.hpp:58` - is inside the
`plugins/CarlaBase/carla` git submodule (`git ls-files` reports only the
gitlink), is not part of this repo's sources nor of its manifests, and its
`QStringList defaultValue = {}` is a parameter default (a construction), not an
assignment.

## The regression test

`tests/Qt5QStringListBraceCheck.py`, registered as CTest
`Qt5QStringListBraceCheck` (`tests/CMakeLists.txt`, beside the other Qt 5
portability checks) and registered in `tests/fork-sources.txt`. The file is
named after its ctest so a selection by name finds it.

It has two halves:

* **A source scan** (authoritative, no Qt needed, so it is red on this Qt 6
  host): it strips comments, literals and preprocessor lines, indexes every
  class member declared as a `QStringList` across the tree, and resolves each
  `x = {...}` / `obj.member = {...}` / `obj->member = {...}` / `(*p).member = {...}`
  / `*p = {...}` / `this->member = {...}` to its declared type. An assignment to
  a `QStringList` is reported; a declaration/parameter default
  (`QStringList x = {...}`), `x += {...}`, an explicitly typed
  `x = QStringList{...}` and `QList<QString> x; x = {...}` are not.
* **A compile probe** when a Qt 5 tree is installed: it compiles the failing
  shape and the fixed shape with the configured compiler, requiring Qt 5 to
  reject the first and accept the second. Without Qt 5 it prints
  `probe: skipped` (never `passed`).

Before scanning, the file runs its own red/green fixtures (an assignment to a
local, a member through `.`, `->` and a dereferenced pointer through a
header-declared struct, and every portable spelling), so a scanner that cannot
fail fails.
