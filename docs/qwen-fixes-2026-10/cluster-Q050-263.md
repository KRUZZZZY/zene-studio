known limits: `docs/050-features/Q050-263.md`. Logs below are in

- **Every acceptance criterion proven by a test I ran:** see the table; exit 0 each.
- **One undo step per edit; honest reversibility:** `plugin.slice_set` is `true_inverse` (Track checkpoint through `addUndoStep`), `plugin.slice_get` is `not_mutating`; the panel test undoes one panel edit and sees the other two edits stay; refusals leave the undo depth unchanged (`badCallsAreRefusedAndTheContractIsStated`). `ReversibilityContractTest` passes with the new rows.
- **Audio thread:** new audio-thread code is `SlicerT::applySliceControls` (called from `playNoteImpl`) and, in `acquirePlaybackSlot`, a `fetch_add` on an atomic counter, two `unitHash` calls and a plain struct assignment into the note's own slot. Per period they do four relaxed atomic loads, `std::tan`/`std::pow`, multiply-adds over the period's frames and one filter state in the slot; no allocation, free, lock, wait, I/O, Qt call or signal. The values the control thread writes are relaxed atomics (`m_sliceControls`); `dataChanged` is emitted only from `setSliceControl`/`loadSettings`/the waveform handlers on the GUI/control thread. Local TSan does not run on this box; the reasoning is in the feature record's Known limits. `sliceMerged`/`sliceSplit` run on the GUI thread like the pre-existing slice-point edits.
- **Old projects:** `loadSettings` resets every control and reads the new attributes only when present; `saveSettings` writes an attribute only for a non-neutral value; `applySliceControls` returns before touching the block when all four are neutral, so an untouched slice renders as before. Measured: `neutralSlicesRenderTheSampleAndOldStateLoadsNeutral` (neutral slice level within 2 % of the sample; state without attributes loads neutral; an untouched SlicerT saves no `sliceGain_` attribute), `valuesSurviveSaveAndReopenAndReadBack` (round trip). Not measured: a bit-exact comparison against a binary built from the base - the neutral path is an early return, but I did not render the same project with both binaries.
- **Portability:** no Qt-6-only API (`QOverload<...>::of`, `QMetaObject::invokeMethod` with `Q_RETURN_ARG`, `QDomElement::setAttribute(QString, float)` all exist in Qt 5.15); `std::numbers` is already used by `include/BasicFilters.h`; no `min`/`max`/`near`/`far` identifiers (the spec fields are `lowest`/`highest`; a gate-adjacent rename after review of my own diff); no `std::filesystem`, no POSIX calls. Not built on Qt 5.15, MSVC or macOS here: unverified.
