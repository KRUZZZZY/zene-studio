# Design: linked clip windows and contained crossfades

Base: `888934e1b` (`bugs/m0-decisions-r3-clips`), per the 2026-10-09 owner ruling.

## 1. Linked MIDI clips

**Problem.** The 2026-10-08 implementation makes trim and resize group operations and cuts every member on split: `include/LinkedClipEdits.h` and `src/core/LinkedClipEdits.cpp`; `clip.trim` and `clip.resize` call those helpers in `src/core/ControlCommandsClipTrim.cpp` and `src/core/ControlCommandsClip.cpp`; `arrangement::splitClipAt` and VCA edit paths also fan geometry out. `ClipView.cpp` checkpoints and propagates edge drags, while `MidiClipView.cpp` group-splits a destructive knife gesture and rebases peers during clear-notes-out-of-bounds. The current link contract also says name and colour are per-member (`include/ClipLinks.h`, `docs/LINKED-CLIPS.md`), and `clip.link_remove` is the only detach action. The 2026-10-09 decision reverses group geometry propagation: notes, name, and colour are shared; each clip instance owns its timeline position, length, source window and loop window.

**Design and invariants.** Keep the persisted integer group id and per-clip note lists. Retain the existing note mirror; mirror name and colour when a linked MIDI clip is edited, and adopt the anchor's presentation when creating or explicitly syncing a group. All these writes and checkpoints occur on the GUI/control thread. A trim, resize, slip, or loop edit mutates only the named instance. A split mutates only the selected instance: `arrangement::splitClipAlone` clones its content and link id, and both resulting windows remain in the original group; no new group id is allocated. Range and loop slicing split only clips their caller actually selects. A VCA edit may still affect each clip explicitly in its lock, but never expands to linked members outside that lock. The arranger's clear-notes-out-of-bounds remains a shared note-content edit; only its edited instance's window is rebased. `clip.link_make_unique` clears the selected instance's id, keeps its already-owned note list/name/colour, and dissolves a two-member relation by clearing the remaining id. Its journal checkpoint covers every id it changes, so one undo restores membership. The context menu invokes that command for one linked MIDI clip. A small chain glyph is painted on linked MIDI clips; the clip view's accessible name identifies linked status.

**Ownership, memory, capacity, and real-time.** The project owns clips and their note lists; a group is discovered by scanning the song, with no shared pointer or second registry. GUI/control handlers own their temporary `QVector`/`QString` work and journal snapshots; they are allocated and released on that thread. Make Unique needs no new note allocation because every member already has its own content copy. Group size has no new fixed cap; it is bounded by the clips in the project, and no queue or bounded pool is introduced. No audio-thread path calls link lookup, mutates clip metadata, emits Qt signals, allocates, locks, waits, or performs I/O. `MidiClip::play` continues to read the same clip-local note list; a user content edit may intentionally change the sound of every linked instance.

**Unchanged behavior and rejected design.** The serialized `link` attribute, project reload, note-edit mirroring, one-step command undo, sample clips' inability to link, and each clip's independent render window remain. Keep per-instance note-list copies rather than introducing shared note storage: this preserves existing lifetimes, serialization, and piano-roll `Note*` ownership. Do not create a second linked group on split; both pieces represent windows onto the same content and should keep following edits. The old rule that every peer must accept an edge edit is removed because peers are no longer part of that edit.

## 2. Contained-clip crossfade

**Problem.** Both `arrangement::crossfadeContained` in `src/core/ArrangementEdits.cpp` and `containedSides` in `src/core/ControlCommandsClipEdits.cpp` currently create a V-shaped envelope on the outer clip by writing paired offset fades. `containedcrossfade::ramps` in `src/core/ContainedCrossfade.cpp` chooses half the inner clip as a fallback when it has no fade-out. This is the default for arranger drops and `clip.crossfade`, contrary to the 2026-10-09 decision to clamp by default and preserve the V only as an explicit gesture/option.

**Design and invariants.** Default crossfade mode uses only edge fades with zero offsets, bounded by the clips' actual overlap. For a contained pair, the ordinary mode never writes an offset fade on the outer clip. Alt at drop/release opts into the container gesture only when the arranger overlap mode is Crossfade; the gesture operates on clips already sharing one track. The control command accepts `mode: "clamp"` by default and `mode: "container"` explicitly; container mode requires a contained pair. Its default entry/exit lengths come from the inner clip's own fade-in/fade-out lengths; absent or non-fitting ramps are a typed refusal/no-op, never a half-length guess. Explicit ramp-length arguments remain validated. The existing clip track checkpoint remains one undo step for both sides.

**Ownership, memory, capacity, and real-time.** Gesture and control calculations edit `ClipEdits` on the GUI/control thread. They allocate no new render object, pool, queue, or persistent crossfade object, so there is no new capacity or overflow state. Audio rendering still reads serialized fade lengths and offsets in `SamplePlayHandle`; this change does not alter that render loop or its allocation/locking behavior. Existing projects' paired offset fades continue to load and render from their stored values unchanged. The audible change is intentional and limited to newly requested default crossfades: they no longer duck the outer clip inside the inner clip's bounds.

**Unchanged behavior and rejected design.** Keep the offset-fade representation, save/load rules, pair validation, audio-thread envelope evaluation, and one-step undo. Do not remove offset-fade support or migrate existing project data. Reject a half-inner-length fallback because it conflicts with the inner clip's authored fade lengths and creates a surprise ramp where the user has authored none.
